# tc-basis — 기획 원문 표에서 기능 골격과 커버리지 보고서를 만드는 도구 명세

<!-- CHANGELOG · v1.0 · 2026-10-27: (추가) 받아 가는 저장소의 프로젝트 스크립트를 tc 모듈 도구로 올리기 위한 명세 -->

규칙은 `core/modules/tc/rules/tc-pipeline.md` 「기획 원문 표에서 골격을 만드는 선택지」와
`core/modules/tc/rules/case-expansion.md` 「기획 누락 역보고」 · 「승인되지 않은 기능 단위도 TC로 씁니다」입니다.
이 문서는 그 규칙을 도는 도구를 tc 모듈에 넣을 때의 명세입니다. 원본은 받아 가는 저장소의 한 프로젝트
스크립트(약 270줄)이며, 그 안의 프로젝트 고유 값을 설정으로 빼는 것이 이관 작업의 대부분입니다.

## 1. 자리와 이름

| 항목 | 제안 |
|---|---|
| 도구 | `core/modules/tc/scripts/tc_basis.py` |
| 프로젝트 설정 | `test-case/{슬러그}-tc-basis.json` (원본은 `-tc-areas.json` — 이름 변경은 받는 쪽에서 한 번 옮깁니다) |
| 골격 출력 | 기본 `spec/{슬러그}-feature-tree.md` — 생성기 경로 버그를 고친 뒤(`tc-feature-tree-path-fix.md`). 그 전에는 설정의 `tree_path`로 바꿀 수 있게 합니다 |
| 보고서 출력 | `test-case/{슬러그}-tc-coverage.md` |
| TC 입력 | `test-case/{슬러그}-tc-input-v{X.Y}.json` — 설정의 `tc_input`으로 버전을 지정합니다(원본은 v1.0 고정) |
| 재생성 | `core/modules/tc/jobs.py`에 「설정 파일이 있을 때만」 작업을 더합니다. 입력은 설정이 가리키는 기획 문서들입니다 |

## 2. 설정 형식

```json
{
  "spec_root": "../{기획 프로젝트}/spec/design",
  "approval_columns": ["승인 상태", "확인 기준"],
  "confirmed_markers": ["사용자 확정", "사용자 지정"],
  "observed_markers": ["구현 관찰"],
  "title_strip_prefix": "규칙 표 · ",
  "id_cell_pattern": "^rule-[a-z0-9-]+$",
  "spec_label_strip": ["{접두}-flow-", ".md"],
  "markers": {"unconfirmed": "[확정 필요]", "gap": "[기획 누락]"},
  "tree_path": null,
  "tc_input": "test-case/{슬러그}-tc-input-v1.0.json",
  "specs": [
    {"file": "{기획 문서}.md", "area": "{영역}", "tables": {"{표 제목 일부}": "{다른 영역}"}}
  ],
  "excluded_specs": {"{기획 문서}.md": "{제외 사유}"}
}
```

원본에서 코드에 박혀 있던 값과 새 설정 키의 대응입니다.

| 원본 코드의 고정 값 | 새 설정 키 | 이유 |
|---|---|---|
| 표 제목 앞의 고정 접두 제거 | `title_strip_prefix` | 접두 문구는 프로젝트 문체입니다 |
| 첫 칸이 규칙 ID이면 다음 칸을 이름으로 | `id_cell_pattern` | ID 형식은 프로젝트가 정합니다 |
| 같은 경로를 가를 때 기획 문서 이름에서 떼는 접두 | `spec_label_strip` | 파일 접두에 프로젝트 이름이 들어 있습니다 |
| Note의 고정 표지(이모지 포함) | `markers` | 표지 문구는 프로젝트가 고릅니다. 기본값은 이모지 없는 대괄호 표지를 권합니다 |
| TC 입력 파일 버전 v1.0 | `tc_input` | 입력 버전이 오르면 도구를 고치지 않게 합니다 |
| 골격 머리말 안의 기획 담당 이름 | (삭제) | 머리말은 「기획 원문 표에서 생성」으로 일반화합니다 |

`excluded_specs`는 원본에서 기록용이었습니다. 이관 때 도구가 이 목록과 `specs`의 겹침을 오류로 보고,
보고서에 제외 사유를 싣게 합니다.

## 3. 동작

1. **행 읽기** — `specs`의 각 기획 문서에서 「머리줄 + `|-` 구분줄」로 시작하는 표를 찾습니다. 머리줄에
   `approval_columns` 중 하나가 있는 표만 읽습니다. 표 제목은 바로 위의 가장 가까운 `##`~`####` 제목(앞
   번호 제거) 또는 굵은 글자 한 줄입니다.
2. **경로** — `영역 > 표 제목 > 행 이름`. 영역은 `tables`에 표 제목 일부가 맞으면 그 값, 아니면 문서의
   `area`. 행 이름은 첫 칸(규칙 ID 칸이면 다음 칸)을 다듬은 값이며, `—`는 `-`로, ` > `는 ` › `로 바꿉니다.
   같은 표에서 이름이 겹치면 다음 칸을 붙이고, 그래도 겹치면 ` #n`을 붙입니다. 서로 다른 문서에서 경로가
   겹치면 표 제목 뒤에 문서 이름을 괄호로 붙입니다.
3. **승인 구분** — 승인 칸에 `confirmed_markers`가 있으면 확정, `observed_markers`가 있으면 관찰, 그 밖은
   미정. 골격에는 확정 / 확정 필요 두 값으로 싣습니다.
4. **행 해시** — 행의 모든 칸을 `|`로 이은 UTF-8 문자열의 SHA-1 앞 10자리. 원본과 같은 계산을 지켜야
   받는 쪽에 이미 기록된 `basis`가 그대로 맞습니다. 알고리즘을 바꾸려면 옛 해시를 새 해시로 옮기는
   변환 명령을 함께 둡니다.
5. **골격 쓰기** — 형식 v2 골격(`parse_feature_tree.py`가 읽는 모양). 잎 노드는
   `- {행 이름} [유형: 결정적] [범위: 구현] — {확정|확정 필요} · {문서} · 행 {해시}`. 머리에 자동 생성
   주석과 전체 행 해시의 지문(SHA-1 앞 12자리)을 둡니다. 확정 필요 행은 「미확인 목록」 절에 모읍니다.
6. **보고서 쓰기** — 영역별 표(확정 행 · TC 있음 · 확정 필요 행 · TC 있음), 전체 합계, 기능 단위를 하나도
   읽지 못한 문서, 그리고 「재검수 필요」(작성 때 해시 → 지금 해시) · 「근거 행 없음」 · 「해시 미기록」 ·
   「기획 누락」(Note가 `markers.gap`으로 시작하는 TC) · 「TC가 없는 기능 단위」 목록.

TC 입력의 모양: `tcs`의 각 줄에서 0번째가 TC ID, 11번째가 Note, 12번째가 covers(있으면)입니다.
covers 중 ` > `가 든 값만 트리 경로로 봅니다(`check_tc_coverage.py`와 같은 규칙). `basis`는 최상위
객체 `{"TC ID": {"경로": "해시"}}`입니다.

## 4. 명령

```text
python core/modules/tc/scripts/tc_basis.py {프로젝트 폴더}                 골격 · 보고서 생성
python core/modules/tc/scripts/tc_basis.py {프로젝트 폴더} --check         골격이 기획 문서보다 낡았으면 exit 1
python core/modules/tc/scripts/tc_basis.py {프로젝트 폴더} --stamp         basis가 없는 TC에만 지금 해시 기록
python core/modules/tc/scripts/tc_basis.py {프로젝트 폴더} --stamp TC-A TC-B   지정한 TC의 해시를 갱신
```

원본은 스크립트 위치로 프로젝트를 찾았습니다. 모듈 도구는 여러 프로젝트가 함께 쓰므로 프로젝트 폴더를
인자로 받습니다. `--stamp`에 아무 ID도 주지 않았을 때 이미 기록된 해시를 덮어쓰지 않는 동작은 반드시
지킵니다 — 덮어쓰면 「재검수 필요」 목록이 대조 없이 비워집니다.

## 5. 알려진 한계 — 이관 때 함께 고칠 것

- 표 칸 안의 이스케이프된 세로줄(`\|`)을 칸 구분으로 잘못 나눕니다.
- 기획 문서가 다른 프로젝트에 있으면 구조 설정의 생성 작업 입력으로 등록할 수 없어(`project_structure`의
  로컬 경로 제한) regen이 변경을 알아채지 못합니다. 같은 저장소 안 다른 프로젝트 자료를 읽기 전용
  입력으로 허용할지는 중앙 남은 작업의 「구조 설정 생성 작업의 다른 프로젝트 입력」과 함께 정합니다.
- 범위 물결표를 `\~`로 쓰는 문서는 칸 내용에 `\~`가 그대로 들어가 해시에 포함됩니다. 해시는 원본
  바이트로 계산한다는 원칙과 맞으므로 고치지 않되, 골격 표시 문자열에서만 `~`로 되돌립니다.

## 6. 점검(check.py에 더할 케이스)

시험 데이터에는 프로젝트 고유명사를 넣지 않습니다(`feature-request.md` 「겪은 것을 중앙에 되돌리기」).

1. 임시 폴더에 승인 열이 있는 표 하나(확정 두 행 · 관찰 한 행)와 승인 열이 없는 표 하나를 가진 기획 문서를
   만들고, 설정 · 빈 TC 입력과 함께 생성합니다. 기능 단위가 3개이고 승인 열 없는 표는 읽지 않았는지 봅니다.
2. TC 하나가 첫 행을 덮게 하고 `--stamp` → 보고서의 「해시 미기록」이 비는지 봅니다.
3. 첫 행의 한 칸을 고친 뒤 생성 → 그 TC가 「재검수 필요」에 뜨고, `--check`가 exit 1인지 봅니다.
4. 행 이름을 바꾼 뒤 생성 → 「근거 행 없음」에 뜨는지 봅니다.
5. Note가 기획 누락 표지로 시작하는 TC가 「기획 누락」 목록에 뜨는지 봅니다.
6. 만든 골격을 `gen_feature_tree_html.py`로 HTML까지 만들어 봅니다 — 경로 버그 같은 결함을 함께 잡습니다.
