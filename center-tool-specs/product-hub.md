# product-hub — 묶음 허브 생성기 명세 (통합 허브 · 업무별 허브)

<!-- CHANGELOG · v1.0 · 2026-10-27: (추가) 받아 가는 저장소의 묶음 허브 생성기를 document-site 도구로 올리기 위한 명세 -->

규칙은 `core/modules/document-site/rules/document-design.md` 「주제별 문서 허브」 · 「묶음 허브 — 통합
허브와 업무별 허브」입니다. 「프로젝트 묶음 — 한 제품의 여러 업무 프로젝트」라는 단위와 묶음 공통 모듈 설정의 상속은 base의
`site-structure.md`가 정합니다(같은 이관 묶음에서 base 담당이 씁니다). 이 문서는 생성기 쪽만 다룹니다.

원본은 받아 가는 저장소의 한 묶음 폴더에 있는 생성기입니다 — 진입점(약 35줄)과 탐색 · 검사 · 조립 ·
출력 네 단계 파일(합계 약 250줄), 묶음 공유 틀(`shared/`의 틀 설정 · 탭 CSS/JS · 검색 단계 JS · 부품
조각), 설정 검사 단위 시험, Playwright 브라우저 검사입니다. 2026-09-08부터 운영됐습니다.

## 1. 자리와 이름

| 항목 | 제안 |
|---|---|
| 도구 | `core/modules/document-site/scripts/build_hub.py` (진입점) + `scripts/hub/`(discover · validate · compose · render) |
| 프로젝트 허브 설정 | `{프로젝트}/docs/hub.json` (원본 이름은 `choice.json` — 받는 쪽은 한 번 옮기거나, 생성기가 옛 이름도 읽게 합니다) |
| 묶음 공유 틀 | `{묶음}/shared/` — `frame.json` · `tabs.css` · `tabs.js` · `search-cascade.js` · `parts/` |
| 묶음 공통 모듈 설정 | `{묶음}/{묶음}-module-config.json` `{"on": [모듈 이름…]}` — 형식과 상속 규칙은 base가 정합니다 |
| 출력 | 통합 허브 `{묶음}/docs/page.html`, 업무별 허브 `{프로젝트}/docs/page.html`, 각 폴더의 생성 안내 `design.md`, 선택된 렌더러의 개별 HTML, 프로젝트 구조 요약 md |
| 재생성 | `jobs.py`에 묶음 작업을 더합니다. 원본은 중앙 regen이 묶음 허브를 만들지 않아 묶음 명령을 따로 돌려야 했습니다 |

## 2. 프로젝트 허브 설정

```json
{
  "schema_version": 1,
  "title": "{묶음} · {프로젝트 표시 이름}",
  "label": "{프로젝트 표시 이름}",
  "order": 10,
  "default_tab": "{탭 ID 또는 null}",
  "tabs": [
    {"id": "{탭 ID}", "label": "{탭 이름}", "content": "parts/content/{파일}.html"},
    {"id": "{탭 ID}", "label": "{탭 이름}", "renderer": "../scripts/{렌더러}.py",
     "scripts": ["{docs 기준 JS}", "module:{모듈}/{모듈 안 JS 경로}"],
     "structure_ref": "{구조 설정 자료 ID}"}
  ]
}
```

| 필드 | 규칙 |
|---|---|
| `schema_version` | 1만 받습니다 |
| `order` · `label` · `title` | 모두 필수. 프로젝트 순서는 `order`, 같으면 폴더 이름 순 |
| `tabs[].id` | `[a-z][a-z0-9-]*`, 묶음 전체에서 하나뿐 |
| `content` / `renderer` | 둘 중 정확히 하나. 경로는 프로젝트 폴더 안이어야 하고 파일이 있어야 합니다 |
| `scripts` | docs 기준 상대 경로 또는 `module:` 참조. 모듈은 base `site-structure.md` 「제품 공통 모듈 설정 — 업무별 설정과 합집합」의 합집합(저장소 모듈 ∪ 묶음 공통 설정 ∪ 업무 설정)에 있어야 합니다. 원본은 저장소 모듈을 빼고 두 설정만 합쳤습니다 |
| `structure_ref` | 프로젝트 구조 설정의 자료 ID. 없는 ID · 한 자료에 탭 두 개 연결은 오류 |
| `default_tab` | 탭이 있으면 그 목록 안의 ID, 없으면 `null` |

## 3. 처리 단계

1. **탐색** — 묶음 폴더 아래 `*/docs/hub.json`을 찾고, 각 프로젝트의 구조 설정을 불러 둡니다(사이드바
   메뉴와 구조 요약 md에 씁니다).
2. **검사** — 2장의 규칙 전부. 하나라도 어긋나면 **어떤 파일도 쓰기 전에** 멈춥니다.
3. **조립** — 탭마다 내용을 얻습니다(`content`는 파일, `renderer`는 `render(tab_id)` 호출). 내용의
   `data-view-panel` 목록이 설정의 탭 목록과 같은지, 한 페이지 안 HTML `id`가 겹치지 않는지 봅니다.
   정적 내용의 `href` · `src` 상대 경로를 출력 위치 기준으로 다시 계산하고(스킴 · 절대 경로 · `#`는
   그대로), 스크립트가 만드는 그림 주소의 기준이 되도록 `data-asset-base`에 내용 소유 폴더를 적습니다.
   스크립트는 경로 기준으로 한 번만 싣습니다.
4. **출력** — 통합 허브 한 장 + 프로젝트마다 한 장. 업무별 허브에만 렌더러의 개별 HTML과 구조 요약
   md를 더합니다. `--check`는 쓰지 않고 낡은 파일만 `STALE`로 알리며 하나라도 있으면 exit 1.

**사이드바 메뉴** — 프로젝트마다 접히는 묶음 하나. 구조 설정이 있으면 자료 트리(`parent`)를 따라 디렉터리
자료를 접히는 묶음으로, 탭이 연결된 자료(`structure_ref`)를 링크로 그리고, 연결되지 않은 탭은 뒤에
붙입니다. 탭이 없으면 「등록된 탭이 없습니다」를 보입니다.

**허브 사이 이동** — 업무별 허브 상단 탭 줄에 통합 허브로 가는 링크(`data-hub-link`), 통합 허브
하단에 업무별 허브 링크 목록.

## 4. 본문 렌더러

```python
def render(tab_id: str) -> str: ...              # 허브에 실을 <section data-view-panel="{tab_id}"> 조각
def standalone_outputs() -> dict[Path, str]: ... # 선택 사항 — 같은 정본의 개별 HTML
```

- 개별 HTML 출력은 그 프로젝트 `docs/` 안의 `.html`이며 `page.html`이 아니어야 하고, 출력 경로가
  겹치면 오류입니다. 선택된 탭의 렌더러만 생성 · `--check` 대상입니다.
- 렌더러는 실행 코드이므로 프로젝트 폴더 안 파일만 받습니다.
- **공용 Markdown 렌더러를 함께 둡니다.** 원본에서는 프로젝트마다 Markdown 부분 집합 렌더러를 따로
  짰고, 그중 하나에 결함 두 개가 있었습니다(`document-site-generator-fixes.md`). 공용 렌더러는 처음부터
  ① `##` 장 번호 검사(또는 설정으로 허용) ② 주석을 지운 본문에서 제목 찾기 ③ `\~` → `~` 되돌리기 ④
  지원 구문 밖의 줄을 줄 번호와 함께 알리기를 갖습니다.
- 개별 HTML과 허브 조각의 본문이 같은지 생성 검사에서 비교합니다(허브 쪽에서만 하는 경로 변환은 비교
  전에 되돌리거나 비교 대상에서 뺍니다).

## 5. 검색 (공유 틀의 검색 단계 JS)

- 검색 데이터는 각 허브에 실린 탭 내용 자체입니다. 실리지 않은 문서는 검색되지 않습니다.
- 결과를 자르지 않고 프로젝트 → 탭 → 결과 세 단계로 묶습니다. 통합 허브는 결과가 있는 프로젝트만 먼저
  보이고, 프로젝트에 올리면 탭을, 탭에 올리면 결과를 펼칩니다. 업무별 허브는 프로젝트 단계를
  건너뜁니다. 프로젝트 · 탭 단계에는 이름과 건수 태그만, 결과에는 일치 제목 · 문구만 보입니다.
- 결과를 누르면 그 탭으로 바꾸고, 대상의 상위 `<details>`와 검색어가 든 안쪽 `<details>`를 펼친 뒤
  스크롤합니다.
- 상세 미리보기 토글은 미리보기만 켭니다(범위 · 건수 불변).
- 마우스가 검색 영역을 벗어나면 잠시 기다린 뒤 하위 메뉴를 닫습니다(메뉴 사이 이동 중 닫힘 방지).
- 키보드: 아래 화살표로 진입, 위 · 아래 이동, 오른쪽 펼치기, 왼쪽 돌아가기, Enter 선택, Escape 닫기.
  좁은 화면은 클릭으로 한 단계씩 열고 「← 이전 단계」로 돌아갑니다.
- 업무별 허브에 다른 프로젝트 탭의 해시로 들어오면 기본 탭으로 돌아갑니다.

## 6. 원본에서 벗길 것

| 원본의 고정 값 | 처리 |
|---|---|
| 통합 허브 제목 문자열(묶음 이름 포함) | 묶음 설정의 `title`에서 읽습니다 |
| 하단 메타의 담당자 이름 | `workspace.json`의 저장소 정보나 묶음 설정에서 읽고, 사람 이름을 코드에 두지 않습니다 |
| 생성 안내 md 안의 묶음 경로와 명령 | 실제 묶음 경로로 채웁니다 |
| 렌더러 출력에 덧붙이는 특정 속성(`data-workflow-player` 앞에 `data-asset-base` 삽입) | 모든 탭 최상위 패널에 `data-asset-base`를 두는 일반 방식으로 바꿉니다 |
| 브라우저 검사의 프로젝트 이름 배열 · 숨겨야 할 탭 ID · 한 프로젝트 전용 검사 줄 | 설정에서 프로젝트 목록을 읽고, 「다른 프로젝트의 첫 탭 ID로 들어가면 기본 탭」으로 일반화합니다 |

## 7. 기술 판단이 필요한 자리

- **어느 셸 위에 짓는가** — 원본은 html-design-kit의 조립기를 불러 `load_part`를 실행 중에 바꿔 끼우는
  방식으로 탭 영역과 검색 스크립트를 넣습니다. 모듈 함수를 덮어쓰는 방식은 조립기가 바뀌면 조용히
  깨집니다. 중앙에 올릴 때는 (가) html-design-kit에 「부품 바꿔 끼우기」 공식 인자를 두거나 (나)
  document-site 셸(`scripts/shell.py`) 위에 다시 짓는 것 중 하나를 고릅니다. (가)면 이 도구의 전제에
  html-design-kit이 들어갑니다.
- **jobs.py의 단위** — 지금 `jobs.py`는 워크스페이스 작업과 프로젝트 작업 두 층만 받습니다. 묶음 작업을
  받는 자리(`bundle_jobs(ctx)` 등)가 base에 생겨야 regen이 묶음 허브를 다시 만듭니다.
- **입력 지문** — 원본 `--check`는 출력 전문을 비교합니다. 탭 수가 많아지면 느리므로, 입력 파일 해시를
  산출물에 찍고 대조하는 방식(regen의 다른 작업과 같은 방식)으로 바꿀지 정합니다.

## 8. 점검

- **단위 시험(check.py)** — 임시 묶음(프로젝트 둘, 하나는 탭 없음)을 만들어 다음을 봅니다: 통합 · 프로젝트별
  허브가 모두 나옴, 출력에 `{{` 자리표시와 `<script src=`가 없음, 탭 없는 프로젝트의 빈 안내, 숨긴 탭의
  패널 · 링크가 없음, 켜지 않은 모듈의 `module:` 참조 · 모듈 밖 경로 · 중복 탭 ID · 잘못된 기본 탭 ·
  패널 불일치가 쓰기 전에 오류, 같은 모듈 스크립트가 통합 허브에 한 번만 실림, `--check`가 생성 직후 0건.
- **브라우저 검사(선택)** — Playwright가 있을 때: 허브 이동 링크, 탭마다 시험 결과 15건을 넣어 뒤쪽 탭
  누락 없음, 상세 미리보기 켜고 꺼도 건수 동일, 다른 프로젝트 결과 0건, 키보드 이동, 좁은 화면의 단계
  이동과 가로 넘침 없음, 두 테마, 콘솔 에러 0. 시험 데이터는 페이지 안에서만 넣고 파일에 남기지 않습니다.
