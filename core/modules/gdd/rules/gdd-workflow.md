# gdd-workflow — 기획서 → 프로토타입 → 구현의 순서와 기획서 표기 규칙

기획서는 **구현 전에 합의하는 자리**입니다. 합의되지 않은 것이 구현으로 새어 나가면, 나중에 기획을
바꿀 때 코드 · 데이터 · 문서를 함께 되돌려야 합니다. 그래서 순서와 표기를 고정합니다.

---

## 1. 순서 — 기획서 → 프로토타입 → 구현

| 단계 | 산출 | 무엇을 확인하나 |
|---|---|---|
| ① 기획서 | `gdd/gdd-NN-{시스템}.html` | 규칙 · 흐름 · 화면 · 예외 · 데이터를 합의합니다 |
| ② 프로토타입 | 프로젝트 루트 `_prototype.html` (한 파일) | 브라우저에서 직접 눌러 흐름과 화면 배치를 확인합니다. 실제 엔진이 없어도 판단할 수 있는 것만 봅니다 |
| ③ 구현 | 엔진 코드 · 구현 문서 | 기획서의 확정 규칙만 옮깁니다 |

- 사용자가 순서를 정했으면 그 순서를 따르고, 한 요청의 여러 기능도 **각 단계를 모두 끝낸 뒤** 다음
  단계로 넘어갑니다.
- 프로토타입은 한 파일로 두고 파일 상단 CHANGELOG에 버전을 올립니다. 엔진에서만 되는 동작(투명
  창 · 여러 모니터 등)은 흉내로 두고, 흉내라는 사실을 화면이나 주석에 적습니다.
- 구현하다가 기획의 빈 곳이 나오면 구현에서 임의로 정하지 않고 기획서의 미결로 올립니다.

## 2. 규칙 번호

- 규칙 표의 각 행은 **시스템 접두 + 번호**(`XX-01`)를 가집니다. 접두는 기획서마다 두 글자로 정합니다.
- **한 번 붙인 번호는 바꾸거나 다시 쓰지 않습니다.** 다른 문서 · 코드 주석 · 이력이 그 번호로
  가리키기 때문입니다. 규칙이 없어지면 그 번호는 비워 두고 행에 폐기를 적습니다.
- 새 규칙은 끝 번호 다음에 붙입니다. 묶음으로 더하면 이력에 범위(`XX-61 ~ 74`)로 적습니다.
- 기능 트리의 번호는 원본 기능 목록의 넘버링을 유지합니다.

## 3. 상태 표기

| 상태 | 표기 | 뜻 |
|---|---|---|
| 확정 | `.pill.green` | 사용자가 정했습니다. 구현으로 옮길 수 있습니다 |
| 제안 | `.pill.amber` | 작성자가 제안했고 아직 승인 전입니다 |
| 미정 | `.pill.red` | 정해야 하는데 안이 없습니다 |

- **제안 · 미정은 전부 미결 사항 표에 올립니다.** 표에서 빠진 제안은 확정처럼 읽힙니다.
- 사용자가 「전부 승인」처럼 묶어 답하면 그 범위를 이력에 적고 상태를 확정으로 바꿉니다.
- 결정된 항목은 미결 표에서 결정 표로 옮기고, 선택지와 근거를 남깁니다.

## 4. 기획서의 섹션

05-A 시스템 기획서의 섹션과 컴포넌트는 `../design-template/gdd-template-catalog.md`가 정합니다.
더 지키는 것:

- **화면 와이어프레임의 번호 마커와 UI 요소 표는 1 : 1**로 맞춥니다. 빌드 도구가 번호 목록을 뽑아
  대조를 돕습니다.
- 코드가 없는 문서이므로 🚀 착수 블록은 두지 않습니다.
- 수치 · 키 이름처럼 다른 문서의 정본이 따로 있는 값은 그 정본의 버전과 함께 적습니다.

## 5. 빌드

기획서는 머리(`<slug>-head.html`)와 본문(`<slug>-body.html`)을 작업 폴더에 쓰고 도구로 조립합니다.

```bash
bash core/modules/gdd/scripts/build_gdd.sh {프로젝트 폴더} {slug} {작업 폴더}
```

도구가 하는 일은 넷입니다 — ① 머리 + 마스터 CSS + 본문 조립, ② 마스터에 없는 클래스 검사(있으면
Case B 신호), ③ 쓰지 않기로 한 용어 검사(`gdd/banned-terms.txt`가 있을 때), ④ 태그 균형 · 번호
마커 목록 출력, 그리고 마지막에 **묶음 전체의 글꼴 내장**입니다(`core/base/rules/html-output.md` §2).
