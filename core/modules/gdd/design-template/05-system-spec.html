00 — 구성 개요

05-A 시스템 기획서 — 섹션 구조 (독자 이해 순서)

독자는 이 시스템이 왜 있는지 알고 → 어떤 기능들로 이뤄졌는지 훑고 → 규칙을 익히고 → 사용자가 실제로 밟는 흐름을 따라가고 → 그 흐름이 화면에 어떻게 놓이는지 보고 → 예외를 확인하고 → 데이터가 어디 사는지 · 다른 시스템과 어떻게 이어지는지 파악한 뒤 → 남은 결정을 확인하는 순서로 이해에 도달합니다. 요청 내용에 맞게 섹션을 추가·흡수·축약할 수 있습니다.

04유저 플로우사용자는 어떤 순서로 무엇을 누르는가.diagram(구워넣은 SVG) + *.mmd 단일 탭 · .pipe-step

07데이터 · 수치값이 어디에 저장되고, 무엇이 튜닝 대상인가.tbl(저장 위치 · 튜닝 파라미터)
08시스템 연동다른 시스템과 무엇을 주고받는가.rel-map(시스템 간 관계)

📐

02-A · 02-B · 04와의 구분 — 이 템플릿은 코드 없는 기획 정의입니다. "누가(클래스) 무엇을 책임지나"는 02-A, "복붙할 .h/.cpp"는 02-B, "변수가 어디 살고 어디로 흐르나"는 04가 담당합니다. 기획서의 07·08 섹션은 저장 위치·연동 대상을 이름 수준으로만 적고, 상세 구현은 해당 구현 문서 이름으로 넘깁니다(🚀 작업 시작하기 블록 생략 가능 — 코드 없음).

06 — 변형 · 05-B 콘텐츠 총괄표

프로젝트 전체 콘텐츠를 한 장으로

시스템 기획서 묶음의 입구 문서입니다. 독자는 제품이 무엇인지 → 화면이 어떻게 나뉘는지 → 콘텐츠가 몇 개 시스템으로 묶이는지 → 언제 만드는지 → 무엇이 비어 있고 어긋나는지 순서로 전체를 파악합니다.

07 — 사용 규칙

이 템플릿의 Do & Don't

✓ 이렇게

  • 모든 규칙·기능·수치에 상태 pill(확정/제안/미정)을 붙이기
  • 제안·미정은 전부 미결 사항 표에 모으기
  • 기능 트리 번호는 원본 기능 목록 넘버링을 그대로
  • 와이어프레임 번호 마커와 UI 요소 표를 1:1로 대응
  • 용어는 처음 1회 풀어 쓰고, 한 개념엔 한 용어만
  • 수치는 확정값만 — 나머지는 튜닝 표기

✗ 이건 피하기

  • 제안을 확정 규칙과 같은 색·문장으로 섞어 쓰기
  • .h/.cpp 코드 넣기 (구현 명세 02-B의 몫)
  • 와이어프레임을 픽셀 시안처럼 꾸미기
  • 정상 경로만 있는 플로우 (취소·ESC·실패 누락)
  • 폐기된 기능·용어를 "폐기됨" 안내로 본문에 남기기 (프로젝트 규칙이 있는 경우)
