# measurement-records — 성능 · 품질 측정 기록을 보관하고 비교하는 기준

<!-- CHANGELOG · v1.0 · 2026-10-27: (추가) 측정 조건 기록 · 조건이 다른 수치의 직접 비교 금지 · 재측정 비덮어쓰기 · 측정 기록의 지위 -->

실기기 성능 측정처럼 **같은 대상을 여러 번 재는 기록**을 QA 문서로 보관할 때의 기준입니다. 측정값은
조건이 조금만 달라도 크게 움직입니다. 그런데 조건이 기록에 없으면, 나중에 두 수치를 나란히 놓았을 때
개선인지 조건 차이인지 가릴 수 없습니다. 그래서 수치보다 **조건을 먼저** 남기고, 조건이 같은
기록끼리만 비교합니다.

원문을 인용 블록으로 보관하고 출처 · 보관 시각 · 해시를 적는 방법, 정정과 재측정 보관, 원자료 범위는
evidence 역할의 공통 규칙인 `core/base/rules/site-structure.md` 「증거 자료는 원문 그대로 보관합니다」가
정합니다. 그 규칙은 「측정 조건의 기록과 조건이 다른 결과의 비교는 켠 모듈이 정한다」고 남겨 두었고, 이
문서가 그 자리를 채웁니다.

---

## 1. 측정 기록은 증거이지 기준이 아닙니다

측정 기록을 담는 폴더는 프로젝트 구조 설정에 evidence 역할로 등록합니다. 측정값을 곧바로 TC 기대값 ·
성능 합격선 · 개선 완료 판정으로 쓰지 않습니다. 측정은 「그때 그 조건에서 이렇게 나왔다」는 사실이고,
「얼마여야 한다」는 승인된 기획 사양이 정합니다.

- 합격선이 필요하면 측정 기록을 근거로 기획 정본 소유자에게 제안하고, 승인된 값만 기대값으로 씁니다
  (`../module.md` 「기획 사양과 QA 분석의 경계」).
- 보고서에 적힌 개선 후보는 합의 없이 실행 작업으로 확정하지 않습니다. 확정된 후속 작업만 프로젝트
  remaining-work에 올립니다.

## 2. 측정 조건을 함께 기록합니다

새 측정 기록의 머리말에 아래 조건을 적습니다. 원문 보고서에 조건이 있으면 그 값을 옮기고, 없으면
머리말에서 「미확인」 또는 「미측정」으로 적습니다. **빈칸으로 두지 않습니다** — 빈칸은 읽는 사람이
「다른 기록과 같겠지」로 채워 읽기 때문입니다.

| 조건 | 적는 내용 | 왜 필요한가 |
|---|---|---|
| 기기 · OS | 기기 모델과 OS 버전 | 같은 앱도 기기 성능과 OS 스케줄러에 따라 수치가 달라집니다 |
| 앱 버전 · 빌드 유형 | 버전 · 빌드 번호와 디버그 / 릴리스 구분 | 디버그 빌드는 최적화와 검사 코드 차이로 릴리스보다 느립니다 |
| 소스 상태 | 소스 커밋과 미커밋 변경 포함 여부 | 같은 버전 번호라도 측정한 코드가 다를 수 있습니다 |
| 측정 도구 | 도구 이름 · 버전 · 수집 방식 | 도구마다 측정 경계와 오버헤드가 다릅니다 |
| 시나리오 · 반복 | 조작 순서 · 입력 데이터 · 반복 횟수 · 대푯값(중앙값 등) | 한 번 잰 값은 편차를 알 수 없습니다 |
| 캐시 · 프로세스 상태 | 첫 실행 / 재실행, 캐시 비움 여부, 백그라운드 프로세스 상태 | 첫 실행과 재실행은 같은 지표라도 다른 현상을 잽니다 |
| 지표의 단위 · 경계 | 단위와 「어디서부터 어디까지」 | 「화면 표시 시간」이 터치부터인지 화면 전환부터인지에 따라 값이 달라집니다 |
| 제외 표본 · 한계 | 버린 표본과 이유, 알려진 한계 | 이상값을 버린 기준이 없으면 결과를 재현할 수 없습니다 |
| 환경 (확인한 범위) | 전원 연결 · 기기 온도 · 화면 주사율 | 발열과 절전 모드는 성능을 떨어뜨립니다 |

## 3. 조건이 다르면 직접 비교하지 않습니다

기기 · 빌드 · 입력 · 캐시 조건 중 하나라도 다른 두 수치를 **개선 전후 비교로 합치지 않습니다.** 차이가
코드 변경 때문인지 조건 때문인지 가를 수 없기 때문입니다.

- 비교가 필요하면 같은 조건으로 다시 잽니다. 조건을 맞출 수 없으면 비교하지 않았다고 적습니다.
- 조건이 다른 기록을 한 표에 함께 보일 때는 그 행 · 열에 「조건이 달라 직접 비교할 수 없음」을 적고,
  다른 조건을 이름으로 밝힙니다.
- 「미확인」 조건이 있는 기록끼리의 비교는 같은 조건으로 보지 않습니다. 확인되기 전까지는 참고 값으로만
  씁니다.

예: 개선 전 기록은 디버그 빌드 · 첫 실행에서 앱 시작 4.1초, 개선 후 기록은 릴리스 빌드 · 재실행에서
1.2초입니다. 이 둘을 「앱 시작 70% 단축」으로 적지 않습니다. 빌드 유형과 캐시 상태가 모두 다르므로,
개선 효과를 말하려면 같은 빌드 유형 · 같은 실행 상태로 두 코드를 다시 잽니다.

## 4. 재측정은 새 기록으로 둡니다

새로 잰 결과를 기존 기록에 덮어쓰지 않는 원칙과 정정 절차는 base 「증거 자료는 원문 그대로 보관합니다」를
따릅니다. 측정 기록에서는 다음을 더합니다.

- **파일 이름에 측정일을 넣고, 같은 날 다른 실행이나 보완 보고서는 실행 · 주제를 가르는 접미사를
  붙입니다.** 예: `{접두}-{플랫폼}-performance-{YYYYMMDD}.md`, 같은 날 두 번째 실행은
  `…-{YYYYMMDD}-run-02.md`, 주제를 좁힌 보완은 `…-{YYYYMMDD}-{주제}.md`. 측정일과 보관일이 다르면
  이름에는 측정일을 씁니다 — 같은 날 잰 기록끼리 나란히 놓여야 조건 대조가 쉽습니다.
- **정정인지 재측정인지 먼저 가립니다.** 원 보고서의 오기를 바로잡는 것은 정정이고, 같은 시나리오를
  다시 돌린 것은 재측정입니다. 「다시 재 보니 값이 달랐다」를 정정으로 처리해 옛 보관본을 고치지
  않습니다.
- **새 기록 머리말에 이전 기록과 같은 조건인지 적습니다.** 같으면 이전 기록으로 가는 상대 링크와 함께
  「같은 조건」을, 다르면 다른 조건의 이름을 적습니다. 3장의 비교 가능 여부가 이 한 줄로 정해집니다.

## 5. 원자료 범위

기본 보관 대상은 사용자가 지정한 측정 보고서(글 문서)입니다. 추적 파일 · 빌드 파일 · 디버그 기호 파일 ·
스크린샷 · 영상 · 원시 로그 같은 원자료의 범위와 개인 정보 처리는 base 「증거 자료는 원문 그대로
보관합니다」를 따릅니다. 측정 기록에서는 **수치를 다시 계산하는 데 쓴 원자료가 보관 범위 밖이면, 그
수치를 재현할 수 없다는 사실을 머리말에 적습니다.**

## 6. 검사

- [ ] 머리말에 2장의 조건이 모두 있고, 없는 값은 「미확인」 · 「미측정」으로 적혔는가
- [ ] 개선 전후 비교가 같은 조건의 기록끼리인가. 아니면 「직접 비교할 수 없음」이 적혔는가
- [ ] 재측정 결과가 새 파일이고 기존 보관본이 바뀌지 않았는가
- [ ] 측정값이 TC 기대값이나 합격선으로 쓰인 자리가 없는가
