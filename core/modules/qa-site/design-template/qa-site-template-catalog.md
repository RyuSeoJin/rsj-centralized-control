# qa-site-template-catalog — QA 분석 문서의 템플릿 목록

이 목록은 테스트 관점의 분석 문서와 기능 골격·TC 관계도 서식을 고르는 기준입니다.
**기존 템플릿 사용 · 마스터 갱신 · 신규 템플릿 제작와 템플릿 선택 절차는 `../../../base/design-template/template-catalog.md`**를
따릅니다. 공통 디자인은 `../../document-site/design-guide/`의 마스터와
`../../document-site/rules/document-design.md`가 정합니다.

## 템플릿 목록

| 파일 | 용도 | 이런 요청일 때 |
|---|---|---|
| `01-feature-tree.html` | 기능 골격과 TC 관계도 시각화 | 등록된 기능 골격과 테스트 케이스의 관계를 보여 줄 때 |
| `02-reverse-analysis.html` | QA 관점의 출시 서비스 역분석 | 동작하는 제품을 관찰해 테스트 대상·상태·예외와 미확인을 정리할 때 |
| `03-spec-analysis.html` | 테스트 관점의 기획서 분석 | 등록된 기획 정본에서 검증할 조건·기대값·누락과 질의를 정리할 때 |

범용 기준서와 지원 환경 작성 안내는 `../../document-site/design-template/`에서 선택합니다.
같은 문서 형식을 QA용으로 복제하지 않습니다. 기능 사양 자체의 작성 기준은
`../../planning-spec/module.md`를 따르며, 이 카탈로그는 그 사양을 독자적으로 결정하지 않습니다.

## 판별 기준

1. 입력과 목적을 함께 확인합니다. 동작하는 제품의 QA 역분석은 02, 기획서의 테스트 관점 분석은
   03, 등록된 기능 골격과 TC 관계도 시각화는 01을 사용합니다.
2. TC와 관계없는 기능 규칙·화면·상태·예외의 작성은 기획 사양의 책임 범위입니다.
   기획 모듈의 등록 정본과 작성 기준을 확인한 뒤 표현할 매체를 고릅니다.
3. 일반 기준서나 공통 문서 사이트가 목적이면 `document-site`의 서식을 확인합니다.
   QA라는 이름을 붙이기 위해 이 모듈의 서식을 선택하지 않습니다.
4. 한 요청에 여러 산출물이 있으면 문서를 나눕니다. 예를 들어 역분석 문서와 TC 관계도는
   각각의 서식을 쓰되, 참조하는 정본의 ID·승인 상태·revision을 함께 추적합니다.

## 관리 단위와 추가 기준

- 색·글꼴·표·카드·테마·셸은 `document-site`의 공통 마스터에서 관리합니다.
- 이 모듈의 번호 있는 HTML은 QA 문서를 읽는 구조를 재사용하는 서식입니다.
- 주제만 다르면 기존 서식을 사용합니다. 표의 열이나 절 이름이 다르다는 이유만으로 새 디자인을
  만들지 않으며, 기존 구조로 내용을 표현하기 어려울 때 신규 템플릿 제작를 제안합니다.
- QA 분석에서 발견한 관찰값·추정값은 확정 사양과 구분합니다. 등록된 기획 정본과 충돌하면
  분석 문서에서 임의로 값을 고르지 않고 질의·변경 제안으로 남깁니다.

## 작업 유형 판별 · 공통 규칙

마스터 갱신로 공통 컴포넌트를 바꿔야 하면 갱신 대상은 `document-site`의 마스터입니다.
QA 템플릿 안에 다른 색·컴포넌트를 독립적으로 추가하지 않습니다. 공통 디자인 변경은 그 모듈의
규칙에 따라 CSS 정본·시각 규칙서·버전 기록·관련 산출물 재생성을 함께 진행합니다.
QA 서식의 읽는 구조만 바뀌면 이 카탈로그와 해당 서식을 승인 범위 안에서 갱신합니다.
