# asset-production — 에셋의 제작 크기를 정하고 AI로 만들 때 요청 · 검사하는 법

에셋을 새로 만들거나 기존 에셋을 정비할 때, **요청한 조건과 검사하는 기준이 같아지도록** 하는
규칙입니다. 요청에는 크기를 적었는데 검사는 눈대중으로 하면, 규격에 맞지 않는 파일이 「요청대로
만들었다」는 이유로 통과합니다. 특정 생성 도구의 기본 출력 크기나 기본 화풍을 프로젝트 기준으로 쓰지
않습니다.

---

## 1. 원본 하나를 모든 기기에서 씁니다

프로젝트가 지원하는 모든 기기에서 **에셋 원본 하나**를 쓰고, 표시 크기와 배치로 맞추는 것이 기본입니다.
기기마다 이미지 세트를 따로 만들면 한 곳을 고칠 때 나머지가 옛 그림으로 남고, 그 차이는 기기를 바꿔
보기 전까지 드러나지 않습니다.

- 상태마다 실제 그림이 다른 파일(누름 · 비활성 등)이나 늘어나는 프레임의 부품 세트는 기기별 사본이
  아닙니다. 이것들은 각각 별개의 에셋입니다.
- 원본 하나로 선명도나 반드시 보여야 하는 그림 영역을 지킬 수 없으면, 실패 조건과 대안(기기군별
  원본 · 부품 분리 등)을 제안하고 승인을 받은 뒤 예외로 둡니다.
- 필요한 정보를 외부 디자인 도구 안에서만 볼 수 있게 두지 않습니다. 설명 · 파일 · 제작 기록을 프로젝트
  안에 갖춥니다.

## 2. 제작 전에 확인할 내용

**기존 에셋**은 전체 목록에서 사용처 · 파일 크기 · 실제 그림 영역 · 투명 여백 · 상태 · 원본과 변환본의
관계를 조사합니다. 이름이 같다는 이유로 같은 에셋이나 중복 파일로 단정하지 않습니다. **새 에셋**도
기존 파일을 다시 쓸 수 있는지 먼저 봅니다.

제작 요청에는 역할 · 사용 화면과 상태 · 공용 여부 · 승인된 참고 파일 · 유지할 특징과 바꿀 부분을
적습니다. 리사이징 방식 · 최대 표시 크기 · 필요한 픽셀 밀도도 함께 확인하고, 재지 않은 값을 사실로
쓰지 않습니다 — 모르는 값은 `?`로 둡니다.

## 3. 제작 크기를 정하는 법

**화면 표시 크기와 파일 제작 픽셀 크기는 다른 값입니다.** 한 화면 해상도를 전체 디자인 기준으로
고정하거나, 모든 파일을 가장 큰 화면 해상도로 만들지 않습니다. 에셋마다 사용 크기 · 비율 · 필요한
선명도에서 정합니다.

1. **출발 계산** — 사용 조건마다 「논리 표시 크기 × 그 조건의 픽셀 밀도」를 구하고, 그중 실제로 필요한
   최대치를 출발 크기로 삼습니다. 예: 논리 24×24로 표시하고 지원 기기의 최대 밀도가 3이면 72×72px이
   출발 크기입니다. 이 예는 계산 방법이며 모든 기기의 밀도를 3으로 정한 것이 아닙니다.
2. **역할별 제작 단위** — 프로젝트가 역할마다 캔버스 단위를 정합니다(예: 정사각형 아이콘은 2의
   거듭제곱, 일반 이미지 캔버스는 정한 px 배수, 화면 배치 기본값은 정한 논리 단위). 출발 크기를 그
   단위의 가까운 위 값으로 올립니다.
3. **일괄 반올림하지 않는 값** — 테두리 · 9분할 절단 좌표 · 반응형 계산 결과는 단위로 일괄 반올림하지
   않습니다. 단위는 캔버스 크기를 정하는 도구이지 모든 좌표를 맞추는 규칙이 아닙니다.
4. **후보표는 출발점입니다** — 역할별 크기 후보표를 둘 수 있지만, 그것은 검토를 시작하는 값이지 최종
   규격도 품질 보장도 아닙니다. 더 작은 원본으로 충분하면 더 작은 규격을, 최대 표시 조건에서
   부족하면 더 큰 규격을 제안합니다. 정사각형이 아닌 그림을 정사각형 후보에 맞추려고 왜곡하지
   않습니다.
5. **확정 규격은 한 곳에 둡니다** — 최종 승인 규격은 리사이징 정책과 에셋 등록부로 연결하고, 후보표와
   따로 두 벌로 관리하지 않습니다.

투명 여백이 있으면 파일 캔버스뿐 아니라 **실제 그림에 배정된 픽셀**도 봅니다. 배경은 전체 채움으로
확대 · 잘린 뒤의 선명도를, 늘어나는 프레임은 고정 부품과 반복 · 확장 부품을 각각 검사합니다.

기존 에셋과 이전 요청문도 같은 단위 기준으로 다시 봅니다. 현재값 · 새 후보 · 그림 비율과 여백 보정
방법 · 영향받는 코드 · 승인 상태를 함께 적고, 실측값과 반입 원본은 지우지 않고 남긴 채 새 규격의
결과를 비교해 등록합니다. 개별 파일을 새 후보로 일괄 변환하지 않습니다.

## 4. AI에 전달할 제작 조건

| 항목 | 반드시 구분할 내용 |
|---|---|
| 대상 | 에셋 이름 · 역할 · 사용 화면 · 공용 또는 전용 |
| 출력 | 목표 너비×높이 px · 파일 형식 · 투명 배경 여부 |
| 비율 | 캔버스 · 그림 · 배치 영역 중 어디에 적용하는지와 유지할 비율 |
| 그림과 여백 | 실제 그림 영역 · 사방 여백 · 정렬 기준점 · 반드시 보일 부분 |
| 시각 기준 | 승인된 참고 파일과 유지할 색 · 선 · 모서리 · 장식 |
| 크기 변화 | 고정 · 확장 · 반복 · 잘림 허용 영역과 관련 정책 |
| 상태 | 필요한 상태 목록, 상태마다 바뀌는 부분과 유지되는 부분 |
| 납품 | 생성 결과 · 적용한 보정 · 검사 결과 · 원본 관계 |

- **상태별 이미지는 캔버스 · 기준점 · 주요 부품 위치를 맞추고, 승인된 차이만 그립니다.** 위치가 흔들리면
  상태가 바뀔 때 화면이 튑니다.
- **동작은 이미지에 굽지 않습니다.** 입력값 · 오류 안내 · 버튼 조작 · 키보드 · 화면 전환은 화면 코드가
  처리합니다. 코드로 표현할 수 있는 단순한 상태 변화 때문에 이미지를 더 만들지 않습니다.
- **도구가 목표 크기나 투명도를 직접 내지 못하면 그 제한을 먼저 적습니다.** 더 크게 낸 뒤 줄이거나
  여백을 정리하는 등 보정 방법을 정하고, **보정한 뒤의 파일을** 검사합니다.
- **「프롬프트에 크기를 적었다」는 규격 준수가 아닙니다.** 규격은 결과 파일을 재서 확인합니다.

## 5. 제작 요청 양식

중괄호는 실제 제작 전에 채울 자리입니다. 값이 필요한 항목을 `?`로 둔 채 최종 규격이 정해진 것처럼
진행하지 않습니다. 탐색용 시안은 시안이라고 표시합니다.

```text
에셋 이름과 역할: {이름 / 용도}
사용처와 상태: {공용 또는 화면 전용 / 필요한 상태}
관련 정의: {화면 흐름 또는 공용 UI 정본의 위치}
리사이징 기준: {정책 이름 · 개정 · 적용 방식}
표시 범위: {논리 크기 · 최대 표시 조건 · 픽셀 밀도 근거}
최종 출력: {너비×높이 px / 형식 / 투명 여부}
제작 단위: {역할의 캔버스 단위 / 적용 대상 / 승인된 예외}
비율 · 그림 영역: {적용 대상 / 비율 / 여백 / 기준점}
참고 파일과 유지할 특징: {프로젝트 안 파일 / 색 · 선 · 형태}
변경할 내용: {이번 제작에서 바꿀 부분}
상태별 차이: {바뀌는 부분 / 위치와 크기를 유지할 부분}
늘어날 부분과 잘리면 안 되는 부분: {영역별 조건}
도구 제한과 보정 방법: {필요한 경우}
검사 기준: {목표값 / 허용 오차 / 화면 비교 조건}
배치 예정 경로: {승인된 폴더와 파일 이름}
```

## 6. 결과 검사와 재작업

| 검사 | 확인할 내용 |
|---|---|
| 파일 규격 | 실제 파일 형식 · 너비 · 높이 · 투명 채널이 요청과 같은가 |
| 단위 체계 | 역할의 캔버스 단위와 배치 기본값을 지켰고, 반응형 결과나 테두리를 일괄 반올림하지 않았는가 |
| 그림 영역 | 투명 여백 · 그림 크기 · 정렬 · 비율이 기준과 같은가 |
| 상태 비교 | 상태가 바뀔 때 위치 · 외곽 크기가 의도 없이 흔들리지 않는가 |
| 작은 표시 | 줄였을 때 선 · 장식 · 의미가 구분되는가 |
| 큰 표시 | 최대 사용 조건에서 흐림 · 계단 현상 · 압축 손상이 없는가 |
| 리사이징 | 프레임 왜곡 · 잘림 · 반복 경계 · 반드시 보일 영역의 손실이 없는가 |
| 표시 환경 | 지원하는 모든 기기의 해당 사용 조건에서 배치와 선명도를 확인했는가 |

- **1px 차이도 목표값과 실제값을 적습니다.** 원인을 원본 · 여백 · 반올림 · 표시 계산 중에서 가립니다.
  허용 오차가 승인되지 않았으면 차이를 임의로 통과시키지 않습니다. 투명 영역은 잰 방법과 기준을 함께
  남깁니다.
- **어긋나면** 기존 승인 범위 안에서 보정하고 다시 검사합니다. 형태 · 구도 · 규격을 바꿔야 하면
  변경안을 제안합니다.
- **저해상도 원본을 키워 픽셀 수만 맞춘 결과는 품질 개선이 아닙니다.** 크기 검사를 통과해도 「큰 표시」
  검사에서 걸러냅니다.
- **확인하지 못한 기기나 상태는 미검증으로 남깁니다.** 검사하지 않은 칸을 통과로 적지 않습니다.

## 7. 추적 — 생성 · 검사 · 승인은 다른 상태입니다

확정 전 결과는 후보로 두고, 최종 승인 파일만 등록합니다(`asset-registry.md`). 확인할 수 있는 범위에서
제작 도구 · 모델 정보, 요청문 · 참고 파일 · 출력 원본 · 보정 방법 · 검사 결과 · 승인 근거를 추적할 수
있게 남깁니다.

- **생성 · 검사 통과 · 승인은 서로 다른 사실입니다.** 세 상태를 한 칸에 합치지 않습니다.
- **기존 에셋 전체를 정비할 때는 파일마다 상태를 둡니다** — 미검토 · 기준 적용 완료 · 재제작 필요 ·
  승인된 예외. 대표 파일 몇 개가 통과한 것을 전체 완료로 표시하지 않습니다.
- 새 파일을 등록하기 전에 승인된 제작 기준과 검사 결과를 확인하고, 사용처의 경로를 함께 잇습니다.
- 생성 도구가 임의로 만든 폴더 분류를 실행용 에셋 구조로 받아들이지 않습니다. 새 폴더가 필요하면
  `asset-folders.md` 「폴더 추가와 구조 변경 절차」를 따릅니다.
