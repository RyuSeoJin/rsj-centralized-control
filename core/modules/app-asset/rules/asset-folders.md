# asset-folders — 에셋을 어디에 어떤 이름으로 두고, 폴더를 어떻게 늘리는가

실행용 에셋의 위치 · 이름 · 공유 방식과 폴더를 늘리는 절차를 정합니다. 폴더를 필요할 때마다 만들면
같은 종류의 파일이 여러 갈래로 흩어지고, 화면 코드와 등록부가 서로 다른 사본을 가리키게 됩니다.
그래서 구조는 미리 승인받은 것만 쓰고, 늘릴 때는 제안 → 승인 → 반영 순서를 거칩니다.

---

## 1. 실행용 에셋과 다른 자료를 구분합니다

| 구분 | 담는 것 | 어디서 정하나 |
|---|---|---|
| 실행용 에셋 | 배경 · 장식 · 버튼 이미지 · 아이콘 · 글꼴처럼 화면이 직접 불러 쓰는 파일 | 이 문서와 등록부 |
| 화면 정의 | 에셋의 사용 영역 · 배치 · 리사이징 정책, 입력 · 포커스 · 오류 · 화면 전환 조건 | 기획 정본 |
| 화면 구현 | 실제 입력창 · 버튼 조작 영역 · 키보드 · 글자 · 상태 전환을 실행하는 코드 | 구현 쪽 |

HTML · CSS · JavaScript 구현 파일과 화면 참고 캡처는 실행용 에셋이 아닙니다. 기존 자료의 HTML은 배치와
동작을 확인하는 데 쓰고, 필요한 정보를 옮겼는지 확인하기 전에 지우지 않습니다. 형식 변환이나 원본
정리는 별도 작업으로 합니다. 편집 도구 전용 원본은 실행용 에셋 루트와 다른 자리에서 관리합니다.

## 2. 기본 폴더 구조

실행용 에셋 루트 아래를 **공용**과 **화면 전용**으로 나누는 것이 기본안입니다. 프로젝트는 이 구조를
승인하고 루트 경로와 실제 폴더 이름을 정합니다. 실제 파일이 필요해질 때 그 폴더를 만들며, 빈 폴더를
미리 만들지 않습니다.

```text
{에셋 루트}/
├── shared/                    공용 에셋 — 여러 화면이 같은 파일을 씀
│   ├── icons/
│   ├── buttons/
│   │   └── {버튼 종류}/       상태별 파일을 한 벌로
│   ├── dialogs/
│   └── fonts/
└── screens/                   화면 전용 에셋
    └── {화면}/
        ├── background.png
        └── {부품}/            여러 장이 한 부품을 이루면 한 폴더로
```

위 파일 이름은 배치 예시이며, 그 파일이 있다거나 디자인이 승인됐다는 뜻이 아닙니다. 비슷한 낱말이
다른 뜻으로 쓰이면 구조 문서에 뜻을 적어 둡니다(예: 알림 · 입력용 창과 이야기 장면의 대사 영역).

## 3. 파일을 배치하는 기준

| 상황 | 배치 기준 |
|---|---|
| 한 화면에서만 쓰는 파일 | 화면 전용 아래 그 화면 폴더에 둡니다 |
| 여러 화면이 같은 파일을 쓰는 경우 | 공용에서 한 번만 관리하고 같은 파일을 참조합니다 |
| 역할은 같지만 그림이 다른 경우 | 서로 다른 에셋입니다. 이름이 같다는 이유로 합치지 않습니다 |
| 한 부품에 여러 이미지가 필요한 경우 | 그 부품 폴더에서 한 벌로 관리합니다 — 늘어나는 프레임의 조각 등 |
| 새 화면 · 부품 · 상태 분류가 필요한 경우 | 「폴더 추가와 구조 변경 절차」를 먼저 거칩니다 |

- **공용 여부는 실제 사용처로 정합니다.** 「나중에 다른 화면도 쓸 것 같다」는 가능성만으로 공용에 넣지
  않습니다. 사용처가 불분명하면 배치를 미루고 확인할 내용을 남깁니다.
- **기존 파일을 공용으로 옮길 때는** 이동 경로와 영향받는 화면을 먼저 제안합니다.
- **같은 파일을 화면마다 복사하지 않습니다.** 기존 이미지 · 변환본 · 내보내기 파일은 내용과 사용처를
  비교하기 전까지 중복으로 단정하거나 지우지 않습니다.

## 4. 이름과 상태별 이미지

- **폴더와 파일 이름은 영문 소문자 · 숫자 · 하이픈으로, 역할이 드러나게 씁니다.** 관리용 약자 · 날짜 ·
  버전 번호 · `final` 같은 진척 표현을 넣지 않습니다. 파일의 변경은 변경 기록이 관리합니다 — 이름에
  넣으면 고칠 때마다 이름이 바뀌어 참조가 끊깁니다.
- **상태별 파일은 그림이 실제로 다를 때만 만듭니다.** 색 · 테두리 · 투명도를 화면 코드로 바꿀 수
  있으면 상태마다 이미지를 만들지 않습니다. 상태가 없는 이미지에 기본 상태 접미사를 의무로 붙이지
  않습니다. 상태 이름은 프로젝트가 한 벌로 정합니다(예: 기본 · 누름 · 비활성 · 포커스 · 오류).
- **함께 움직이는 장식은 묶고, 따로 크기를 바꾸거나 상태가 바뀌는 부품은 나눕니다.**
- **이미지에 입력값 · 오류 문구 · 조작 영역을 굽지 않습니다.** 글자와 입력 동작은 화면 정의를 기준으로
  화면 코드가 처리합니다.

## 5. 화면 정본에서 참조하는 법

화면 정본의 구성 항목에 영역 이름 · 실제 파일 경로 · 표시 방법 · 적용할 리사이징 정책을 적습니다.
Markdown 링크는 그 문서 위치에서 실제 파일로 이어지게 걸고, 설명용 경로를 실제 링크처럼 쓰지
않습니다.

예: 회원가입 화면의 이름 입력칸은 입력 장식 이미지와 실제 입력 요소를 나눠 적습니다. 포커스 때 쓸
이미지가 있으면 그 파일을 잇고, 코드로 테두리 색을 바꾸면 그 동작을 적습니다. 키보드가 올라오는 것과
화면 이동은 이미지가 아니라 화면 동작으로 정의합니다.

## 6. 폴더 추가와 구조 변경 절차

상태나 사용 화면이 늘 때도 구조를 함께 검토할 수 있도록, **승인된 구조 밖의 폴더는 먼저 제안하고
승인을 받은 뒤에 만듭니다.** 새 화면 폴더 · 공용 분류 · 부품 폴더 · 상태별 하위 폴더가 모두
해당합니다. 파일을 넣으려고 임시 폴더를 먼저 만드는 방식으로 이 절차를 건너뛰지 않습니다.

1. **필요성 확인** — 기존 승인 폴더에 넣을 수 없는 이유와 필요한 사용처를 확인합니다.
2. **제안** — 아래 표의 항목으로 추가 · 변경안을 사용자에게 보입니다.
3. **승인 대기** — 승인 전에는 폴더를 만들거나 파일을 놓지 않습니다. 응답이 없거나 검토 중인 상태는
   승인이 아닙니다.
4. **기록과 반영** — 승인된 경로 · 범위를 프로젝트의 에셋 구조 문서(기본 구조 또는 「승인된 추가
   구조」)와 change-log에 남긴 뒤 폴더를 만들고 파일을 놓습니다.
5. **참조 확인** — 등록부 · 화면 정본 · 화면 코드의 경로를 함께 고치고, 파일 존재 · 링크 · 중복을
   확인합니다.

| 제안에 넣을 항목 | 적는 내용 |
|---|---|
| 추가 이유 | 어떤 화면 · 상태에 필요하며, 기존 구조로는 왜 부족한가 |
| 제안 경로 | 에셋 루트부터 시작하는 정확한 경로 |
| 놓을 파일 | 넣을 파일과 각 역할. 아직 만들지 않은 파일은 예정이라고 표시합니다 |
| 영향 범위 | 바뀌기 전 · 뒤의 구조, 기존 파일 이동과 참조 수정 여부 |
| 요청할 승인 | 어느 폴더 생성과 파일 배치까지 승인을 구하는가 |

- 이미 승인된 정확한 경로를 필요한 때 만드는 것은 다시 승인받지 않습니다. 승인된 폴더에 역할이 맞는
  파일을 더하는 것도 구조 변경이 아닙니다.
- **구조 승인은 디자인 승인이 아닙니다.** 폴더를 승인받았다고 그 안에 놓을 그림의 디자인이나 사용
  조건까지 승인된 것은 아닙니다.
- 승인 범위를 넘는 폴더 추가 · 이름 변경 · 통합 · 분리는 다시 제안합니다. 승인되지 않은 안은
  remaining-work에 두고 승인된 구조에 섞지 않습니다.
- 구조를 처음 적용할 때 기존 참고 자료 폴더를 실행용 에셋으로 자동 편입하지 않습니다. 파일마다
  사용처와 원본 · 변환본 관계를 확인한 뒤 승인된 구조에 놓습니다. 옛 분류를 새 구조로 바꿔도 옛
  변경 기록은 당시 기록으로 남깁니다.
