앱 기획의 다섯 문서를 두 종류의 슬라이드로 냅니다. 내용은 사람이 프롬프트로 주고, Claude가 정해진
입력(JSON)을 채우고, 도구(`scripts/build_slides.py`)가 그 입력에서 .pptx를 만듭니다. 도구를 거치는
이유는 문서마다 구성과 모양이 갈리지 않게 하려는 것입니다 — 손으로 만들면 프로젝트마다, 기능마다
목차와 표의 열이 조금씩 달라집니다.

---

## 1. 두 문서

| 문서 | 몇 벌 | 담는 것 |
|---|---|---|
| **프로젝트 전체 문서** | 프로젝트당 한 벌 | 표지 · 문서 이력 · 목차(쪽 번호) · **읽는 법** → **개요서**(기획 배경 · 해결할 문제 · 페르소나 · 핵심 가치 제안 · 범위 · KPI) → **정보 구조도**(메뉴 · 화면 트리, 주요 흐름) → **기능 정의서 목록**(기능 ID · 기능명 · 화면 · 요약 · 정책 · 외부 연동 · 우선순위, 우선순위 장은 MoSCoW → 영향×노력) → 기능별 문서 색인 → 미결 사항 |
| **기능별 문서** | 기능 ID마다 한 벌 | 표지(기준 문서) · 문서 이력 · 목차 · **읽는 법** → **01 기능 개요**(현행 · 개선 비교, 요약 · 사용자 스토리 · 앱 안의 위치 · 용어, **이 기능의 화면** 표와 바로가기 · 연결 화면) → **02 흐름**(기능 흐름도 · 화면 흐름) → **03 기능 정의**(입력값 · 처리 순서, 조건 · 정책 · 외부 연동, 수용 기준) → **04 화면 상세**(화면마다 한 묶음: 와이어프레임(역할 · 영역 · 이동) → 화면설계서 → 화면 상태 → 예외 처리) → 미결 사항 |

두 문서는 **기능 ID**로 이어집니다. 전체 문서의 기능 목록에 있는 ID가 기능별 문서의 표지가 됩니다.
`build_slides.py all`이 양쪽 ID를 대조합니다 — 목록에 없는 기능별 문서는 오류이고, 기능별 문서가
아직 없는 ID는 알림입니다. 범위 밖 기능(`scope: out` 또는 `moscow: wont`)은 문서가 없어도 알리지 않습니다.

### 1-1. 작성 순서

**전체 문서를 먼저 확정하고 기능별 문서로 내려갑니다.** 아래 문서일수록 세부가 늘어나므로, 위가
흔들린 채 아래를 그리면 다시 그리게 됩니다. 특히 와이어프레임은 기능 정의가 끝난 뒤에 그립니다 —
먼저 그리면 빠진 기능을 뒤늦게 발견합니다.

1. 개요서 — 팀이 같은 방향을 보는지 여기서 맞춥니다
2. 정보 구조도 — 화면을 그리기 전에 빠진 화면과 끊긴 경로를 찾습니다
3. 기능 정의서 — 큰 기능을 세부 동작 단위로 쪼개고 **정책까지 이 단계에서 확정합니다**
4. 기능별 문서 — 와이어프레임 → 화면설계서 → 예외 처리

### 1-2. 기능별 문서는 처음 보는 사람이 앞에서부터 읽힙니다

기능별 문서는 프로젝트를 모르는 사람(새로 온 개발자 · 디자이너)이 앞에서부터 읽어 이해할 수 있는 순서입니다
— 「무엇이고 어디 있나 → 무슨 일이 어떤 순서로 → 어떤 규칙으로 → 화면마다 무엇을」. 그래서

- 기호 · 표기는 앞쪽 「읽는 법」 한 장에 모읍니다.
- 화면 찾기는 목차가 아니라 01 개요의 「이 기능의 화면」 표가 맡습니다(쪽 번호는 그 장으로 가는 링크).
  다른 기능의 화면으로 이동하면 그 화면도 이름과 함께 표에 나옵니다 — `linked_screens`.
- 흐름(02)을 규칙(03)보다 먼저 둡니다. 무슨 일이 일어나는지 알아야 규칙이 읽힙니다.
- 화면 하나에 관한 것(배치 · 동작 · 상태 · 예외)은 04에서 한 묶음입니다. 섹션 라벨에 화면 ID가 붙습니다.

**처음 읽는 사람 점검** — 기능별 문서의 구성이나 패턴을 바꾸면, 맥락을 모르는 사람(또는 맥락 없이 띄운
검토 에이전트)에게 렌더링한 장만 앞에서부터 보이고 아래를 답하게 합니다. 틀리거나 막힌 곳을 고치고 다시
시험합니다.

1. 이 기능은 무엇이고 앱의 어디에 있나, 앞뒤 기능은?
2. 어떤 화면이 있고 각각 무슨 역할인가, 다른 기능의 어느 화면으로 나가나?
3. 핵심 행동을 하면 어떤 순서로 무슨 일이 일어나나?
4. 대표 예외(비로그인 · 데이터 없음 · 네트워크 오류)에서는 어떻게 되나?
5. 문서의 기호와 표기는 각각 무슨 뜻인가, 변경 배지는 무엇에 비해 바뀐 것인가?
6. 아직 정해지지 않은 것은?
7. 어디서 처음 막혔고, 무엇을 몰라서 막혔나?

### 1-3. 화면설계서는 예외까지가 끝입니다

화면마다 **비로그인 · 데이터 없음 · 네트워크 오류 · 잘못된 입력** 네 경우를 항상 찍습니다. 같은 오류라도 「불러올 때」와 「행동할 때」가 다르면 처리 칸에 나눠 적습니다. 입력에
없으면 `?`로 찍어 미결로 드러냅니다. 해당하지 않으면 「해당 없음」처럼 적습니다 — 빈칸과 「해당
없음」은 다릅니다. 네 경우 밖의 예외(동시 신청 등)는 더 적으면 그대로 뒤에 붙습니다.

### 1-4. 화면 이동과 처리 경로를 구분합니다

처리·조건 노드를 화면으로 그리면 실제로 없는 화면이 생깁니다. 그래서 화면 흐름의
`screens[].next[].to`에는 `screens` 또는 `linked_screens`에 등록한 **화면 ID만** 씁니다.
화면 ID는 화면·시트·팝업처럼 사용자가 보는 UI를 식별하고, `flow.nodes[].id`는 행동·판정·처리
단계를 식별합니다. 화면 이름의 접두나 코드 모양만 보고 종류를 추측하지 않습니다.

- 화면 사이의 행동·조건·처리는 `flow.nodes`와 `flow.edges`에 보존합니다. `next`는 그 경로의
  도착 화면을 요약하며 `when`에 도착 조건을 적습니다. 여러 조건을 거치면 요소의 `behavior`·`sub`에
  조건과 관련 노드 코드를 적어 요약에서 빠진 경로를 찾을 수 있게 합니다.
- 처리만 일어나 화면이 유지되면 새 화면을 만들지 않습니다. 해당 요소의 `behavior`에 처리와
  유지되는 화면을 적고, 실제로 이동할 때만 `next`를 씁니다.
- 도착 화면이 미정이면 가짜 화면이나 자기 자신으로 연결하지 않습니다. 해당 이동을 `next`에서
  빼고 출발 화면·행동·미확인 조건을 `open_questions`에 남깁니다.
- 도구는 미등록 이동 대상, 빈 화면 ID, 중복 화면 ID와 처리·조건 노드를 가리키는 이동을 오류로
  막습니다. 등록한 이름이 실제 화면인지는 정본과 대조해 사람이 확인합니다.
- 원본 노드와 화면이 같은 ID를 쓰는 기존 자료는 화면 노드(`input`·`output`)인 경우에만 그 ID를
  함께 쓸 수 있습니다. `process`·`decision` 등 다른 종류의 노드를 화면 목록에 등록해 오류를
  우회하지 않습니다.

### 1-5. 중첩 UI는 배경과 닫힌 뒤 상태까지 적습니다

팝업·시트만 설명하면 아래 화면과 닫힌 뒤 동작을 알 수 없습니다. 해당 UI를 여는 요소의
`behavior`·`sub`에 아래 항목을 적습니다. 별도 화면으로 상세를 정의하면 화면 ID도 연결합니다.

| 항목 | 기록할 내용 |
|---|---|
| 표시 방식 | 전체 화면 교체 · 시트 · 팝업 · 토스트 · 화면 내 안내 중 실제 방식 |
| 아래 화면 | 유지되는 화면 ID와 보존되는 입력·스크롤·선택 상태 |
| 중첩 상태 | 추가 UI의 위치·가리는 범위·배경 조작 가능 여부 |
| 닫기 | 확인·취소·뒤로·바깥 누르기별 닫힘 여부와 복귀 화면·상태 |
| 처리 결과 | 닫기 전후 저장·요청 취소·재조회 여부와 중복 실행 방지 조건 |

확인하지 못한 항목은 `?`와 미결 사항으로 남깁니다. `modal` 같은 구현 이름만으로 표시 방식을
정하거나, 닫으면 항상 홈으로 간다고 가정하지 않습니다. 와이어프레임에는 유지되는 배경과 추가
UI의 관계를 보여 주고, 기능 흐름 화살표와 설명을 찾아가는 문서 링크를 구분합니다.

예를 들어 상세 화면 위 확인 시트에서 취소하면 원래 화면을 유지하는 사양이라면, 요소 설명에
「상세 화면 유지 · 확인 시트 중첩 · 취소 시 시트만 닫음 · 입력 보존」을 적습니다. 화면 흐름에는
확인 후 실제로 이동하는 도착 화면을 적고, 저장·판정은 기능 흐름에 적습니다. 이 예시는 프로젝트의
실제 취소 정책을 대신하지 않습니다.

### 1-6. 공통 UI와 상태별 차이는 함께 찾을 수 있게 적습니다

같은 배치를 상태마다 복제하면 수정할 때 문구와 동작이 갈라집니다. 공통 배치·구성·동작은
프로젝트가 정한 정본에 한 번 정의하고, 각 화면 요소의 `behavior`·`sub`에 그 문서·절 또는
화면 ID를 적습니다. 이 참조는 현재 생성기에서 설명 글로 표시하며 자동 링크나 상속으로 처리하지 않습니다.

- `states.empty`·`loading`·`error`의 `message`에는 상태별 실제 문구, `action`에는 사용자가
  할 행동, `note`에는 노출·해제 조건과 유지·변경 요소 및 공통 정의의 위치를 적습니다.
- 세 상태 밖의 선택·완료·중첩 상태는 관련 요소의 `behavior`·`sub`에 이름과 차이를 적습니다.
  생성기가 지원하지 않는 상태 키를 임의로 추가하지 않습니다.
- 공통 배치가 같아도 조건이나 문구가 다르면 상태를 합치지 않습니다. 반대로 시스템 처리만
  달라지고 UI가 같으면 화면을 추가하지 않습니다.
- 출처와 승인 상태는 관련 설명에 함께 적습니다. 구현 관찰과 사용자 확정을 구분하고,
  개략 와이어프레임을 실제 실행 화면이나 확정된 픽셀 배치로 설명하지 않습니다.

### 1-7. 기존 입력과 산출물의 이행

먼저 화면 목록과 이동 대상을 정본에 대조합니다. 미등록 화면은 이름·담당 기능을 확인해
`linked_screens`에 등록하고, 처리·조건 노드는 기능 흐름과 요소 설명으로 옮깁니다. 다음으로
중첩·복귀와 공통 상태 설명을 보완한 뒤 입력 검증·PPTX 재생성·렌더 검토를 진행합니다.
원문에 없는 조건이나 복귀 정책은 새로 확정하지 않고 미결로 남깁니다.

화면을 잘못 표시한 기존 산출물은 입력을 고친 뒤 재생성합니다. 과거 기록은 고치지 않으며,
이미 Google Slides로 정본이 넘어간 문서는 §2에 따라 공유본에서 수정합니다. 내용 변경이
필요 없는 기존 문서는 다음 편집 때 설명 규칙을 맞춥니다.

### 1-8. 기획 승인과 구현 확인을 별개로 적습니다

승인된 기획이 아직 구현되지 않을 수 있고, 실행 화면에서 본 동작이 승인된 정책이 아닐 수도
있습니다. 그래서 관련 규칙·요소 설명에 다음 두 상태와 근거를 함께 적습니다.

| 구분 | 표기와 근거 |
|---|---|
| 기획 상태 | 확정 · 검토 중 · 미정 · 보류. 확정에는 승인 기록의 위치와 승인 범위를 명시 |
| 구현 확인 | 실행 확인 · 코드 확인 · 미확인. 확인 대상 버전·환경과 출처를 명시 |

프로젝트에서 이미 사용하는 동등한 상태명은 유지하고 문서 앞에서 뜻을 설명합니다. `NEW`·`UPDATE`·
`DELETE`는 버전 간 변경 표시이며 승인이나 구현 완료 표시로 쓰지 않습니다. 날짜나 근거가 없으면
임의로 채우지 않고 미결로 남깁니다. 기계 검사 통과도 승인·구현 확인 상태를 바꾸지 않습니다.

현재 입력에서는 정책의 설명, `elements[].behavior`·`sub`, `states`의 `note`에 관련 상태·근거를
붙입니다. 같은 화면 안에서도 승인 범위가 다르면 행별로 구분하고, 문서 전체에 하나의 확정 상태를
붙여 개별 미정 항목을 가리지 않습니다.

### 1-9. 화면·흐름·설명은 같은 대상을 참조합니다

서로 다른 문서가 같은 화면을 다른 이름으로 가리키면 수정할 곳을 놓칩니다. 전체 문서의
`features[].screen`, 기능별 `screens`·`linked_screens`, 요소 설명과 예외 설명에서 같은 화면 ID를
사용하고 이름을 대조합니다. 처리 노드는 화면 ID로 바꾸지 않고 해당 노드 코드를 함께 참조합니다.

- 자동으로 만드는 목차·화면별 쪽 링크와 기능 흐름도의 화면 쪽(`nodes[].screen`)·기능 사이 이동
  연결자 링크는 생성기에 맡깁니다. 설명 속 참조는 문서명·ID·절을
  적어 클릭하지 않아도 목적지를 알 수 있게 합니다. 현재 설명 문자열의 ID·주소는 자동 링크로
  변환되지 않으므로 링크가 있다고 주장하지 않습니다.
- 문서 탐색 링크와 서비스의 실제 이동은 구분합니다. 화면 상세를 읽으러 가는 링크를 기능 흐름의
  화살표로 추가하지 않습니다. 외부 문서를 가리키면 문서 위치와 버전을 함께 적습니다.
- 이름이나 표시 번호를 바꿀 때는 화면 목록·흐름·요소·예외·관련 문서 참조를 함께 대조합니다.
  같은 대상을 여러 장에 다시 보여도 새로운 ID를 만들지 않습니다.
- 공통 UI는 정본 위치와 상태별 차이를 함께 읽을 수 있게 연결합니다. 정본을 못 찾으면
  내용을 추측해 복제하지 않고 미결로 남깁니다.

### 1-10. 분기와 복귀를 검수합니다

정상 경로만 읽으면 취소·실패 뒤 처리가 빠져도 발견하기 어렵습니다. 생성 전에 구조를 검사하고,
렌더링한 문서에서는 아래 의미를 검토합니다. 검사 절차를 모든 화면에 반복해 싣지 않습니다.

| 자동 검사 | 처리 |
|---|---|
| 빈·중복 흐름 노드 ID, 알 수 없는 도형·구역·연결 종류, 없는 노드 연결, 도착을 찾지 못한 반복 지점, 이전 형식 흐름, 미등록 화면 이동, 등록되지 않은 노드 `screen`, `path`가 없는 판정 객체 | 오류로 생성 중단 |
| 예(`yes`)·아니오(`no`) 출구가 모두 있지 않은 조건 노드 | 경고로 표시하고 실제 조건을 검토 |
| 시작·종료(`term`)가 아닌 노드의 출구 누락 | 경고로 표시하고 종료·복귀·미정 여부를 검토 |
| 자기 기능 ID로 가는 연결, 조건이 아닌 노드의 `check` | 경고로 표시하고 실제 도착 노드·조건 여부를 검토 |

| 사람이 확인할 것 | 확인 내용 |
|---|---|
| 조건 | 조건 하나의 판단 기준과 각 결과의 도착지, 여러 갈래라면 누락·중복 조건 |
| 취소·실패·재시도 | 보존되는 입력·상태, 재시도 가능 시점, 중복 요청·중복 지급 여부 |
| 복귀 | 돌아갈 화면과 상태, 시트·팝업을 닫는 범위, 필요한 재조회 |
| 참조 | 화면·노드·설명 ID의 실제 의미와 링크 목적지 |

조건의 「아니오」가 곧 오류는 아닙니다. 정상 대체 경로와 실제 예외를 구분하며 위치나 색을
맞추려고 조건을 뒤집지 않습니다. 미확정 분기는 임의 연결로 검사만 통과시키지 않습니다.
`open_questions`에는 대상 ID·상황·부족한 근거·정해야 할 내용을 적습니다. 구조 검사는
조건의 타당성이나 모든 경로의 도달 가능성을 보증하지 않습니다.

### 1-11. 기존 목차에 배치합니다

위 여섯 기준은 장을 여섯 개 더 만드는 순서가 아닙니다. 기존 읽기 순서를 유지합니다.

| 자리 | 담는 내용 |
|---|---|
| 읽는 법·앞부분 용어 | 승인·구현 확인 상태의 뜻, 화면 ID·노드 ID·참조 표기 |
| 01 기능 개요 | 화면 목록과 관련 문서 안내 |
| 02 흐름 | 화면과 처리 경로의 구분, 정상·대체·예외·복귀 경로 |
| 03 기능 정의 | 규칙과 그 규칙의 승인·구현 확인 상태 |
| 04 화면 상세 | 중첩·닫기·복귀, 공통 UI 참조와 상태별 차이 |
| 상세 사양 부록이 있는 경우 | 기존 상세 사양·근거를 유지하며 본문 ID와 연결 |
| 미결 사항 | 미확정 정책과 검수에서 발견한 누락 |

현재 기본 「읽는 법」 장은 기호 안내입니다. 프로젝트별 상태 정의는 `feature.terms`에 적어
앞부분 용어 표에 보이며, 이를 읽는 법 장의 자동 확장 기능으로 설명하지 않습니다. 모든 항목에
같은 검사 문구를 반복하거나 승인 상태만을 위한 별도 본문 장을 만들지 않습니다.

## 2. 정본과 공유본

```
planning/*.json (정본) ──build_slides.py──▶ .pptx (파생) ──Drive 업로드·변환──▶ Google Slides (공유본)
```

- **입력 JSON이 정본입니다.** 내용을 고칠 때는 JSON을 고치고 다시 만듭니다. .pptx는 파생물이라 손으로
  고치지 않습니다.
- Google Slides는 팀이 보고 의견을 다는 **공유본**입니다. 변환하면 처음 만든 .pptx와는 연결이 끊긴
  별도 파일이 됩니다.
- **공유본을 직접 고치기 시작하면 그 문서의 정본은 공유본으로 넘어갑니다.** 그때 프로젝트 change-log에
  「{문서} 정본을 Google Slides로 옮김」과 링크를 적고, 그 문서는 더 이상 JSON에서 다시 만들지 않습니다.
  다시 만들면 공유본에서 고친 내용이 사라집니다. 정본은 하나뿐이어야 합니다.
- 공유본의 링크는 프로젝트 change-log에 적습니다. 저장소에는 링크만 남기고 공유 범위는 Drive에서 정합니다.

## 3. 프로젝트 안의 자리

```
planning/
├─ {슬러그}-overview.json        프로젝트 전체 문서의 입력
├─ features/
│   └─ {기능 ID}.json            기능별 문서의 입력 — 파일 이름은 기능 ID 그대로
└─ slides/                       생성물(.pptx) — 커밋하지 않습니다
```

- `slides/`의 .pptx는 언제든 다시 만들 수 있는 이진 파일이라 커밋하지 않습니다. 프로젝트의
  `.gitignore`에 `planning/slides/`를 더합니다.
- 화면 ID(`S2-01`)와 기능 ID(`F-MEET-02`)는 프로젝트가 정합니다. 한 번 정하면 바꾸지 않습니다 — 기능별
  문서 파일 이름과 다른 문서의 참조가 함께 끊깁니다.

## 4. 프롬프트로 만드는 순서

1. **요청을 받습니다.** 사용자가 쓸 수 있는 프롬프트는 `../design-template/prompt-guide.md`에 있습니다.
2. **물을 것을 묻습니다.** 같은 문서의 「물을 것」 목록에서 비어 있는 것을 한 번에 묻습니다. 사용자가
   「모르면 비워 두라」고 하면 `?`로 남깁니다. **추측으로 채우지 않습니다** — 추측한 값이 슬라이드에
   찍히면 확정된 값처럼 읽힙니다.
3. **입력을 채웁니다.** `../design-template/`의 예시와 같은 형식으로 `planning/`에 씁니다.
4. **만들고 검사합니다.**

   ```bash
   python core/modules/app-planning-slides/scripts/build_slides.py all projects/{제품}/{슬러그}/planning
   ```

   오류가 있으면 만들지 않습니다. 경고(IA에 없는 화면 · 번호가 맞지 않는 요소 등)와 미결 수를 사용자에게
   알립니다.
5. **Google Slides로 옮깁니다.** Google Drive에 .pptx를 올리고 Google 형식으로 변환합니다(Drive
   설정의 「업로드 파일 변환」, 또는 파일을 열어 「Google 프레젠테이션으로 저장」). 연결된 Drive 도구로
   올릴 때는 변환을 끄지 않습니다.
6. 공유본 링크를 프로젝트 change-log에 적습니다.

## 5. 입력 형식

필드 전부는 예시 파일이 보여 줍니다. 여기에는 규칙이 있는 것만 적습니다.

| 자리 | 규칙 |
|---|---|
| `schema` | `app-planning/overview@1` · `app-planning/feature@1`. 다르면 만들지 않습니다 |
| `project` | 두 문서에 같은 값을 씁니다. `name`이 없으면 만들지 않습니다 |
| `overview.personas` | 1~2명. 넓은 정의(「20~40대」) 대신 구체적인 한 사람으로 씁니다. 셋째부터는 그리지 않습니다 |
| `overview.value` | 핵심 가치 제안은 **한 문장**입니다 |
| `ia.tree` | `id` · `name` · `children`. 잎이 14개를 넘으면 최상위 메뉴마다 한 장으로 나눠 그립니다. 선택: `kind`(`page` · `tab` · `popup` · `external`) · `login`(참 · 거짓) · `change`(`NEW` · `UPDATE` · `DELETE`) — 화면 목록과 범례가 이 값을 씁니다 |
| `ia.flows` | `path`는 트리의 `id` 목록입니다. 트리에 없는 ID는 경고입니다 |
| `ia.flows[].exceptions` | 선택. 예외 갈래 `from` · `when` · `to` · `back`(선택). `from`은 그 흐름의 `path`에 있어야 합니다(없으면 오류). `to`는 화면 ID 또는 글이며, 화면 ID처럼 보이는데 IA에 없으면 경고합니다. 정상 단계 아래 줄에 주황 점선 상자로 그려집니다 |
| `features[].id` | 프로젝트 안에서 겹치지 않습니다. 기능별 문서 파일 이름이 됩니다 |
| `features[].screen` | 문자열 또는 목록(기능 하나가 여러 화면에 걸칠 때). IA의 잎 화면(외부 링크 제외)마다 범위 안 기능이 하나 이상 있어야 합니다 — 없으면 경고합니다 |
| `features[].scope` | 선택. `in`(기본) · `out`. `out`이거나 `moscow`가 `wont`이면 범위 밖 — 기능 목록 맨 아래, 영향×노력 · 기능별 문서 색인에서 빠집니다(`slide-patterns.md` §4). `out`인데 `moscow`가 `must` · `should`면 오류입니다 |
| `features[].policy` | 정책이 없으면 「없음」이라고 적습니다. 비우면 미결로 셉니다 |
| `features[].impact` · `effort` · `moscow` | 선택. `high` · `low`와 `must` · `should` · `could` · `wont`. 있으면 우선순위 장이 생깁니다(MoSCoW 장 → 영향×노력 장). 기능 목록 「우선」 칸은 MoSCoW가 있으면 그 이름(반드시 · 해야 함 · 하면 좋음), 없으면 `priority`입니다 |
| `overview.journey` · `glossary` · `policies` · `roadmap` | 선택. 사용자 여정 · 용어 정의 · 공통 정책 · 로드맵 장이 생깁니다. 모양은 예시 입력과 `slide-patterns.md` §3 |
| `feature.story` · `acceptance` | 사용자 스토리 한 문장과 수용 기준(`given` · `when` · `then`) |
| `feature.location` | 앱 안의 위치 — `path`(메뉴 경로) · `before` · `after`(앞뒤 기능). 비면 미결로 셉니다 |
| `feature.terms` | 이 문서에 나오는 용어(`term` · `definition`) — 처음 읽는 사람이 막히는 말 |
| `screens[].role` | 화면의 역할 한 문장 — 화면 표와 와이어프레임 장에 나옵니다. 비면 미결로 셉니다 |
| `linked_screens` | 이동 대상이지만 다른 기능의 화면(`id` · `name` · `feature`). ID는 비어 있거나 자체 화면과 중복될 수 없습니다. 이름이 없으면 경고합니다. 처리·조건을 화면으로 등록하지 않습니다 |
| `project.base` | 기준 문서(예: 프로젝트 전체 기획서 v0.2). 없으면 프로젝트 버전으로 적습니다 |
| `project.change_base` | 전체 문서의 변경 배지(신규 · 수정)를 무엇과 비교했는지(예: 출시된 v1.0 앱). 전체 문서 「읽는 법」 장에 그대로 보입니다. 비었는데 배지가 있으면 경고합니다 |
| 변경 배지 | 문서 이력이 두 줄 이상일 때만 뜻이 있습니다 — 이력이 한 줄인데 배지가 있으면 경고합니다 |
| `flow` | 선택. 기능 흐름도 — 워크플로우 탐색기의 흐름 형식(`workflow-explorer/rules/explorer.md` §1)을 따릅니다. 기호 · 배치는 `slide-patterns.md` §3-1 |
| `flow.lanes` | 선택. `[{"key": "u", "label": "유저 구역"}, {"key": "s", "label": "시스템 구역"}]` — 생략하면 이 둘입니다. 유저가 입력·선택하는 도형은 유저 구역, 판단·처리·노출은 시스템 구역에 둡니다 |
| `flow.sections` | 선택. 코드 앞부분별 섹션 이름(`{"A1": "신청 확인"}`). 코드가 `A1-02`면 섹션은 `A1`이고, 섹션마다 한 장입니다 |
| `flow.nodes` | `id`(겹치지 않음) · `code`(보이는 단계 번호 · 없으면 `id`) · `type`(`term` 시작·종료 · `action` 행동·처리 · `input` 입력 · `output` 출력·노출 · `decision` 조건 · `process` 공통 처리 · `ref` 반복 지점) · `lane`(`flow.lanes`의 키) · `text`. `ref`만 `target`(되돌아갈 노드 `id`)을 가집니다 |
| `flow.nodes[].screen` | 선택. 그 도형이 보이는 화면 ID — `screens` 또는 `linked_screens`에 있어야 합니다(없으면 오류). 도형 곁의 「p. N」이 이 기능의 화면이면 와이어프레임 장, 다른 기능의 화면이면 「이 기능의 화면」 장으로 갑니다. 화면 이동(`screens[].next`)을 대신하지 않습니다(§1-4) |
| `flow.nodes[].check` | 선택 · 조건(`decision`)에만. 판정 기준 — 사람이 읽는 글, 또는 탐색기 객체 `{"path": …, "equals": …}`(「path = equals」로 보임). 마름모 곁에 「판정: …」으로 찍힙니다. 조건이 아닌 노드에 있으면 경고, 객체에 `path`가 없거나 글·객체가 아니면 오류입니다. 탐색기의 `state`는 시뮬레이터 전용이라 덱에서 쓰지 않습니다 |
| `flow.edges` | `from` · `to` · `kind`(`normal` · `yes` 조건 충족 · `no` 조건 불충족) · `label`(선택). 조건 노드에서는 `yes`·`no`를 씁니다. `to`는 노드 `id` 또는 다른 기능 ID(`F-MEET-03`) — 기능 ID면 「→ F-MEET-03」 연결자로 그리고 이 덱의 「이 기능의 화면」 장에 링크합니다(다른 기능의 덱은 별도 파일이라 파일 사이 링크를 걸지 않습니다). 자기 기능 ID면 경고입니다 |
| `flow` 이전 형식 | 오류로 만들지 않고 고칠 곳을 알립니다. `start`·`end` → `term`, `screen`·`io` → 노출이면 `output` · 입력이면 `input`, `process` → `action`(여러 흐름이 함께 쓰는 처리만 `process`), 레인 `사용자` → `u` · `앱`·`서버` → `s`, `label` → `text`, `kind: exception` → 조건 불충족이면 `no`, 아니면 `normal` |
| `compare` | 선택. 현행 · 개선처럼 두 칸 비교 — `left` · `right`에 `label` · `items` |
| `screens[].path` · `change` | 화면 정보 띠의 경로(메뉴 위치)와 변경 배지. 경로가 비면 미결로 셉니다 |
| `screens[].states` | 선택. `empty` · `loading` · `error`마다 `message` · `action` · `note` |
| `screens[].regions` | `type`은 `header` · `nav` · `tab` · `button` · `input` · `list` · `image` · `text` · `card` · `banner` · `other`. `x` · `y` · `w` · `h`는 화면에 대한 백분율(0~100)이며, 생략하면 위에서부터 쌓습니다 |
| `screens[].elements` | `no`는 영역의 번호와 맞춥니다. 화면설계서의 번호 표식과 Description이 이 번호로 이어집니다. 선택: `sub`(하위 규칙 목록 — `1-1)` 형식으로 찍힘) · `change` |
| `screens[].exceptions` | `case` · `handling`과 선택 `message`(사용자에게 보이는 문구) · `id`(없으면 `E-{화면 ID}-{순번}`) |
| `screens[].next` | `element`(영역 번호) · `when`(조건 — 「누름」보다 버튼 이름 · 상황) · `to`(등록된 화면 ID) · `kind: exception`(예외 이동). 미등록 대상과 처리·조건 노드는 오류입니다(§1-4). kind가 없어도 조건이 기본 예외 말(비로그인 · 오류 등)이면 예외로 그립니다 |
| 목록 자리 전부 | `problems` · `needs` · `pains` · `scope` · `conditions` · `policies` · `compare.items` 등은 항목 다음에 목록을 두면 하위 단이 됩니다(`["상위", ["하위 1", "하위 2"]]`). 단마다 기호가 바뀝니다 — `slide-patterns.md` §4 |
| `open_questions` | 확정 전에 정할 것. 도구가 `?` 자리와 함께 「미결 사항」에 모읍니다 |

## 6. Google Slides에서 고칠 수 있게 — 변환 규칙

.pptx를 Google Slides로 변환하면 텍스트 상자 · 표 · 도형 · 선은 그대로 고칠 수 있지만, 아래 요소는
그림으로 굳거나 모양이 바뀝니다. 도구는 처음부터 이것을 쓰지 않고, `lint`가 확인합니다.

| 쓰지 않는 것 | 이유 | 대신 |
|---|---|---|
| Noto Sans KR 밖의 글꼴 | Google에 없는 글꼴은 다른 글꼴로 바뀌어 줄바꿈이 어긋납니다 | Noto Sans KR 하나 |
| 차트 · SmartArt | 변환 뒤 그림이 되어 고칠 수 없습니다 | 트리 · 흐름은 도형과 선 |
| 그라데이션 · 그림자 | 모양이 달라집니다 | 단색 |
| 이미지 | 와이어프레임 원칙(색 · 이미지 없음)과 맞지 않고, 붙인 그림은 저작권 게이트 대상입니다 | 회색 상자 · X자 선 |
| 자간 | Google Slides에 자간 설정이 없어 사라질 수 있습니다(쓰기는 하되 기대지 않음) | 줄 간격으로 여유를 함께 줍니다 |
| 슬라이드 레이아웃(마스터)에 기댄 자리 | 일부만 옮겨집니다 | 슬라이드마다 직접 놓습니다 |

```bash
python core/modules/app-planning-slides/scripts/build_slides.py lint {파일}.pptx
```

## 7. 디자인

장 구성 · 패턴 · 가독성 규칙의 정본은 `slide-patterns.md`입니다. 여기에는 색과 모양의 요점만 둡니다.


- 16:9 와이드. 짙은 남색 잉크(`22313F`)와 주홍 강조(`E4572E`) 하나, 카드 바탕은 옅은 회색입니다.
- 목차의 쪽 번호는 도구가 다 만든 뒤 채웁니다. 손으로 적지 않으므로 장이 늘어도 어긋나지 않습니다.
  기능별 문서는 화면이 10개를 넘으면 화면별 쪽표가 목차 다음 장으로 이어집니다.
- 표는 **테두리를 한 색 · 한 두께**(`BAC4CD` · 0.75pt)로 씁니다 — 바깥 · 안쪽 · 머리줄 · 본문이 모두 같습니다.
  선이 갈리면 이음새가 어긋나고 머리줄만 떠 보이므로, 구분은 선이 아니라 칸 채우기가 맡습니다.
  머리줄은 옅은 청회색(`E6EBF0`) 바탕에 짙은 굵은 글자, 본문은 흰 바탕에 짝수 행만 아주 옅은
  바탕(`F8FAFB`)입니다. 화면 정보 띠 · 여정 · 로드맵의 격자도 같은 선과 머리 칸 색을 씁니다.
  값은 `slidekit.py`의 `TABLE` 한 곳에서 정합니다.
  칸 테두리는 변환 뒤에도 Google Slides 표 테두리로 남습니다.
- 와이어프레임은 회색 단색만 씁니다. 「무엇이 어디에 있는가」를 정하는 단계라 색이 들어가면 디자인
  논의로 번집니다.
- 화면설계서는 왼쪽에 번호 표식이 붙은 와이어프레임, 오른쪽에 번호별 동작 표를 둡니다. 요소가 7개를
  넘으면 같은 화면을 이어지는 장으로 나눕니다.
- 디자인을 바꿀 때는 도구의 색 상수를 고치고 예시 둘로 다시 만들어 확인합니다.
