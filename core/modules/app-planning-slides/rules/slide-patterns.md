# slide-patterns — 기획 슬라이드의 장 구성 · 패턴 · 가독성 규칙

기획 슬라이드는 장마다 모양이 달라지기 쉽습니다. 같은 정보는 같은 모양으로, 같은 자리에 두어야
읽는 사람이 장을 넘겨도 눈이 같은 곳을 봅니다. 이 문서는 **어떤 정보를 어떤 패턴으로 그리는가**와
**모든 장이 지키는 가독성 · 일관성 규칙**을 정합니다. 국내 화면설계서 관례와 공개된 기획 · 슬라이드
설계 자료를 참고해 정했습니다(§6).

패턴은 `scripts/patterns.py`에, 패턴이 쓰는 부품(색 · 글꼴 · 도형 · 표 · 배지 · 범례)은
`scripts/slidekit.py`에 있습니다. 모든 패턴이 들어간 견본 덱은 아래 명령으로 만들어 봅니다.

```bash
python core/modules/app-planning-slides/scripts/build_slides.py gallery {출력 폴더}
```

## 1. 화면설계서 프레임

화면을 다루는 장(와이어프레임 · 화면설계서 · 화면 상태 · 예외 처리)은 모두 같은 틀을 씁니다.

```
┌ 섹션 라벨 · 제목 ─────────────────────────────────────────────┐
│ [화면 ID│값][화면명│값][경로│값               ][버전│값]  (변경 배지) │  ← 화면 정보 띠
│ ①─┌──────┐   Description                                   │
│ ②─│ 화면  │   ① 요소 이름          (변경 배지)               │
│ ③─│ 틀    │      동작 설명                                  │
│   │       │      1-1) 하위 규칙                             │
│   └──────┘   ② …                                          │
└ 푸터 · 쪽 번호 ─────────────────────────────────────────────┘
```

- **화면 정보 띠**: 화면 ID · 화면명 · 경로 · 버전. 경로는 메뉴 위치를 `상위 > 하위`로 씁니다.
  화면은 쪽 번호가 아니라 **화면 ID로 가리킵니다** — 장이 늘어도 다른 문서의 참조가 어긋나지 않습니다.
- **번호 표식**: 와이어프레임 영역 왼쪽 바깥에 강조색 원을 두고 지시선으로 잇습니다. 번호는 1부터
  건너뛰지 않고, Description의 같은 번호와 1:1로 맞춥니다. 화면 안의 색은 무채색만 씁니다.
- **Description**: 번호 · 굵은 요소 이름 · 동작 설명. 하위 규칙은 `1-1)` 형식입니다. 넘치면 같은
  화면을 이어지는 장으로 나눕니다(높이로 계산합니다).
- **동작 설명에 적는 것**: 누르면 어디로 가는가(화면 ID · 열림 방식), 목록의 개수 · 정렬 · 빈 상태,
  확인 · 취소 창의 문구와 각 버튼의 결과, 조건에 따라 달라지는 노출.
- **동적 데이터**는 `{모임 이름}`처럼 중괄호로 씁니다. 더미 글자(Lorem 등) 대신 실제와 비슷한 예를 씁니다.
- **변경 표시**: 화면 · 요소가 새로 생기거나 바뀌면 `NEW`(신규) · `UPDATE`(수정) · `DELETE`(삭제) 배지를
  답니다. 같은 내용을 문서 이력에도 적습니다. 배지는 색만이 아니라 글자를 함께 씁니다.

## 2. 장 구성 순서

`[선택]`은 입력에 그 자리가 있을 때만 생깁니다. 없는 장의 자리를 비워 두지 않습니다.

| 프로젝트 전체 문서 | 기능별 문서 |
|---|---|
| 표지 · 문서 이력 · 목차 | 표지 · 문서 이력 · 목차(화면별 쪽표) |
| 01 개요서 — 배경 · 문제 / 페르소나 / 핵심 가치 · 범위 / KPI | 01 기능 정의 — 요약 · 입력값 · 처리 순서 |
| [선택] 사용자 여정 · 용어 정의 | [선택] 사용자 스토리 · 수용 기준 |
| 02 정보 구조도 — IA 트리 / 화면 목록 / 주요 흐름 | 조건 · 정책 · 외부 연동 |
| [선택] 공통 정책 | [선택] 기능 흐름도 · 현행 · 개선 비교 |
| 03 기능 정의서 — 기능 목록 | 02 와이어프레임 — 화면 흐름 / 화면별 영역 · 이동 |
| [선택] 우선순위(영향 × 노력 · MoSCoW) · 로드맵 | 03 화면설계서 — 화면별 Description / [선택] 화면 상태 |
| 04 기능별 문서 색인 · 미결 사항 | 04 예외 처리 · 미결 사항 |

## 3. 패턴 카탈로그

| 패턴 | 쓰는 자리 | 입력 | 최대 · 넘칠 때 |
|---|---|---|---|
| 목차 (`draw_toc`) | 두 문서의 목차 | 자동 | 쪽 번호는 도구가 끝에서 채웁니다 |
| IA 트리 (`draw_tree`) | 정보 구조도 | `ia.tree` — `kind` · `change` | 잎 14개 — 넘으면 최상위 메뉴마다 한 장 |
| 화면 목록 | 정보 구조도 | IA 잎에서 자동 — `login` | 12행 — 다음 장 |
| 주요 흐름 칩 | 정보 구조도 | `ia.flows` | 흐름 4개 · 단계 7개 |
| 사용자 여정 (`journey_map`) | 개요서 | `overview.journey` | 단계 6개 · 칸당 2줄 |
| 용어 · 공통 정책 표 | 개요서 · IA | `glossary` · `policies` | 10행 · 9행 — 다음 장 |
| 우선순위 2×2 (`priority_matrix`) | 기능 정의서 | `features[].impact` · `effort` | 사분면당 6개. 값이 없는 기능은 「판단 전」에 모읍니다 |
| MoSCoW 보드 (`moscow_board`) | 기능 정의서 | `features[].moscow` | 칸당 8개 |
| 로드맵 (`roadmap`) | 기능 정의서 | `roadmap` | 트랙 6개. 오늘 선 하나 |
| 사용자 스토리 · 수용 기준 | 기능 정의 | `feature.story` · `acceptance` | 기준 7개 |
| 순서도 · 스윔레인 (`flowchart`) | 기능 정의 | `flow` — `lane`이 있으면 레인 | 노드 15개 · 레인 5개 |
| 비교 (`compare`) | 기능 정의 | `compare` | 칸당 6개 |
| 화면 정보 띠 (`storyboard_header`) | 화면 장 전부 | `screens[].path` · `change` | — |
| 와이어프레임 (`phone`) | 화면 장 | `screens[].regions` | 영역 표 8행 |
| Description (`description_list`) | 화면설계서 | `screens[].elements` — `sub` · `change` | 높이로 나눠 다음 장 |
| 화면 상태 (`ui_states`) | 화면설계서 | `screens[].states` | 빈 화면 · 불러오는 중 · 오류 |
| 예외 처리 표 | 예외 처리 | `screens[].exceptions` — `message` | 기본 네 경우는 항상, 9행까지 |
| 배지 (`badge`) · 범례 (`legend`) | 어디서나 | — | 범례는 오른쪽 아래 같은 자리 |

### 3-1. 순서도 기호

| 기호 | 뜻 |
|---|---|
| 캡슐(짙은 색) | 시작 · 종료 |
| 사각형 | 화면 |
| 둥근 사각형 | 처리 |
| 평행사변형 | 입력 · 출력 |
| 마름모 | 분기 — 질문 하나, 나가는 갈래에 「예 · 아니오」 라벨 |
| 점선(강조색) | 예외 경로 — 정상 경로를 먼저 실선으로 그립니다 |

같은 줄의 다음 노드로는 오른쪽 변에서 나갑니다. 분기의 위 · 아래 갈래는 마름모의 위 · 아래 꼭짓점에서
나가고, 되돌아가는 선은 출발 상자의 위 · 아래 변에서 대상의 오른쪽 변으로 들어갑니다. 선이 노드를
지나지 않게 하려는 배치입니다. 노드가 15개를 넘으면 흐름을 나눠 그립니다.

### 3-2. IA 노드 형태

| 형태 | 모양 |
|---|---|
| `page` 페이지 | 둥근 사각형 |
| `tab` 탭 | 옅은 색 캡슐 |
| `popup` 팝업 | 점선 테두리 |
| `external` 외부 링크 | 점선 테두리 + ↗ |

## 4. 가독성 · 일관성 규칙

| 항목 | 규칙 |
|---|---|
| 여백 | 좌우 0.6in(폭의 약 5%). 본문은 제목 아래 1.45in부터 푸터 위까지 |
| 제목 | 모든 장이 같은 자리 · 같은 크기(섹션 라벨 11pt · 제목 26pt). 마침표를 찍지 않습니다 |
| 글자 크기 | 단계를 줄입니다 — 제목 26 · 소제목 14~16 · 본문 12~14 · 표 10~11 · 화면 안 8 · 각주 9. 화면 안 글자도 8pt 밑으로 내리지 않습니다 |
| 양 | 목록은 한 칸에 6개 이하, 한 줄은 한글 30자 안팎. 넘치면 장을 나눕니다 — 글자를 줄여 밀어 넣지 않습니다 |
| 표 | 테두리는 바깥 · 안쪽 · 머리줄 · 본문 모두 한 색 · 한 두께(`BAC4CD` · 0.75pt). 머리줄은 옅은 청회색 바탕에 짙은 굵은 글자, 짝수 행은 아주 옅은 바탕. 열은 3~7개, 행은 10~12개. 글은 왼쪽 정렬 |
| 선 | 1pt 이하, 글자보다 옅은 색. 연결선은 직선과 직각 꺾임만 씁니다 |
| 색 | 무채색이 기본이고 강조색은 하나(번호 표식 · 섹션 라벨 · 예외 경로). 상태색(신규 · 수정 · 삭제 · 진행)은 뜻이 있을 때만, 글자와 함께 |
| 번호 정렬 | 번호 표식(원 · 큰 숫자) 오른쪽 글은 **첫 줄의 세로 중심을 표식의 세로 중심에 맞춥니다**. 위끝을 맞추면 글이 표식보다 높아 보입니다. 둘째 줄부터는 아래로 이어집니다. 도구는 `numbered_item` · `first_line_top`으로 계산하므로 좌표를 손으로 맞추지 않습니다 |
| 글머리 기호 | 단계마다 기호를 바꿔 깊이를 보입니다 — 1단 ■(강조색) · 2단 ◆ · 3단 ● · 4단 –(회색). 채움만 다른 짝(◆ · ◇, ■ · □)은 작으면 구분되지 않아 쓰지 않습니다. 기호 뒤는 내어쓰기라 줄이 넘어가도 글자 시작선이 맞습니다. 「•」는 쓰지 않습니다. 입력에서 항목 다음에 목록을 두면 그 항목의 하위 단이 됩니다 |
| 소제목 | 카드 · 칸 안의 소제목 앞에는 ▼를 붙여 「아래가 이 묶음」임을 보입니다(토글처럼). ▼ 뒤 글자와 소제목 아래 내용(글 · 글머리 · 번호 목록 · 표)은 모두 `TOGGLE_STEP`(0.3in)만큼 들어가 한 선에 맞습니다. 장 제목과 표 머리줄에는 붙이지 않습니다 |
| 범례 | 비표준 기호가 있는 다이어그램은 오른쪽 아래 같은 자리에 범례를 둡니다 |
| ID | 화면 ID · 기능 ID · 정책 ID · 예외 ID로 문서 사이를 잇습니다. 쪽 번호로 가리키지 않습니다(목차만 예외) |
| 모르는 값 | `?`로 찍고 미결 사항에 모읍니다 |

## 5. 패턴을 더하거나 고칠 때

1. 번호 목록은 `numbered_item`, 글머리 목록은 `bullets`, 카드 소제목은 `subhead`를 씁니다 — 정렬 · 기호 규칙(§4)이
   그 안에 들어 있어, 새 패턴도 따로 맞추지 않아도 같은 모양이 됩니다.
2. 부품이 필요하면 `slidekit.py`에, 구성 단위는 `patterns.py`에 둡니다. 덱 조립(`build_slides.py`)에
   좌표를 흩어 두지 않습니다.
3. Google Slides에서 고칠 수 있는 요소만 씁니다(`planning-slides.md` §6). `lint`가 확인합니다.
4. 예시 입력에 그 패턴이 쓰는 자리를 더해 견본 덱에 나타나게 하고, 렌더링해 눈으로 봅니다.
5. 이 문서의 §2 · §3과 `planning-slides.md` §5의 입력 표를 함께 고칩니다.
