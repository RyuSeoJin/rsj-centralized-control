# slide-patterns — 기획 슬라이드의 장 구성 · 패턴 · 가독성 규칙

기획 슬라이드는 장마다 모양이 달라지기 쉽습니다. 같은 정보는 같은 모양으로, 같은 자리에 두어야
읽는 사람이 장을 넘겨도 눈이 같은 곳을 봅니다. 이 문서는 **어떤 정보를 어떤 패턴으로 그리는가**와
**모든 장이 지키는 가독성 · 일관성 규칙**을 정합니다. 국내 화면설계서 관례와 공개된 기획 · 슬라이드
설계 자료를 참고해 정했습니다(§6).

패턴은 `scripts/patterns.py`에, 패턴이 쓰는 부품(색 · 글꼴 · 도형 · 표 · 배지 · 범례)은
`scripts/slidekit.py`에 있습니다. 모든 패턴이 들어간 견본 덱은 아래 명령으로 만들어 봅니다.

```bash
python core/modules/app-planning-slides/scripts/build_slides.py gallery {출력 폴더}
```

## 1. 화면설계서 프레임

화면을 다루는 장(와이어프레임 · 화면설계서 · 화면 상태 · 예외 처리)은 모두 같은 틀을 씁니다.

```
┌ 섹션 라벨 · 제목 ─────────────────────────────────────────────┐
│ [화면 ID│값][화면명│값][경로│값               ][버전│값]  (변경 배지) │  ← 화면 정보 띠
│ ①─┌──────┐   Description                                   │
│ ②─│ 화면  │   ① 요소 이름          (변경 배지)               │
│ ③─│ 틀    │      동작 설명                                  │
│   │       │      1-1) 하위 규칙                             │
│   └──────┘   ② …                                          │
└ 푸터 · 쪽 번호 ─────────────────────────────────────────────┘
```

- **화면 정보 띠**: 화면 ID · 화면명 · 경로 · 버전. 경로는 메뉴 위치를 `상위 > 하위`로 씁니다.
  화면은 쪽 번호가 아니라 **화면 ID로 가리킵니다** — 장이 늘어도 다른 문서의 참조가 어긋나지 않습니다.
- **번호 표식**: 와이어프레임 영역 왼쪽 바깥에 강조색 원을 두고 지시선으로 잇습니다. 번호는 1부터
  건너뛰지 않고, Description의 같은 번호와 1:1로 맞춥니다. 화면 안의 색은 무채색만 씁니다.
- **Description**: 번호 · 굵은 요소 이름 · 동작 설명. 하위 규칙은 `1-1)` 형식입니다. 넘치면 같은
  화면을 이어지는 장으로 나눕니다(높이로 계산합니다).
- **동작 설명에 적는 것**: 누르면 어디로 가는가(화면 ID · 열림 방식), 목록의 개수 · 정렬 · 빈 상태,
  확인 · 취소 창의 문구와 각 버튼의 결과, 조건에 따라 달라지는 노출.
- **동적 데이터**는 `{모임 이름}`처럼 중괄호로 씁니다. 더미 글자(Lorem 등) 대신 실제와 비슷한 예를 씁니다.
- **변경 표시**: 화면 · 요소가 새로 생기거나 바뀌면 `NEW`(신규) · `UPDATE`(수정) · `DELETE`(삭제) 배지를
  답니다. 같은 내용을 문서 이력에도 적습니다. 배지는 색만이 아니라 글자를 함께 씁니다.

## 2. 장 구성 순서

`[선택]`은 입력에 그 자리가 있을 때만 생깁니다. 없는 장의 자리를 비워 두지 않습니다.

| 프로젝트 전체 문서 | 기능별 문서 |
|---|---|
| 표지 · 문서 이력 · 목차 · **읽는 법** | 표지(기준 문서) · 문서 이력 · 목차 · **읽는 법** |
| 01 개요서 — 배경 · 문제 / 페르소나 / 핵심 가치 · 범위 / KPI | 01 기능 개요 — [선택] 현행 · 개선 비교 / 요약 · 스토리 · 위치 · 용어 / 이 기능의 화면 |
| [선택] 사용자 여정 · 용어 정의 | 02 흐름 — [선택] 기능 흐름도 · 화면 흐름 |
| 02 정보 구조도 — IA 트리 / 화면 목록 / 주요 흐름 | 03 기능 정의 — 입력값 · 처리 순서 / 조건 · 정책 · 외부 연동 / [선택] 수용 기준 |
| [선택] 공통 정책 | 04 화면 상세 — 화면마다: 와이어프레임 → 화면설계서 → [선택] 화면 상태 → 예외 처리 |
| 03 기능 정의서 — 기능 목록 · [선택] 우선순위(MoSCoW → 영향×노력) · 로드맵 | 미결 사항 |
| 04 기능별 문서 색인 · 미결 사항 | |

기능별 문서가 왜 이 순서인지는 `planning-slides.md` §1-2(처음 보는 사람이 앞에서부터 읽힘)에 있습니다.

우선순위 두 장은 묻는 것이 다릅니다. **MoSCoW 장을 먼저** 둡니다 — 이번 출시에 넣을지를 정합니다.
**영향×노력 장은 그다음**입니다 — 범위 안 기능을 어떤 순서로 만들지를 정하므로 범위 밖 기능은 빠집니다.

### 3-1. 기능 흐름도 기호

기능 흐름도는 워크플로우 탐색기의 흐름도 규칙(`core/modules/workflow-explorer/rules/explorer.md`
§1 데이터 형식 · §3 흐름도)을 슬라이드로 옮겨 그립니다(2026-10-12 사용자 결정). 탐색기 HTML을
실행하는 것이 아니라 도형 · 구역 · 연결선 · 자동 배치 규칙을 생성기 안에 따라 만든 것입니다.
같은 흐름을 탐색기와 기획 슬라이드에서 같은 모양으로 읽게 하려는 것입니다.

| 기호 | `type` | 뜻 |
|---|---|---|
| 알약 | `term` | 시작 · 종료 |
| 사각형 | `action` | 행동 · 처리 |
| 평행사변형 | `input` · `output` | 입력(유저가 넣거나 고름) · 출력(화면 · 시트 · 알림 노출) |
| 마름모 | `decision` | 조건 판단 — 질문 하나, 나가는 갈래에 「예 · 아니오」 |
| 양옆 세로선 사각형 | `process` | 공통 처리 — 여러 흐름이 함께 쓰는 처리 묶음 |
| 원 | `ref` | 반복 지점 — `target`의 도형으로 되돌아감 |
| 오각형 「→ 코드」 | (자동) | 이동 연결자 — 다른 섹션의 도형으로 감. 그 도형이 그려진 흐름도 장으로 슬라이드 링크가 걸립니다 |
| 오각형 「→ F-XXX-NN」 | (자동 · 연결의 `to`가 기능 ID) | 기능 사이 이동 연결자 — 다른 기능으로 넘어감. 이 덱의 「이 기능의 화면」 장으로 가는 링크 |
| 오각형 「↩ 코드」 | (자동) | 먼 복귀 — 두 열 이상 앞 도형으로 되돌아감(`FAR_BACK` 2) |
| 작은 「p. N」 | (도형의 `screen`) | 화면 쪽 링크 — 이 도형이 보이는 화면의 장으로 감 |
| 「판정: …」 | (조건의 `check`) | 판정 기준 — 조건이 무엇을 보고 예 · 아니오를 가르는가 |

- **구역**: 위가 유저 구역, 아래가 시스템 구역입니다. **유저가 입력 · 선택하는 도형은 유저 구역,
  판단 · 처리 · 노출은 시스템 구역**에 둡니다. 이름은 `flow.lanes`로 바꿀 수 있습니다.
- **도형 글**: 굵은 코드(`A1-02`) 아래에 문구를 둡니다.
- **섹션**: 코드 앞부분(`A1-02` → `A1`)이 섹션이고, 섹션마다 한 장입니다. 이름은 `flow.sections`.
  다른 섹션으로 가는 연결은 긴 선 대신 출발 도형 곁의 「→ 코드」 연결자와 짧은 선으로 그립니다.
- **배치**: 섹션으로 들어오는 도형을 맨 앞 열에 두고, 연결 순서대로 왼쪽에서 오른쪽으로 나아갑니다.
  주 경로는 앞 도형의 행을 이어 곧게 가고, 갈래는 새 행으로 쌓습니다 — 유저 구역은 구역 경계에서
  위로, 시스템 구역은 아래로 쌓습니다. 좌표는 입력에 적지 않습니다.
- **선 색**: 예 파랑(`2563EB`) · 아니오 빨강(`DC2626`) · 일반 진한 회색(`1E1E1E`) — 탐색기와 같습니다.
  이 장에만 있는 색 예외입니다(§4 「색」).
- **나가고 들어오는 점**: 조건은 오른쪽 · 아래 · 위 꼭짓점에서 나가고, 들어오는 선은 왼쪽 면을 나눠
  씁니다. 라벨(예 · 아니오 등)은 선이 시작되는 첫 선분 위에 선 색 테두리의 작은 상자로 얹습니다.
- **선끼리**: 선은 도형을 지나지 않고, 나란한 두 선은 0.12in 이상 떨어지며, 도형으로 들어가는
  마지막 구간은 약 0.2in 이상이라 화살표 머리가 꺾임을 덮지 않습니다. 연결 하나는 연결선 도형
  하나입니다(§4 「연결선」).
- **기능 사이 이동**: 연결의 `to`가 다른 기능 ID(`F-MEET-03`)면 그 기능으로 넘어가는 이동입니다.
  다른 섹션처럼 출발 도형 곁에 「→ F-MEET-03」 오각형을 두고 짧은 선으로 잇습니다. 다른 기능의 덱은
  별도 파일이고 Google Slides에서 파일 사이 링크는 믿을 수 없으므로, 연결자는 **이 덱의 「이 기능의
  화면」 장**(연결 화면 · 담당 기능이 있는 자리)으로 갑니다. 자기 기능 ID를 가리키면 경고입니다.
- **화면 쪽 링크**: 도형에 `screen`(등록된 화면 ID)이 있으면 도형 곁에 작은 「p. N」을 두고, 이 기능의
  화면이면 그 화면의 와이어프레임 장, 다른 기능의 화면(`linked_screens`)이면 「이 기능의 화면」 장으로
  링크합니다. 탐색기의 UI 구역 축소판 대신입니다 — 한 장에 흐름도와 축소판을 함께 두면 둘 다 작아져
  읽히지 않습니다.
- **판정 기준**: 조건(`decision`)에 `check`가 있으면 마름모 곁에 「판정: …」을 작게 적습니다. 글이면
  그대로, 탐색기 객체 `{"path", "equals"}`면 「path = equals」로 보입니다.
- **옮기지 않은 것**: 탐색기의 상호작용 기능 — 마우스를 올린 설명, 경로 강조, 시뮬레이터(`state`),
  배치 힌트 값, 노드 표 원본, UI 구역 축소판, 선 교차 다리 — 은 정적인 슬라이드에서 보일 수
  없어 옮기지 않습니다(2026-10-12 사용자 결정). 위 세 가지만 장 위에 보이는 형태로 옮겼습니다.
- **하위 섹션 · 서브루틴은 필요할 때 옮깁니다**(2026-10-12 사용자 결정): 기능 하나의 흐름이 탐색기의 하위 섹션
  조건(한 화면에서 고를 행동 2개 이상 · 그 뒤 도형 5개 이상)에 걸릴 만큼 커지면, 하위 섹션을 별도 장으로 그리고
  서브루틴 도형(공통 처리와 같은 양옆 세로선 사각형 · 보라 테두리 · 「▸」)에서 그 장으로, 하위 장의 「↑ 화면 코드」에서
  돌아오는 링크를 겁니다. 그때까지 그런 흐름은 섹션(코드 앞부분)을 나눠 그립니다.

화면 흐름(`screen_flow`)은 이 기호를 쓰지 않고 정상 실선 · 예외 주황 점선을 그대로 씁니다.

## 4. 가독성 · 일관성 규칙

| 항목 | 규칙 |
|---|---|
| 여백 | 좌우 0.6in(폭의 약 5%). 본문은 제목 아래 1.45in부터 푸터 위까지 |
| 제목 | 모든 장이 같은 자리 · 같은 크기(섹션 라벨 11pt · 제목 26pt). 마침표를 찍지 않습니다 |
| 글자 크기 | 단계를 줄입니다 — 제목 26 · 소제목 14~16 · 본문 12~14 · 표 10~11 · 화면 안 9 · 각주 9. 와이어프레임 화면 안 글자도 9pt 밑으로 내리지 않습니다 |
| 자간 · 줄 간격 | 모든 글에 자간(글자 크기의 3%)과 줄 간격 1.2배를 줍니다. Google Slides에는 자간 설정이 없어 변환하면 자간이 사라질 수 있으므로, 여유는 줄 간격이 함께 맡습니다. 값은 `slidekit.py`의 `LETTER_SPACING` · `LINE_SPACING` |
| 한글 줄바꿈 | 모든 글자를 한국어(`ko-KR`)로 표시해 띄어쓰기 단위로 줄을 바꿉니다. 표시가 없으면 한글을 글자 단위로 끊어 「있습 / 니다」처럼 음절이 다음 줄로 떨어집니다. 그래도 한 단어가 칸보다 길면 칸 폭을 넓히거나 열 비율을 바꿉니다 |
| 카드 높이 | 카드는 내용 높이에 맞춥니다 — 「본문 시작 위치(`CARD_BODY`) + 내용 높이(`est_text_height`) + 아래 여백(`CARD_PAD`)」 한 공식이라 어느 카드든 소제목 아래 · 카드 아래 여백이 같습니다. 카드 묶음은 남는 높이의 35%를 위에 두고 놓습니다(`group_top`). 큰 카드에 글 몇 줄만 있으면 비어 보입니다. 나란한 카드는 가장 긴 쪽에 맞춰 같은 높이로 둡니다 |
| 표 행 | 본문 표는 행 최소 높이 0.4in로 통일하고, 글이 길면 행이 늘어납니다. 화면 장 옆의 좁은 표만 0.32in입니다 |
| 화면 정보 띠 | 변경 배지가 있어도 띠는 항상 끝까지 늘이고, 배지는 마지막 칸 안 오른쪽에 둡니다 |
| 와이어프레임 글자 | 9pt 이상, 짙은 슬레이트(`3D4851`). 버튼은 짙은 회색 바탕에 흰 글자 |
| 양 | 목록은 한 칸에 6개 이하, 한 줄은 한글 30자 안팎. 넘치면 장을 나눕니다 — 글자를 줄여 밀어 넣지 않습니다 |
| 표 | 테두리는 바깥 · 안쪽 · 머리줄 · 본문 모두 한 색 · 한 두께(`BAC4CD` · 0.75pt). 머리줄은 옅은 청회색 바탕에 짙은 굵은 글자, 짝수 행은 아주 옅은 바탕. 열은 3~7개, 행은 10~12개. 글은 왼쪽 정렬 |
| 선 | 1pt 이하, 글자보다 옅은 색. 연결선은 직선과 직각 꺾임만 씁니다 |
| 연결선 | 도형과 도형을 잇는 선은 **꺾은선 연결선 도형 하나**로 그립니다 — 짧은 선 여러 개를 이어 붙이지 않습니다. 한 번 꺾으면 L자, 두 번 꺾으면 Z자, 위로 돌아 들어가면 ㄷ자입니다(`elbow`). 양 끝은 가능하면 도형의 연결점(위 · 왼쪽 · 아래 · 오른쪽 변 가운데)에 붙여 편집기에서 도형을 옮겨도 선이 따라오게 합니다. 평행사변형처럼 연결점 번호가 다른 도형, 화면 틀 바깥 자리(화면 이름 위 등), 한 변에서 여러 선이 비켜 나가는 자리처럼 연결점에 붙일 수 없는 끝에는 **보이지 않는 작은 앵커 도형(`connector-anchor`, 채움 · 테두리 없음)**을 그 자리에 두고 붙입니다 — 시작점은 나가는 방향 쪽 변, 끝점은 들어오는 쪽 변의 연결점을 씁니다. 붙지 않은 끝이 있으면 PowerPoint · Google Slides가 경로를 다시 계산할 때 선이 엉뚱한 방향으로 꺾입니다(`elbow`가 자동으로 둡니다). Z자의 꺾임 자리는 가능하면 두 끝 사이 가운데에 둡니다 — 편집기가 다시 그려도 기본 꺾임 자리와 같습니다. 범례 견본 · 구분선 같은 홑선은 그대로 `line`입니다. 기능 흐름도는 여기에 탐색기에서 옮긴 규칙을 더합니다 — 선은 도형을 지나지 않고, 나란한 선은 0.12in 이상 떨어지며, 마지막 구간은 약 0.2in 이상이고, 조건은 오른쪽 · 아래 · 위 꼭짓점에서 나갑니다(§3-1) |
| 색 | 무채색이 기본이고 강조색은 하나(섹션 라벨 · 번호 표식 · 1단 글머리 ■ · ▼ 표식 · 예외 경로 — 소제목 글자에는 쓰지 않음). 상태색(신규 · 수정 · 삭제 · 진행)은 뜻이 있을 때만, 글자와 함께. **예외: 기능 흐름도**는 탐색기와 같게 선 색을 예 파랑(`2563EB`) · 아니오 빨강(`DC2626`) · 일반 진한 회색(`1E1E1E`)으로 나눕니다(2026-10-12 사용자 결정 · 그 장에만). 예 · 아니오 라벨 글자를 함께 둡니다 |
| 번호 정렬 | 번호 표식(원 · 큰 숫자) 오른쪽 글은 **첫 줄의 세로 중심을 표식의 세로 중심에 맞춥니다**. 위끝을 맞추면 글이 표식보다 높아 보입니다. 둘째 줄부터는 아래로 이어집니다. 글자 중심은 줄 상자 중심이 아니라 렌더링해 잰 값(`GLYPH_MID`, 글자 크기의 0.70배)을 씁니다 — 크기가 다른 두 글을 맞출 때 어긋나지 않습니다. 원은 본문 한 줄 높이 정도, 원 뒤는 글머리처럼 짧은 간격이고, 항목 간격은 고정값이 아니라 「글 높이 + 0.16in」입니다. 도구는 `numbered_list` · `first_line_top`으로 계산하므로 좌표를 손으로 맞추지 않습니다 |
| 글머리 기호 | 단계마다 기호를 바꿔 깊이를 보입니다 — 1단 ■(강조색) · 2단 ◆ · 3단 ● · 4단 －(회색). 기호는 **본문과 같은 크기**로 찍어 첫 줄 글자의 세로 가운데에 놓습니다 — Noto Sans KR의 도형 기호는 같은 크기일 때만 중심이 한글과 같고, 줄이면 기준선 쪽으로 처집니다. 위첨자(기준선 올리기)로 맞추지 않습니다 — PowerPoint와 Google Slides가 글자를 더 줄입니다. 글꼴에 없는 기호(◾ · ⬥ · ▾ 등)는 다른 글꼴로 바뀌므로 쓰지 않습니다. 채움만 다른 짝(◆ · ◇, ■ · □)은 작으면 구분되지 않아 쓰지 않습니다. 기호와 글 사이는 공백 한 칸 너비이고, 내어쓰기라 줄이 넘어가도 글자 시작선이 맞습니다. 「•」는 쓰지 않습니다. 입력에서 항목 다음에 목록을 두면 그 항목의 하위 단이 됩니다 |
| 소제목 (토글 기준) | ▼ 소제목은 **같은 면(카드 하나, 또는 카드 없는 본문)에 소제목 묶음이 둘 이상일 때만** 씁니다 — ▼와 들여쓰기가 묶음의 시작과 범위를 보입니다(토글처럼). 예: 페르소나 카드의 원하는 것 · 불편한 것, 주요 흐름 이름들, 기능 개요의 사용자 스토리 · 앱 안의 위치 · 용어, 입력값 · 처리 순서, 와이어프레임 옆 역할 · 영역 구성 · 이동 흐름. ▼만 강조색이고 소제목 글자는 짙은 잉크 굵게입니다 — 글자까지 강조색이면 한 장에 강조색이 너무 많아집니다. ▼ 뒤 글자와 소제목 아래 내용(글 · 글머리 · 번호 목록 · 표)은 모두 `TOGGLE_STEP`(0.28in)만큼 들어가 한 선에 맞습니다. **카드 하나에 제목 하나뿐이면**(기획 배경 · 해결할 문제, 이번 범위 · 범위 밖, 조건 · 정책 · 외부 연동 카드) 카드 테두리가 이미 묶음이므로 ▼ 없이 굵은 잉크 제목(`card_title`)을 쓰고 본문은 제목과 같은 선에서 시작합니다. 곁에 하나뿐인 소제목(우선순위 장의 읽는 법, 화면설계서의 Description)도 ▼를 붙이지 않습니다. 장 제목 · 표 머리줄 · 카드 이름(페르소나 이름 · KPI) · 비교 카드 제목(전 · 후를 색으로 구분)에도 붙이지 않습니다 |
| 소제목 묶음 간격 | 한 카드 안에 ▼ 소제목 묶음이 여럿이면 고정 위치에 두지 않고, 앞 묶음이 끝난 자리에서 `SECTION_GAP`(0.22in)만 띄워 다음 소제목을 둡니다. 소제목에서 그 아래 본문까지는 `HEAD_BODY`(0.36in)입니다 |
| 목차 | 큰 번호와 제목은 글자 중심을 맞추고, 쪽 번호는 제목과 설명 두 줄 묶음의 세로 가운데에 둡니다. **목차의 쪽 번호와 「화면별 쪽」 표의 쪽 칸에는 그 장으로 가는 슬라이드 내부 링크를 겁니다**(`Deck.link`). 기능 흐름도의 「p. N」(화면 쪽)과 「→ 기능 ID」 연결자에도 같은 방법으로 덱 안 링크를 겁니다(§3-1). 쪽 번호와 링크 대상은 도구가 다 만든 뒤 함께 채우므로 어긋나지 않습니다. 링크 글자는 테마 링크 색을 본문 잉크색으로 바꿔 파랗게 바뀌지 않고, 밑줄은 누를 수 있다는 표시로 둡니다 |
| 범례 | 비표준 기호가 있는 다이어그램은 오른쪽 아래 같은 자리에 범례를 둡니다 |
| 범위 밖 | 기능의 `scope`가 `out`이거나 `moscow`가 `wont`이면 범위 밖입니다. 기능 목록 맨 아래에 두고 「우선」 칸에 「범위 밖」을 적습니다. 화면 목록의 기능 칸에는 「(범위 밖)」을 붙이고, 영향×노력 매트릭스와 기능별 문서 색인에서는 빼며 색인 아래에 그 안내를 한 줄 둡니다. 「우선」 칸은 MoSCoW가 있으면 그 이름(반드시 · 해야 함 · 하면 좋음), 없으면 `priority`입니다 |
| ID | 화면 ID · 기능 ID · 정책 ID · 예외 ID로 문서 사이를 잇습니다. 쪽 번호로 가리키지 않습니다(목차만 예외) |
| 모르는 값 | `?`로 찍고 미결 사항에 모읍니다 |

## 5. 패턴을 더하거나 고칠 때

1. 번호 목록은 `numbered_list`, 글머리 목록은 `bullets`, 카드 소제목은 `subhead`(▼ 묶음이 둘 이상일 때) · `card_title`(카드 하나에 제목 하나일 때), 도형 사이 연결선은 `elbow`를 씁니다 — 정렬 · 기호 규칙(§4)이
   그 안에 들어 있어, 새 패턴도 따로 맞추지 않아도 같은 모양이 됩니다.
2. 부품이 필요하면 `slidekit.py`에, 구성 단위는 `patterns.py`에 둡니다. 덱 조립(`build_slides.py`)에
   좌표를 흩어 두지 않습니다.
3. Google Slides에서 고칠 수 있는 요소만 씁니다(`planning-slides.md` §6). `lint`가 확인합니다.
4. 예시 입력에 그 패턴이 쓰는 자리를 더해 견본 덱에 나타나게 하고, 렌더링해 눈으로 봅니다.
5. 이 문서의 §2 · §3과 `planning-slides.md` §5의 입력 표를 함께 고칩니다.
