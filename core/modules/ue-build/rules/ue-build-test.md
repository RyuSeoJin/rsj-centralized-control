# ue-build-test — 명령으로 빌드하고 게임 창을 조작해 점검하는 절차

「고쳤다」가 아니라 **「실행해서 확인했다」**를 보고하려면, 빌드 · 실행 · 조작 · 기록이 매번 같은
순서여야 합니다. 이 문서는 그 순서와 이미 겪은 함정을 정합니다. 경로 · 명령은 자리 표시자로 적고,
실제 값은 프로젝트의 change-log 현행 기준이나 README에 둡니다.

---

## 1. 빌드

아래 두 명령은 터미널에서 바로 실행합니다(파일에 넣는 코드가 아닙니다).

```bash
# 에디터 대상 — 에디터가 불러 쓰는 DLL을 만듭니다. 평소에는 이것으로 빌드합니다
"{엔진}/Engine/Build/BatchFiles/Build.bat" {프로젝트}Editor Win64 Development -Project="{uproject}" -WaitMutex -NoXGE

# 게임 대상 — 실행 파일 하나를 따로 만듭니다. 에디터 DLL과 겹치지 않아 에디터가 켜져 있어도 컴파일됩니다
"{엔진}/Engine/Build/BatchFiles/Build.bat" {프로젝트} Win64 Development -Project="{uproject}" -WaitMutex -NoXGE
```

- **사용자가 켜 둔 에디터는 끄지 않습니다.** 그 에디터에는 저장하지 않은 작업이 있을 수 있고,
  켜고 끄는 것은 사용자의 몫입니다.
- Live Coding이 켜진 에디터가 떠 있으면 에디터 DLL을 잡고 있어 **에디터 대상 빌드가 막힙니다.**
  그때는 같은 소스를 **게임 대상**으로 빌드해 컴파일 오류 · 경고만 확인합니다. 에디터 대상 빌드는
  아직 끝나지 않은 것이므로 「에디터를 끈 뒤 에디터 대상 빌드」를 프로젝트 remaining-work에 남기고,
  보고에도 「게임 대상으로 컴파일만 확인함」이라고 적습니다.
- **시험용으로 직접 띄운 게임 · 에디터는 닫아도 됩니다.** 닫기 전에 그 프로세스의 실행 인자를 보고
  시험 인스턴스인지 확인합니다(§2 · §4에서 붙인 점검 전용 저장 폴더 같은 인자). 실행 파일 이름만
  보고 닫으면, `-game`으로 띄운 게임도 에디터와 같은 실행 파일이라 사용자의 에디터까지 닫힙니다.
- 결과는 **오류 0 · 경고 0**으로 보고합니다. 경고가 남으면 무엇인지 적습니다.
- 헤더에 `UPROPERTY` · `UFUNCTION`을 더했거나, 새 클래스 · `Build.cs` 수정이 있으면 Live Coding으로
  끝내지 않고 전체 빌드합니다.

실행 인자는 아래처럼 봅니다. 터미널(PowerShell)에서 바로 실행합니다.

```powershell
# 에디터 실행 파일로 뜬 프로세스를 전부 나열하고, 각 프로세스의 실행 인자 전체를 보여 줍니다
# CommandLine에 시험 때 붙인 인자(예: -saveddirsuffix={시험 이름})가 있는 것만 시험 인스턴스입니다
Get-CimInstance Win32_Process -Filter "Name='UnrealEditor.exe'" | Select-Object ProcessId, CommandLine
```

### 1-1. 여러 작업이 동시에 빌드할 때

여러 에이전트 · 터미널이 한 프로젝트를 함께 빌드하면, 빌드 도구는 한 번에 하나만 돌 수 있어 뒤의
빌드가 곧바로 실패하고, 다른 작업이 고치는 중인 파일 때문에 내 빌드가 깨지기도 합니다. 그래서
아래 넷을 지킵니다.

1. **빌드 명령에 늘 `-WaitMutex`를 붙입니다.** 붙이면 앞 빌드가 끝날 때까지 기다렸다가 돌고,
   빼면 다른 빌드가 도는 동안 곧바로 실패합니다.
2. **다른 작업이 고치는 파일에서 난 컴파일 오류는 내가 고치지 않습니다.** 그 작업의 중간 상태
   때문에 생긴 오류일 수 있고, 내가 손대면 두 작업이 같은 파일을 덮어씁니다. 잠시 뒤 다시
   빌드하고, 그래도 남으면 그 파일을 맡은 작업에 알립니다.
3. **결과는 빌드 도구 로그에서 셉니다.** 콘솔 출력은 다른 빌드의 출력과 섞이거나 잘리기
   때문입니다. 로그는 다음 빌드가 덮어쓰므로 내 빌드가 끝난 직후에 읽습니다.
4. **「성공」이어도 내가 고친 파일이 실제로 컴파일됐는지 로그에서 봅니다.** 다른 작업의 빌드가
   같은 소스를 먼저 컴파일했으면, 내 빌드는 「이미 최신」으로 건너뛰고 성공을 냅니다. 이때 내 빌드가
   확인한 것은 없습니다. 고친 파일 이름이 컴파일 줄에 없으면 앞 빌드의 결과를 확인하거나, 다른
   빌드가 끝난 뒤 그 파일을 다시 컴파일시켜 봅니다.

로그는 아래처럼 셉니다. 터미널에서 바로 실행합니다. 로그 자리는 엔진 판 · 컴퓨터에 따라 다를 수
있습니다.

```bash
# 컴파일러가 남긴 경고 · 오류 줄 수를 셉니다 — MSVC 형식은 「파일(줄): warning C…」입니다
grep -cE '\): (warning|error)' "{사용자}/AppData/Local/UnrealBuildTool/Log.txt"

# 고친 파일이 이번 빌드에서 컴파일됐는지 봅니다 — 줄이 하나도 안 나오면 건너뛴 것입니다
grep -n "{고친 파일}.cpp" "{사용자}/AppData/Local/UnrealBuildTool/Log.txt"
```

### 1-2. 일부만 커밋할 때 빌드 확인

작업 트리에 원인이 다른 변경이 섞였으면 커밋을 원인별로 나눕니다(`core/base/rules/git-rules.md`
§2-1). 그런데 작업 트리 전체로는 빌드가 되어도, **앞 커밋의 몫만으로는 빌드되지 않을 수 있습니다** —
뒤 커밋에 들어갈 선언을 앞 커밋의 코드가 쓰는 경우입니다. 그대로 커밋하면 이력의 그 시점은 빌드되지
않습니다. 그래서 앞 커밋을 제안하기 전에, 그 몫만 꺼낸 임시 작업 트리에서 처음부터 빌드해 봅니다.

1. 앞 커밋에 넣을 몫만 스테이징합니다. 공용 헤더처럼 여러 원인이 한 파일에 섞였으면 **hunk 단위로**
   그 몫만 담습니다 — 대화형 `git add -p`를 쓰거나, 그 몫의 hunk만 남긴 패치를
   `git apply --cached`로 스테이징합니다.
2. 스테이징한 몫을 패치로 떼어 임시 worktree에 적용합니다.
3. 임시 worktree에서 처음부터 빌드합니다. 중간 산출물이 없어 전체 빌드가 됩니다.
4. 결과를 커밋 제안에 적고(「앞 커밋 단독 빌드: 오류 0 · 경고 0」), 임시 worktree와 패치를 지웁니다.

아래는 1 ~ 4를 터미널에서 차례로 실행하는 명령입니다. `{임시 폴더}`는 저장소 밖의 빈 자리입니다.

```bash
# 1) 원래 작업 트리 — 앞 커밋 몫의 파일을 스테이징합니다(공용 헤더는 위 1의 방법으로 hunk만)
git add {앞 커밋 파일들}

# 2) 스테이징한 몫만 패치로 떼고, 마지막 커밋 상태의 임시 worktree를 만들어 그 패치를 적용합니다
git diff --cached > "{임시 폴더}.patch"
git worktree add --detach "{임시 폴더}" HEAD
git -C "{임시 폴더}" apply "{임시 폴더}.patch"

# 3) 임시 worktree의 uproject로 빌드합니다 — 컴파일 확인이 목적이라 게임 대상이면 충분합니다
"{엔진}/Engine/Build/BatchFiles/Build.bat" {프로젝트} Win64 Development -Project="{임시 폴더}/{uproject 파일 이름}" -WaitMutex -NoXGE

# 4) 빌드 산출물이 남아 있어 --force로 지우고, 패치 파일도 지웁니다
git worktree remove --force "{임시 폴더}"
rm "{임시 폴더}.patch"
```

## 2. 실행

- 게임은 에디터 바이너리로 `-game -windowed -ResX= -ResY=`처럼 창 모드로 띄웁니다. 점검용 데이터가
  필요하면 **점검 전용 저장 파일**을 인자로 넘기고, 사용자의 실제 저장 파일은 건드리지 않습니다.
- 첫 프레임 뒤에 엔진이 해상도 설정을 한 번 더 적용합니다. 창 크기 · 위치를 코드로 정했다면 **잠깐
  뒤에 한 번 더 적용**해야 값이 남습니다.

## 3. 창 조작 점검

1. **입력은 게임 창이 맨 앞에 있을 때만 보냅니다.** 다른 창이 앞에 있으면 클릭이 그 창으로 가서,
   사용자의 작업을 건드리거나 잘못된 결과를 「동작함」으로 읽게 됩니다. 도구가 앞 창을 확인하고
   아니면 멈추게 합니다.
2. **좌표계를 맞춥니다.** Windows 배율(예: 125%)에서 게임 프로세스가 DPI 가상화되면, 게임 안의 좌표는
   논리 픽셀이고 측정 도구는 물리 픽셀을 보고합니다. 창 크기가 「틀려 보이면」 먼저 배율을 의심합니다.
3. **스크린샷으로 확인합니다.** 누르기 전 · 뒤를 찍고, 확대가 필요하면 잘라 봅니다. 토스트처럼 잠깐
   떴다 사라지는 것은 찍는 시점을 맞춰야 하며, 못 봤다고 곧바로 버그로 적지 않습니다 — 개발용
   명령으로 다시 띄워 확인합니다.
4. 점검용 **개발 콘솔 명령**(특정 화면 열기 · 알림 띄우기 등)을 두면 빠릅니다. 배포 전에 남길지
   뺄지를 remaining-work에 적어 둡니다.

## 4. 자동 플레이 시험 운영

게임 안에서 정해 둔 순서대로 클릭 · 입력을 보내고 결과를 기록하는 개발용 시험(이하 자동 시험)을 둔
프로젝트의 운영 규칙입니다. 시험의 단계와 판정은 프로젝트가 정하고, 여기서는 돌리는 법과 결과를
읽는 법만 정합니다.

1. **시험 전용 저장 폴더로 돌립니다.** `-saveddirsuffix={시험 이름}`처럼 저장 자리를 바꾸는 실행
   인자를 붙여 실제 저장 · 설정 파일을 건드리지 않습니다. 같은 인자로 §1에서 시험 인스턴스인지도
   가립니다.
2. **OS 커서를 움직이는 단계가 있으면 인스턴스를 동시에 돌리지 않습니다.** 클릭을 게임 안에서 만든
   합성 입력으로 보내더라도, 휠 · 끌기 · 마우스 올리기처럼 커서 위치를 쓰는 단계는 실제 OS 커서를
   옮깁니다. 둘이 동시에 돌면 서로 커서를 빼앗아 매번 다른 단계가 실패합니다. 에이전트를 여러 개
   써도 시험은 한 줄로 세워 차례로 돌립니다.
3. **바깥 요인부터 가립니다.** 시험 중에 사용자가 마우스를 쓰면 「클릭을 보냈지만 받지 못함」 같은
   실패가 연달아 남습니다. 이런 실패는 같은 단계를 다른 언어로 돌리거나 다시 돌려, 같은 자리에서 다시
   나는지 본 뒤에 버그로 적습니다. 다시 나지 않으면 바깥 요인으로 적고 넘어갑니다.
4. **입력칸을 찾는 단계는 화면 밖의 칸도 찾게 만듭니다.** 찾는 단계가 지금 보이는 칸만 훑으면, 칸이
   모두 스크롤 상자 밖에 있을 때 하나도 못 찾고 실패합니다. 보이는 칸이 하나도 없을 때도 스크롤 상자
   안을 끌어와 찾게 합니다. 이 실패는 게임이 아니라 시험 도구 쪽의 함정입니다.
5. **결과는 세 갈래로 나눠 보고합니다** — 단계 실패(누르지 못함 · 기대한 화면이 아님) · 글자 넘침
   (글자가 칸 밖으로 나감) · 번역 없음(키가 그대로 나오거나 원문 언어로 나옴). 갈래마다 고칠 자리와
   고칠 사람이 다르기 때문입니다.
6. **화면 사진은 직접 봅니다.** 통과 · 실패 개수만 보고 「통과」라고 하지 않습니다. 겹침 · 잘림 ·
   엉뚱한 자리처럼 판정에 넣지 않은 문제는 사진에만 남습니다.

## 5. 결과 기록

- 확인한 것 · 못 한 것을 가릅니다. 「어느 렌더러 · 어느 모드에서 확인했는가」를 함께 적습니다.
- 버그로 보였다가 점검 방법의 문제로 밝혀진 것은 **정정 항목**으로 이력에 남깁니다(옛 항목을 고치지
  않습니다).
- 사용자 컴퓨터를 쓰는 점검은 사용자가 컴퓨터를 쓰지 않는다고 한 동안에만 합니다.

## 6. 알려진 함정

| 증상 | 원인 | 대응 |
|---|---|---|
| 빌드가 성공했는데 바뀐 동작이 안 보임 | 실행 중인 에디터 · 게임이 옛 DLL을 잡고 있음 | 시험용으로 띄운 것은 닫고 다시 빌드 · 실행. 사용자가 켠 에디터면 끈 뒤에 에디터 대상 빌드(§1) |
| 에디터 대상 빌드가 Live Coding 때문에 막힘 | Live Coding이 켜진 에디터가 에디터 DLL을 잡고 있음 | 사용자의 에디터는 끄지 않고 게임 대상으로 컴파일만 확인, 에디터 대상 빌드는 remaining-work에(§1) |
| 다른 빌드가 도는 동안 빌드가 곧바로 실패 | 빌드 도구는 한 번에 하나만 돎 | `-WaitMutex`(§1-1) |
| 빌드는 성공인데 고친 파일이 컴파일되지 않음 | 다른 작업의 빌드가 먼저 컴파일해 「이미 최신」으로 건너뜀 | 로그에서 그 파일의 컴파일 줄 확인(§1-1) |
| 나눠 커밋한 앞 커밋이 혼자서는 빌드되지 않음 | 뒤 커밋 몫의 선언을 앞 커밋이 씀 — 작업 트리 전체 빌드로는 안 보임 | 임시 worktree에서 그 몫만 빌드(§1-2) |
| 창이 설정보다 크거나 작게 보임 | DPI 가상화 — 논리 · 물리 픽셀 차이 | 배율을 곱해 비교(§3-2) |
| 창 크기가 첫 프레임 뒤 되돌아감 | 엔진이 해상도 설정을 다시 적용 | 잠깐 뒤 재적용(§2) |
| `SetRenderScale`로 줄인 위젯의 버튼이 안 눌림 | 렌더 변환은 그림만 바꾸고 누르는 영역은 그대로 | 배율 상자(ScaleBox)로 크기 자체를 바꾸기 |
| 자동 시험을 여럿 동시에 돌리면 매번 다른 단계가 실패 | 커서를 쓰는 단계가 OS 커서를 서로 빼앗음 | 시험은 한 줄로 차례로(§4-2) |
| 「클릭을 보냈지만 받지 못함」이 연달아 남 | 시험 중 사람이 마우스를 씀 | 다시 돌려 같은 자리에서 나는지 본 뒤 버그로(§4-3) |
| 입력칸이 있는데 찾는 단계가 실패 | 시험 도구가 보이는 칸만 훑음 — 칸이 모두 스크롤 밖 | 스크롤 상자 안을 끌어와 찾게(§4-4) |
| 층을 가진(layered) 창에서 투명색이 안 먹거나 창 전체가 검게 뜸 | DX12의 flip 방식 스왑 체인은 투명색(color key)을 쓰지 않음 | 투명 창이 필요하면 DX11 + tearing 끔(blt 방식), 아니면 영역 자르기(SetWindowRgn)로 대체 |
| 투명색으로 정한 순수 검정이 그림 속에서도 뚫림 | 투명색은 정확히 같은 색 전부에 걸림 | 그림 · UI에 순수 검정을 쓰지 않는 미술 규칙을 프로젝트에 둠 |
