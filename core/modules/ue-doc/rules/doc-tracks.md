# doc-tracks — UE 문서 요청을 트랙 · 저장 위치 · 허브 · 용어집으로 가르는 규칙

모든 문서 요청은 `core/base/doc-playbook.md`를 처음부터 끝까지 따릅니다. 이 문서는 그 위에서
**요청 유형에 따라 달라지는 것** — 저장 위치 · 허브 · 용어집 — 을 정합니다. 저장 위치 · 허브 ·
용어집의 정본은 이 파일이고, 템플릿 구조의 정본은 `../design-template/ue-doc-template-catalog.md`입니다.

---

## 1. 요청 유형과 트랙

| 유형 | 요청 성격 | 트랙 | 저장 위치 |
|---|---|---|---|
| **①** | 엔진이 **자체 제공하는 기능 · 구조(프레임워크)** 문서 (GameMode 구조, Subsystem, DataTable 등) | **지식 위키** | 위키 프로젝트의 `ue-architect/<카테고리>/` (§2-1) |
| **②** | 마켓플레이스 등에서 **판매되는 에셋**을 에디터 연동 도구(MCP)로 **분석** | **지식 위키** | 위키 프로젝트의 `ue-asset/<판매에셋이름>/` |
| **③** | **특정 프로젝트의 특정 기능**을 개발하기 위한 문서 | **프로젝트** | 그 프로젝트 폴더 |

- 판별 시점: 절차서 STEP 2에서 템플릿과 함께 가판별하고, **STEP 3 확인 ② 질문에 저장 위치를
  밝혀** 확정받습니다.
- ②는 ①의 기능을 직간접적으로 쓰므로 둘 다 지식 위키로 묶습니다.
- ②의 에셋 폴더에는 **같은 에셋의 후속 분석 문서도 쌓아** 에셋 단위로 관리합니다. 폴더 이름은 판매
  에셋 이름이며 공백 대신 하이픈을 씁니다.
- **어느 프로젝트가 위키인가**는 그 프로젝트의 `{폴더}-site.json`에 `"track": "wiki"`로 적습니다.
  적지 않은 프로젝트는 개발 프로젝트(`"track": "project"`)입니다. 허브 파일 이름은 같은 파일의
  `hub`에 적습니다.

## 2. 지식 위키 트랙 (유형 ① · ②)

**성격**: 프로젝트와 무관하게 다시 쓰이는 엔진 지식. 누가 언제 봐도 유효한 범용 문서입니다.

1. **저장**: ① → `ue-architect/<카테고리>/`(§2-1), ② → `ue-asset/<판매에셋이름>/`.
2. **출력**: base 출력 규칙(`core/base/rules/html-output.md`)을 따릅니다 — 허브를 포함해 마스터를
   inline합니다.
3. **위키 허브 등록**: 문서를 만들 때마다 위키 허브의 문서 목록에 등록합니다. 유형 ① 문서는 **해당
   카테고리 소구획의 표**에 넣고, 카테고리가 새로 생겼으면 허브에 소구획도 더합니다. 링크는 허브
   기준 상대 경로입니다(`./ue-architect/<카테고리>/파일.html` · `./ue-asset/<에셋>/파일.html`).
4. **위키 용어집**: 어려운 용어는 위키 허브의 용어집에 등록하되 §4를 따릅니다. **범용 엔진 API ·
   구조 용어만** 넣고, 특정 에셋의 고유명사는 넣지 않습니다(그 분석 문서 안에서 풀어 설명합니다).

### 2-1. 유형 ① 카테고리 (ue-architect 하위 폴더)

유형 ① 문서는 `ue-architect/` 바로 아래가 아니라 **반드시 카테고리 폴더 안에** 저장합니다. **이 표가
카테고리의 정본**입니다 — 새 카테고리 폴더를 만들면 반드시 이 표에 행을 더합니다(중앙 저장소에서,
`core/base/rules/central-sync.md` §3).

| 폴더명 | 범위 (판별 기준) | 예 |
|---|---|---|
| `core-cpp/` | C++ 언어 구조 · 리플렉션 · UHT · 모듈 · 빌드 등 **코드 자체의 구조** | 클래스 계층, UCLASS/UPROPERTY 매크로 |
| `framework/` | 게임플레이 프레임워크 · Subsystem · 상태 머신 등 **엔진이 제공하는 게임 구조 · 패턴** | GameMode, GameInstanceSubsystem |
| `ui/` | UMG · Slate · Common UI 등 **UI 계층 전반** | 위젯 블루프린트, SWidget, 레이어 스택 |
| `data/` | DataTable · DataAsset · Config 등 **데이터 관리** | 마스터 데이터, 행 구조체 |
| `rendering/` | 머티리얼 · 셰이딩 · 포스트 프로세스 등 **화면을 그리는 기법** | 툰 셰이딩, 아웃라인, Custom Depth |
| `2d/` | Paper2D · 스프라이트 · 직교 카메라 · 타일맵 등 **2D 게임 제작 전반** | 2D 사이드뷰 카메라, 스프라이트 애니메이션 |

**폴더 이름 규칙**: 영문 소문자 kebab-case, 단수형 우선, `ue-` 접두 금지(상위 폴더가 이미 ue-architect).
파일 이름은 `ue-….html`입니다.

**배치 판별 절차** (문서 1건당 카테고리 1개):

1. 문서의 **핵심 주제 시스템**이 위 표의 판별 기준에 맞으면 그 폴더에 둡니다. 두 영역에 걸치면
   **「독자가 이 문서를 찾을 때 먼저 떠올릴 영역」**을 따릅니다(예: UMG + C++ 연동 → `ui/`).
2. 맞는 카테고리가 없으면 표준 후보에서 골라 새 폴더를 만듭니다: `animation/` · `networking/` ·
   `ai/` · `physics/` · `audio/` · `editor-tools/` · `build-pipeline/`.
3. 후보에도 없으면 kebab-case 이름을 새로 제안하고, **확인 ① 때 저장 폴더(기존 · 신규 여부)를 함께
   공유**해 확인받습니다.
4. 새 폴더를 만들면 **① 위 표에 행 추가(중앙) ② 위키 허브에 카테고리 소구획 추가**를 함께 합니다.

## 3. 프로젝트 트랙 (유형 ③)

**성격**: 특정 프로젝트의 설계 결정 · 수치 · 규칙이 담긴 문서. 그 프로젝트 안에서만 유효합니다.

1. **저장**: 그 프로젝트 폴더(하위 폴더 규칙은 프로젝트가 정합니다).
2. **출력**: base 출력 규칙을 따릅니다. 프로젝트 폴더는 통째로 옮겨질 수 있으므로 문서가 자립해야 합니다.
3. **프로젝트 허브**: 각 프로젝트는 자기 허브(`hub`, 기본 `<프로젝트 이름 소문자>-index.html`)를
   가집니다. 문서를 만들 때마다 허브의 **문서 목록**과 **프로젝트 용어집**을 갱신합니다. 허브 안의
   문서 링크는 같은 폴더 기준(`./`)만 씁니다 — 폴더째 옮겨도 깨지지 않습니다.
4. **프로젝트 용어집**: 그 **프로젝트의 고유명사를 넣어도 됩니다**(권장). 규칙 · 수치 · 시스템 이름 ·
   구조체 이름 같은 프로젝트 정의 용어의 자리입니다.
5. **위키 허브에는 프로젝트 허브 행 하나만** 둡니다. 개별 문서는 프로젝트 허브가 관리합니다.

### 3-1. 새 프로젝트의 첫 문서

1. 프로젝트 폴더를 만들거나 등록합니다(`core/base/rules/project-scaffold.md`).
2. 프로젝트 허브를 만듭니다 — 문서 목록 · 아키텍처 개요 · 프로젝트 용어집. 마스터를 inline합니다.
3. 위키 허브 문서 목록에 프로젝트 허브 행 하나를 등록합니다.

## 4. 용어 배치

| 용어 성격 | 배치 | 예 |
|---|---|---|
| 범용 엔진 API · 클래스 · 패턴 (프로젝트가 없어도 정의가 성립) | **위키 용어집** | `GameInstanceSubsystem`, `DataTable`, `FTimerHandle`, 상태 머신 |
| 정의에 프로젝트의 수치 · 규칙 · 이름이 들어감 | **프로젝트 용어집** | 그 게임의 재화 규칙, 그 게임 고유의 구조체 |
| 일반 기법이지만 이 저장소에서는 프로젝트 맥락으로만 정의됨 | **프로젝트 용어집** | 그 게임의 집중 타이머 주기 |
| 특정 판매 에셋의 고유명사 | **등록하지 않음** — 분석 문서 안에서 자체 설명 | 에셋 내부 컴포넌트 · 노드 이름 |

- 판단 요령: **「정의 문장에서 프로젝트 · 에셋 이름을 지워도 성립하는가?」** 성립하면 위키, 아니면
  프로젝트(또는 미등록).
- 양쪽 성격을 다 가지면 범용 정의는 위키에, 프로젝트 특화 정의는 프로젝트 용어집에 따로 둡니다
  (두 정의 문장은 서로 달라야 합니다).

## 5. 범용 개념 승격 (프로젝트 → 지식 위키)

프로젝트 문서를 쓰다 나온 개념이 **범용 지식으로 필요**해지면:

1. 프로젝트 내용(수치 · 규칙 · 이름)을 지우고 일반화한 **유형 ① 문서**를 따로 씁니다 — 절차서의
   확인 ① · ②를 새로 거칩니다.
2. `ue-architect/<카테고리>/`에 두고 위키 허브에 등록합니다.
3. 위키 용어집의 그 용어 「자세히 →」 링크를 새 범용 문서로 잇습니다.
4. **원본 프로젝트 문서는 고치지 않습니다** — 프로젝트 맥락 설명은 그대로 유효합니다.

범용 문서가 아직 없는 범용 용어는 위키 용어집에 두되 링크가 임시로 프로젝트 문서를 가리킬 수
있습니다. 그 경우 소스 주석에 `TODO`를 적고, 범용 문서가 생기면 바꿉니다.
