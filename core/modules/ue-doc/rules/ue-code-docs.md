# ue-code-docs — C++ 코드가 들어가는 UE 문서에서 더 지키는 것

코드 표기 · 주석의 공통 규칙은 `core/base/rules/code-example.md`가 정본입니다. 이 문서는 **언리얼
C++ 문서에서 더 지키는 것**만 정합니다.

---

## 1. 🚀 이 문서로 작업 시작하기 블록

**구현성 문서(코드 · 스켈레톤이 있는 문서)**는 코드 섹션 첫머리에 이 블록을 둡니다. 독자가
「무엇부터 해야 하는가」를 문서 안에서 찾을 수 있게 하려는 것입니다. 네 요소를 그 문서에 맞춰 담습니다.

1. **전제 조건** (`callout info`) — 선행 문서 · 프로젝트 상태 · 이 문서의 착수 순서상 위치.
2. **만들 파일 표** (`.tbl`) — 파일명 · 부모 클래스(**클래스 위저드 검색어** 그대로) · 비고. 기존
   파일에 채우는 경우 「새 파일 아님 — ○○에 추가」로 가릅니다.
3. **코드 외 작업** (`callout tip`) — 에디터에서 할 일(에셋 생성 · 데이터 입력 · Project Settings ·
   콜리전 등). **없으면 「없음」이라고 적습니다** — 없다는 것도 정보입니다.
4. **컴파일 주의** (`pitfall`) — Live Coding으로 되는 범위와 에디터를 닫고 다시 빌드해야 하는 지점
   (헤더의 UPROPERTY · UFUNCTION 추가, 새 클래스, Build.cs 수정 등).

클래스 위저드 · Build.cs · 컴파일 규칙처럼 **모든 문서가 공유하는 반복 절차는 블록에서 되풀이하지
않습니다.** 그 절차는 지식 위키의 공통 절차 문서가 맡고, 블록에서는 그 문서를 **이름으로만**
언급합니다(본문 상대 링크 금지 — `core/base/rules/html-output.md` §5). 코드가 없는 개념 · 설계
문서는 이 블록을 생략할 수 있습니다.

## 2. 책임 배치 결정표 (02-B 기능 구현 명세)

기능 구현 문서의 핵심은 **「이 데이터 · 기능을 어느 클래스에, 왜 두는가」**를 먼저 정하는 것입니다.
GameMode · GameState · PlayerController · Pawn · GameInstance · SaveGame · Subsystem 중 어디에
두는지와 그 근거를 결정표(`.tbl .owner`)로 남긴 뒤 코드를 씁니다. 근거 없이 코드부터 쓰면 나중에
「왜 여기 있지」를 되짚을 수 없습니다.

## 3. 주석에서 꼭 적는 것 (UE 예)

`code-example.md` §4의 「의미 있는 모든 줄에 · 왜 중심으로」를 언리얼 코드에 적용하면 이렇습니다.

- **매크로 · 지정자의 뜻** — `UPROPERTY()`가 가비지 컬렉션 추적에 미치는 효과, `BlueprintType`의
  노출 범위, `EditAnywhere`와 `VisibleAnywhere`의 차이.
- **엔진이 언제 부르는가** — `BeginPlay`, `SetupPlayerInputComponent`(폰이 컨트롤러에 빙의될 때),
  `Initialize`(Subsystem이 만들어질 때)처럼 호출 시점을 적습니다.
- **값의 범위 · 단위** — 축 입력은 -1.0 ~ 1.0, 시간은 초 단위 등.
- **전방 선언 · include를 왜 쓰는가**, `nullptr` 검사를 빼면 언제 멈추는가.

## 4. 하이라이팅

C++ 하이라이팅은 생성 시점에 `hljs-*` `<span>`으로 구워 넣고, 주석은 `hljs-comment`로 넣습니다
(`core/base/rules/html-output.md` §4). `.h`와 `.cpp` 탭 모두 같은 기준입니다.
