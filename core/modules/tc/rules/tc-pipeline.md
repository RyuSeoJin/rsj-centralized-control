tc 모듈을 켠 프로젝트에서 문서 제작 절차(`core/base/doc-playbook.md`)의 「상세 설계」와 「본문 작성 · 출력」 사이에
끼워 넣는 단계입니다. 규칙의 정의는 이 모듈의 각 규칙 문서가 정본이며, 이 문서는 **순서**로
엮습니다. 절차서이므로 지시가 먼저 오고 이유는 뒤에 붙습니다.

프로젝트에 구조 설정이 있으면 등록된 자료의 경로 · 역할을 먼저 확인합니다. 아래 `spec/` 경로는
기본안이며 등록 경로가 우선합니다. 미승인 내용을 TC 기대값으로 쓰지 않습니다. 미승인 행을
덮는 TC는 판정이 아니라 관찰 기록으로만 씁니다(`case-expansion.md` 「승인되지 않은 기능 단위도 TC로 씁니다」).

---

## 1. 기능 골격 작업

정본은 `spec/{프로젝트}-feature-tree.md` 하나뿐입니다. 다만 아래 「기획 원문 표에서 골격을 만드는
선택지」를 고른 프로젝트에서는 기획 원문 표가 정본이고, 골격 md는 거기서 만드는 파생물입니다.

`analysis/`는 조사 전량, `reference/`는 채택분, `spec/`은 확정 결정입니다. **TC의 기대값은 골격과
`spec/design/`에서만 가져옵니다** — analysis · reference의 수치는 아직 남의 값이거나 미확정 값입니다.
`spec/rationale/`은 판단 기록이라 기대값이 아닙니다. 근거 문서는 두 부류로 나눠 담습니다.

- **「노드 보강」** — 조사에 없어 직접 세운 노드(`ADD`)의 근거. 「조사에 없다」는 사실과 그래도
  넣는 이유를 함께 적습니다
- **「수치 확정」** — 노드는 있으나 값이 공개되지 않아 직접 정한 것의 근거

근거는 판단한 시점에 한 줄씩 적립합니다. 하루 지나 되짚으면 근거가 빈약해집니다.

1. **Depth 정규화** — 명칭이 아니라 역할로 묶고, 상태(로그인 · 구독 · 플랫폼)는 Depth가 아니라
   Pre-Condition으로 흡수합니다. → `depth-and-tn.md`
2. **검증유형 표기** — 출력이 매번 같지 않은 기능이 있으면 검증유형 분리가 기능 목록보다
   먼저입니다. → `verification-types.md`
3. **지원 표기** — `O / X / △ / ?`. `?`는 정본의 「미확인 목록」 절에 모읍니다.
4. **정본 수정 체크리스트(한 묶음)** — ① md 수정 → ② HTML 재생성(`regen.py`) → ③
   `spec/archive/{프로젝트}-tree-change-log.md` 기록(날짜 · 노드 경로 · 유형 · 사유 · 변경 전 상태),
   골격 버전이 바뀌면 프로젝트 change-log에 한 줄 포인터 → ④ 커밋 시점 제안.
5. **버전** — 방향성이 바뀌는 큰 개정은 major(v1.x → v2.0), 노드 추가 · 수정은 minor. major 개정 시
   개정 직전 정본을 `spec/archive/{프로젝트}-feature-tree-vX.Y.md`로 동결하고 태그와 버전을 맞춥니다.

사용자가 골격을 1차 확인 · 최종 확정한 뒤에만 「TC 설계 & 산출」로 넘어갑니다.

### 기획 원문 표에서 골격을 만드는 선택지

기획 정본이 규칙을 표로 적고 그 표에 **승인 상태 열**을 두는 프로젝트는, 골격을 사람이 다시 쓰지
않고 그 표의 행에서 만들 수 있습니다. 같은 기능을 기획 정본과 골격에 두 번 적으면 기획이 바뀐 뒤
골격만 옛 상태로 남습니다. 그 상태는 아무 에러도 내지 않아서, TC가 옛 기대값으로 계속 통과합니다.
행에서 골격을 만들고 행마다 내용 해시를 남기면 「기획이 바뀌었는데 TC는 그대로인 곳」을 기계가
찾을 수 있습니다.

이 방식은 프로젝트가 고르는 선택지입니다. 고르면 프로젝트 change-log 「현행 기준」에 적고, 골격을
손으로 쓰는 위 절차 대신 아래 계약을 따릅니다.

| 항목 | 규칙 |
|---|---|
| 기능 단위 | 승인 상태 열이 있는 표의 **한 행**입니다. 경로는 「영역 > 표 제목 > 행 이름」입니다. 승인 열이 없는 표는 읽지 않습니다 |
| 골격의 지위 | 생성 파생물입니다. 골격 md는 손으로 고치지 않고, 머리에 자동 생성 표시와 입력 전체의 지문을 둡니다. 골격을 바꾸려면 기획 정본을 고칩니다 |
| 승인 구분 | 승인 열의 값이 프로젝트가 정한 확정 표지에 해당하면 「확정」, 그 밖은 「확정 필요」입니다. 확정 필요 행도 기능 단위로 싣고 미확인 목록에 모읍니다 |
| 근거 해시 | 행의 모든 칸을 이은 문자열의 해시를 골격 비고에 적습니다. TC 입력은 `basis`에 「TC ID → covers 경로 → 해시」를 기록합니다 |
| 낡음 판정 | 지금 행의 해시가 TC의 `basis`와 다르면 그 TC를 「재검수 필요」로 보고합니다. covers 경로의 행이 없어졌으면 「근거 행 없음」, `basis`가 비었으면 「해시 미기록」으로 따로 보고합니다 |
| 해시 갱신 | 재검수를 마친 TC만 골라 갱신합니다. 전체를 한꺼번에 갱신해 「재검수 필요」 목록을 비우지 않습니다 — 목록이 비는 것은 대조가 끝났다는 뜻이어야 합니다 |

**순서**

1. **입력 설정** — 프로젝트의 설정 파일에 읽을 기획 문서 목록 · 승인 열 이름 · 확정 표지 · 문서별
   영역 이름을 적습니다. 값은 프로젝트의 것이므로 이 모듈에 두지 않습니다.
2. **골격 · 보고서 생성** — 골격 md와 커버리지 보고서를 함께 만듭니다. 보고서는 영역별 확정 행 ·
   확정 필요 행과 그중 TC가 있는 수, 「재검수 필요」 · 「근거 행 없음」 · 「해시 미기록」 ·
   「기획 누락」 목록, TC가 없는 기능 단위를 싣습니다. 기능 단위를 하나도 읽지 못한 기획 문서는
   이름을 남깁니다 — 표 형식이 바뀌어 통째로 빠진 것을 알아채기 위해서입니다.
3. **TC 작성 직후** — `basis`가 없는 TC에만 지금 해시를 기록합니다.
4. **기획 개정 뒤** — 골격과 보고서를 다시 만들고 「재검수 필요」 TC마다 기대값을 새 행과 대조해
   고칩니다. 고친 TC만 지정해 해시를 갱신합니다. 「근거 행 없음」은 행 이름이 바뀌었는지 지워졌는지
   확인해 covers를 옮기거나 TC를 정리합니다.
5. **커밋 전** — 검사 모드로 골격이 기획 정본보다 낡지 않았는지 확인합니다. 낡았으면 실패로 끝나야
   합니다.

**판단이 필요한 자리**

- **표기만 고쳐도 해시가 바뀝니다.** 오타 수정이나 표기 정리로 뜬 「재검수 필요」도 기대값을 대조한
  뒤 해시만 갱신합니다. 「표기만 바뀐 것 같다」는 짐작으로 대조를 건너뛰지 않습니다.
- **행 이름은 경로입니다.** 행 이름을 바꾸면 그 행을 덮던 covers가 모두 「근거 행 없음」이 됩니다.
  그래서 행 이름 변경은 기능 ID 이전처럼 대응표를 만들고 covers를 함께 옮깁니다
  (`../../../base/rules/doc-write-style.md` 「기존 ID를 이전하는 순서」). 같은 표에 같은 이름의 행이
  있으면 다음 칸을 붙여 가르고, 그래도 같으면 순번을 붙입니다.
- **해시는 그 행의 칸만 봅니다.** 다른 행이 늘거나 순서가 바뀐 것은 이 TC의 낡음이 아닙니다.
  여러 행에 걸친 규칙이면 TC가 그 행들을 모두 covers에 적어야 각 행의 변경이 잡힙니다.
- **기획 정본이 다른 프로젝트에 있으면** 구조 설정의 생성 작업이 그 변경을 알아채지 못할 수
  있습니다. 그때는 기획 정본을 고친 뒤 검사 모드를 따로 돌리고, 그 사실을 change-log 「현행 기준」에
  적습니다.
- 이 선택지에서는 위 「정본 수정 체크리스트」의 골격 이력을 따로 두지 않습니다. 골격의 변경 이유는
  기획 정본의 이력에 있고, 골격에는 입력 지문만 남습니다.
- 골격 생성 · 검사 모드 · 해시 갱신 도구는 아직 이 모듈에 없습니다. 이 선택지를 고른 프로젝트는 도구가
  들어오기 전까지 자기 도구로 위 계약을 지키고, 그 도구의 자리를 구조 설정에 도구 역할로 등록합니다.

예: 기획 정본의 「알림 설정」 표에 「야간 알림 끄기」 행이 있고 TC-NOTI-004가 그 행을 덮습니다.
기획자가 그 행의 적용 시각을 고치면 행 해시가 바뀌고, 다음 생성 때 보고서의 「재검수 필요」에
`TC-NOTI-004 · 알림 > 알림 설정 > 야간 알림 끄기 (작성 때 해시 → 지금 해시)`가 뜹니다. 담당자가
기대 결과의 시각을 고친 뒤 TC-NOTI-004만 지정해 해시를 갱신하면 목록에서 빠집니다.

## 2. TC 설계 & 산출

1. **시트 규칙 확인** — `tc-sheet-format.md`를 읽고 `../design-template/tc-sheet-master.xlsx`의
   '명세서' 시트와 교차 검증합니다. 어긋나면 사용자에게 묻습니다.
2. **케이스 전개** — 노드마다 정상 · 경계 · 예외 · 우회. → `case-expansion.md`
3. **TN 부여 · 우선순위** — 한 행 = 한 TN = 한 스텝. Pre-Condition · Priority는 TN 1행에만.
   → `depth-and-tn.md`
4. **관계도(선택)** — 선행 TC는 설계 입력(json)에만 두고 시트에는 싣지 않습니다. → `tc-relations.md`
5. **산출** — 이 모듈의 도구로 정본에서 xlsx를 만듭니다. 기준 골격 버전을 시트에 기록하고 이슈
   관리 시트를 내장합니다. 수식 검증을 합니다.

**산출 후 점검 체크리스트**

- [ ] TN이 케이스마다 1부터 끊김 없이 이어지는가
- [ ] Pre-Condition · Priority가 TN 1행에만 있는가
- [ ] Test-Step · Expected-Result가 시트 표기 규약대로이고, 기대 결과가 판정 가능한 문장인가
- [ ] (관계도) 선행 TC가 실재하고 순환이 없는가
- [ ] `?` 항목이 미확인 목록에 빠짐없이 있는가
- [ ] 기준 골격 버전이 시트에 기록됐는가
- [ ] (원문 행 골격) 「재검수 필요」 · 「근거 행 없음」 · 「해시 미기록」 목록이 비었는가
- [ ] 「확정 필요」 · 「기획 누락」 표지가 붙은 TC가 보고서 건수와 맞는가
- [ ] HTML 산출물은 렌더해 눈으로 확인했는가 — 콘솔 에러 0건
