# Depth 계층 · TN · 우선순위

테스트 케이스의 뼈대를 이루는 셋을 정합니다 — 기능을 계층으로 정리할 때 **어디까지 내려갈지**(Depth), 케이스 하나 안에서 동작을 **몇 번으로 나눠 적을지**(TN), 그리고 **무엇부터 확인할지**(우선순위)입니다. 이 셋이 흔들리면 같은 기능을 두 사람이 다른 모양으로 적게 되고, 나중에 두 케이스가 같은 것을 보는지조차 알 수 없게 됩니다.

## Depth 계층 (1~7)

트리는 최대 7단계까지 내려가되, **모든 노드가 7단계를 채울 필요는 없습니다.**
의미가 있는 깊이까지만 내려가고 나머지는 비웁니다.

| Depth | 역할 | 예시 |
|---|---|---|
| 1 | 화면 (탐색 전이라면 기능 영역) | 메인 화면 |
| 2 | 화면 내 영역·패널 | 스테이터스 패널 |
| 3 | 구성 요소 | 길드 이름 |
| 4 | 세부 항목·케이스 구분 | 미로그인 최초 실행 |
| 5~7 | 더 쪼갤 필요가 있을 때만 | |

### 명칭이 아니라 역할로 묶기

서비스마다 UI 명칭이 다릅니다. 같은 역할이면 같은 노드에 넣고, 대상별 명칭은 비고에 적습니다.

> `서사 시스템 > 세계관 > 키워드 트리거 주입`
> 비고: 크랙=키워드북 / 제타=로어북 / 러비더비=로어북(Luvi+ 전용)

### 지원 표기

`O` 지원 확인 · `X` 미지원 확인 · `△` 부분·조건부 · `?` 미확인(실측 필요).
`?`를 추측으로 메우지 마세요. `?`의 개수와 분포가 곧 실측 계획입니다.

## 도달 경로 뎁스 (2026-08-03 확정)

뎁스를 기능 분류가 아니라 **앱 진입부터의 화면 도달 경로**로 쓰는 방식입니다. 처음 보는
사람이 뎁스만 따라 읽어도 그 케이스까지 어떻게 가는지가 보입니다. 이때 **영역(무엇을
검증하나)은 TC ID 접두가 담고, 뎁스는 어디서 실행하나만 담습니다** — 집계·자동화 파일
분할·이슈 레이블·결함 매트릭스는 전부 ID 접두를 축으로 삼으므로, 한 영역의 케이스가 여러
뎁스에 흩어져도 ID가 다시 모읍니다.

화면 네비게이션은 트리가 아니라 그래프라서(한 화면에 오는 길이 여럿), 누적 경로를 끝까지
밀면 같은 케이스가 경로 수만큼 복제됩니다. 그래서 경계를 긋는 기준과 케이스의 소속을 정하는
규칙이 필요합니다.

### 뎁스 경계·소속 규칙

**경계 기준 셋** — 어떤 화면이 새 1-Depth가 되는지를 정합니다. 이 번호 순서로 판정합니다.

| # | 기준 | 판정 질문 | 판정 결과 | 예 |
|---|---|---|---|---|
| ① | 합류점 | 이 화면에 오는 길이 둘 이상인가? | 새 1-Depth로 끊음 | 상세 화면 — 오는 길 넷(목록에서 열기 / 이어하기 / 최근 탭 선택 / 저장 불러오기 「새로 시작」) |
| ② | 전역 | 어느 화면에서든 열리는가? | 새 1-Depth로 끊음 | 상단 바·하단 내비(전역 셸) · 포인트/충전 패널 · 디버그 콘솔 |
| ③ | 오버레이 | 뒤 화면이 살아 있는 채로 뜨는가? | 끊지 않고 그 화면의 하위 뎁스로 | 로그인 모달(전역 셸 하위) · 저장/불러오기 패널(상세 화면 하위) |

**소속 규칙 하나** — 케이스가 어느 1-Depth 아래 놓이는지를 정합니다.

| # | 기준 | 판정 질문 | 판정 결과 | 예 |
|---|---|---|---|---|
| ④ | 트리거 화면 소속 | 케이스가 화면을 건너는가? | 첫 동작(트리거)이 일어나는 화면 소속으로 두고 케이스 끝까지 유지 — 확인 화면 소속이 아님. 이동·확인은 새 규칙이 아니라 기존 TN 스텝 구조가 처리 | 콘텐츠 필터 — 토글을 누르는 「설정 탭」 소속. TN 1 토글 ON → TN 2 홈 탭 이동한다 → TN 3 제한 콘텐츠를 뺀 목록이 노출된다 |

경계 기준은 시트의 뼈대(열에 어떤 화면이 오나)를, 소속 규칙은 행의 주소(케이스가 어디
아래 놓이나)를 정합니다 — 층이 다릅니다.

**보조 규칙 둘**

- **끊어낸 자리의 진입 검증은 출발 화면에 남습니다.** 「목록 화면에서 항목을 열면 상세
  화면으로 진입된다」는 목록 화면 소속이고, 상세 화면 1-Depth는 Pre-Condition
  「상세 화면 진입 상태」로 시작합니다. 경로 검증이 사라지는 게 아니라 소속이 갈리는 것입니다.
- **같은 검증이 여러 지점에서 반복되면**(로그인 필요 동작 차단 등) 시도 지점마다 그 화면
  소속으로 쪼개고, TC ID 접두가 하나로 묶습니다.

「이동은 Depth가 아니라 스텝으로」 — 아래 「상태는 Depth가 아니라 Pre-Condition으로」와
같은 계열의 문장입니다. 상태 조합은 Pre-Condition이, 화면 이동은 TN 스텝이 흡수하므로
뎁스 계층은 화면 구조만 담고 폭발하지 않습니다.

## TN (테스트 넘버링)

**Depth로 화면 구성을 끝까지 구분하면 Depth가 너무 많아집니다.** TN은 그 문제를 피하려고,
테스트 수행 순서에 맞춰 **마지막 Depth에서 이어지는 동작을 눕혀서 번호로 제어**하는 장치입니다.

- **1번** — 마지막 Depth에서 이어지는 동작
- **2번** — 1번 이후에 이어지는 동작
- **3번** — 2번 이후에 이어지는 동작

즉 TN은 **하나의 테스트 케이스 안에서의 스텝 번호**입니다.

### TN으로 이을 수 있는 것은 연쇄뿐입니다 (2026-08-03 보강)

「이어지는」이 핵심입니다. TN을 올리는 자리는 **앞 스텝의 결과로 새 UI가 떠서** 그것을 확인해야
하는데, 그 UI를 별도 Depth로 두기는 애매한 경우입니다 — 진입했더니 뜬 화면, 눌렀더니 뜬
팝업·다이얼로그·모달이 여기 해당합니다.

**같은 사전조건에서 각자 새로 시작하는 동작은 연쇄가 아닙니다.** 대상만 바꿔 같은 검증을
되풀이하는 것은 TN이 아니라 **케이스를 나눠야 합니다.** TN으로 늘어놓으면 한 케이스에 묶여
Total Result가 하나로 뭉치고, 대상 하나만 깨져도 케이스 전체가 Fail이 되어 어느 대상이 깨졌는지
ID로 읽히지 않습니다.

| | 연쇄 — TN으로 이음 | 나열 — 케이스를 나눔 |
|---|---|---|
| 관계 | 앞 스텝의 **결과** 위에서 다음 동작이 일어남 | 각자 사전조건에서 **처음부터** 시작 |
| 예 | 주소로 진입한다 → (로그인 화면이 뜸) → 계정을 고른다 → 원래 화면으로 복귀 | 채팅 탭 주소로 진입한다 · MY 탭 주소로 진입한다 · 내 작품 탭 주소로 진입한다 |
| 되돌리면 | 앞 스텝을 빼면 다음 스텝을 수행할 수 없음 | 어느 것 하나만 떼어 내도 그대로 수행됨 |

마지막 줄이 판정에 쓰기 좋습니다 — **스텝 하나를 떼어 내도 나머지가 성립하면 그건 나열**이고,
케이스로 갈라야 합니다.

> ⚠️ TN을 TC와 TC 사이의 선행 관계나 실행 순서 DAG로 해석하면 안 됩니다.
> 이름은 비슷해 보여도 완전히 다른 물건이 되고, 산출물 전체가 어긋납니다.

### 시트에 앉히는 규칙

- **한 행 = 한 TN = 한 스텝.**
- Depth는 스텝 행마다 반복해서 적습니다.
- Pre-Condition은 **TN 1행에 케이스 진입 조건**을 적습니다. 중간 스텝에서 **앞 스텝의
  결과로는 만들어지지 않는 새 상태**가 필요하면 그 행에도 적습니다(2026-08-02 보강) —
  시간 경과나 외부 변화처럼 유저 조작으로 도달할 수 없는 상태가 여기 해당합니다.
  예: TN 1에서 로그인 상태로 진입해 두고, TN 3에서 "세션이 자동 만료된 상태"로 새로고침.
- **앞 스텝의 기대 결과로 이미 성립한 상태는 적지 않습니다.** 그건 사전조건이 아니라 앞
  스텝이 검증을 마친 결과이고, 사전조건란에 적으면 무엇이 검증 대상인지가 흐려집니다.
- 그 상태를 실제로 어떻게 만드는지(테스트 설비·상태 조작 API)는 Note에 적습니다. 사전조건은
  "무엇이 성립해 있어야 하는가"만 말하고, "어떻게 만드는가"는 참고사항입니다.
- Priority는 Depth와 마찬가지로 **행마다 반복해서** 적습니다(2026-08-02 개정 ·
  2026-08-03 기대결과 추가 행 포함으로 보강).
  우선순위가 개념상 케이스의 속성인 것은 그대로지만, Summary가 행 단위로 집계하므로
  1행에만 적으면 우선순위 분포만 케이스 수로 세어져 TC 수와 단위가 어긋납니다.
  행마다 값이 있어야 필터·정렬로 잘라 봐도 우선순위가 따라옵니다.
- 한 스텝에 기대 결과가 여러 개면 행을 늘리고 **TN·Test-Step을 그 범위로 세로 병합**합니다
  (2026-08-03 확정 — TN 값 무관, 어느 스텝에서든). No·Depth·Priority는 그 행들에도 반복
  기재합니다. 열별 병합/반복/금지의 정본 표는 `tc-sheet-format.md` §셀 병합 규칙입니다.
- 새 케이스가 시작되면 TN이 1로 돌아갑니다.

```
No  1-Depth  2-Depth       Pre-Condition        TN  Test-Step              Expected-Result
2   메인 화면                                     1   좌측 상단 영역 확인한다    스테이터스 패널 노출된다
3   메인 화면  스테이터스 패널                        1   길드 이름 확인한다        설정한 길드 이름 노출된다
11  메인 화면  기록 탭                            ┌ 1 ┐ ┌ 레코드 패널 확인한다 ┐   집중 버튼 노출된다
12  메인 화면  기록 탭                            │병합│ │      (병합)        │   퀘스트 버튼 노출된다
13  메인 화면  기록 탭                            └   ┘ └                   ┘   기록 저장소 버튼 노출된다
14  메인 화면  레코드 패널   프로그램 실행 후 최초 선택    1   집중 버튼 선택한다        집중 리스트 노출된다
```

### 문체

- **Test-Step** — `~한다` (확인한다 / 선택한다 / 실행한다). 조사 없이 `[대상] [동작]한다`.
- **Expected-Result** — `~된다` (노출된다 / 차감된다 / 전이된다).

## 케이스를 쪼개는 기준 (2026-08-03 확정)

한 케이스에 스텝을 몇 개까지 담을지, 언제 두 케이스로 가를지를 정합니다. 판정 질문을 순서대로
던져 처음 걸리는 자리에서 끊습니다.

**⓪이 먼저입니다 — 스텝들이 연쇄인가?** 나열이면 아래를 따질 것도 없이 케이스를 나눕니다
(→ §TN으로 이을 수 있는 것은 연쇄뿐입니다). 연쇄일 때만 ①~③으로 넘어가며, 거기서는
**스텝이 여럿이라는 이유만으로는 쪼개지 않습니다.**

| # | 기준 | 판정 질문 | 왜 |
|---|---|---|---|
| ⓪ | 연쇄 여부 | 스텝 하나를 떼어 내도 나머지가 그대로 수행되는가? | 그렇다면 나열입니다. TN으로 묶으면 Total Result가 하나로 뭉쳐 어느 대상이 깨졌는지 ID로 읽히지 않습니다 |
| ① | 검증유형 | 스텝마다 검증유형이 달라지는가? | **검증유형은 케이스 단위 값**이라 한 케이스에 하나만 붙습니다. 「진입 확인(결정적)」과 「차단 확인(금칙)」이 한 케이스에 있으면 한 값을 공유해야 하고, 금칙은 사실상 전부 High이며 집계도 따로 보는 축이라 섞이면 둘 다 변별력을 잃습니다 |
| ② | 판정 단위 | 앞 스텝은 정상인데 뒤 스텝만 실패한 것을 남겨야 하는가? | **Total Result는 케이스 단위**라 스텝 하나가 Fail이면 케이스 전체가 Fail입니다. 앞이 정상이었다는 사실이 묻히면 결함의 위치를 리포트에서 읽을 수 없습니다 |
| ③ | 선행 관계 | 앞이 실패하면 뒤는 **확인 자체가 불가능한가**? | 쪼개서 선행 TC를 걸면 뒤 케이스가 Blocked로 기록됩니다. 한 케이스로 두면 결함 1건이 후속 스텝 수만큼 Fail로 중복 계상됩니다 → §실행 결과 기록 |

셋 다 아니면 **쪼개지 않습니다.** 같은 유형·같은 판정 단위의 연속 동작은 한 케이스 안에서 TN으로
잇는 편이 낫습니다 — 쪼갤수록 사전조건이 케이스마다 복제되어 시트가 길어지고, 실행자가 같은
상태를 반복해서 만들게 됩니다.

**쪼갠 뒤에는 둘을 다시 이어 둡니다.** 뒤 케이스의 **선행 TC 칸에 앞 케이스 ID**를 적고,
**사전조건은 앞 케이스가 끝난 상태**로 적습니다. 그래야 뒤 케이스만 따로 실행할 때도 시작점이
서고, 앞이 Fail일 때 Blocked 판정의 근거가 생깁니다.

```
쪼개기 전 — 한 케이스                        쪼갠 후 — 두 케이스
TC-ENT-003  TN 1  SUT 주소 재진입한다         TC-ENT-003  TN 1  SUT 주소 재진입한다
TC-ENT-003  TN 2  상단 바 확인한다            TC-ENT-003  TN 2  상단 바 확인한다
TC-ENT-003  TN 3  채팅 탭 선택한다            TC-ENT-004  TN 1  채팅 탭 선택한다   ← 유형이 금칙으로 갈림
                                                              선행 TC = TC-ENT-003
```

행 모양과 판정 수는 그대로입니다. 바뀌는 것은 **TC ID와 TN 번호**이며, 그 둘이 바뀌면서 집계·
이슈 귀속·자동화 함수 분할이 함께 갈립니다.

## 상태 축과 [상태:] 선언 (2026-08-04 확정)

게이팅·세션 상태는 여러 기능 단위를 가로지르는 **횡단 축**입니다. 기능 단위 하나가 여러 상태를
묶고 있으면 기능 단위 커버리지 대조로는 「그중 한 상태의 케이스를 안 썼다」가 잡히지 않으므로,
상태로 갈리는 기능 단위는 트리에 선언합니다.

**어떤 상태가 있는지는 프로젝트가 정합니다.** 로그인·인증·구독·권한 중 무엇이 동작을 가르는지는
그 서비스의 사정이라 중앙에 목록을 두지 않습니다. 정본은 TC 입력 json의 `gate_states`이고,
아래 설명은 그 목록을 `상태 ①`·`상태 ②`로 두고 읽습니다.

**선언의 뜻** — `[상태: A·B·C]`가 붙은 기능 단위는 **선언된 상태 각각에서 최소 한 케이스**가 있어야
합니다. 커버리지 대조가 기능 단위×상태 조합으로 요구하며, 하나라도 비면 「기능 단위 × 상태 — 미검증」으로
잡힙니다. 지점 축(covers의 testid)과는 독립입니다 — 상태가 하나뿐인 기능 단위가 지점 여럿으로
갈리기도 하고, 지점이 하나인 기능 단위가 상태 여럿으로 갈리기도 합니다.

```
검증 단위 = 기능 단위 × (기능 단위가 선언한 상태) × (지점 = covers testid)
```

**어느 기능 단위에 선언하는가 — 소속 규칙 셋.** 상태를 노드로 세우지 않습니다(트리의 축은 기능).
상태가 자기 기능 단위를 갖고 있는지로 갈립니다.

| # | 규칙 | 예시 |
|---|---|---|
| ① | **자기 기능 단위가 있는 상태**는 그 기능 단위가 검증을 요구합니다. 확인할 화면이 여럿이면 기능 단위를 늘리지 않고 **그 기능 단위 케이스의 covers 지점(testid)을 넓힙니다** | 미로그인의 카드 상세 열람 — 「미로그인 진입」 기능 단위(미로그인 열람 범위에 카드 상세가 들어 있음)의 케이스가 `s3-screen`을 covers로 덮습니다. **「페이지 진입」 기능 단위에 미로그인을 선언하지 않는 이유**가 이것입니다 — 선언하면 같은 검증을 두 기능 단위가 요구해 소속만 흐려집니다 |
| ② | **자기 기능 단위가 없는 상태(기생 상태)**는 그 상태로 동작이 갈리는 기능 단위마다 선언합니다. 트리 어디에도 집이 없으므로 **선언이 유일한 검증 요구 지점**입니다 — 선언을 빠뜨리면 그 상태는 커버리지 요구에서 통째로 빠집니다 | 자격 제한 × 제한 콘텐츠 게이트 — 「자격 제한」은 자기 기능 단위가 없어, 게이트 기능 단위의 `[상태: …·자격 제한·…]` 선언이 없으면 차단 케이스를 안 써도 아무도 잡지 못합니다 |
| ③ | 자기 기능 단위가 있는 상태라도 특정 기능에서 **그 상태만의 고유 동작**이 있으면 그 기능 단위에 선언합니다 | 제한 콘텐츠 게이트가 미로그인을 선언하는 이유 — 미로그인의 게이트는 「블러 + 로그인하면 해제 가능」이라는 고유 모양이라(자격 제한은 해제 수단 없음), 「미로그인 진입」 기능 단위의 일반 열람 검증으로는 덮이지 않습니다 |

**상태 5종 × 자기 기능 단위** (예시 — 프로젝트마다 이 표를 다시 그립니다)

| 상태 | 자기 기능 단위 | 처리 |
|---|---|---|
| 진입 전 상태 | 진입 · 차단 | 진입·열람·차단은 그 기능 단위들 소속 |
| 세션 만료 | 만료 처리 | 만료 안내·복귀는 그 기능 단위. 차단은 차단 기능 단위의 선언(규칙 ③) |
| 기본 상태 | 없음 — **대부분 케이스가 이 상태** | 동작이 갈리는 기능 단위에만 선언(게이트 통과) |
| 권한 미충족 | 없음 — **기생** | 규칙 ② — 게이트 기능 단위에 선언 |
| 자격 제한 | 없음 — **기생** | 규칙 ② — 게이트·격리 기능 단위에 선언 |

**positive 케이스 원칙** — 차단이 있는 기능 단위는 통과도 선언합니다. 게이트의 통과 상태는
「막히지 않고 정상 노출된다」를 요구하는 자리입니다. 게이트가 과하게 걸리는 것도 결함인데,
차단 상태만 선언하면 그 결함을 잡는 케이스가 강제되지 않습니다.

**TC 쪽 짝은 상태 열입니다** — 케이스가 실제로 밟는 상태를 적는 열이며(정의는
`tc-sheet-format.md` §상태 열), 트리 선언과 상태 열이 맞물려 기능 단위×상태 대조가 돕니다. 같은
값이 추출 축도 됩니다 — 상태 열 필터로 한 상태만 뽑고, 자동화는 pytest 마커로
매핑합니다.

## 상태는 Depth가 아니라 Pre-Condition으로

로그인 여부, 인증 상태, 구독 상태, 플랫폼은 **화면이 아니라 상태**입니다.
이걸 Depth로 쪼개면 화면마다 조합이 붙어 계층이 폭발합니다 — TN을 만든 이유와 같은 문제가
Depth 쪽에서 재발합니다.

- 상태는 **Pre-Condition 행**으로 흡수합니다. 조합이 늘어도 행만 늘고 계층은 그대로입니다.
  Pre-Condition 문장은 사람이 읽는 조건 서술이고, **상태 열은 같은 사실의 기계용 구조화**라
  서로 대체가 아니라 짝입니다.
- 대신 **"어떤 상태에서 어느 화면이 뜨는가" 자체를 검증 대상으로 올립니다.**

```
1-Depth: 앱 진입   Pre-Condition: 앱 최초 설치, 미로그인
  TN 1  앱 실행한다           앱이 정상 기동된다
  TN 2  노출 화면 확인한다      로그인 화면 노출된다

1-Depth: 앱 진입   Pre-Condition: 로그인 세션 유지 상태
  TN 1  앱 실행한다           앱이 정상 기동된다
  TN 2  노출 화면 확인한다      홈 화면 노출된다
```

## 실행 결과 기록

Result는 **`Pass / Fail / NI / Blocked` 4종**입니다(2026-08-01 확정). 옛 `N/A`·`Skip`은
`NI`(Not Implemented — 미구현이거나 스펙에 없어 실행 대상이 아님)로 흡수해 없앴습니다.
정의와 Pass율 분모 규칙의 정본은 `tc-sheet-format.md`입니다.

선행 조건이 되는 케이스가 Fail이면 그에 딸린 후속 케이스는 **Blocked**로 기록합니다.
Fail로 기록하면 결함 수가 과대 계상됩니다. 집계는 이렇게 나눕니다.

> 실행률 = (Pass + Fail + Blocked) / 전체
> Pass율 = Pass / (Pass + Fail)   ← NI·Blocked는 분모에서 제외

## 우선순위

### High — 다음 중 하나에 해당

| 축 | 내용 |
|---|---|
| 금전 | 포인트 오차감·이중 차감·미지급, 잔액 정합 붕괴, 중복 결제 |
| 보호 | 자격 없는 사용자 노출, 게이팅 우회, 무관용 콘텐츠 통과 |
| 유실 | 복구 불가한 데이터 손실, 저장 실패 시 기존 데이터 손상 |
| 중단 | 서비스 다운, 프리즈, 핵심 플로우 차단 |
| 법규 | 확률 공시 불일치, 약관 위반, 기만적 고지, 광고 미표시 |

금칙 검증유형은 사실상 전부 High입니다.

### Medium

핵심 플로우는 동작하되 사용성·품질이 저하되는 항목. 우회 수단이 존재하는 결함.

### Low

제약 상한 등 경계값 중 실사용 빈도가 낮고 영향이 국소적인 항목.

### 분포 감각

High가 전체의 40~70%면 정상 범위입니다. Low가 10%를 넘으면 경계값 TC를 과생성한 것이고,
High가 80%를 넘으면 우선순위가 변별력을 잃은 것입니다.
