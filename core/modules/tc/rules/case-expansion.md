# 케이스 전개 규칙

기능 하나에 케이스 하나만 쓰면 **설계대로 되는 경우만 확인하고 끝납니다.** 결함은 대개 제한의 언저리나 실패했을 때, 막아 둔 길을 돌아갈 때 나옵니다. 그래서 기능마다 네 갈래로 펼칩니다 — 정상(설계대로 되는가) · 경계(제한의 앞뒤에서 되는가) · 예외(실패·빈 상태에서 되는가) · 우회(막은 길을 돌아갈 수 있는가).

## 1. 정상 (Happy path)

기능이 의도대로 쓰이는 경로. 노드당 최소 1건. 이것이 그 노드의 TN 앵커가 되는 경우가 많습니다.

## 2. 경계 (Boundary)

수치 제약이 있는 모든 곳에 **경계-1 / 경계 / 경계+1** 세 점을 찍습니다.

전개 대상이 되는 제약의 종류:

| 종류 | 예 |
|---|---|
| 글자수 | 이름 2~30자, 입력 상한, 한 줄 소개 |
| 개수 | 스탯 7개, 키워드 노트 20개, 세이브 슬롯 100개, 예시 대화 3개 |
| 용량·수량 | 이미지 5MB, 1회 업로드 1,000장, 총 1,600장 |
| 금액·포인트 | 결제 한도, 잔액 부족 직전, 무료 한도 소진 직전 |
| 시간 | 일일 리셋 시각, 유효기간 만료일, 만료 24시간 |
| 상태 임계 | 관계 단계 전이값, 엔딩 조건 턴수, 스탯 구간 경계 |
| 주기 | "10턴 이후 5턴마다" 같은 검사 주기 — 검사/미검사 턴 모두 확인 |

**등호 포함 여부를 반드시 확인합니다.** `>= 50`인지 `> 50`인지가 오프바이원 결함의 단골입니다.

**제약값을 모르면 경계 TC를 쓰지 말고 "상한 실측" TC를 씁니다.** 추측한 경계값으로 만든
TC는 전부 오탐이 됩니다.

## 3. 예외 (Exception)

정상 경로가 실패하는 상황. 다음 축을 기계적으로 훑습니다.

- **네트워크** — 단절, 저속, 타임아웃, 요청 중 백그라운드 전환
- **동시성** — 버튼 연타, 다중 기기 동시 조작, 재시도 중복
- **권한** — 알림·마이크·사진 권한 거부, 인증 만료, 구독 만료
- **입력 이상** — 빈 값, 공백만, 특수문자, 이모지, 매우 긴 입력, 예약어
- **자원 부족** — 잔액 0, 저장 공간 부족, 광고 재고 없음
- **서버 오류** — 5xx, 레이트리밋, 필터 차단, 모델 제공사 거부

예외 TC의 기대 결과에는 **"포인트 미차감"과 "데이터 무손실"을 항상 명시**합니다.
실패 경로에서 돈이 빠지거나 데이터가 날아가는 것이 이 도메인의 대표 사고입니다.

## 4. 우회 (Bypass)

의도된 제약을 뚫으려는 시도. **금칙 검증유형은 대부분 여기서 나옵니다.**

- **경로 우회** — 검색으로 막혔으면 링크 직접 접근, 딥링크, 뒤로가기, API 직접 호출
- **상태 우회** — 인증 해제 후 기존 세션 재사용, 구독 만료 후 캐시된 화면
- **표현 우회** — 은유·완곡, 인코딩, 다국어, 오타·자모 분리
- **시간 우회** — 점진적 에스컬레이션(N턴에 걸쳐 서서히), 세션 재시작 후 재시도
- **주체 우회** — 사전 설정에 미리 심어두기, 사용자 메모에 넣기, 파일 업로드로 주입
- **어뷰징** — 다중 계정, 동일 기기 반복, 자기 콘텐츠 자기 소비로 지표 부풀리기

## SUT 특성에 따른 축 조정

위 축들은 **모든 프로젝트가 전부 훑어야 하는 목록이 아닙니다.** 테스트 대상의 구조상 재현할
수단이 없는 축이 있고, 그런 축까지 기계적으로 훑으면 실행할 수 없는 TC를 설계하거나 시트에
빈칸을 남기게 됩니다.

프로젝트를 시작할 때 축마다 셋 중 하나로 판정하고, 그 결과를 프로젝트 문서에 남깁니다.

| 판정 | 뜻 | 처리 |
|---|---|---|
| 그대로 적용 | 대상에서 그대로 재현 가능 | 정상 전개 |
| 수단 치환 | 검증 의도는 유효한데 재현 방법만 다름 | 테스트 설비·mock·결함 주입으로 대체해 전개 |
| 제외 | 재현 수단도 대체도 없음 | TC를 만들지 않고 **사유를 기록** |

**제외는 누락과 다릅니다.** 사유를 남기지 않으면 나중에 "왜 이 축의 TC가 없나"에 답할 수
없고, 빠뜨린 것으로 읽힙니다. 제외 목록은 산출물의 "SUT 한계와 검증 범위" 절로 이어집니다.

수단 치환이 가장 흔합니다. 서버가 없어 5xx를 만들 수 없어도 mock의 실패 응답으로 "생성 실패
시 포인트 미차감"이라는 원래 검증 의도는 그대로 살릴 수 있습니다. 축을 버리기 전에 치환할 수단이
있는지 먼저 봅니다.

## 전개량 조절

노드 하나가 TC 20건이 되면 시트가 읽히지 않습니다. 다음 기준으로 압축합니다.

- **같은 밸리데이션 로직을 공유하는 필드는 대표 1개만** 전개하고 나머지는 비고에 나열.
  (이름 2~30자, 소개 30자, 스탯 이름 10자 → "글자수 경계" TC 1건 + 필드 목록)
- **경계 3점은 절차 안에 묶어 1건으로** 씁니다. 3건으로 쪼개지 않습니다.
- **우회 변형은 1건 안에 N종 시도로** 묶습니다. 변형마다 TC를 만들면 관리가 무너집니다.
- 반대로 **금전·보호·유실 축은 쪼갭니다.** 여기서는 한 건이라도 뭉뚱그리면 원인 규명이 안 됩니다.

목표 감각: 기능 트리 노드 수와 TC 수가 대략 1:1 ~ 1:1.5. 이 범위를 크게 벗어나면
트리가 너무 성기거나 TC를 과생성한 것입니다.

## 차단은 도달 경로마다 확인합니다 (2026-08-04 확정)

금칙 기능 단위(차단·격리·잔존 차단·재등장 차단)은 **「나오지 않는다」를 증명하는 검증**입니다. 정상
검증은 한 번 나오면 증명이 끝나지만, 차단은 확인한 길에서만 증명됩니다. 그래서 판정 지점을
한 번 밟는 것으로는 부족합니다 — **그 지점에 이르는 다른 길이 통째로 빠집니다.**

### 판정 질문 — 그 상태를 만드는 코드가 경로마다 다른가?

| 답 | 처리 | 왜 |
|---|---|---|
| 같다 (한 곳을 지난다) | **1건에 N종 시도로 묶습니다** → §전개량 조절 | 변형마다 케이스를 만들면 같은 코드를 여러 번 밟을 뿐이고 관리가 무너집니다 |
| 다르다 (경로마다 담당 코드가 있다) | **케이스를 나눕니다** | 한 경로가 깨져도 다른 경로 케이스는 멀쩡히 통과합니다. 묶어 두면 깨진 경로가 영원히 안 보입니다 |

**판정 지점이 하나라는 사실에 속지 않는 것**이 이 규칙의 핵심입니다. 판정을 한 함수가 하더라도,
그 함수가 볼 **상태를 만들어 두는 일**은 경로마다 다른 코드가 합니다. 결함은 판정이 아니라
그 준비 쪽에서 납니다.

### 예시 ① 나누는 쪽 — 삭제 기억 재등장 차단

기능 단위는 하나입니다. 「삭제된 정보가 이후 응답에 나오면 실패」.
판정도 한 곳입니다 — 응답 후보가 참조하는 기억이 지금 목록에 있는지만 봅니다.

그런데 기억이 목록에서 빠지는 길은 여럿이고, 갈래마다 담당 코드가 다릅니다.

| 경로 | 어떻게 사라지나 | 담당 코드 |
|---|---|---|
| 기억 삭제 | 지운 기억 명단에 올림 | 삭제 함수 |
| 로드·분기 | 명단을 새 방으로 옮기거나 스냅샷에서 되돌림 | 로드 복원 · 분기 복사 (**서로 다른 두 줄**) |
| 메시지 삭제·재생성 | 기억이 대화 기록에서 파생되므로 원본이 없어지면 함께 | 목록 재구성 |

삭제 경로만 보는 케이스로는 **로드·분기의 두 줄 중 하나가 빠져도 잡히지 않습니다.** 삭제
직후에는 멀쩡하기 때문입니다. 그래서 셋으로 나눕니다.

```
TC-MEM-007  지운 기억이 이후 응답에 나오지 않음
  사전조건  대화 중 한 메시지를 기억으로 등록해 둔 상태
  1. 그 기억을 삭제한다
  2. 메시지를 N회 보낸다
  → 응답 어디에도 그 기억 내용이 나오지 않는다 (N회 중 0건)

TC-MEM-008  지운 기억이 로드·분기 뒤에도 나오지 않음        선행 TC = TC-MEM-007
  사전조건  기억을 등록·삭제한 방에서 세이브가 있는 상태
  1. 세이브를 로드하거나 분기로 새 방을 만든다
  2. 메시지를 N회 보낸다
  → 응답 어디에도 그 기억 내용이 나오지 않는다 (N회 중 0건)

TC-MEM-009  원본 메시지가 사라진 기억은 참조되지 않음
  사전조건  대화 중 한 메시지를 기억으로 등록해 둔 상태
  1. 그 원본 메시지를 삭제하거나 AI 응답을 재생성한다
  2. 메시지를 N회 보낸다
  → 응답 어디에도 그 기억 내용이 나오지 않는다 (N회 중 0건)
```

셋은 **나열입니다** — 하나를 떼어 내도 나머지가 그대로 성립합니다. 연쇄가 아니므로 TN으로
잇지 않습니다(`depth-and-tn.md` §TN으로 이을 수 있는 것은 연쇄뿐입니다). 008만 선행 TC를
거는 것은 앞이 깨지면 확인 자체가 불가능해서가 아니라, 사전조건을 앞 케이스의 끝 상태로
적어 두는 편이 짧기 때문입니다.

### 예시 ② 묶는 쪽 — 금칙 입력 필터

기능 단위는 「금칙 입력 차단」이고, 우회 변형은 은유·인코딩·다국어·자모 분리로 여럿입니다. 그런데
변형은 전부 **같은 정규화 한 곳**을 지나 같은 대조표에 걸립니다. 담당 코드가 하나이므로
케이스를 나누지 않고 **1건 안에 N종 시도**로 묶고, 기대 결과에 시도 횟수를 숫자로 적습니다.

두 예시의 차이는 변형의 개수가 아니라 **담당 코드가 갈리는가**입니다.

### 기능 단위와의 관계

이 규칙은 기능 단위 하나에 케이스가 여럿 붙는 것을 허용합니다. 목표 감각(노드 : TC ≒ 1:1~1:1.5)을
벗어나지 않는 이유는, 나누는 대상이 **금칙 기능 단위 중 경로가 갈리는 것에 한정**되기 때문입니다.
정상·경계 기능 단위까지 경로별로 나누면 시트가 사전조건 복제로 부풀고, 얻는 것이 없습니다.

## 기대 결과 작성

판정 가능한 문장으로 씁니다.

| ✗ | ✓ |
|---|---|
| 정상 동작한다 | 20자 저장 성공, 21자 저장 차단 및 안내 문구 노출 |
| 잘 기억한다 | 10턴·20턴 시점 모두 정확히 회상 (각 10회 중 9회 이상) |
| 필터가 작동한다 | 우회 변형 포함 30종 모두 차단 (0건 통과) |
| 응답이 자연스럽다 | 성격 일관성 루브릭 20턴 평균 4점 이상 |
| 과금이 맞다 | 잔액 감소분이 고지 차감량과 정확히 일치, 실패 시 0 |

확률적 TC는 임계값을, 루브릭 TC는 합격선을, 금칙 TC는 시도 횟수를
**기대 결과 문장 안에** 숫자로 적습니다. 별도 문서에 두면 실행자가 보지 않습니다.

## 커버리지 보증 (2026-08-03 확정)

**TC를 전부 수행하고 나면 SUT에서 할 수 있는 동작이 하나도 남지 않아야 합니다.** 검증이 일인
프로젝트에서 「어쩌다 빠진 화면」은 설계 실패이므로, 완결성을 감이 아니라 대조로 보증합니다.

### 기준선은 둘입니다

| 축 | 무엇 | 빠뜨리는 것 |
|---|---|---|
| ① 기획 | 기능 트리의 **구현 기능 단위** | 트리에 없는 화면 요소 — 푸터 링크·모달 닫기·빈 상태 안내 |
| ② 구현 | 화면의 **조작 가능한 요소** (청사진 §3-1의 testid) | 화면에 드러나지 않는 규칙 — 집계·격리·잔존 차단 |

한 축만 대조하면 반대쪽이 통째로 샙니다. **둘 다 봐야 합니다.**

①의 기능 단위가 여러 게이팅 상태로 갈리면 기능 단위로는 부족합니다 — 트리의 `[상태:]` 선언과 TC의
상태 열이 맞물려 **기능 단위 × 상태** 조합까지 요구합니다(2026-08-04 신설,
`depth-and-tn.md` §상태 축).

### 트리에 없는데 화면에 있는 조작

셋 중 하나로 처리하고, 어느 쪽이든 **기록을 남깁니다.**

| 처리 | 언제 | 기대값 출처 |
|---|---|---|
| 트리에 편입 | 유저가 쓰는 기능이라고 볼 수 있을 때 | 트리 개정 후 `design/` |
| SUT 검증 케이스 | 기획 기능은 아니나 유저가 조작하는 것 — 스텁 안내·빌드 표기 등 | `sut-design/`(청사진). 기획 검증이 아님을 Note에 밝힙니다 |
| 제외 + 사유 | 검증 대상이 아닐 때 — 테스트 설비(디버그 콘솔)가 여기 | — |

**제외는 누락이 아니라 판단이므로 사유가 함께 남습니다.** 그 사유들이 리포트의
「SUT 한계와 검증 범위」 절 재료가 됩니다.

### 대조는 기계가 합니다

사람 눈으로는 보증되지 않습니다. 케이스가 100건을 넘으면 「다 썼나」를 훑어서 아는 것은
불가능하고, 뎁스가 도달 경로라 한 기능의 케이스가 여러 1-Depth에 흩어지기까지 합니다.

**그래서 케이스마다 무엇을 덮는지를 입력에 적어 둡니다.** 스크립트가 그 좌표를 트리 구현 기능 단위·
청사진 testid 목록과 맞춰 **덮이지 않은 것을 목록으로** 뱉고, 그 목록이 빌 때까지가 TC 설계입니다.
좌표 없이 케이스만 쌓으면 나중에 전수를 다시 읽어야 하므로, **케이스를 쓰는 시점에 함께 적습니다.**

### 기능 단위를 겸해 덮지 않습니다 (2026-08-04 신설)

**covers의 트리 경로는 케이스당 기능 단위 하나가 원칙입니다.** 한 케이스가 기능 단위 둘을 적으면 대조는
통과하는데 실제 검증은 그중 하나만인 상태가 만들어집니다.

covers는 **자기 신고**이기 때문입니다. 대조기는 좌표가 적혔는지를 볼 뿐, 본문이 그 기능 단위를
실제로 봤는지는 모릅니다. 기능 단위를 겸하는 순간 대조기의 눈이 멀고, 그 기능 단위는 「덮였다」로 집계된 채
영영 검증되지 않습니다 — 빠진 것보다 나쁩니다. 빠진 것은 목록에 뜨지만, 겸한 것은 안 뜹니다.

실제로 그렇게 샌 사례입니다.

```
TC-MEM-005  기억 삭제와 재등장 차단
  covers  ["메모리/컨텍스트 > 기억 삭제",            ← 결정적
           "메모리/컨텍스트 > 삭제 기억 재등장 차단"]  ← 금칙. 본문이 밟지 않음
  본문    기억을 지우고 → 목록에서 사라졌는지 확인하고 끝

  대조기   두 기능 단위 다 덮임 (통과)
  실제     재등장 차단은 한 번도 검증되지 않음
```

결함을 일부러 심어 돌리는 매트릭스에서야 드러났습니다. 재등장을 막는 판정을 무력화했는데
**메모리 영역이 전부 통과**했습니다 — 그 자리를 보는 케이스가 없었기 때문입니다.

둘 이상을 적고 싶어지면 그것은 **케이스가 두 기능 단위를 겸하고 있다는 신호**이므로, 적기 전에
쪼개기 기준을 먼저 통과시킵니다(`depth-and-tn.md` §케이스를 쪼개는 기준). 위 사례는 ①에서
바로 걸립니다 — 「기억 삭제」는 결정적이고 「재등장 차단」은 금칙이라, 검증유형이 달라
애초에 한 케이스에 있을 수 없었습니다.

**예외** — 두 기능 단위가 한 판정으로 동시에 결정되는 경우는 겸할 수 있습니다. 선택지 클릭 한 번이
「항목이 추가된다」와 「누적 수치가 오른다」를 함께 결정하는 식입니다. 이때는 제외 파일에 사유와
함께 적습니다. **사유 없이 겸한 covers는 위 사례와 구분되지 않습니다.**

### 판단은 낡습니다 — 제외도 검사받게 둡니다 (2026-08-04 신설)

제외는 판단이고, 판단은 시간이 지나면 근거를 잃습니다. 사유를 문장으로만 적어 두면 근거가
사라져도 아무 일도 일어나지 않습니다 — 사람이 다시 읽지 않기 때문입니다. 「나중에 재검토」는
운영되지 않습니다.

그래서 사유에 **기계가 확인할 수 있는 조건**을 함께 답니다.

```json
{
  "target": "TC-DSC-049",
  "kind": "겸함 인정",
  "requires": ["TC-DSC-041", "TC-DSC-042"],
  "reason": "두 기능 단위의 「MY 활동 목록에 반영」 절반을 한 화면에서 함께 봅니다.
             토글 동작 자체는 requires의 두 케이스가 따로 검증합니다"
}
```

| 필드 | 뜻 | 대조기가 보는 것 |
|---|---|---|
| `kind` | 제외의 성격 (testid 제외 · 기능 단위 제외 · 겸함 인정) | 값 목록 밖이면 실패 — 성격이 다른 제외가 한 통에 섞이는 것을 막습니다 |
| `requires` | 그 사유가 **기대는 근거** (다른 TC·testid) | 근거가 사라지면 실패 — 사유가 거짓이 된 순간 드러납니다 |
| `target` | 제외 대상 | 덮는 것이 없으면 실패 — 대상이 사라졌는데 남은 항목을 걷어냅니다 |
| `reason` | 사유 | 없으면 제외로 인정하지 않습니다 |

제외 건수는 대조 결과에 항상 찍습니다. **제외가 늘어나는 것 자체가 신호**이기 때문입니다 —
겸함은 쪼개는 것이 기본이고 제외는 예외라, 예외가 쌓이면 기준이 무너지고 있다는 뜻입니다.
