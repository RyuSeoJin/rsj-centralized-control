# TC 시트 서식

설계한 테스트 케이스를 실제로 적어 넣는 **엑셀 시트의 서식**을 정합니다 — 어떤 열을 두고, 한 행에 무엇을 담고, 실행 결과를 어떤 값으로 적을지입니다. 받는 사람이 시트를 읽는 법부터 배우지 않도록 실무에서 쓰는 서식을 그대로 따르고, 규칙만 이 문서로 못박습니다.

## 원칙: 기존 서식이 있으면 그 서식을 씁니다

**새 레이아웃을 발명하지 마세요.** 조직에 이미 쓰는 TC 시트가 있으면 컬럼 구성·문체·상단
블록을 그대로 따릅니다. 없을 때만 아래 표준 서식으로 만듭니다. 서식을 확인하지 않고 임의
레이아웃을 만드는 것은 이 스킬에서 가장 흔한 실수입니다 — 반드시 먼저 물어보거나 기존 파일을
읽으세요.

이 워크스페이스의 기준 서식은 `modules/tc/design-template/tc-sheet-master.xlsx`이며, 그 안의
**'명세서' 시트가 규칙 정본**입니다. 이 문서는 md 쪽 짝으로, 작업 시 둘을 교차 검증하고
불일치가 발견되면 임의로 판단하지 않고 사용자에게 어느 쪽 기준인지 질문합니다.

**여기는 구조·컬럼 규칙만 담습니다.** 색·테두리·폰트 같은 서식의 정본은
`modules/tc/design-template/xlsx-design-guide.md`이며, 시트별 옵션(틀 고정·자동 필터·상태 배색·
실행 채움 셀)도 그 문서의 표에서 제어합니다.

## 표준 서식 (기본값 — 2026-08-01 확정)

한 행이 곧 한 스텝입니다. 상단에 테스트 환경 블록, 그 아래 데이터 행이 이어집니다.
워크북은 명세서(규칙 정본) · 목록(드롭다운 참조 정본) · Summary(케이스 단위 집계) ·
Test Case(작성·실행) · 이슈 관리 시트(결함 기록, 내장 운영) 시트로 구성합니다
(이슈 관리 시트 서식 2026-08-02 확정).

**탭 순서가 곧 읽는 순서입니다**(2026-08-05 개정) — 규칙과 값을 먼저 보이고, 집계를 지나
본문으로 갑니다. 처음 받는 사람이 「이 시트가 무엇인가」부터 읽게 하려는 것입니다.
다만 **파일을 열면 작업 자리인 Test Case가 선택된 채로** 뜹니다. 읽는 순서와 작업 동선은
다르기 때문입니다. 수식은 위치가 아니라 시트 이름으로 참조하므로 순서는 집계에 영향을
주지 않습니다.

### 컬럼

| 컬럼 | 내용 | 채우는 규칙 |
|---|---|---|
| No | 행 번호 | 자동 (`=ROW()-기준`) |
| 1-Depth ~ 7-Depth | 기능 계층 | **행마다 반복**(기대결과 추가 행 포함 — 행 단위 집계·필터의 전제). **트리 경로를 있는 그대로** 넣고, 경로 다음 칸에 **케이스**가 올 수 있습니다 → §케이스(뎁스 마지막 칸). 시트는 7단까지 지원하지만 **실제로 쓰인 깊이까지만 열이 만들어집니다** — 아래 참조 |
| Pre-Condition | 사전조건 | **TN 1행에 케이스 진입 조건.** 중간 스텝에 앞 스텝이 만들지 못하는 새 상태가 필요하면 그 행에도 적습니다(앞 스텝의 결과로 성립한 상태는 적지 않음). **케이스로 올라간 조건은 여기에 적지 않습니다** → §케이스(뎁스 마지막 칸) |
| TN | 스텝 번호 | 케이스마다 1부터. → `depth-and-tn.md` |
| Test-Step | 수행 동작 | `~한다` 체 |
| Expected-Result | 기대 결과 | `~된다` 체. 판정 가능한 문장 |
| 실행 주체 | 누가 수행하는가 | **행마다 반복**(드롭다운 3종 — 자동화 전용 / 공통 / 사람 전용). → §실행 주체 |
| Priority | 우선순위 | **행마다 반복**. High/Medium/Low — 케이스의 속성이지만 행 단위 집계에 맞춰 반복 기재합니다 |
| Total Result | 행 판정 | 플랫폼별 수식 열. **병합하지 않고 한 행씩** — 같은 플랫폼에 단말이 여럿일 때 그 행의 단말 결과를 요약합니다. 직접 입력 금지 |
| Result | 스텝 실행 결과 | 플랫폼별. **Pass/Fail/NI/Blocked** 드롭다운 |
| Issue No. | 관련 이슈 | 해당 TC를 수행하는 과정에서 이슈가 발생하면, **먼저 이슈 관리 시트에 이슈를 등록하고 거기서 부여된 Issue No.를 이 칸에 적습니다.** 실행 단계에서 채웁니다 |
| Comment | **수행 중 기록** | TC를 수행하다 생긴 문제·관찰을 실행 단계에서 적습니다. 설계 시점에는 비어 있는 노란 셀 |
| Note | **수행 전 참고사항** | 사람이 읽을 안내만 담습니다 — ①함께 볼 것 ②수행 방법 ③조건 만드는 법. 스텝 범위 세로 병합 |
| TC ID | 조인 키 | **행마다 반복**. 자동화 케이스명·추적 매트릭스·이슈 연결이 참조합니다 |
| 검증유형 | 판정 방식 | **행마다 반복**(드롭다운 4종). **반복 횟수는 적지 않습니다** → §검증유형과 반복 |
| 상태 | 케이스가 밟는 게이팅·세션 상태 | **행마다 반복**. 값은 프로젝트가 정함(정본은 입력 json), 복수는 쉼표, 생략 시 `state_default` → §상태 열 |

### 상단 환경 블록

데이터 행 위에 OS / 단말 / 버전 / 작업자 이름 / 작업 시작일을 플랫폼 열마다 적는 칸을 둡니다.
실행자가 어떤 환경에서 돌렸는지가 결과 해석의 전제입니다.

**이 블록까지가 틀 고정 영역입니다**(2026-08-03 확정) — 데이터 첫 행 위에서 고정해 스크롤해도
제목·헤더·환경 블록이 남고, 그 영역의 빈 면은 회색으로 채워 데이터 영역과 갈라 둡니다.
색 값의 정본은 `modules/tc/design-template/xlsx-design-guide.md`입니다.

### 케이스 (뎁스 마지막 칸) — 2026-08-04 확정

**뎁스의 마지막에는 「케이스」가 올 수 있습니다.** 반드시 오는 것은 아닙니다.

#### 케이스란 무엇인가

**케이스는 더 큰 범위의 Pre-Condition을 정의하는 칸입니다.** 같은 뎁스 경로에서 **연속된**
데이터 행의 **TN 1 사전조건**이 동일한 부류를 하나로 묶어 올린 것입니다.

- **TN 1만 봅니다.** TN 2 이후의 사전조건은 고려 대상이 아닙니다 — 중간 스텝의 사전조건은
  그 스텝의 것이지 케이스 전체의 진입 조건이 아니기 때문입니다
- 케이스로 올라간 조건은 **Pre-Condition 칸에 적지 않습니다.** 두 곳에 같은 말이 남으면
  훑을 때 같은 것을 두 번 읽게 되고, 고칠 때 한쪽만 고쳐 어긋납니다

```
쓰기 전 — 케이스가 행마다 다르고 Pre가 되풀이됨
  웹 진입 > 주소 직접 진입 > 로그인 필요 화면 차단…   Pre: 미로그인 상태
  웹 진입 > 주소 직접 진입 > 채팅 탭 차단            Pre: 미로그인 상태
  웹 진입 > 주소 직접 진입 > MY 탭 차단             Pre: 미로그인 상태
  웹 진입 > 주소 직접 진입 > 내 작품 탭 차단          Pre: 미로그인 상태

쓴 뒤 — TN 1 사전조건이 케이스로 올라가고 Pre는 빈칸
  웹 진입 > 주소 직접 진입 > 미로그인 상태           Pre: (빈칸)
  웹 진입 > 주소 직접 진입 > 미로그인 상태           Pre: (빈칸)
  웹 진입 > 주소 직접 진입 > 미로그인 상태           Pre: (빈칸)
  웹 진입 > 주소 직접 진입 > 미로그인 상태           Pre: (빈칸)
```

#### 케이스에 넣지 않는 것

**「무엇을 보는가」는 케이스가 아닙니다.** Test-Step·Expected-Result와 같은 맥락이면
케이스에서 뺍니다. 위 예시의 「채팅 탭 차단」·「MY 탭 차단」은 **기대 결과를 그대로 옮겨
적은 것**이라 열 하나가 통째로 중복이 됩니다 — 어느 탭인지는 Test-Step이, 차단인지 통과인지는
Expected-Result가 이미 말합니다.

#### 언제 쓰고 언제 비우는가

| 조건 | 마지막 뎁스 |
|---|---|
| TN 1 사전조건이 같은 TC가 **연속으로 둘 이상** | 그 조건을 **케이스로 씁니다** |
| 그 경로에서 자기 혼자인 TC | **빈칸** — Pre-Condition 칸에 그대로 둡니다 |
| 시트의 **모든** TC가 케이스 없이 뎁스로 끝남 | 케이스 열 자체가 만들어지지 않습니다 |

같은 경로 안에서 어떤 TC는 케이스가 있고 어떤 TC는 없을 수 있습니다. 그때 케이스 없는 TC의
마지막 뎁스는 빈칸이고, 사전조건은 Pre-Condition 칸에 남습니다.

#### 행 순서는 바꾸지 않습니다

**케이스를 묶으려고 TC 행의 위치를 옮기는 것은 금지입니다.** 행 순서는 TC를 수행하는 자연스러운
흐름이고, 묶음을 위해 그 흐름을 흐트러뜨리면 실행자가 화면을 오가며 조건을 다시 만들게 됩니다.
**연속인 것만 묶습니다** — 떨어져 있으면 같은 조건이라도 각자 둡니다.

### 뎁스 채움 색

뎁스 열의 **값 있는 셀만** 텍스트별 고유색으로 채워, 같은 경로를 공유하는 케이스 묶음이
한눈에 갈리게 합니다. 경로와 케이스 모두 대상이고 빈칸만 흰 배경입니다. 규칙 여섯(빈칸 제외 · 같은 텍스트 같은 색 ·
다른 텍스트 다른 색 · 연한 계열 · 인접 회피 · 색상환 등분)의 정본은
`xlsx-design-guide.md` §5이며, 생성 스크립트가 계산해 적용합니다.

**케이스 값이 TC마다 다르면 이 색이 묶음이 아니라 소음이 됩니다.** 값이 전부 다르면 행마다
다른 색이 칠해져, 같이 볼 것을 갈라 주라고 만든 장치가 정확히 반대로 작동합니다.

### 실행 채움 셀 구분

**설계 시점에는 비어 있고 실행 단계에서 채워지는 칸**(환경 정보 / Result / Issue No. /
Comment)은 배경색(노란색)으로 구분해, 설계 산출물(Depth·절차·기대결과)과 시각적으로
분리합니다. 설계 칸은 실행 중 건드리지 않습니다.

뒤집어 말하면 **설계 데이터를 노란 칸에 두지 않습니다.** 설계 시점에 정해지는 값은 흰 칸에
둡니다 — TC ID·검증유형은 각자 열을 갖고, 수행 안내는 Note에 적습니다.

**Comment와 Note는 시점으로 갈립니다**(2026-08-02 확정) — 수행 **전에** 알아야 할 것은 전부
Note에, 수행 **중에** 생긴 것은 Comment에 적습니다. 실행자가 케이스를 시작하기 전에 Note
하나만 읽으면 되도록 참고사항을 한곳에 모으는 것이 목적입니다.

노란색의 뜻은 "누가 채우는가"가 아니라 **"언제 채워지는가"** 입니다(2026-08-02 재정의).
자동화가 결과를 채우는 프로젝트에서도 규약이 그대로 성립하며, 자동 생성되는 결과 시트에서는
노란색 대신 상태 배색을 씁니다(`xlsx-design-guide.md` §4-1).

## 상태값 4종 (2026-08-01 확정)

| 상태 | 정의 | Pass율 분모 |
|---|---|---|
| Pass | 성공 | 포함 |
| Fail | 실패 | 포함 |
| NI (Not Implemented) | 미구현이거나 스펙에 없어 실행 대상이 아님 | **제외** |
| Blocked | 기능은 구현됐으나 **확인할 수 없는 상태** — 선행 케이스 Fail·환경 결함·데이터 준비 불가 등. **사유는 실행 과정에서 Comment에** 적습니다 | **제외** |

결함 1건이 후속 Blocked 수만큼 중복 계상되는 것을 막기 위해, NI·Blocked는 Pass율 분모에
넣지 않습니다. 대신 확인 못 한 규모가 지표 뒤에 숨지 않도록 **Blocked 개수를 Summary에 별도
열로 노출**합니다. 선행 케이스 Fail로 인한 Blocked의 판정 기준은 `tc-relations.md`를 따릅니다.

## 한 행 = 한 TN = 한 스텝

핵심 규칙입니다. 케이스 하나가 스텝 여러 개면 행 여러 개로 펼쳐집니다.

```
No  1-Depth  2-Depth       Pre-Condition           TN  Test-Step           Expected-Result       Priority
5   앱 진입   최초 실행       로그인 후 세션 만료         1   앱 실행한다           앱이 정상 기동된다      High
6   앱 진입   최초 실행                                2   노출 화면 확인한다     로그인 화면 노출된다
7   앱 진입   최초 실행                                3   재로그인 수행한다      재로그인 성공한다
8   앱 진입   최초 실행                                4   복귀 화면 확인한다     만료 직전 화면으로 복귀된다
```

- No·Depth·Priority·실행 주체·TC ID·검증유형은 **행마다 반복**해서 적습니다(기대결과 추가 행 포함).
- **뎁스 열은 쓰는 만큼만 만들어집니다** (2026-08-03 확정). 입력에 트리 경로를 배열로 적으면
  생성 시 가장 깊은 경로를 세어 그만큼만 열을 만들고, Pre-Condition·Priority·Result와
  Summary의 집계식이 그 자리에 맞춰 계산됩니다.
  - 트리 깊이는 프로젝트마다 다르고 같은 프로젝트 안에서도 가지마다 다릅니다. 7칸을 늘 두면
    빈 열이 남고, 경로를 3칸에 욱여넣으면 트리와 시트가 어긋나 추적 매트릭스를 다시 맞춰야
    합니다
  - **다 만든 뒤 남는 열을 지우는 방식은 쓰지 않습니다.** Summary가 Test Case의 열 문자를
    직접 가리키므로(COUNTIFS), 열을 지우면 Priority·Result가 앞으로 밀려 집계가 엉뚱한 열을
    셉니다 — openpyxl은 다른 시트의 수식을 따라 고쳐 주지 않습니다
- Pre-Condition은 **TN 1행에 케이스 진입 조건**을 적고, 중간 스텝에 앞 스텝이 만들지 못하는
  새 상태가 필요하면 그 행에도 적습니다. → `depth-and-tn.md`
- 기대 결과가 한 스텝에 여러 개면 행을 늘리고 **TN·Test-Step을 그 범위로 세로 병합**합니다
  (2026-08-03 확정 — TN 값 무관). TN을 행마다 반복 기재하면 독립 동작 여러 개로 오독됩니다.
  No·Depth·Priority 등 케이스 단위 값은 그 행들에도 반복 기재합니다. → §셀 병합 규칙
- **입력에서는 기대결과를 스텝별 배열로 적습니다** (2026-08-03 개정). 어느 판정이 어느 동작에
  붙는지를 입력이 직접 말해야 중간 스텝에도 판정을 여럿 달 수 있습니다. 문장을 이어 쓴 문자열
  하나로 주면 그 소속 정보가 없어 스텝 수와 문장 수가 같을 때만 순서로 짝지어지고, 다르면 전부
  마지막 스텝에 실립니다 — 옛 입력 호환으로만 남은 동작이며 새 케이스는 배열로 적습니다

  ```json
  "1. SUT 주소 진입한다\n2. 상단 바 확인한다",
  [["로그인 화면 없이 홈 화면 노출된다"],
   ["포인트 잔액 노출되지 않는다", "프로필 자리에 로그인 버튼 노출된다"]]
  ```
- 새 케이스가 시작되면 TN이 다시 1로 돌아갑니다.

## 셀 병합 규칙 (2026-08-03 확정)

**병합은 스텝(TN 그룹) 범위 하나뿐입니다.** 한 동작에 딸린 행들을 묶는 것이며, 케이스·뎁스
블록·화면 범위로는 병합하지 않습니다.

| 열 | 결정 | 병합 범위 | 이유 |
|---|---|---|---|
| No | 병합 없음, 행마다 기재 | — | 자동 수식(`=ROW()-기준`)이 행마다 값을 만듦 |
| 1~N-Depth | 병합 없음, 행마다 반복 | — | Summary 행 단위 집계 + 필터로 잘라 볼 때 값이 따라와야 함(병합 블록은 필터에 첫 행만 걸림) |
| Pre-Condition | 병합 | 같은 조건이 걸리는 스텝 범위 — TN 값 무관 | 조건 공유를 형태로 보임. **케이스 전체 병합 금지** — 중간 스텝의 새 상태 사전조건 자리가 사라짐 |
| TN | 병합 | 한 스텝의 기대결과 행 범위 — TN 값 무관 | 반복 기재하면 독립 동작으로 오독 |
| Test-Step | 병합 | TN과 동일 범위 | 동작은 하나 |
| Expected-Result | 병합 없음 | — | 한 행 = 한 판정 |
| Priority | 병합 없음, 행마다 반복 | — | 행 단위 집계·필터 |
| Note | 병합 | TN·Test-Step과 동일 범위 | 스텝마다 다른 주의사항이 앉을 자리가 있어야 함 |
| Total Result | 병합 없음 | — | 행 판정 — 그 행의 단말별 Result 요약 |
| Result | 병합 없음 | — | 스텝(행)별 실행 입력 |
| Issue No. · Comment | 병합 없음 | — | 발생한 그 행에 기록 |
| 실행 주체 · TC ID · 검증유형 · 상태 | 병합 없음, 행마다 반복 | — | 필터로 잘라 볼 때 값이 따라와야 함 |

- 병합해도 기계 판독에는 영향이 없습니다 — 자동화·커버리지 대조는 xlsx가 아니라 tc-input
  json을 읽고, xlsx 내부에서 병합은 "좌상단 값 + 빈칸"으로 저장되어 COUNTIFS 관점에서
  비움과 등가입니다.
- 병합이 있는 범위는 Excel에서 **정렬이 막힙니다**(기존 Total Result 병합 때부터의 제약).
  자르기는 정렬이 아니라 필터로 합니다 — Depth·Priority를 행마다 반복하는 이유입니다.
- **Test Case Edit 열은 제거**했습니다(2026-08-03 사용자 결정) — 케이스 개정 이력은
  tc-input json과 git 커밋이 담당합니다.

## 실행 주체 (2026-08-03 확정)

케이스마다 **누가 수행하는가**를 정합니다. 판정 질문을 순서대로 던져 처음 걸리는 값으로 하며,
기본값은 「공통」이고 나머지 둘은 **사유가 있을 때만** 붙입니다.

| 순서 | 값 | 판정 질문 | 예 |
|---|---|---|---|
| ① | 자동화 전용 | 사람이 화면만 봐서 **판정할 수 없는가**? | 슬롯 간 격리(상태 훅으로만 확인) · 저장소 잔존 |
| ② | 사람 전용 | 자동화가 **판정 기준을 세울 수 없는가**? | 루브릭 채점 · 레이아웃 깨짐 · 문구 어색함 |
| ③ | 공통 | 위 둘에 안 걸리면 (기본값) | 잔액 정합 · 경계값 · 게이팅 |

**반복 횟수는 판정 근거가 아닙니다.** 20회 반복이 필요하다고 자동화 전용이 되는 게 아니라,
"사람이 1회 봐도 의미가 있는가"로 갈립니다.

- **공통 케이스는 자동화가 있으면 자동화가 돌리고 사람은 생략합니다**(2026-08-03 확정).
  「공통」은 둘 다 *가능*하다는 뜻이지 둘 다 *해야* 한다는 뜻이 아닙니다. SUT가 없는
  프로젝트에서는 자동화가 없으므로 자연히 사람이 전부 맡습니다
- 산출물은 **한 시트**이며, 실행 주체 열의 자동 필터로 잘라 봅니다 — 자동화 담당은
  「자동화 전용 + 공통」, 사람 담당은 「사람 전용 + 공통」. 대상별 파일을 따로 만들지 않습니다

## 상태 열 (2026-08-04 확정)

케이스가 실제로 밟는 게이팅·세션 상태를 적는 열입니다. **값은 프로젝트가 정합니다** — 어떤
게이팅이 동작을 가르는지는 그 서비스의 사정이라 중앙에 목록을 두지 않습니다. 정본은 TC 입력
json의 `gate_states`이고, 목록 시트의 「상태」 항목은 거기서 채워집니다.

- **행마다 반복·병합 없음** — 실행 주체·검증유형과 같은 케이스 단위 필터 축입니다
- **복수 상태는 쉼표**로 적습니다(관측자 열 전례 — 멀티 선택 드롭다운이 xlsx 표준에 없어
  드롭다운 검증을 걸지 않고 자유 입력). 전환을 밟는 케이스가 여기 해당합니다 — 막힌 동작을
  이어받는 케이스는 차단 상태에서 시작해 통과 상태로 끝나므로 둘을 함께 적습니다
- **생략하면 `state_default`**로 읽습니다 — 대부분 케이스가 도는 기본 상태를 프로젝트가 입력에
  적어 둡니다. 다른 상태를 밟는 케이스는 반드시 명시합니다
- 쓰임 셋 — ① **추출**: 자동 필터를 「포함」 조건으로 걸어 상태별 TC를 뽑습니다(영역은 TC ID
  접두, 상태는 이 열 — 축이 다릅니다) ② **커버리지 대조**: 트리의 `[상태:]` 선언과 맞물려
  기능 단위×상태 조합을 요구합니다(`depth-and-tn.md` §상태 축) ③ **자동화**: pytest 마커로 매핑해
  부분 실행합니다(`-m unverified` 식)
- Pre-Condition 문장과의 관계 — Pre-Condition은 사람이 읽는 조건 서술이고 상태 열은 같은
  사실의 기계용 구조화입니다. 서로 대체가 아니라 짝이며, 두 값이 어긋나면 케이스 오기입니다

## 검증유형과 반복 (2026-08-03 확정)

시트에는 **유형 이름만 적고 반복 횟수는 적지 않습니다.** 수동 실행자가 자기에게 내려진
지시로 오독하기 때문입니다 — 사람이 손으로 20번 눌러 성공률을 세면 시행 조건이 매번 흔들려
숫자가 의미를 잃습니다.

- **반복은 자동화가 수행하고, 사람은 어떤 유형이든 1회**입니다
- 확률적·루브릭 케이스를 사람이 1회 수행했다면 결과는 Pass가 아니라 **관찰 기록**입니다.
  판정은 자동화 반복이나 채점이 담당하고, 사람은 이상 여부만 Comment에 남깁니다
- **검증유형이 수행 방식을 바꾸는 경우 그 사실은 Note에 문장으로** 적습니다(예: 루브릭
  채점 대상임과 채점 축). 유형 열은 분류와 집계를 위한 값이지 실행자에게 내리는 지시가
  아닙니다
- 판정 규칙 문장(반복 횟수·합격선)의 정본은 `verification-types.md`와 명세서 시트입니다

## TC ID와 영역코드 (2026-08-03 확정)

형식은 `TC-{영역코드}-{번호 3자리}`이고 번호는 **영역 안에서만** 증가합니다. 다른 영역에
케이스가 늘어도 기존 ID가 흔들리지 않습니다.

- **영역코드의 키는 기능 트리 1-Depth 영역명**이며, 이슈 관리 시트 「레이블」 목록과 **같은
  값**을 씁니다. 두 곳이 어긋나면 영역별 이슈 집계가 TC 영역과 대응되지 않습니다
- **매핑의 정본은 TC 설계 입력(`tc-input` json)의 `area_codes`** 입니다. 항목마다 코드와
  **영문 표기**를 함께 담습니다 — 코드만 남기면 나중에 읽는 사람이 무엇의 약자인지 복원할
  수 없기 때문입니다. 코드는 영문 표기의 앞 세 글자입니다
- 생성 시 **명세서 시트 §5-1 「영역코드 매핑」** 으로 나갑니다. 시트만 받은 사람도 표에서
  읽을 수 있어야 하므로, 매핑을 입력 파일에만 두지 않습니다. 정의가 없는 프로젝트에서는
  그 절이 통째로 생략됩니다
- 뎁스는 **어디서 실행하나**를, ID 접두는 **무엇을 검증하나**를 담습니다. 한 영역의 케이스가
  여러 뎁스에 흩어져도 ID가 다시 모읍니다 → `depth-and-tn.md` §도달 경로 뎁스

## 문구 통일의 절대 규칙 (2026-08-04 확정)

케이스는 **글자 일치**로 묶입니다. 같은 조건이 다른 문장으로 적혀 있으면 묶이지 않으므로,
케이스를 세우기 전에 사전조건 문구를 통일합니다. 그 과정에 절대 규칙이 하나 있습니다.

### 검증 구간이 다르면 절대 합치지 않습니다

문구 통일은 **표현만 맞추는 일**입니다. 검증 범위를 넓히거나 좁히는 일이 **절대** 아닙니다.

| | 판정 | 왜 |
|---|---|---|
| 「항목이 있는 상태」 ↔ 「항목이 하나 이상 있는 상태」 | **합칩니다** | 같은 검증 구간을 다르게 쓴 것뿐입니다 |
| 「항목이 있는 상태」 ↔ 「항목이 둘 이상 있는 상태」 | **절대 합치지 않습니다** | 구간이 다릅니다. 합치면 **항목이 하나일 때가 통째로 미검증**이 되고, 그 사실이 시트 어디에도 남지 않습니다 |

빠진 검증은 목록에 뜨지만 **합쳐서 사라진 검증은 아무 데도 뜨지 않습니다.** 문구가 비슷해
보인다는 이유로 합치지 않습니다 — 조건이 가리키는 **구간이 같은지**만 봅니다.

「여러 턴 진행한」·「3턴 이상 진행한」·「11턴 이상 진행한」처럼 한쪽이 모호하고 한쪽이
구체적일 때도 합치지 않습니다. 모호한 쪽이 구체적인 쪽을 포함한다고 볼 근거가 없습니다.

| | 형식 | 예 |
|---|---|---|
| Test-Step | `[대상] [동작]한다` | 좌측 상단 영역 확인한다 / 집중 버튼 선택한다 / 앱 실행한다 |
| Expected-Result | `[대상] [상태]된다` | 상태 패널 노출된다 / 포인트가 차감된다 / 연인 단계로 전이된다 |

### 내부 식별자를 쓰지 않습니다 (2026-08-04 확정)

**뎁스 영역 · Pre-Condition · Test-Step · Expected-Result에는 디버그 환경에서만 통하는
내부 식별자를 쓰지 않습니다.** 이 네 열은 테스터가 디버그 환경을 보지 않고도 읽을 수 있어야
합니다. 「계정 A」는 저장소 안에서만 통하는 이름이고, 사전조건은 그 밖에서도 읽힙니다.

| ✗ 내부 식별자 | ✓ 테스터가 아는 말 |
|---|---|
| 계정 A로 로그인한 상태 | 성인 계정으로 로그인한 상태 |
| 계정 A로 로그인하고 인증을 끈 상태 | 인증하지 않은 계정으로 로그인한 상태 |
| 계정 B(자격 제한)로 로그인한 상태 | 자격이 제한된 계정으로 로그인한 상태 |
| 시드 1로 진입한 상태 | (조건 만드는 법은 Note로) |

**디버그 환경에서 설정해야 만들 수 있는 조건은 Note에 세팅 방법을 적습니다.** 사전조건에는
「무엇이 참인 상태인가」를 쓰고, 「그 상태를 어떻게 만드는가」는 Note가 담습니다 —
Note의 세 갈래 중 ③조건 만드는 법이 이 자리입니다.

```
Pre-Condition   추천 후보가 하나도 없는 상태
Note            조건 만드는 법 — 디버그 콘솔에서 좋아요 임계를 후보가 없을 만큼 올립니다
```

이 규칙은 **시트가 SUT와 같은 말을 쓰게 만드는 것까지 포함합니다.** 시트에서 「성인인증
계정」이라 부르는 것을 화면이 「계정 A」로 표시하면 테스터가 둘을 이어 붙여야 합니다. 화면
라벨도 함께 바꿉니다.

기대 결과는 **판정 가능**해야 합니다. "정상 동작한다"는 기대 결과가 아닙니다. 확률적 TC는
임계값을, 루브릭 TC는 합격선을, 금칙 TC는 시도 횟수를 문장 안에 숫자로 적습니다.
→ 판정 규칙은 `verification-types.md`.

## Total Result 수식

**그 행의** Result를 하나로 요약합니다. 우선순위는 **Fail > Blocked > NI > Pass**입니다.

```
=IF(COUNTIF(범위,"Fail")>0,"Fail",
 IF(COUNTIF(범위,"Blocked")>0,"Blocked",
 IF(COUNTIF(범위,"NI")>0,"NI",
 IF(COUNTIF(범위,"Pass")>0,"Pass",""))))
```

플랫폼 열이 여러 개면(Web/And/iOS) 각 열마다 별도로 요약합니다. **병합하지 않고 데이터 한
행씩** 세웁니다 — 같은 플랫폼에 단말이 여럿일 때(예: And에 Galaxy·LG 둘) 그 행의 단말별
결과를 한 칸으로 요약하는 자리이며, 스텝 여러 개를 한 칸으로 묶으면 어느 행의 판정인지
읽히지 않습니다.

### 플랫폼 열 규칙

마스터의 기본값은 Web/And/iOS 3열입니다. 프로젝트에서 TC 설계를 시작할 때 **대상 플랫폼을
사용자에게 재확인**하고, Test Case의 Total Result·Result 하위 열과 Summary의 플랫폼 열을
함께 조정합니다.

## 커버리지 집계 (Summary)

Summary 시트는 **전부 행 단위**로 집계합니다(2026-08-02 변경). 세는 단위가 열마다 다르면
"TC 4개인데 Pass 2"처럼 어긋난 표가 되므로, TC 수와 결과 집계를 같은 스텝 행 기준으로
맞춥니다. 수식으로 자동 계산되게 두어, 행을 추가해도 범위만 넓히면 갱신되도록 합니다.

- TC 수 = 1-Depth가 해당 영역인 **행의 개수**
- Pass / Fail / Blocked = **Result(스텝 실행 결과) 열의 집계** — 플랫폼별
- Pass율 = Pass / (Pass + Fail) — NI·Blocked는 분모에서 제외
- Priority 분포 — Priority를 스텝 행마다 반복 기재하므로 합이 TC 수와 일치합니다

**기준 골격 버전은 Summary 상단(C4)에 생성 스크립트가 자동 기입**합니다(2026-08-02 확정).
값 형식은 `{프로젝트}-tree-v{X.Y}`이며 TC 설계 입력(tc-input json)의 `tree_version`을 그대로
씁니다. 사람이 옮겨 적지 않으므로 TC 세트와 골격 버전이 어긋날 수 없고, 이 형식은 골격 태그
규칙(`git-rules.md` §7)과 같아 태그·시트·파일명이 한 좌표로 읽힙니다. 골격이 개정된 뒤
시트를 열었을 때 누락과 미존재를 가르는 근거가 됩니다.

## 이슈 관리 시트 · 목록 시트 (2026-08-02 확정)

컬럼별 상세 정의는 마스터의 '명세서' 시트 §8·§9가 정본입니다. 여기에는 구조 결정만 적습니다.

- **JIRA를 쓰지 않고 시트에 내장**해 운영합니다. JIRA의 이슈 등록·관리 방식을 시트로 옮긴
  형태이며, 상태 5종(Open / In Progress / Resolved / Reopen / Closed)과 해결책 8종을 씁니다
- **이슈 기록의 정본은 TC 설계 원본과 다른 파일입니다** — `test-case/{프로젝트}-issues.json`.
  크기 때문이 아니라 생명주기가 달라서입니다. TC 세트는 v1.0으로 확정되면 고정되지만 이슈는
  실행하면서 계속 늘고 상태가 바뀌므로, 한 파일에 두면 이슈를 갱신할 때마다 설계 원본이
  변경되어 "이 TC 세트가 언제 확정됐나"가 흐려집니다. 파일명에 버전을 두지 않는 것도 같은
  이유이며, 어느 빌드에서 발견됐는지는 「영향 받는 버전」이 말합니다
- **버전 표기는 `{테스트환경}_{개발목표버전}_{스프린트}_{확인버전}`** 네 토막입니다.

| 토막 | 뜻 | 예 |
|---|---|---|
| 테스트환경 | 어디서 확인했는가 | `PC웹` |
| 개발목표버전 | 무엇을 향해 개발 중인가 | `Ver1.0` |
| 스프린트 | 그 목표 버전의 주 목표 | `Dev`(개발) · `RT1`(Release Train 1차) |
| 확인버전 | 그 시점의 RC 빌드 | `RC1` |

  예: `PC웹_Ver1.0_Dev_RC1` · `PC웹_Ver1.1_RT1_RC1`

- **스프린트 칸에는 확인버전을 뺀 앞 세 토막**을 적습니다(`PC웹_Ver1.0_Dev`). 스프린트 하나가
  RC1·RC2·RC3에 걸치므로, 스프린트는 QA 사이클을 가리키고 버전은 그 안의 빌드를 가리킵니다.
  두 칸이 접두를 공유하므로 서로 어긋나면 바로 눈에 띕니다
- **확인버전(RC)은 검증 대상 빌드가 바뀔 때마다 올립니다** — 화면 슬라이스가 끝났을 때든
  결함 수정이 반영됐을 때든, 새로 확인해야 할 빌드가 나오면 다음 번호입니다. 테스트 대상을
  직접 만드는 프로젝트는 **그 값을 SUT 화면(푸터)에 표시**합니다. 테스터가 어느 빌드에서
  재현했는지 화면에서 확인할 수 있어야 이슈의 버전 칸이 신뢰됩니다
- **두 시트의 `Issue No.`는 역할이 다릅니다.** 이슈 관리 시트의 것은 **발생한 이슈를 등록하며
  부여하는 식별자**(`{프로젝트}-{번호}`)이고, Test Case의 것은 **그 TC를 수행하다 이슈가
  발생했을 때 이슈 시트에 등록한 뒤 받아 적는 참조**입니다. 순서는 언제나 이슈 시트 등록이
  먼저입니다
- **연결의 정본은 이슈 레코드의 「발견 기록」 배열입니다** (2026-08-03 개정). 원소 하나가
  `{TC ID, 확인버전}` 한 쌍이며, 그 TC를 그 빌드에서 수행하다 이슈가 나왔다는 사실을 담습니다.
  개정 전에는 연결이 Test Case 시트의 `Issue No.` 칸에만 있었는데, 그 시트는 생성될 때마다 다시
  써지는 파생물이라 사람이 적은 연결이 지워졌습니다. 이제 정본이 `issues.json` 쪽에 있어 재생성이
  연결을 지우는 대신 되살립니다
- **Test Case 시트의 `Issue No.`는 조인으로 채워집니다.** 키는 번호 하나가 아니라 **TC ID와
  확인버전 둘**이며, 그 시트가 대표하는 확인버전의 발견 기록만 끌어옵니다. 키를 TC ID 하나로
  두면 그 TC에서 예전에 나온 이슈가 이번 회차 시트에도 딸려 들어와, 이번에는 통과했는데 실패한
  것처럼 보입니다. 지난 회차의 이슈는 시트에 뜨지 않고 이슈 관리 시트에서 이력으로만 읽힙니다
- **발견 기록은 덧붙이기만 합니다** — 중간 삽입도 재정렬도 하지 않습니다. 그래야 첫 원소가
  최초 발견을 뜻하고, **「최초 발견 회차」를 따로 저장하지 않고 배열에서 계산해** 이슈 관리
  시트의 열로 표시할 수 있습니다. 따로 저장하면 같은 사실이 두 곳에 생겨 어긋납니다
- 한 이슈가 여러 회차에 걸쳐 재현되는 것은 정상입니다 — 상태값에 Reopen이 있는 이상 발견은
  본래 여러 번 일어나며, 배열이 그 횟수를 그대로 담습니다. 역방향(이슈 → TC)도 이 배열로 만듭니다
- **조인에 걸리지 않는 이슈**는 TC 실행이 아닌 경로로 나온 것입니다 — 탐색적 테스트로 발견했거나
  개발 단계에서 자체 발견한 것입니다. 시트를 나누지 않고 필드로 갈라 읽습니다. 이력이 갈리면
  재발·회귀를 대조할 수 없기 때문입니다
- 스프린트 칸이 **발견 단계를 가릅니다** — `PC웹_Ver1.0_Dev`는 개발 단계 자체 발견,
  `PC웹_Ver1.0_RT1`은 QA 사이클 실행 중 검출입니다. 필터 한 번으로 갈립니다
- **레이블은 기능 트리 1-Depth 영역명**을 씁니다. 영역별 이슈 집계가 TC 영역코드와 대응됩니다
- **드롭다운의 정본은 '목록' 시트 한 곳**이며, 숨기지 않습니다(2026-08-05 개정 — 「맨 뒤에
  둔다」는 폐기했습니다. 탭 순서가 읽는 순서가 되면서 목록은 규칙 바로 다음 자리로
  올라왔습니다). 목록 명칭이 바뀌어도
  이미 적힌 데이터 행은 고치지 않습니다(검증은 신규 입력에만 작동 — 이력 보존).
  기능 트리 개정 시 레이블 목록 갱신을 정본 수정 체크리스트에 포함합니다
- 복수 값 컬럼(관측자)은 멀티 선택 드롭다운이 xlsx 표준에 없으므로 **쉼표 구분 자유 입력**입니다
- 날짜는 전부 `YYYY-MM-DD`입니다

## 생성 스크립트

`scripts/build_tc_template_xlsx.py`가 이 서식으로 5시트를 만듭니다. 절차의 `1. / 2. / 3.`을
TN 스텝으로 자동 분해하고, `scripts/norm.py`가 문체를 `~한다` / `~된다`로 정규화합니다.
입력 JSON의 빈 포맷 골격은 `modules/tc/design-template/tc-input-master.json`입니다.

```bash
python scripts/build_tc_template_xlsx.py input.json -o 결과.xlsx
powershell -ExecutionPolicy Bypass -File scripts/verify_xlsx_opens.ps1 결과.xlsx
```

**생성 후 검증은 두 단계입니다.** 수식 재계산과, 위 `verify_xlsx_opens.ps1`로 Excel에서
'복구' 프롬프트 없이 열리는지 확인하는 것입니다. openpyxl은 XML이 올바로 파싱되어도 Excel
스키마를 어긴 파일을 만들 수 있어(틀 고정 해제 시 남는 selection · 데이터 검증식의 `=` 접두 ·
`=`로 시작하는 설명 문구), 파싱 검사만으로는 잡히지 않습니다. 2026-08-02에 이 세 가지를
실제로 밟았고 스크립트에 회피 코드와 주석을 남겼습니다.

**스크립트 출력은 md·명세서 시트와 3자 동기화 대상**이며, 서식이 개정되면 스크립트도 함께
갱신합니다.
