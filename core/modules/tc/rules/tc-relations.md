# TC 관계도 (선행 관계)

케이스 하나를 실행하려면 **먼저 통과해 있어야 하는 다른 케이스**가 있습니다. 로그인이 되어야 결제를 볼 수 있는 식입니다. 그 선행 관계를 적어 두어 실행 순서를 정하고, 앞선 케이스가 실패했을 때 뒤따르는 케이스를 어떻게 처리할지도 함께 정합니다. 한 케이스 **안**의 스텝 순서(TN)와는 다른 층위입니다.

- **TN** — 한 케이스 *안*의 스텝 순서. → `depth-and-tn.md`
- **TC 관계도** — 케이스 *사이*의 실행 순서.

케이스 하나를 실행하려면 먼저 통과해 있어야 하는 다른 케이스가 있습니다. 로그인 케이스가
Pass여야 채팅 케이스를 실행할 수 있고, 채팅 케이스가 Pass여야 메모리 케이스를 실행할 수
있습니다. 이 선행 관계를 이어 붙이면 실행 순서 그래프가 됩니다.

> 이 층은 조직 프레임워크에 원래 없을 수 있습니다. 유용하다고 판단될 때만 얹으세요.
> 시트에 넣을 때는 Note 열에 `선행 TC ID`를 적는 정도로 가볍게 시작합니다.

---

## 왜 필요한가

### 1. 결함 수 과대 계상 방지

로그인이 Fail인 상태에서 하위 200건이 줄줄이 Fail로 기록되면 리포트가 쓸모없어집니다.
**선행이 Fail이면 후속은 `Blocked`로 기록**하고, Pass율 계산의 분모에서 제외합니다.

> 실행률 = (Pass + Fail + Blocked) / 전체
> Pass율 = Pass / (Pass + Fail)   ← Blocked 제외

결함이 1건인지 200건인지가 여기서 갈립니다.

### 2. 병렬 실행 단위 정의

같은 단계에 있으면서 선행이 서로 다른 케이스는 독립 계정·독립 세션에서 동시에 돌릴 수
있습니다. 어디서 갈래가 갈라지는지를 알면 계정을 몇 개 준비할지가 정해집니다.

---

## 단계 계산

각 케이스의 선행을 루트까지 거슬러 올라간 깊이가 그 케이스의 **실행 단계**입니다.
단계가 깊을수록 앞서 통과해야 하는 케이스가 많다 = 실행 비용이 높다는 뜻입니다.

```
단계(케이스) = 1                    (선행이 없는 루트)
             = 단계(선행) + 1        (그 외)
```

단계를 계산하면 자연스럽게 드러나는 것들:

- **루트는 하나여야 이상적입니다.** 전체가 한 진입점(예: 앱 최초 실행)에서 뻗으면, 그 하나가
  깨졌을 때 나머지가 전부 Blocked라는 사실이 리포트에 그대로 드러납니다. 루트가 여러 개로
  흩어져 있으면 진입 자체를 검증하는 케이스가 빠진 신호입니다.
- **병목이 보입니다.** 한 케이스에 후속이 수십 건 매달리면(예: "첫 발화"에 대화·모델·메모리·
  미디어가 전부 의존) 그 케이스가 막히면 대량이 멈춥니다. 우선 안정화 대상입니다.
- **병렬 시작점이 보입니다.** 한 단계에서 여러 영역이 동시에 갈라지면 그 수만큼 계정을
  준비해 병렬 실행합니다.

---

## 실행 순서 읽는 법

| | 규칙 |
|---|---|
| 순차 | 화살표를 따라갑니다. 선행이 Pass여야 후속을 실행합니다. |
| 병렬 | 같은 단계이면서 선행이 다르면 동시에 실행할 수 있습니다. |
| 차단 | 선행이 Fail이면 후속은 전부 Blocked입니다. 후속을 Fail로 적으면 결함이 부풀려집니다. |
| 우선순위 | 앞 단계가 깨지면 아래를 볼 이유가 없으므로, 얕은 단계부터 실행합니다. |

---

## 시트에 앉히기

**Note 열**(수행 전 참고사항)에 한 줄로 적으면 정렬만으로 실행 순서가 나옵니다. 선행 관계는
케이스를 시작하기 전에 알아야 하는 정보이므로 Comment(수행 중 기록)가 아니라 Note에 둡니다.

```
TC-ENT-001 · 1단계 · 선행 - · 대상 A/B/C
TC-AUTH-001 · 2단계 · 선행 TC-ENT-001 · 대상 A/B/C
TC-CHT-001 · 5단계 · 선행 TC-DSC-001 · 대상 A/B/C
```

별도 도구(테스트 관리 시스템)를 쓴다면 그 도구의 dependency 필드에 선행 TC를 연결합니다.
표준 용어로는 이 관계를 **test dependency** 또는 **execution order**라고 부릅니다 — 외부
공유 문서에서는 "TC 관계도"보다 이 표현이 오해가 적습니다.

---

## 검증

- 선행으로 지정한 TC ID가 실제로 존재하는가
- 순환이 없는가 (A→B→A 금지)
- 자기 자신을 선행으로 두지 않았는가
- 진짜 순차 시나리오(턴수별 기억 감쇠, 관계 단계 상승)가 아닌 한 체인이 지나치게 깊지 않은가
  — 깊으면 중간에 복합 사전조건 케이스를 두어 평탄화
