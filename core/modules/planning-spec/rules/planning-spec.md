# planning-spec — 기획 정본의 기능 골격과 상세 사양 작성 기준

<!-- CHANGELOG · v1.0 · 2026-10-12: base에서 기획 작성 방법을 분리하고 공통 정본 규칙 참조 -->

정본 관리의 공통 기준은 `../../../base/rules/canonical-source.md`입니다. 소유 · 상속 · 승인 ·
개정 · 이전 · 파생물 반영은 그 문서를 따르며 이 모듈이 재정의하지 않습니다. 아래 기준은 기획의
책임을 나누고 기능 · 화면 · 상태를 기술하는 방법만 구체화합니다.



기능 목록과 상세 사양에 같은 규칙을 각각 적으면 한쪽만 바뀌어도 서로 다른 동작을 지시합니다.
그래서 기능 골격은 기능의 구성 · 범위 · 담당 정본을 안내하고, 동작의 상세는 등록된 책임 정본에서
결정합니다. 같은 파일 안에서 절로 나누거나 부모 · 자식 정본으로 나눌 수 있으며, 파일 수보다
규칙의 소유가 겹치지 않는지가 기준입니다.

## 1. 자료별 책임

| 자료 | 소유하거나 기록하는 내용 | 다른 자료와의 관계 |
|---|---|---|
| 기능 골격 | 기능 ID · 기능 계층 · 구현/보류/제외 범위와 사유 | 각 기능의 담당 정본 ID를 연결합니다. 상세 동작은 해당 정본을 참조합니다 |
| 상세 기획 정본 | 진입 조건 · 화면 구성 · 사용자 동작 · 상태 전이 · 분기 · 수치 · 예외 · 처리 결과 | 부모의 공통 규칙을 따르고 자기 범위의 규칙만 결정합니다 |
| 판단 근거 | 선택 이유 · 조사 출처 · 비교안 · 미확인 사항 | 확정된 규칙 ID를 가리키며 미승인 판단을 기대값으로 쓰지 않습니다 |
| 구현 사양 | 내부 구조 · 테스트용 데이터 · 디버그 설정 · 구현 방법 | 서비스 동작을 바꾸지 않습니다. 사용자에게 보이는 동작 변경은 기획 정본에서 먼저 결정합니다 |
| 파생물 | 정본에 따른 화면 · 흐름도 · 시뮬레이터 · 설명 자료 | 정본 ID와 반영 revision을 추적하고, 구현 관찰을 기획 확정으로 승격하지 않습니다 |

기능 골격은 기능 구성의 정본일 수 있지만 모든 상세 규칙까지 소유하는 것은 아닙니다. 상세 규칙을
요약한다면 규칙 ID와 원문 위치를 함께 적습니다. 반대로 상세 문서에서 기능 구성이나 포함 범위를
바꾸려면 그 범위를 소유한 골격부터 변경합니다. 승인 상태와 등록 정보는 base 정본 관리 규칙 「프로젝트마다 등록대장을 하나 둡니다」의 등록대장을 기준으로
조회하며 문서 머리의 요약을 별도 승인 기록으로 관리하지 않습니다.

## 2. 기능 · 화면 · 상태는 서로 다른 축입니다

같은 기능이 여러 화면에서 실행된다는 이유만으로 정본을 여러 개 만들지 않습니다. 기능은 사용자
목적과 독립된 책임으로 나누고, 화면은 실행 위치와 진입 경로로, 상태는 동작이 달라지는 조건으로
연결합니다. 한 기능의 경로가 여러 개여도 기능 ID는 유지하며, 독립된 책임으로 분리할 때에만 새
기능 ID와 소유 범위를 정합니다.

- 기능 ID는 페이지 번호 · 목차 순서 · 화면 진입 경로가 달라져도 유지합니다.
- 화면 ID와 흐름 노드 ID는 기능 ID와 구분합니다. 필요하면 한 기능에 여러 화면 · 노드를 연결합니다.
- 여러 경로가 같은 화면에 합류하면 도착 화면과 규칙을 한 번 정의하고 진입 경로별 조건만 기록합니다.
- 상태는 해당 기능의 조건으로 선언합니다. 상태별로 허용 · 차단 · 표시 · 전이 결과를 적고,
  상태 이름이 다르다는 이유로 같은 기능을 복제하지 않습니다.
- 공통 기능은 공통 정본 한 곳에서 소유합니다. 각 화면은 공통 규칙을 참조하며 해당 화면만의
  차이는 부모의 위임 범위에서 기록합니다.

### 기능 골격은 동작 순서와 화면 배치 순서로 읽습니다

기능을 실제로 사용하는 흐름을 따라 읽을 수 있도록 **동작 순서를 먼저 적용하고, 같은 시점에
선택할 수 있는 항목에는 화면 배치 순서를 적용합니다.** 기능의 소유와 계층은 유지하면서
각 묶음 안의 나열 순서를 정합니다.

1. 자동 확인 · 로딩 · 필수 안내처럼 후속 조작의 선행 조건인 동작을 먼저 적습니다.
   첫 진입에서만 필요한 동작은 조건을 붙이고, 재진입이나 완료 상태의 건너뛰기는 분기로 적습니다.
2. 같은 시점에 사용자가 선택할 수 있는 항목은 **좌측 상단 → 우측 상단 → 좌측 하단 → 우측 하단**
   순으로 적습니다. 세로 목록과 가운데 본문은 위에서 아래로, 같은 줄은 왼쪽에서 오른쪽으로
   읽습니다. 구획이 나뉘면 각 영역 안에도 같은 기준을 적용합니다.
3. 항목 선택 후의 하위 흐름은 다시 동작 순서를 따릅니다. 입력 · 처리 · 결과 · 복귀의 순서는
   실제 사양을 기준으로 적고, 선택 · 취소 · 예외는 분기로 표현합니다.
4. 화면 배치에 따른 나열은 읽는 순서입니다. 앞 항목을 반드시 실행해야 다음 항목을 선택할 수
   있다는 뜻이나 개발 우선순위로 해석하지 않습니다. 필수 선행 관계는 조건으로 따로 명시합니다.
5. 재사용 기능은 한 곳에서 정의하고 각 호출 위치에서는 같은 기능 ID를 참조합니다. 정의가
   뒤에 있다는 이유로 실행 시점이 늦어지는 것은 아니며, 순서를 맞추려고 기능을 복제하지 않습니다.
6. 화면 · 상태 · 화면 크기에 따라 배치가 달라지면 적용 대상을 구분합니다. 승인된 화면 사양과
   대조하고, 코드 선언 순서만으로 시각 배치를 확정하지 않습니다. 확인하지 못한 위치는 미결로
   연결합니다. 골격의 나열만으로 상세 화면 좌표를 승인한 것으로 보지 않습니다.

### 화면 구획은 기능 이름과 영역으로 표기합니다

구획 이름만 읽어도 내용을 알 수 있도록 **기능 이름 + 영역**으로 표기합니다. `본문 위쪽` ·
`다음 본문`처럼 위치나 순번만으로 이름 붙이지 않습니다. 위치 정보는 나열 순서나 보조 설명에
적고, 같은 구획은 골격 · 상세 기획 · 파생물에서 같은 이름으로 참조합니다.

여러 기능이 모이는 영역은 공통 목적이 드러나는 이름으로 묶고, 각 기능의 담당 정본을 연결합니다.
영역 하나가 반드시 기능 하나나 정본 하나를 뜻하지 않습니다. 영역 이름을 바꾸거나 배치를
옮기는 것만으로 기능 ID · 소유 범위 · 부모 정본을 바꾸지 않습니다.

### 기획 ID에 기능의 의미를 담습니다

명명과 이전의 공통 기준은 `../../../base/rules/doc-write-style.md`의 「ID는 대상과 역할이 드러나는 이름으로 정합니다」를 따릅니다.
기획에서는 다음처럼 서로 다른 대상을 구분하며, 각 ID에 한글 이름과 소유 정본을 함께 등록합니다.
아래는 형식 예시이며 특정 프로젝트의 기능을 확정하지 않습니다.

| 대상 | 의미가 드러나는 ID 예시 | 한글 이름 |
|---|---|---|
| 기능 | `feature-account-profile-edit` | 계정 프로필 수정 |
| 화면 | `screen-account-settings` | 계정 설정 화면 |
| 흐름 노드 | `flow-account-profile-save` | 프로필 저장 처리 |
| 규칙 | `rule-account-profile-name-required` | 프로필 이름 필수 입력 |
| 정본 | `spec-account-profile` | 계정 프로필 정본 |

기능 계층 · 동작 순서 · 화면의 배치 순서는 ID와 별도로 관리합니다. 부모가 달라지거나 목차를
재정렬해도 동일한 책임의 ID는 유지합니다. 이름이 바뀌었다는 이유만으로 새 기능을 만들지 않습니다.
워크플로우 · 시뮬레이터 · 기획서는 이 ID를 공통으로 참조하고, 화면에 표시할 때는 한글 이름을
함께 제공합니다. 기존 숫자 ID를 사용하는 자료는 공통 이전 절차를 마친 뒤 전환합니다.
기능을 조회 · 대조 · 검수할 때는 의미가 있는 기능 ID 전체를 기준으로 삼습니다. 숫자 순번이나
숫자 접두사로 기능의 동일성 · 소유 · 분류를 판단하지 않습니다. 숫자는 표시 순서로만 별도 관리합니다.
기존 검사 도구가 숫자 형식을 요구하면 ID 이전 작업에 해당 검사와 생성기의 수정도 포함합니다.


## 3. 기획 정본의 공통 작성 골격

범위에서 동작으로, 동작에서 판정으로 읽을 수 있도록 다음 순서를 기본으로 사용합니다. 이 표는
정본에 담을 내용의 골격입니다. 출력 매체의 장수 · 지면 · 시각 템플릿을 바꾸는 규칙이 아닙니다.
기존 출력 템플릿을 사용할 때에는 아래 항목이 어느 절에 대응하는지 확인합니다.

| 순서 | 절 | 담을 내용 |
|---|---|---|
| 1 | 문서 책임 범위 · 부모 정본 · 승인 상태 | 정본 ID와 등록대장 위치, 포함/제외 범위, 부모 ID와 적용 규칙, 기준 revision과 승인 근거 참조 |
| 2 | 기능 구성과 하위 정본 | 기능 ID · 이름 · 역할 · 계층 · 구현/보류/제외 · 담당 정본 ID. 자식이 없으면 해당 없음과 이유 |
| 3 | 진입 조건과 사용자 흐름 | 시작점 · 선행 조건 · 사용자 행동 · 시스템 처리 · 분기 조건 · 도착점 · 종료/취소/복귀 |
| 4 | 화면 구성과 동작 | 화면 ID · 담당 기능 ID · 구성 요소 · 표시 조건 · 입력/선택 · 처리 결과 · 이동 대상 · 공통 UI 참조 |
| 5 | 상태 · 분기 · 예외 · 수치 정책 | 규칙 ID별 조건 · 허용/차단 · 다음 상태 · 오류/빈 값/로딩 · 경계값과 단위 · 복구 방법 |
| 6 | 검수 기준 · 파생물 연결 · 미결 사항 | 규칙 ID별 관찰 가능한 기대 결과, 파생물 추적 위치, 미확인 값과 결정할 항목 |

해당 없는 항목은 이유를 적고, 아직 모르는 값은 `?`와 결정할 항목으로 남깁니다. 빈칸이나 미확인을
기본값 · 승인으로 해석하지 않습니다. 부모 규칙의 전문을 복사해 빈 절을 채우지 않습니다.


### 기획서의 설명을 세부 기능 단위로 연결합니다

처음 읽는 사람이 기능의 역할과 이용 위치·대상·방법을 함께 이해하도록 개요를 작성합니다.
세부 기능마다 정상 이용, 화면과 조작, 판정 규칙, 관련 예외를 연결하며 설명과 예외를 서로 먼
장으로 나누지 않습니다. 승인된 서비스 조건·수치·복귀 결과는 요약에서도 보존합니다.

출력 문서는 정본 전문의 복사본이 아닙니다. 내부 실행 정보와 중복 설명은 정본으로 연결할 수
있지만, 본문에 요약한 규칙과 정본 참조만 제공한 항목을 대응 기록에서 구분합니다. 미기재 조건을
확정하거나 구현 관찰을 서비스 승인으로 바꾸지 않습니다. 시각 배치와 페이지 분할은 출력 모듈의
규칙을 따릅니다.

### 화면 진입과 이탈은 필요한 경우 흐름도로 보여 줍니다

화면 구성만으로는 어디서 들어와 어디로 나가는지 알 수 없으므로, **다른 화면·시트로 이동하거나,
진입 조건에 따른 분기·합류·복귀가 있는 기획에는 화면 이동 흐름도를 포함합니다.** 진입 경로가
여러 개이거나 같은 버튼의 결과가 상태에 따라 달라지는 경우도 해당합니다. 화면 이동과 조건
분기가 없는 단순 정보·외형 정의라면 생략 사유를 적고 구성 표로 설명할 수 있습니다.

흐름도는 「진입 조건과 사용자 흐름」에 배치하거나 해당 절에서 문서 안의 상세 흐름도를 연결합니다.
노드·전이 표와 같은 사양을 표현하며, 그림만의 별도 규칙이나 두 번째 정본을 만들지 않습니다.

- **진입**: 출발 화면·호출 기능, 진입 버튼이나 자동 사건, 선행 조건, 도착 화면을 표시합니다.
  외부 문서에서 들어오는 경로도 연결자로 표시하고 담당 정본과 의미 있는 ID를 연결합니다.
- **이탈**: 해당 화면에서 다른 화면·시트를 여는 버튼의 실제 이름과 도착 대상을 표시합니다.
  탭 전환·내용 갱신·시트 열기·전체 화면 이동을 구분하고, 모든 조작을 화면 이동으로 그리지 않습니다.
- **조건**: 자동 판단과 사용자 선택을 구분합니다. 연결선에는 버튼 이름 또는 참·거짓을 판별할 수
  있는 조건을 붙이고, 주요 분기의 도착점을 빠뜨리지 않습니다. UI 나열 순서를 실행 순서로 잇지 않습니다.
- **복귀**: 완료·취소·닫기·뒤로 가기의 도착 화면과 유지·초기화할 상태를 표시합니다.
  여러 화면에서 호출되는 공통 기능은 호출 원점으로 돌아가는 계약을 정의하고 경로별 차이만 적습니다.
- **상태와 승인**: 버튼의 노출·비활성·편집 상태 때문에 경로가 달라지면 표시 조건을 함께 적습니다.
  알 수 없는 연결과 복원 정책은 미결 ID와 담당 정본을 붙이고 확정된 화살표로 표현하지 않습니다.
- **분할과 검수**: 공통 진입도와 화면별 상세도를 나눌 수 있으나 양쪽 연결자와 도착 ID를 맞춥니다.
  화면의 이동 버튼 목록과 흐름도의 출구, 진입 목록과 입구, 조건별 복귀를 대조합니다. 문서 대조와
  실제 시뮬레이터 조작 검수 결과는 따로 기록합니다.

도형·연결선·배치와 탐색 동작은 활성화된 출력 모듈의 흐름도 규칙을 따릅니다. 이 기준을 추가하는
것만으로 출력 모듈이 자동 활성화되거나 렌더링·의미 검사가 완료되지는 않습니다. 초안에서는
텍스트 흐름도로 경로를 검토할 수 있으며, 최종 출력에서는 해당 매체의 규칙으로 렌더링해 확인합니다.

### 골격에서 발견한 불일치는 담당 정본과 해결 시점을 연결합니다

골격 정리 중 발견한 상세 정책까지 한꺼번에 확정하면 기능 구성과 동작 결정이 섞입니다.
불일치는 발견 즉시 기록하되, 영향을 받는 범위에 따라 다음 시점에 해결합니다.

| 불일치 종류 | 해결 시점과 담당 |
|---|---|
| 기능의 존재 · 중복 · 분할 · 소유 정본 | 해당 범위의 기능 골격을 확정하기 전에 해결합니다 |
| 진입 조건 · 동작 · 수치 · 예외 · 화면 문구 | 해당 기능의 상세 기획 정본을 작성할 때 해결합니다 |
| 여러 기능이 공유하는 정책 | 부모 공용 정본에서 먼저 해결하고 자식 정본에 적용합니다 |
| 정본과 워크플로우 · 시뮬레이터 · 기획서의 차이 | 승인된 정본과 수정 범위를 확인한 뒤 파생물에 반영합니다 |

분류는 항목 이름보다 영향으로 판단합니다. 상세 조건처럼 보여도 기능의 존재나 소유 범위를
바꾸는 문제라면 골격 확정 전에 해결합니다. 상세 작성 중 이런 영향이 드러나면 골격 변경으로
되돌려 연결합니다. 영향을 받지 않는 범위는 계속 진행할 수 있습니다.

골격에는 **불일치 요약 · 관련 자료의 경로와 항목 제목 · 담당 정본 · 해결 시점**을 연결합니다.
상세 비교와 결정 대기 내용은 담당 정본의 미결 사항에 두고, 프로젝트 remaining-work에는 그
위치와 착수 조건을 연결합니다. 담당 정본이 아직 없으면 remaining-work에 먼저 기록하고 정본을
작성할 때 연결합니다. 여러 문서에 같은 미결 내용이나 상태를 독립적으로 관리하지 않습니다.

상세 기획에 착수할 때 연결된 불일치를 먼저 확인합니다. 자료가 다르다는 이유만으로 어느 쪽을
확정하지 않으며, 판단과 승인 절차는 `../../../base/rules/rule-conflict.md`를 따릅니다.
해결 시점을 늦추는 것은 미확정 내용을 구현하거나 검수 기대값으로 사용하는 승인이 아닙니다.
결정되지 않은 부분은 미결로 표시하고 해당 범위를 확정하거나 검수 완료로 처리하지 않습니다.

결정 후에는 담당 정본과 승인 근거를 연결하고 파생물의 반영 · 검수 상태를 기록합니다.
정책 결정 완료와 파생물 반영 완료를 구분합니다. 완료된 작업은 remaining-work에서 지우고
결정과 변경 기록은 change-log에 남깁니다. 파생물 반영이 남았다면 그 작업은 계속 추적합니다.

## 4. 기획 규칙의 적용 지점을 검수합니다

추적과 검수 상태 관리는 base 정본 관리 규칙 「프로젝트마다 등록대장을 하나 둡니다」 · 「파생물은 적용한 정본의 규칙을 지킵니다」 · 「검사 범위와 현재의 한계」 · 「분야별 모듈은 공통 규칙을 참조하고 검수를 구체화합니다」을 따릅니다. 기획에서는 다음
대응을 기존 등록대장과 검수 기록에 연결합니다.

| 기능 ID | 소유 정본 ID · 규칙 ID | 화면/흐름 노드 ID | 파생물 위치 · 반영 revision | 검수 기준과 결과 위치 |
|---|---|---|---|---|
| {기능 ID} | {담당 정본과 규칙} | {적용 지점 또는 해당 없음} | {등록대장 파생물 행} | {기대 결과와 실제 검수 기록} |

- 골격의 선행 동작과 동시 선택 항목을 구분하고, 화면 배치에 따른 나열과 영역 이름을 대조합니다.
- 기능별로 선언한 상태에서 허용 · 차단 · 표시 · 전이 결과를 확인합니다.
- 주요 분기 · 취소 · 복귀 · 오류와 경계값을 대조합니다. 화면 개수만으로 검수를 완료하지 않습니다.
- 화면 구성 · 사용자 행동 · 시스템 처리를 구분하고 흐름도의 조건과 시뮬레이터의 동작을 대조합니다.
- 출력 매체가 요약한 내용은 원문 규칙으로 추적 가능해야 하며, 생략으로 다른 동작을 뜻하지 않는지 봅니다.

현재 이 모듈은 작성 규칙과 수동 검수 기준을 제공합니다. 자동 의미 검사나 산출물 생성기는
포함하지 않습니다. 원문에서 확인되지 않은 규칙은 기획의 미결 사항으로 관리합니다.
