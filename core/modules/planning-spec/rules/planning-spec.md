정본 관리의 공통 기준은 `../../../base/rules/canonical-source.md`입니다. 소유 · 상속 · 승인 ·
개정 · 이전 · 파생물 반영은 그 문서를 따르며 이 모듈이 재정의하지 않습니다. 아래 기준은 기획의
책임을 나누고 기능 · 화면 · 상태를 기술하는 방법만 구체화합니다.



기능 목록과 상세 사양에 같은 규칙을 각각 적으면 한쪽만 바뀌어도 서로 다른 동작을 지시합니다.
그래서 기능 골격은 기능의 구성 · 범위 · 담당 정본을 안내하고, 동작의 상세는 등록된 책임 정본에서
결정합니다. 같은 파일 안에서 절로 나누거나 부모 · 자식 정본으로 나눌 수 있으며, 파일 수보다
규칙의 소유가 겹치지 않는지가 기준입니다.

## 1. 자료별 책임

| 자료 | 소유하거나 기록하는 내용 | 다른 자료와의 관계 |
|---|---|---|
| 기능 골격 | 기능 ID · 기능 계층 · 구현/보류/제외 범위와 사유 | 각 기능의 담당 정본 ID를 연결합니다. 상세 동작은 해당 정본을 참조합니다. 보류한 기능은 예정 스펙 문서의 위치를 연결합니다(「지금 만들지 않는 스펙은 예정 스펙으로 분리합니다」) |
| 상세 기획 정본 | 진입 조건 · 화면 구성 · 사용자 동작 · 상태 전이 · 분기 · 수치 · 예외 · 처리 결과 | 부모의 공통 규칙을 따르고 자기 범위의 규칙만 결정합니다 |
| 판단 근거 | 선택 이유 · 조사 출처 · 비교안 · 미확인 사항 | 확정된 규칙 ID를 가리키며 미승인 판단을 기대값으로 쓰지 않습니다 |
| 구현 사양 | 내부 구조 · 테스트용 데이터 · 디버그 설정 · 구현 방법 | 서비스 동작을 바꾸지 않습니다. 사용자에게 보이는 동작 변경은 기획 정본에서 먼저 결정합니다 |
| 파생물 | 정본에 따른 화면 · 흐름도 · 시뮬레이터 · 설명 자료 | 정본 ID와 반영 revision을 추적하고, 구현 관찰을 기획 확정으로 승격하지 않습니다 |

기능 골격은 기능 구성의 정본일 수 있지만 모든 상세 규칙까지 소유하는 것은 아닙니다. 상세 규칙을
요약한다면 규칙 ID와 원문 위치를 함께 적습니다. 반대로 상세 문서에서 기능 구성이나 포함 범위를
바꾸려면 그 범위를 소유한 골격부터 변경합니다. 승인 상태와 등록 정보는 base 정본 관리 규칙 「프로젝트마다 등록대장을 하나 둡니다」의 등록대장을 기준으로
조회하며 문서 머리의 요약을 별도 승인 기록으로 관리하지 않습니다.

## 2. 기능 · 화면 · 상태는 서로 다른 축입니다

같은 기능이 여러 화면에서 실행된다는 이유만으로 정본을 여러 개 만들지 않습니다. 기능은 사용자
목적과 독립된 책임으로 나누고, 화면은 실행 위치와 진입 경로로, 상태는 동작이 달라지는 조건으로
연결합니다. 한 기능의 경로가 여러 개여도 기능 ID는 유지하며, 독립된 책임으로 분리할 때에만 새
기능 ID와 소유 범위를 정합니다.

- 기능 ID는 페이지 번호 · 목차 순서 · 화면 진입 경로가 달라져도 유지합니다.
- 화면 ID와 흐름 노드 ID는 기능 ID와 구분합니다. 필요하면 한 기능에 여러 화면 · 노드를 연결합니다.
- 여러 경로가 같은 화면에 합류하면 도착 화면과 규칙을 한 번 정의하고 진입 경로별 조건만 기록합니다.
- 상태는 해당 기능의 조건으로 선언합니다. 상태별로 허용 · 차단 · 표시 · 전이 결과를 적고,
  상태 이름이 다르다는 이유로 같은 기능을 복제하지 않습니다.
- 공통 기능은 공통 정본 한 곳에서 소유합니다. 각 화면은 공통 규칙을 참조하며 해당 화면만의
  차이는 부모의 위임 범위에서 기록합니다.

### 기능 골격은 동작 순서와 화면 배치 순서로 읽습니다

기능을 실제로 사용하는 흐름을 따라 읽을 수 있도록 **동작 순서를 먼저 적용하고, 같은 시점에
선택할 수 있는 항목에는 화면 배치 순서를 적용합니다.** 기능의 소유와 계층은 유지하면서
각 묶음 안의 나열 순서를 정합니다.

1. 자동 확인 · 로딩 · 필수 안내처럼 후속 조작의 선행 조건인 동작을 먼저 적습니다.
   첫 진입에서만 필요한 동작은 조건을 붙이고, 재진입이나 완료 상태의 건너뛰기는 분기로 적습니다.
2. 같은 시점에 사용자가 선택할 수 있는 항목은 **좌측 상단 → 우측 상단 → 좌측 하단 → 우측 하단**
   순으로 적습니다. 세로 목록과 가운데 본문은 위에서 아래로, 같은 줄은 왼쪽에서 오른쪽으로
   읽습니다. 구획이 나뉘면 각 영역 안에도 같은 기준을 적용합니다.
3. 항목 선택 후의 하위 흐름은 다시 동작 순서를 따릅니다. 입력 · 처리 · 결과 · 복귀의 순서는
   실제 사양을 기준으로 적고, 선택 · 취소 · 예외는 분기로 표현합니다.
4. 화면 배치에 따른 나열은 읽는 순서입니다. 앞 항목을 반드시 실행해야 다음 항목을 선택할 수
   있다는 뜻이나 개발 우선순위로 해석하지 않습니다. 필수 선행 관계는 조건으로 따로 명시합니다.
5. 재사용 기능은 한 곳에서 정의하고 각 호출 위치에서는 같은 기능 ID를 참조합니다. 정의가
   뒤에 있다는 이유로 실행 시점이 늦어지는 것은 아니며, 순서를 맞추려고 기능을 복제하지 않습니다.
6. 화면 · 상태 · 화면 크기에 따라 배치가 달라지면 적용 대상을 구분합니다. 승인된 화면 사양과
   대조하고, 코드 선언 순서만으로 시각 배치를 확정하지 않습니다. 확인하지 못한 위치는 미결로
   연결합니다. 골격의 나열만으로 상세 화면 좌표를 승인한 것으로 보지 않습니다.

### 화면 구획은 기능 이름과 영역으로 표기합니다

구획 이름만 읽어도 내용을 알 수 있도록 **기능 이름 + 영역**으로 표기합니다. `본문 위쪽` ·
`다음 본문`처럼 위치나 순번만으로 이름 붙이지 않습니다. 위치 정보는 나열 순서나 보조 설명에
적고, 같은 구획은 골격 · 상세 기획 · 파생물에서 같은 이름으로 참조합니다.

여러 기능이 모이는 영역은 공통 목적이 드러나는 이름으로 묶고, 각 기능의 담당 정본을 연결합니다.
영역 하나가 반드시 기능 하나나 정본 하나를 뜻하지 않습니다. 영역 이름을 바꾸거나 배치를
옮기는 것만으로 기능 ID · 소유 범위 · 부모 정본을 바꾸지 않습니다.

### 기획 ID에 기능의 의미를 담습니다

명명과 이전의 공통 기준은 `../../../base/rules/doc-write-style.md`의 「ID는 대상과 역할이 드러나는 이름으로 정합니다」를 따릅니다.
기획에서는 다음처럼 서로 다른 대상을 구분하며, 각 ID에 한글 이름과 소유 정본을 함께 등록합니다.
아래는 형식 예시이며 특정 프로젝트의 기능을 확정하지 않습니다.

| 대상 | 의미가 드러나는 ID 예시 | 한글 이름 |
|---|---|---|
| 기능 | `feature-account-profile-edit` | 계정 프로필 수정 |
| 화면 | `screen-account-settings` | 계정 설정 화면 |
| 흐름 노드 | `flow-account-profile-save` | 프로필 저장 처리 |
| 규칙 | `rule-account-profile-name-required` | 프로필 이름 필수 입력 |
| 정본 | `spec-account-profile` | 계정 프로필 정본 |

기능 계층 · 동작 순서 · 화면의 배치 순서는 ID와 별도로 관리합니다. 부모가 달라지거나 목차를
재정렬해도 동일한 책임의 ID는 유지합니다. 이름이 바뀌었다는 이유만으로 새 기능을 만들지 않습니다.
워크플로우 · 시뮬레이터 · 기획서는 이 ID를 공통으로 참조하고, 화면에 표시할 때는 한글 이름을
함께 제공합니다. 기존 숫자 ID를 사용하는 자료는 공통 이전 절차를 마친 뒤 전환합니다.
기능을 조회 · 대조 · 검수할 때는 의미가 있는 기능 ID 전체를 기준으로 삼습니다. 숫자 순번이나
숫자 접두사로 기능의 동일성 · 소유 · 분류를 판단하지 않습니다. 숫자는 표시 순서로만 별도 관리합니다.
기존 검사 도구가 숫자 형식을 요구하면 ID 이전 작업에 해당 검사와 생성기의 수정도 포함합니다.


## 3. 기획 정본의 공통 작성 골격

범위에서 동작으로, 동작에서 판정으로 읽을 수 있도록 다음 순서를 기본으로 사용합니다. 이 표는
정본에 담을 내용의 골격입니다. 출력 매체의 장수 · 지면 · 시각 템플릿을 바꾸는 규칙이 아닙니다.
기존 출력 템플릿을 사용할 때에는 아래 항목이 어느 절에 대응하는지 확인합니다.

| 순서 | 절 | 담을 내용 |
|---|---|---|
| 1 | 문서 책임 범위 · 부모 정본 · 승인 상태 | 정본 ID와 등록대장 위치, 포함/제외 범위, 부모 ID와 적용 규칙, 기준 revision과 승인 근거 참조 |
| 2 | 기능 구성과 하위 정본 | 기능 ID · 이름 · 역할 · 계층 · 구현/보류/제외 · 담당 정본 ID. 자식이 없으면 해당 없음과 이유 |
| 3 | 진입 조건과 사용자 흐름 | 시작점 · 선행 조건 · 사용자 행동 · 시스템 처리 · 분기 조건 · 도착점 · 종료/취소/복귀 |
| 4 | 화면 구성과 동작 | 화면 ID · 담당 기능 ID · 구성 요소 · 표시 조건 · 입력/선택 · 처리 결과 · 이동 대상 · 공통 UI 참조 |
| 5 | 상태 · 분기 · 예외 · 수치 정책 | 규칙 ID별 조건 · 허용/차단 · 다음 상태 · 오류/빈 값/로딩 · 경계값과 단위 · 복구 방법 |
| 6 | 검수 기준 · 파생물 연결 · 미결 사항 | 규칙 ID별 관찰 가능한 기대 결과, 파생물 추적 위치, 미확인 값과 결정할 항목 |

해당 없는 항목은 이유를 적고, 아직 모르는 값은 `?`와 결정할 항목으로 남깁니다. 빈칸이나 미확인을
기본값 · 승인으로 해석하지 않습니다. 부모 규칙의 전문을 복사해 빈 절을 채우지 않습니다.


### 기획서의 설명을 세부 기능 단위로 연결합니다

처음 읽는 사람이 기능의 역할과 이용 위치·대상·방법을 함께 이해하도록 개요를 작성합니다.
세부 기능마다 정상 이용, 화면과 조작, 판정 규칙, 관련 예외를 연결하며 설명과 예외를 서로 먼
장으로 나누지 않습니다. 승인된 서비스 조건·수치·복귀 결과는 요약에서도 보존합니다.

출력 문서는 정본 전문의 복사본이 아닙니다. 내부 실행 정보와 중복 설명은 정본으로 연결할 수
있지만, 본문에 요약한 규칙과 정본 참조만 제공한 항목을 대응 기록에서 구분합니다. 미기재 조건을
확정하거나 구현 관찰을 서비스 승인으로 바꾸지 않습니다. 시각 배치와 페이지 분할은 출력 모듈의
규칙을 따릅니다. 정본 하나를 특정 독자의 작업에 맞게 줄인 문서를 따로 두려면 「독자용 요약본은
정본을 줄인 별도 층입니다」를 따릅니다.

### 화면 진입과 이탈은 필요한 경우 흐름도로 보여 줍니다

화면 구성만으로는 어디서 들어와 어디로 나가는지 알 수 없으므로, **다른 화면·시트로 이동하거나,
진입 조건에 따른 분기·합류·복귀가 있는 기획에는 화면 이동 흐름도를 포함합니다.** 진입 경로가
여러 개이거나 같은 버튼의 결과가 상태에 따라 달라지는 경우도 해당합니다. 화면 이동과 조건
분기가 없는 단순 정보·외형 정의라면 생략 사유를 적고 구성 표로 설명할 수 있습니다.

흐름도는 「진입 조건과 사용자 흐름」에 배치하거나 해당 절에서 문서 안의 상세 흐름도를 연결합니다.
노드·전이 표와 같은 사양을 표현하며, 그림만의 별도 규칙이나 두 번째 정본을 만들지 않습니다.

- **진입**: 출발 화면·호출 기능, 진입 버튼이나 자동 사건, 선행 조건, 도착 화면을 표시합니다.
  외부 문서에서 들어오는 경로도 연결자로 표시하고 담당 정본과 의미 있는 ID를 연결합니다.
- **이탈**: 해당 화면에서 다른 화면·시트를 여는 버튼의 실제 이름과 도착 대상을 표시합니다.
  탭 전환·내용 갱신·시트 열기·전체 화면 이동을 구분하고, 모든 조작을 화면 이동으로 그리지 않습니다.
- **조건**: 자동 판단과 사용자 선택을 구분합니다. 연결선에는 버튼 이름 또는 참·거짓을 판별할 수
  있는 조건을 붙이고, 주요 분기의 도착점을 빠뜨리지 않습니다. UI 나열 순서를 실행 순서로 잇지 않습니다.
- **복귀**: 완료·취소·닫기·뒤로 가기의 도착 화면과 유지·초기화할 상태를 표시합니다.
  여러 화면에서 호출되는 공통 기능은 호출 원점으로 돌아가는 계약을 정의하고 경로별 차이만 적습니다.
- **상태와 승인**: 버튼의 노출·비활성·편집 상태 때문에 경로가 달라지면 표시 조건을 함께 적습니다.
  알 수 없는 연결과 복원 정책은 미결 ID와 담당 정본을 붙이고 확정된 화살표로 표현하지 않습니다.
- **분할과 검수**: 공통 진입도와 화면별 상세도를 나눌 수 있으나 양쪽 연결자와 도착 ID를 맞춥니다.
  화면의 이동 버튼 목록과 흐름도의 출구, 진입 목록과 입구, 조건별 복귀를 대조합니다. 문서 대조와
  실제 시뮬레이터 조작 검수 결과는 따로 기록합니다.

도형·연결선·배치와 탐색 동작은 활성화된 출력 모듈의 흐름도 규칙을 따릅니다. 이 기준을 추가하는
것만으로 출력 모듈이 자동 활성화되거나 렌더링·의미 검사가 완료되지는 않습니다. 초안에서는
텍스트 흐름도로 경로를 검토할 수 있으며, 최종 출력에서는 해당 매체의 규칙으로 렌더링해 확인합니다.

### 골격에서 발견한 불일치는 담당 정본과 해결 시점을 연결합니다

골격 정리 중 발견한 상세 정책까지 한꺼번에 확정하면 기능 구성과 동작 결정이 섞입니다.
불일치는 발견 즉시 기록하되, 영향을 받는 범위에 따라 다음 시점에 해결합니다.

| 불일치 종류 | 해결 시점과 담당 |
|---|---|
| 기능의 존재 · 중복 · 분할 · 소유 정본 | 해당 범위의 기능 골격을 확정하기 전에 해결합니다 |
| 진입 조건 · 동작 · 수치 · 예외 · 화면 문구 | 해당 기능의 상세 기획 정본을 작성할 때 해결합니다 |
| 여러 기능이 공유하는 정책 | 부모 공용 정본에서 먼저 해결하고 자식 정본에 적용합니다 |
| 정본과 워크플로우 · 시뮬레이터 · 기획서의 차이 | 승인된 정본과 수정 범위를 확인한 뒤 파생물에 반영합니다 |

분류는 항목 이름보다 영향으로 판단합니다. 상세 조건처럼 보여도 기능의 존재나 소유 범위를
바꾸는 문제라면 골격 확정 전에 해결합니다. 상세 작성 중 이런 영향이 드러나면 골격 변경으로
되돌려 연결합니다. 영향을 받지 않는 범위는 계속 진행할 수 있습니다.

골격에는 **불일치 요약 · 관련 자료의 경로와 항목 제목 · 담당 정본 · 해결 시점**을 연결합니다.
상세 비교와 결정 대기 내용은 담당 정본의 미결 사항에 두고, 프로젝트 remaining-work에는 그
위치와 착수 조건을 연결합니다. 담당 정본이 아직 없으면 remaining-work에 먼저 기록하고 정본을
작성할 때 연결합니다. 여러 문서에 같은 미결 내용이나 상태를 독립적으로 관리하지 않습니다.

상세 기획에 착수할 때 연결된 불일치를 먼저 확인합니다. 자료가 다르다는 이유만으로 어느 쪽을
확정하지 않으며, 판단과 승인 절차는 `../../../base/rules/rule-conflict.md`를 따릅니다.
해결 시점을 늦추는 것은 미확정 내용을 구현하거나 검수 기대값으로 사용하는 승인이 아닙니다.
결정되지 않은 부분은 미결로 표시하고 해당 범위를 확정하거나 검수 완료로 처리하지 않습니다.

결정 후에는 담당 정본과 승인 근거를 연결하고 파생물의 반영 · 검수 상태를 기록합니다.
정책 결정 완료와 파생물 반영 완료를 구분합니다. 완료된 작업은 remaining-work에서 지우고
결정과 변경 기록은 change-log에 남깁니다. 파생물 반영이 남았다면 그 작업은 계속 추적합니다.

## 4. 기획 규칙의 적용 지점을 검수합니다

추적과 검수 상태 관리는 base 정본 관리 규칙 「프로젝트마다 등록대장을 하나 둡니다」 · 「파생물은 적용한 정본의 규칙을 지킵니다」 · 「검사 범위와 현재의 한계」 · 「분야별 모듈은 공통 규칙을 참조하고 검수를 구체화합니다」을 따릅니다. 기획에서는 다음
대응을 기존 등록대장과 검수 기록에 연결합니다.

| 기능 ID | 소유 정본 ID · 규칙 ID | 화면/흐름 노드 ID | 파생물 위치 · 반영 revision | 검수 기준과 결과 위치 |
|---|---|---|---|---|
| {기능 ID} | {담당 정본과 규칙} | {적용 지점 또는 해당 없음} | {등록대장 파생물 행} | {기대 결과와 실제 검수 기록} |

- 골격의 선행 동작과 동시 선택 항목을 구분하고, 화면 배치에 따른 나열과 영역 이름을 대조합니다.
- 기능별로 선언한 상태에서 허용 · 차단 · 표시 · 전이 결과를 확인합니다.
- 주요 분기 · 취소 · 복귀 · 오류와 경계값을 대조합니다. 화면 개수만으로 검수를 완료하지 않습니다.
- 화면 구성 · 사용자 행동 · 시스템 처리를 구분하고 흐름도의 조건과 시뮬레이터의 동작을 대조합니다.
- 출력 매체가 요약한 내용은 원문 규칙으로 추적 가능해야 하며, 생략으로 다른 동작을 뜻하지 않는지 봅니다.

### 요약본과 정본을 자동으로 대조합니다

요약본(「독자용 요약본은 정본을 줄인 별도 층입니다」)은 정본이 바뀔 때마다 손으로 따라 고치므로,
사람이 읽어서는 빠진 규칙이나 낡은 문서를 놓칩니다. 그래서 요약본은 문장마다 정본 노드 ID를
앵커로 달고(「정본 앵커」), 끝의 「정본 대조」 표에 원본 정본의 해시를 적어 둡니다. 검사기는 이
두 가지를 읽어 다음을 확인하며, 하나라도 걸리면 실패로 끝납니다.

| 검사 | 걸리는 경우 | 고치는 법 |
|---|---|---|
| 빠진 노드 | 원본 정본의 노드 표에 있는 실행 노드가 요약본의 앵커에 한 번도 나오지 않음 | 그 노드의 규칙을 요약 문장으로 옮기거나, 이미 옮긴 문장 끝에 앵커를 붙입니다 |
| 없는 노드 | 앵커의 ID가 등록된 어느 정본의 노드 표에도 없음 | 오타를 고치거나, 정본에서 바뀐 ID로 바꿉니다. 정본에서 지운 노드라면 그 문장을 지웁니다 |
| 깨진 링크 | 상대 경로 링크나 그림 경로가 가리키는 파일이 없음 | 경로를 고치거나 실제로 있는 그림만 넣습니다 |
| 외부 디자인 링크 불일치 | 외부 디자인 도구 링크의 노드 번호가 프로젝트의 화면 대응표에 없거나, 링크 글자(화면 키)와 대응표의 화면이 다름 | 대응표에서 링크를 다시 만듭니다 |
| 해시 불일치 | 「정본 대조」 표의 SHA-256이 지금 정본 파일의 바이트 해시와 다름 | 정본의 차이를 읽고 요약본을 고친 뒤 개정과 해시를 갱신합니다(「요약본을 고칠 때」) |

- **해시는 원본 바이트로 계산합니다.** 줄바꿈 변환이나 표기 되돌리기를 거친 글로 계산하면,
  정본이 그대로여도 도구마다 다른 값이 나옵니다.
- 노드 표가 없는 정본은 빠진 노드 검사를 건너뛰고 해시만 대조합니다. 건너뛴 사실은 결과에 남깁니다.
- 등록대장 파생물 행의 반영 revision 칸은 그 요약본의 「정본 대조」 표를 가리키고, 해시 값을
  따로 다시 적지 않습니다. 같은 값을 두 자리에 두면 한쪽만 갱신됩니다.
- **검사 통과는 덮었다는 뜻이지 같다는 뜻이 아닙니다.** 앵커가 붙은 문장이 정본과 다른 동작을
  말해도 검사기는 알지 못합니다. 문장의 뜻 · 조건 · 예외가 정본과 같은지는 사람이 대조하고,
  자동 검사 결과와 따로 기록합니다.

이 검사기는 아직 이 모듈에 들어 있지 않습니다. 들어오기 전에는 프로젝트가 위 다섯 항목을 보는
스크립트를 두거나 손으로 대조하고, 어느 방법으로 확인했는지 검수 기록에 적습니다. 모듈에 들어오면
프로젝트 스크립트를 지우고 모듈의 검사기로 바꿉니다.

### 생성기는 정본 입력 계약을 검사합니다

정본을 읽어 워크플로우 · 시뮬레이터 · 발표물을 만드는 생성기는, 형식이 어긋난 정본에서도 그럴듯한
산출물을 만들어 냅니다. 그래서 생성기는 만들기 전에 정본이 입력 계약을 지키는지 검사하고, 어긋나면
만들지 않습니다. 정본 ID와 개정이 적혀 있는지, 노드 ID가 겹치지 않는지, 연결이 없는 노드를
가리키지 않는지가 기본이며, 산출물에 입력 지문(입력 파일의 해시)을 찍어 낡은 산출물을 찾게 합니다.
검사 항목의 세부와 명령은 각 출력 모듈이 정합니다. 이 모듈은 「생성에 성공했다」를 「정본을
반영했다」로 보고하지 않는다는 원칙만 정합니다.

원문에서 확인되지 않은 규칙은 기획의 미결 사항으로 관리합니다(「미결 확인 사항은 해결되면 지웁니다」).

## 5. 독자용 요약본은 정본을 줄인 별도 층입니다

정본은 판정 기준 · 근거 · 승인 출처 · 이력까지 담아 길고, 개발자나 그래픽 디자이너는 그중 자기
작업에 필요한 규칙만 사용 순서대로 읽고 싶어 합니다. 정본을 독자용으로 고쳐 쓰면 근거가 사라지고,
독자용 문장을 정본에 섞으면 같은 규칙이 두 문체로 두 번 적힙니다. 그래서 **정본 하나를 특정 독자의
작업에 필요한 규칙만 사용 순서로 줄인 문서를 별도 층으로 둡니다.** 이 문서를 독자용 요약본(줄여서
요약본)이라 부릅니다. 요약본은 정본이 아니며 정본을 대신하지 않습니다.

| 항목 | 기준 |
|---|---|
| 원본 | 기능 정본 하나에 요약본 하나가 기본입니다. 다른 정본의 규칙은 다시 쓰지 않고 그 정본이나 형제 요약본으로 넘깁니다 |
| 문서 ID | 원본 정본 ID와 짝을 맞춥니다. 예: `spec-account-profile` → `brief-account-profile` |
| 등록 | 프로젝트 등록대장의 파생물 표에 파생 역할로 올리고, source IDs에 원본 정본과 넘기는 범위의 정본을 적습니다 |
| 다음 쓰임 | 발표물(슬라이드 · PDF)을 만든다면 요약본만 읽어 만듭니다. 발표물이 정본 규칙을 새로 가져오거나 고쳐 쓰지 않습니다 |
| 작성 규칙 | 읽는 사람 · 장 이름 · 문체 같은 프로젝트 값은 프로젝트 규칙 문서에 두고, 각 요약본에는 되풀이하지 않습니다 |

### 담는 것과 빼는 것

요약본에 정본에 없는 문장이 하나라도 들어가면 독자는 그것을 승인된 규칙으로 읽습니다. 그래서
더하지 않는 것을 먼저 정하고, 뺄 것은 「독자의 작업에 쓰이지 않는 것」으로 정합니다.

- **더하지 않습니다:** 정본에 없는 규칙 · 추측 · 개선 제안 · 작성자의 판단.
- **뺍니다:** 행마다 붙은 근거 표시(사용자 확정 · 구현 관찰 같은 출처 라벨), 날짜, 변경 이력,
  생성기와 시뮬레이터를 위한 내부 키(실행 사건 이름 · 상태 키 등), 설계 근거와 보류안, 재현용 대응 표.
- **지난 동작은 넣지 않습니다.** 「이전에는 …였습니다」처럼 바뀌기 전 동작이나 폐기한 동작을 적으면
  독자가 두 동작을 함께 기억합니다.
- 근거 표시를 빼도 승인 상태는 그대로입니다. 승인되지 않은 규칙을 확정 문장으로 옮기지 않고
  「정해지지 않은 것」에 둡니다(「기획서의 설명을 세부 기능 단위로 연결합니다」).
- **값이 정해지지 않은 곳**은 본문에 「정해지지 않음」으로 적고, 문서 끝 「정해지지 않은 것」 표에
  모읍니다.
- **정본이 시안 예시라고 한 값**(이름 · 수량 · 가격 · 문장 · 콘텐츠 등)은 「시안 예시」로 표시합니다.
  어떤 값이 시안 예시인지는 「정해지지 않은 것」 표의 「시안 예시 값」 행에 모읍니다. 예시 값을
  확정 값처럼 적으면 그래픽 · 문구 작업이 예시에 맞춰 끝나 버립니다.
- **정본끼리 어긋나면 요약본에서 풀지 않습니다.** 실행 흐름을 정의한 노드 표와 승인된 규칙 쪽을
  적고, 어긋남은 프로젝트 remaining-work에 올립니다. 요약본에서 한쪽을 골라 쓰면 그 선택이 승인
  없이 확정됩니다.

### 기본 구성

아래는 기본 구성입니다. 프로젝트는 장 이름과 순서를 프로젝트 규칙 문서에서 바꿀 수 있지만, 정본
앵커 · 「정해지지 않은 것」 · 「정본 대조」는 대조 검사의 입력이라 유지합니다.

1. 첫 줄의 파일 CHANGELOG와 제목
2. **개요** — 기능이 무엇인지 한두 문장과 표(대상 · 들어오는 곳 · 주요 기능 · 끝나는 곳). 원본 정본의
   기능 설명과 이 문서의 단계에 있는 내용만 쓰고, 정본에 없는 항목은 행을 두지 않습니다.
3. **기획 의도** — 원본 정본의 기능 의도 중 확정된 행만 옮깁니다. 확정된 행이 없으면 장을 두지 않습니다.
4. **전체 흐름** — 단계 번호로 아래 단계를 가리키는 텍스트 도식. 문서를 열면 개요 다음에 바로 보이게 둡니다.
5. **참조 문서** — 표(문서 | 볼 내용). 첫 행은 원본 정본과 개정, 다음 행부터 이 문서가 넘기는 범위의
   정본 · 요약본입니다.
6. **단계** — 단계마다 한 장(쪽 구분선으로 나눔): 제목 → 지금 단계를 표시한 흐름 띠 → 한두 줄 소개 →
   번호 규칙 → 필요한 표 → 예외 → 화면 칸(그림 · 외부 디자인 링크).
   - 운영이 정하는 값이나 시각 기준 · 누적 · 소멸처럼 여러 단계에 걸친 판정이 있으면, 사용 단계 앞의
     첫 단계들로 둡니다. 이런 단계는 설정 표 · 규칙 · 날짜별 예시 표로 쓰고 화면 칸은 두지 않아도 됩니다.
7. **정해지지 않은 것**(표)과 **정본 대조**(정본 경로 | 개정 | SHA-256 표). 정본 대조 표의 첫 행이
   원본 정본입니다.

### 정본 앵커

요약 문장이 어느 정본 규칙에서 왔는지 기계가 따라갈 수 있도록, 규칙 문장 끝에 근거 노드 ID를
코드 표시 안의 대괄호로 붙입니다. 예: 「이름을 저장하면 프로필 화면으로 돌아갑니다.
`` `[flow-account-profile-save → flow-account-profile-view]` ``」. 여러 ID는 ` · ` 또는 ` → `로 나눕니다.

- 원본 정본의 실행 노드는 하나도 빠짐없이 한 번 이상 붙입니다. 다른 정본의 노드도 붙일 수 있으며,
  실제로 있는 ID만 씁니다.
- 앵커는 요약본(Markdown)에서 정본과 대조하는 데만 씁니다. 발표물 · PDF에는 그리지 않습니다.
  독자에게는 의미 없는 기호이고, 대조는 Markdown과 검사기가 맡습니다.
- 노드 표가 없는 정본을 요약할 때는 단계마다 정본 항목 이름을 적어 대신하지 않습니다. 원본 정본은
  「참조 문서」 · 「정본 대조」 표로 찾습니다.
- 문장을 지워 앵커가 없어지면, 그 앵커를 같은 규칙의 남은 문장 끝으로 옮깁니다. 앵커만 지우면
  빠진 노드로 걸립니다.

### 화면 문구와 링크 표시

- 버튼은 [대괄호], 화면 문구는 「낫표」로 씁니다. 버튼 바로 뒤에 괄호를 붙이면 Markdown이 링크로
  읽으므로 한 칸 띄웁니다. 예: `[저장] (편집 중일 때)`.
- 그림은 실제로 있는 파일만 넣습니다. 그림이 없는 화면은 외부 디자인 링크만 겁니다.
- 외부 디자인 도구 링크는 프로젝트의 화면 대응표(화면 키 → 디자인 노드 번호)에서 만들고, 링크 글자는
  화면 키를 그대로 씁니다. 손으로 옮겨 적은 노드 번호는 검사기가 대응표와 맞춰 봅니다.

### 요약본을 고칠 때

- 정본이 바뀌면, 바뀐 노드 ID의 앵커가 붙은 문장과 그 항목을 참조한 단계를 고칩니다. 그다음
  「정본 대조」 표의 개정과 SHA-256을 지금 정본으로 바꿉니다.
- 정본에서 링크 경로처럼 의미가 없는 부분만 바뀌었다면 본문은 그대로 두고 SHA-256만 갱신합니다.
  해시만 갱신하기 전에 정본의 차이를 읽어 규칙이 바뀌지 않았는지 확인합니다 — 해시만 맞추면
  검사기는 더 이상 낡았다고 알리지 않습니다.
- 고친 뒤 「요약본과 정본을 자동으로 대조합니다」의 검사를 다시 돌립니다.

## 6. 지금 만들지 않는 스펙은 예정 스펙으로 분리합니다

지금 개발하지 않는 스펙이 정본의 실행 규칙에 섞여 있으면, 구현 · 시뮬레이터 · 테스트 케이스가
그것을 현재 동작으로 읽습니다. 그래서 **지금 개발할 수 없거나 출시 뒤로 미룬 스펙은 정본의 실행
규칙에서 빼고 예정 스펙 문서로 옮깁니다.** 정본의 실행 규칙에는 현재 동작만 남습니다.

- 예정 스펙 문서의 자리는 프로젝트가 구조 설정과 등록대장에 정합니다. 옮긴 스펙마다 원래 정본 ID와
  규칙 ID를 함께 적어, 채택할 때 되돌아갈 자리를 알 수 있게 합니다.
- 예정 스펙은 테스트 케이스의 기대값 · 시뮬레이터 동작 · 요약본 본문으로 쓰지 않습니다.
- 채택하면 원래 정본으로 되돌리고, 정본 개정 순서(base 정본 관리 규칙 「파생물은 적용한 정본의
  규칙을 지킵니다」)를 따릅니다. 예정 스펙 문서에서 그 항목을 지우고 원래 정본의 위치를 남깁니다.

### 출시 범위를 정하면 정본을 출시 스펙에 맞춥니다

출시 시점에 들어갈 범위(출시 스펙)와 그 뒤로 미루는 범위를 가르기로 했다면, 정본 · 요약본 ·
시뮬레이터가 모두 같은 범위를 보여야 합니다. 한쪽만 고치면 구현과 테스트 케이스가 서로 다른 범위를
기준으로 삼습니다.

- 범위가 정해지면 기능 정본과 데이터 구조 정본을 먼저 출시 스펙으로 고치고, 출시 뒤로 미룬 내용은
  예정 스펙 문서로 옮깁니다. 그다음 요약본 · 시뮬레이터 기본값 · 흐름도처럼 정본을 따르는 파생물을
  다시 만듭니다(base 정본 관리 규칙 「파생물은 적용한 정본의 규칙을 지킵니다」).
- 이미 정본에 반영했던 변경을 출시 뒤로 미루면, 정본을 그 변경 이전 구조로 되돌리고 되돌린 범위를
  change-log에 적습니다. 빠진 연결(다른 정본에서 그 기능으로 들어가던 경로 등)도 함께 지웁니다.
- 예정 스펙 문서는 프로젝트가 정한 이름 하나로 부릅니다(예: 「추후 개선 과제」). 같은 문서를 「출시 후
  스펙」 · 「업데이트 예정」처럼 여러 이름으로 부르지 않습니다. 이름을 바꾸면 그 문서를 가리키는 다른
  문서의 표기도 함께 바꿉니다.

### 예정 스펙 문서에는 정본 원문을 그대로 옮깁니다

정본에서 뺀 내용을 요약해서 옮기면, 채택할 때 무엇을 되돌려야 하는지 처음부터 다시 조사해야 합니다.
그래서 **정본에서 뺀 내용은 정본 형식 그대로 옮기고, 그 앞에 바꾸려는 이유와 정할 것을 붙입니다.**

항목 하나는 다음 순서로 씁니다.

1. **현재 동작** — 지금 정본이 정한 동작입니다.
2. **바꾸려는 사유** — 왜 미뤘고 무엇을 개선하려는지입니다.
3. **현재 동작과 바뀔 동작 비교** — 표로 나란히 둡니다.
4. **정본 구조와 도입 때 정할 것** — 채택하면 바뀔 정본 · 화면 · 데이터와 아직 정하지 않은 값입니다.
5. **정본 원문(되돌릴 때 쓸 내용)** — 정본에서 뺀 규칙 표 행 · 노드 표 행 · 결정 행 · 미결 행 · 데이터
   구조 항목을 열과 ID를 바꾸지 않고 옮깁니다. 묶음마다 앞에 원래 정본 · 장 · 개정을 적습니다.

- 규칙 행의 열은 원래 정본의 규칙 표와 같게 둡니다. 열을 줄이거나 문장으로 풀면 되돌릴 때 다시 표로
  만들어야 합니다.
- 문서 앞에는 목록 표(항목 | 원래 정본 | 옮긴 날 | 도입 때 정할 것)를 둡니다.
- 폐기한 안은 예정 스펙 문서에 두지 않습니다. 원래 정본의 결정 이력에만 남깁니다(「보류 · 제외 결정은
  이력으로 남깁니다」).
- 채택하면 「정본 원문」을 원래 정본의 같은 자리로 되돌립니다. 옮긴 뒤 그 정본이 바뀌었을 수 있으므로,
  되돌리기 전에 지금 규칙 · 노드 ID와 겹치거나 어긋나는 곳을 대조합니다. 되돌린 뒤 예정 스펙 문서에서
  그 항목을 지웁니다.

### 보류 · 제외 결정은 이력으로 남깁니다

스펙 본문은 예정 스펙 문서로 옮겨도, **왜 미뤘는지는 원래 기능 정본의 결정 근거 항목에 남깁니다.**
결정 이력이 기능 정본에 있어야 그 기능을 고치는 사람이 같은 논의를 처음부터 되풀이하지 않습니다.
같은 결정을 별도 문서에 복제하지 않고, 예정 스펙 문서와 결정 이력은 서로를 링크로 가리킵니다.

| 결정 대상 | 결정 ID | 상태 | 사유 | 적용 범위 | 근거 · 결정일 | 재검토 조건 |
|---|---|---|---|---|---|---|
| {보류한 스펙} | {의미가 드러나는 결정 ID} | {보류 · 제외 · 폐기 · 재개} | {이유} | {영향받는 기능 · 화면} | {승인 기록 위치 · 날짜} | {다시 볼 조건} |

예: 프로필 배경 이미지 변경을 다음 업데이트로 미루면, 그 스펙은 예정 스펙 문서로 옮기고, 프로필
정본의 결정 이력에는 `decision-account-profile-background-hold` 행을 「보류」로 남기고 재검토 조건(예:
이미지 검수 도구 도입)을 적습니다.

- **결정이 바뀌어도 옛 행을 지우지 않습니다.** 새 결정 행을 더하고 옛 행에 대체 관계(「→ {새 결정 ID}로
  대체」)를 적은 뒤 현행 규칙을 고칩니다. 옛 행을 지우면 같은 안이 왜 한 번 미뤄졌는지 사라집니다.
- 사유나 날짜를 확인하지 못하면 `?`로 두고 미결 사항에 올립니다. 지금 떠올린 검토안을 과거 결정으로
  적지 않습니다.
- **파생물은 보류 · 제외 · 폐기된 내용을 되살리지 않습니다.** 생성기가 결정 이력이나 예정 스펙 문서를
  실행 흐름의 입력으로 읽지 않게 합니다.
- 작업 방법에 관한 결정(문서 구성 · 생성 방식 등)은 프로젝트 작성 규칙에 기록하고 기능 정본에
  섞지 않습니다.

## 7. 미결 확인 사항은 해결되면 지웁니다

확인 사항이 해결된 뒤에도 목록에 남으면, 읽는 사람은 무엇이 아직 열려 있는지 매번 다시 가려야
합니다. 그래서 확인 사항은 해당 정본의 미결 사항 절에서 관리하고, 해결되면 반영한 뒤 행을 지웁니다.
프로젝트 remaining-work에는 정본의 위치와 진행 순서만 둡니다(「골격에서 발견한 불일치는 담당 정본과
해결 시점을 연결합니다」).

| 확인할 사항 | 필요한 결정 또는 근거 | 완료 기준 | 상태 |
|---|---|---|---|
| {무엇이 정해지지 않았나} | {누가 무엇을 정하거나 확인해야 하나} | {무엇이 되면 끝인가} | {미해결 · 확인 중 · 보류 · 해결} |

보류도 미해결로 셉니다. 완료 기준을 채우면 다음 순서로 처리합니다.

1. 결정된 규칙을 본문(기능 정의 · 화면 · 흐름)에 반영합니다.
2. 선택한 이유와 비교한 대안을 결정 근거 항목에 남깁니다.
3. 필요한 승인 · 검증을 확인한 뒤 프로젝트 change-log에 결과를 적습니다.
4. 확인 행을 지웁니다. 해결된 행을 「해결」 상태로 남겨 두지 않습니다.

- **미해결 행이 하나도 없으면 미결 장과 그 목차 · 탭 항목을 출력하지 않습니다.** 제목만 있거나
  「문제 없음」만 적힌 장을 남기지 않습니다. 생성기는 장을 만들지 않는 방식으로 처리하고, 만든 뒤
  CSS로 숨기지 않습니다 — 숨긴 장은 검색 · 목차 · 인쇄에 다시 나타납니다. 새 문제가 생기면 같은 장에
  더해 다시 보입니다.
- 문서 화면에서 완료 버튼을 누른 것만으로 해결로 처리하지 않습니다. 해결은 위 순서를 마친 상태입니다.
- **본문에 `?`가 남아 있으면 대응하는 행을 지우지 않습니다.** 내용이 정해지지 않은 채로 행만 지우면
  `?`가 어디서 풀릴지 아무도 모르게 됩니다(`../../../base/rules/writing-principles.md` 「근거」).
- 미결 장이 사라진 것은 기록된 확인 사항을 처리했다는 뜻입니다. 문서 전체의 승인이나 실기 검증
  완료를 뜻하지 않습니다.

## 8. 출시 스펙 확정 점검표는 정본에서 만듭니다

출시 스펙이 확정되었는지를 사람이 정본을 하나씩 훑어 판단하면, 규칙 문장 안에 남은 미결이나
시뮬레이터를 보고 적은 규칙이 빠집니다. 그래서 **확정 조건을 정본에서 기계로 모은 점검표로
판단합니다.**

출시 스펙이 확정된 상태는 아래 세 가지가 모두 끝난 상태입니다.

1. **정해지지 않은 것** — 정본 미결 사항 절의 항목을 정하거나, 정할 주체(개발 · 운영)로 넘깁니다.
2. **구현 관찰 규칙** — 근거가 「구현 관찰」인 규칙 · 예외 행을 승인된 규칙으로 바꾸거나, 고칠 내용을
   정하거나, 정할 주체로 넘깁니다.
3. **규칙 안의 미결 표기** — 규칙 문장 안에 남은 「미결」 · 「정해지지 않음」을 정합니다.

근거가 「구현 관찰」인 흐름 노드는 그 노드의 규칙이 확정될 때 함께 바꿉니다. 점검표는 이 노드의 개수를
보여 주지만 확정 조건에는 넣지 않습니다.

| 모으는 것 | 빼는 것 |
|---|---|
| 미결 사항 절의 행 | 상태가 「해결」인 행 |
| 규칙 · 예외 표에서 근거가 「구현 관찰」인 행 | 「구현 관찰」이 옛 근거 표기(「이전: 구현 관찰」)에만 있는 행 — 이미 정한 것입니다 |
| 규칙 문장 안의 「미결」 · 「정해지지 않음」 | — |
| 노드 표에서 근거가 「구현 관찰」인 노드 | — |

- 결정 이력 · 재현 대응 · 검수 기록 장은 모으지 않습니다. 그 장의 「구현 관찰」은 과거 기록입니다.
- 예정 스펙 문서는 대상이 아닙니다. 출시 뒤로 미룬 범위는 출시 스펙의 확정 조건이 아닙니다.
- **점검표는 파생물입니다. 손으로 고치지 않고, 정본을 고친 뒤 다시 만듭니다.** 생성기에는 점검표가
  지금 정본과 맞는지만 보는 확인 모드(`--check`)를 둡니다. 항목이 점검표에서 사라지면 끝난 것입니다.
- 점검표 맨 앞에는 「먼저 정할 것」을 둡니다. 사용자가 기획 판단으로 남긴 결정 대기와, 출시 전에
  구현하기로 정한 항목입니다. 그 아래에 기능별 개수 요약(정본 개정 포함)과 기능별 항목을 둡니다.
- 점검표와 생성기의 자리는 프로젝트 구조 설정에 출력 · 도구 역할로 등록합니다.
- 이 생성기는 아직 모듈 도구로 없습니다. 프로젝트가 만들어 쓰고, 모으는 규칙은 이 절을 따릅니다.
