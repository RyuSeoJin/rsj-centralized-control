document-site 모듈의 마스터(인디고 · 라이트 기본)로 문서와 셸을 그릴 때의 규칙입니다.
모든 HTML 산출물에 공통인 출력 규칙(단일 파일 · 네트워크 0건 · 구워 넣기 · 링크)은
`core/base/rules/html-output.md`가 정본이고, 이 문서는 **이 마스터의 색 · 타이포 · 컴포넌트 ·
셸**만 정합니다. 아래 대원칙 1은 base 규칙을 이 모듈의 산출물에 맞춰 풀어 쓴 것입니다.

## 대원칙

1. **단일 파일 · 자기완결.** CSS·JS·차트 라이브러리·다이어그램을 전부 인라인합니다. 열었을 때
   네트워크 요청이 0건이어야 합니다 (사내망·오프라인·아카이브 대비). 기준 마스터 버전은 파일
   상단 CHANGELOG 주석과 footer에 기록합니다. `<link>`·`<script src>` 참조는 **디자인 규칙서와
   템플릿에만** 허용합니다 — 그 둘은 항상 최신 마스터를 비춰야 하기 때문입니다.
   검증 대상(`sut/`)은 문서가 아니라 프로그램이므로 이 규칙의 예외입니다(→ `sut-build.md`).

   **래스터 이미지(png·jpg·gif)는 상대 경로를 허용합니다**(2026-08-05 신설). 인라인 대상은
   **없으면 문서가 무너지는 것**(CSS·JS·다이어그램 SVG)이고, 사진은 **없어도 본문이 성립하는
   보조 자료**라 성격이 다릅니다. base64로 넣으면 용량이 33% 불어 문서에 얹히므로 자산으로
   둡니다. 대신 셋을 지킵니다.
   - **`alt`를 반드시 답니다** — 이미지가 안 떠도 무엇이 있었는지 읽힙니다
   - **그림이 없어도 문장이 성립해야 합니다** — 사진에만 있는 정보를 두지 않습니다
   - **자산은 `projects/{제품}/{프로젝트}/docs/`에 둡니다** — 문서와 자산이 흩어지지 않게

   자기완결이 지키려는 것은 오프라인·사내망 열람인데, 사진이 빠져도 글은 그대로 읽힙니다.
   랜딩의 실행 GIF가 이 규칙으로 예외에서 정상이 됩니다.
2. **문서지 대시보드가 아니다.** 세로로 읽어 내려가는 분석 문서입니다. 섹션마다 리드 문장으로
   "이 섹션이 무엇을 말하는가"를 먼저 밝히고, 표·차트는 그 주장의 근거로 놓습니다.
3. **라이트 기본 · 다크 토글 · 인디고 포인트.** 강조는 한 색(인디고)뿐이고 색을 늘리지 않습니다.
   기본값은 라이트이며, 처음 여는 사람은 OS 설정과 무관하게 라이트를 봅니다 — 사람마다 다른
   화면을 보면 문서에 첨부한 화면과도 어긋납니다. 다크는 고른 사람에게만 남습니다.
4. **셸은 여러 장이 서로를 참조하는 산출물에만.** 프로젝트 허브·QA 리포트·추적 매트릭스에는
   사이드바와 상단 바를 입혀 한 사이트처럼 오가고, 한 장으로 끝나는 문서는 그대로 둡니다.
   테마 토글은 예외 없이 **모든 문서**에 답니다(셸이 없으면 문서 머리말 오른쪽).

## 색 (라이트 기본 · 다크 토글)

CSS 변수로 정의하고 역할로만 참조합니다. 원색 hex를 본문에 흩뿌리지 않습니다.
**역할 이름은 테마와 무관하게 고정이고 값만 갈아 끼웁니다** — 그래서 문서와 생성기는 테마를
몰라도 되고, 테마를 늘려도 컴포넌트 CSS는 그대로입니다.

값의 정본은 `design-guide/design-guide-master.css`(이 모듈)이며, 이 문서는 그 체계를 설명만 합니다.

```css
:root{                  /* 라이트 = 기본 */
  --page:#f4f6fa;       /* 페이지 바탕 */
  --surface:#ffffff;    /* 카드·표 표면 */
  --ink:#1f2328;        /* 본문 */
  --accent:#4f46e5;     /* 인디고 포인트 */
  --on-accent:#ffffff;  /* 인디고 채움 위 글자 — 라이트에서 잉크를 쓰면 안 읽힌다 */
  --side-bg:#212a3a;    /* 사이드바 — 두 테마 모두 어둡다 */
}
:root[data-theme="dark"]{ --page:#0d0d0d; --surface:#16161a; --ink:#f4f4f5;
  --accent:#818cf8; --on-accent:#f4f4f5; --side-bg:#121215; }
```

상태·우선순위·검증유형 색은 두 벌을 따로 잡습니다. 형광 계열(`#34d399` 등)은 흰 배경에서
흐려지므로 라이트 값은 한 단 어둡게(`#15803d`) 씁니다. 반대로 **차트 카테고리 색은 두 테마에서
같습니다** — 밝은 배경에서도 어두운 배경에서도 읽히는 값을 골랐기 때문입니다.

### 차트 색은 검증된 팔레트에서

카테고리 차트의 색은 눈대중으로 고르지 않습니다. `dataviz` 스킬의 검증된 팔레트를 쓰고,
다크 표면에 맞는 단계를 씁니다. 4계열까지의 안전한 기본값:

```
계열1 파랑 #3987e5 · 계열2 주황 #d95926 · 계열3 청록 #199e70 · 계열4 노랑 #c98500
순서형(도넛·단일 램프): #86b6ef → #2a78d6 → #184f95
```

- 카테고리는 **고정 순서**로 배정합니다. 필터로 계열이 빠져도 남은 계열의 색을 다시 칠하지
  않습니다("Acme는 파랑"을 학습한 독자를 배신하지 않기).
- 5계열을 넘기면 색을 늘리지 말고 "기타"로 접거나 표로 전환합니다.
- 지원 여부(O/X/△/?) 같은 상태 색은 카테고리 색과 구분되는 별도 팔레트를 씁니다
  (초록/빨강/노랑/회색 계열).

## 타이포

- 시스템 산세리프 하나만: `system-ui, -apple-system, "Segoe UI", "Malgun Gothic", sans-serif`.
  디스플레이·세리프 폰트를 섞지 않습니다.
- 본문 15px / 행간 1.7. 표는 12.5~13px.
- 큰 숫자(스탯 타일의 값)는 비례 숫자, 세로로 정렬돼야 하는 표·축 눈금만 `tabular-nums`.
- 섹션 제목 앞에 인디고 세로 막대 마커를 붙여 스캔을 돕습니다.

## 레이아웃 구성

세로 흐름으로 다음 순서를 권장합니다. (섹션 이름은 내용에 맞게 조정)

1. **헤더** — 제목, 한 문단 리드, 메타 배지(조사일·대상·규모·근거 범위), 목차(앵커 링크).
2. **스탯 타일** — 핵심 수치 6개 안팎. 큰 숫자 + 라벨 + 한 줄 설명.
3. **왜 이 접근인가** — 방법론의 전제. 표가 아니라 문장으로.
4. **핵심 개념 정의** — 검증유형·판정 규칙 등을 카드로.
5. **기능 트리 / 매트릭스** — 카드 그리드(요약) + 필터 가능한 전체 표.
6. **분포 차트** — 영역별 수·구성. 각 차트에 "표로 보기" 토글.
7. **관계·구조 다이어그램** — Mermaid.
8. **전체 목록 표** — 필터 버튼 + 스크롤 영역.
9. **파이프라인 / 후속 작업**.
10. **미확인 항목** — 실측으로 채울 값.

## 컴포넌트 패턴

- **카드** — `--surface` 배경 + `--hair` 테두리 + 12px 라운드 + 20px 패딩.
- **표** — 헤더는 `--surface-2` 배경에 sticky. 행 구분선은 `--grid` 헤어라인. 얼룩(zebra)은
  아주 옅게. 테두리로 셀을 가두지 않습니다.
- **칩** — 검증유형·우선순위·지원여부를 작은 색 배경 칩으로. 텍스트는 칩 색이 아니라 잉크 색.
- **필터 버튼** — 표 위 한 줄에. 누른 상태는 `--accent-dim` 배경에 `--on-accent` 글자.
  차트별 필터를 카드 안에 넣지 않습니다(한 줄로 모아 전체에 적용).
- **표 도구** — 행이 수십 줄을 넘으면 눈으로 찾는 비용이 검증 비용을 넘습니다. 그런 표에는
  `.tbl-tools`로 검색·필터·건수를 얹고 헤더에 `sortable`을 붙입니다. 동작은 문서마다 다시
  짜지 않고 **동작 정본(`design-guide-master.js`)이 붙입니다** — 생성기는
  `shell.table_tools()`로 마크업만 냅니다.
- **셸** — 사이드바(`.side`)는 위쪽에 산출물 사이 이동을, 아래쪽에 그 문서의 절 목록을 둡니다.
  항목의 정본은 `scripts/shell.py`의 `NAV`·`OUT` 하나뿐이며, 생성기는 「지금 어느 문서인가」와
  절 목록만 넘깁니다. 문서마다 메뉴를 적어 두면 갈라지기 때문입니다.
- **콜아웃** — 경고·주의는 왼쪽 색 막대 + 옅은 바탕. 남발하지 않습니다.

## 차트

- **Chart.js를 인라인**합니다(`chart.umd.js` 전문을 `<script>`에 넣기). CDN 링크 금지.
- 정적 문서이므로 애니메이션을 끕니다(`Chart.defaults.animation=false`) — 스크린샷·인쇄에서
  중간 프레임이 잡히지 않게.
- 막대는 얇게, 데이터 끝만 4px 라운드. 그리드는 헤어라인. 값 라벨은 전부가 아니라 선택적으로.
- 축은 하나만. 스케일이 다른 두 지표를 한 차트 두 축에 넣지 않습니다(별도 차트로).
- 모든 차트에 **표로 보기 토글**을 답니다(접근성·검증용 트윈).

## 다이어그램

### Mermaid

- **런타임 렌더링 대신 SVG로 미리 렌더해 인라인**합니다. Playwright로 Mermaid를 그려 SVG
  문자열을 뽑고, 그 SVG를 HTML에 박습니다. 이렇게 하면 CDN 의존이 사라지고, 한글 글자가
  깨지지 않으며(런타임 폰트 로딩 실패 방지), 파일이 자기완결이 됩니다.
- 노드가 20개를 넘어 다이어그램이 장황해지면, 트리형 그림은 **HTML 카드 그리드**로 대체하는
  편이 읽기 낫습니다(Mermaid는 관계·흐름에, 카드 그리드는 계층 나열에).
- 파이프라인은 세로 단계 + 각 단계 내부 가로(`direction LR`)로 두면 폭이 눌립니다.
- 테마 변수를 다크 표면에 맞춥니다: 배경 `#16161a`, 노드 `#1c1c21`, 테두리 `#2c2c2a`,
  선 `#4a4a52`, 텍스트 `#e8e8ea`.

### 여러 문서가 공유하는 다이어그램

같은 그림을 md와 HTML이 함께 쓸 때, md는 SVG 파일을 이미지로 참조할 수 있지만 HTML 산출물은
자기완결 규칙 때문에 마크업을 직접 품어야 합니다. 손으로 맞추면 한쪽만 고쳤을 때 두 그림이
갈라지는데 아무 에러도 나지 않아 오래 발견되지 않습니다.

**그래서 사본을 아예 두지 않습니다.** SVG 파일이 정본이고, 그림을 싣는 페이지의 **생성기가
만들 때마다 그 파일을 읽어 인라인**합니다. 고정된 사본이 없으므로 갈라질 것도 없고, 동기를
확인하는 장치도 필요 없습니다.

- **실리는 쪽이 변환 없이 그대로 들어가게 만듭니다.** 변환 로직을 두면 그 로직 자체가 어긋나는
  원인이 됩니다. 정본 SVG의 root에 HTML 쪽 CSS가 걸릴 클래스(`sd`)를 미리 달고, id는 페이지 안에서
  충돌하지 않을 이름으로 지어 둡니다. 그러면 읽어 넣기가 문자열 잘라내기 하나로 끝납니다.
- **크기 속성은 남겨 둡니다.** SVG 파일을 단독으로 열 때 필요하고, HTML 쪽에서는 CSS가
  presentation attribute보다 우선하므로 `width:100%;height:auto`가 덮습니다.
- 정본 파일 머리에는 CHANGELOG와 함께 **어느 페이지가 이 그림을 읽어 가는지, 그리고 root의
  클래스·id를 바꾸지 말라는 경고**를 적어 둡니다. 이것을 바꾸면 그림은 실리는데 테마가 걸리지 않아
  조용히 깨집니다.

- **그림은 밝은 배경 기준으로 그립니다.** 라이트가 기본 테마라 그 색이 그대로 맞고, 다크에서만
  마스터 CSS의 `.sd` 규칙이 표면 색으로 덮습니다. 그림 파일을 테마마다 두지 않기 위해서입니다.
  그래서 정본 SVG의 fill·stroke는 **presentation attribute로** 두고(단독 열람용), 덮는 쪽은
  클래스 선택자로만 씁니다.

이 모듈의 적용 사례는 저장소 구조도와 설명 다이어그램입니다. 정본은 이 모듈의 `diagrams/`이고,
읽어 가는 쪽은 진입 페이지 생성기(`scripts/gen_intro_html.py`)입니다.

## Pages 링크 규칙

이 저장소는 GitHub Pages로 공개됩니다. Pages에서 **`.md`는 원본 텍스트로 뜨고 폴더 경로는
404가 되므로**, HTML 산출물 안에서는 링크의 종류에 따라 주소를 다르게 적습니다.

| 대상 | 어떻게 적나 |
|---|---|
| md 문서 · 폴더 · xlsx | GitHub 저장소 **절대 URL** (`https://github.com/…/blob\|tree/main/…`) |
| HTML 문서 | **상대 경로** |

생성기는 이 구분을 `scripts/shell.py`의 `BLOB`·`REPO` 상수로 처리합니다.

## 주제별 문서 허브

허브는 HTML 파일의 목록이 아니라 **주제의 목록**입니다. 파일마다 탭을 하나씩 만들면 문서가 늘 때마다
탭이 늘어 원하는 문서를 찾는 데 오래 걸립니다. 생성된 HTML을 전부 자동으로 등록하면 서식 견본과
시험 산출물까지 섞여 들어옵니다. 그래서 허브에 무엇을 싣는지는 사람이 고르고, 고른 것은 주제로
묶습니다. 문서 사이의 이동을 탐색 층이 맡는다는 원칙은 `core/base/rules/html-output.md` 「링크 —
문서 사이 이동은 탐색 층이 맡습니다」가 정하며, 이 절은 그 탐색 층 중 허브의 모양을 정합니다.

### 탭은 주제 단위로 둡니다

- **프로젝트의 허브 설정이 노출할 주제 탭을 고릅니다.** 폴더나 HTML 파일을 더한 것만으로 탭이
  생기지 않습니다. 탭 순서는 설정의 배열 순서를 따릅니다.
- **탭 안에 문서가 하나면 본문을 바로 보이고, 여럿이면 문서 목록에서 골라 본문을 봅니다.** 목록을
  거치지 않고 본문으로 바로 가는 경우와 목록을 거치는 경우가 탭마다 섞여도, 같은 탭 안에서는 한
  방식만 씁니다.
- **탭마다 「원본 문서 열기」로 개별 HTML을 엽니다.** 여기서 원본은 열람용 개별 HTML을 뜻하고, 편집
  정본(md · 데이터)과는 다릅니다. 편집하려는 사람이 이 링크를 정본으로 오해하지 않도록 도움말에 그
  차이를 적습니다.
- **탭 ID는 허브 전체에서 하나뿐입니다.** 여러 프로젝트의 탭이 한 허브에 함께 실리기 때문입니다.
  기본 탭은 실제 탭 목록에 있어야 하고, 아직 탭이 없는 프로젝트는 빈 목록과 빈 기본 탭으로 둡니다.
  그때 허브는 「등록된 탭이 없습니다」 안내를 보입니다.
- **서식 견본은 프로젝트 허브에 싣지 않습니다.** 견본은 모듈의 카탈로그에서 찾고, 프로젝트 허브에는
  그 프로젝트의 실제 문서만 둡니다.

### 개별 HTML과 허브 본문은 같은 정본에서 만듭니다

같은 내용을 개별 HTML과 허브에 손으로 옮겨 두면, 한쪽만 고쳤을 때 두 화면이 갈라지는데 아무 에러도
나지 않습니다. 「여러 문서가 공유하는 다이어그램」과 같은 이유로 사본을 두지 않습니다.

- **한 생성기가 같은 정본에서 개별 HTML과 허브 본문 조각을 함께 만듭니다.** 파생 HTML을 직접 고치지
  않습니다. 목록 · 본문 · 검색 데이터는 같은 문서 ID로 잇습니다.
- **두 본문이 같은지 생성 검사에서 봅니다.** 같은 생성기가 만들어도 허브 쪽에만 덧붙이는 처리(경로
  변환 · 접힘 영역)가 있으면 갈라질 수 있습니다.
- **개별 HTML은 그 프로젝트의 문서 폴더 안에만 씁니다.** 허브 페이지와 같은 이름은 쓸 수 없고, 두
  문서가 같은 출력 경로를 가리키면 오류입니다. 허브에 선택된 문서의 산출물만 생성과 낡음 검사
  대상에 넣습니다.
- **입력을 모두 검사한 뒤에 씁니다.** 검사 도중 멈추면 일부 파일만 새것이 되어, 허브와 개별 HTML이
  서로 다른 개정을 보여 줍니다.

### 검색은 선택된 문서만 대상으로 합니다

- **링크를 등록하는 것만으로는 본문이 검색되지 않습니다.** 문서를 허브에 연결할 때 생성기가 그 문서의
  본문 검색 데이터를 함께 싣습니다.
- **선택되지 않은 문서는 결과와 미리보기에 나오지 않습니다.** 다른 프로젝트의 문서, 허브에 등록하지
  않은 문서가 여기에 해당합니다.
- **결과 수를 자르지 않습니다.** 앞쪽 탭에 결과가 많으면 자르는 순간 뒤쪽 탭의 결과가 통째로
  빠집니다. 결과는 프로젝트 → 탭 순으로 묶고, 긴 목록은 각 묶음 안에서 스크롤합니다. 묶음에는 이름과
  건수만 보이고, 결과마다 프로젝트 · 탭 이름을 되풀이하지 않습니다.
- **결과를 누르면 그 탭 · 문서 · 본문 위치로 이동합니다.** 대상이 접힌 `<details>` 안에 있으면 상위
  `<details>`와, 검색어가 든 안쪽 `<details>`까지 펼친 뒤 이동합니다. 표의 행 안에 근거를 접어 둔
  문서에서 행으로만 이동하면 일치한 문구가 보이지 않기 때문입니다.
- **상세 미리보기는 미리보기를 켜는 기능입니다.** 켜고 꺼도 검색 범위와 결과 수는 같아야 합니다.
- **키보드와 좁은 화면에서도 같은 단계로 움직입니다.** 검색창에서 아래 화살표로 결과에 들어가고,
  위 · 아래로 이동, 오른쪽으로 펼치기, 왼쪽으로 돌아가기, Enter로 선택, Escape로 닫습니다. 좁은
  화면에서는 클릭으로 한 단계씩 열고 「이전 단계」 버튼으로 돌아갑니다.

### 조사 · 제안 · 승인 상태를 구분해 보입니다

같은 탭에 있다는 사실이 같은 승인 상태를 뜻하지 않습니다. 조사 자료와 승인된 사양이 한 주제에 함께
실리면, 독자는 화면 위치만 보고 둘을 같은 무게로 읽습니다. 그래서 문서 목록과 본문 머리에 그 문서의
상태(조사 · 제안 · 승인)를 보입니다. 상태 값은 프로젝트 구조 설정의 역할과 정본 등록대장의 승인
상태에서 가져오고, 허브가 새로 정하지 않습니다(`core/base/rules/canonical-source.md`).

## 묶음 허브 — 통합 허브와 업무별 허브

한 제품을 여러 업무 프로젝트가 나눠 맡는 묶음(`core/base/rules/site-structure.md` 「프로젝트 묶음 —
한 제품의 여러 업무 프로젝트」)에서는, 독자가 묶음 전체를 한 번에 찾고 싶을 때와 자기 업무만 보고 싶을
때가 갈립니다. 허브를 하나만 두면 자기 업무 문서를 찾을 때마다 다른 업무의 결과를 헤쳐야 하고, 업무마다
따로 두면 메뉴 · 검색 · 테마가 업무마다 조금씩 달라집니다. 그래서 **공통 틀은 한 벌, 허브는 두 층**으로
만듭니다. 묶음이 무엇을 갖고 모듈 설정을 어떻게 합치는지는 base가 정하고, 이 절은 허브 생성 쪽만 정합니다.

- **각 업무 프로젝트가 자기 허브 설정을 소유합니다.** 설정에는 표시 이름 · 페이지 제목 · 묶음 안의
  순서 · 탭 목록 · 기본 탭을 둡니다. 생성기는 묶음 안의 업무 폴더에서 이 설정을 찾아 모으며, 설정이
  없는 폴더는 허브에 들어오지 않습니다. 탭을 더하는 데 생성기 코드를 고치지 않습니다.
- **공통 틀은 묶음의 공유 자리에 한 벌만 둡니다.** 메뉴 · 검색 · 테마 · 탭 전환은 공유 자리에서,
  탭 내용은 각 업무에서 관리합니다. 업무 폴더에 공통 틀의 사본을 두지 않습니다.
- **한 번 실행으로 통합 허브 한 장과 업무별 허브를 함께 만듭니다.** 통합 허브는 모든 업무가 고른 탭을,
  업무별 허브는 자기 탭만 담고 자기 탭만 검색합니다. 업무별 허브에 다른 업무 탭의 주소로 들어오면
  기본 탭을 보입니다.
- **허브 분리는 접근 통제가 아닙니다.** 묶음은 함께 배포되고, 파일을 아는 사람은 누구나 다른 허브를
  열 수 있습니다. 공개 범위를 나눠야 하면 배포 단위를 나눕니다. 반대로 묶음의 일부만 배포하면
  허브 사이의 이동 경로가 끊깁니다.
- **허브 사이 이동을 둡니다.** 업무별 허브의 상단에는 통합 허브로 가는 버튼을 두고, 통합 허브에는
  두지 않습니다. 통합 허브는 업무별 허브로 가는 링크를 모아 둡니다.
- **모듈의 실행 파일은 복사하지 않고 참조합니다.** 탭이 모듈의 런타임 스크립트를 쓰면 설정에
  `module:{모듈}/{모듈 안 경로}` 형식으로 적습니다. 생성기는 그 업무에서 쓸 수 있는 모듈(base 「제품 공통
  모듈 설정 — 업무별 설정과 합집합」의 합집합)만 허용하고, 모듈 밖 경로와 없는 파일은 막습니다. **쓸 수 있는 것과
  화면에 싣는 것은 다릅니다** — 탭이 그 스크립트를 고른 페이지에만 인라인하고, 통합 허브는 같은
  스크립트를 한 번만 싣습니다.
- **동적 탭의 렌더러는 그 프로젝트 안의 파일만 받습니다.** 렌더러는 실행 코드이므로 프로젝트 폴더
  밖의 경로를 받지 않고, 신뢰하는 로컬 파일만 등록합니다.
- **상대 경로는 출력 위치에 맞춰 다시 계산합니다.** 같은 탭 내용이 업무별 허브와 통합 허브의 서로
  다른 폴더에 실리므로, 정적 내용의 `href` · `src`는 생성 때 변환하고 스크립트가 만드는 주소는 허브가
  알려 주는 기준 경로에서 계산합니다.
- **입력이 잘못되면 쓰기 전에 멈춥니다.** 설정 형식 버전, 중복 탭 ID, 없는 파일, 목록에 없는 기본 탭,
  내용의 탭 패널과 설정의 불일치, 한 페이지 안의 HTML `id` 중복을 검사합니다. 검사 모드는 파일을 쓰지
  않고 낡은 산출물만 보고하며, 하나라도 있으면 실패로 끝납니다.

이 모듈에 묶음 허브 생성기가 들어오기 전에는 묶음이 자기 생성기로 이 계약을 지키고, 그 사실을 묶음의
change-log 「현행 기준」에 적습니다.

## 반드시 하는 마무리

- **렌더해서 눈으로 봅니다.** 검증 스크립트는 색만 보지 레이아웃은 못 봅니다. Playwright로
  스크린샷을 찍어 라벨 충돌·오버플로·글자 깨짐을 확인합니다.
- **콘솔 에러 0.** `pageerror`가 잡히면 대개 인라인 누락(차트/폰트)입니다.
- **두 테마를 다 봅니다.** 라이트에서만 확인하면 다크에서 대비가 무너진 것을 놓칩니다. 표 도구가
  있는 문서는 검색·필터·정렬도 한 번씩 눌러 봅니다.
- **허브는 브라우저로 동작을 검사합니다.** 개별 HTML과 허브 본문의 일치, 다른 프로젝트 탭의 검색
  결과 0건, 탭마다 결과를 많이 넣어도 뒤쪽 탭이 빠지지 않는지, 접힌 영역의 펼침과 이동, 원본 열기와
  허브 사이 이동 버튼, 좁은 화면의 가로 넘침 없음을 봅니다. 시험용 검색 데이터는 검사 안에서만
  넣고 산출물에 남기지 않습니다.
- 파일 크기가 커지는 것은 정상입니다(Chart.js + SVG 인라인). 자기완결의 대가입니다.

## 지속 사용 팁

이 문서는 한 번 만들고 끝이 아니라 **계속 수정해 나가는 자산**입니다. 그래서:

- 생성 로직을 파이썬 스크립트로 두고, 데이터(TC·트리)를 별도 파일로 분리합니다. 데이터만
  갱신하면 문서가 다시 나오게.
- 색·타이포·컴포넌트는 이 가이드의 CSS 변수 블록을 재사용합니다. 매번 새로 정하지 않기.
- 릴리즈마다 기능 트리 diff를 반영하면, 같은 디자인으로 버전별 문서가 쌓입니다.
