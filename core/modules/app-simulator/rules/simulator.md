## 기획 정본과 연결

작업 전에 `../../planning-spec/rules/planning-spec.md`와 프로젝트의 등록된 기획 정본 · 부모 정본을
읽습니다. planning-spec 활성화를 프로젝트 모듈 목록에서 확인하며 누락되면 module.md의 활성화
절차를 먼저 따릅니다. 정본 관리와 승인 · 개정 · 이전은 `../../../base/rules/canonical-source.md`를
따릅니다. 이 문서는 기획 내용을 새로 결정하지 않고 HTML의 표현과 구현 방법을 정합니다.

1. 기능 ID · 규칙 ID와 적용 화면 · 흐름 노드를 연결합니다. 노드 번호나 화면 경로를 기능 ID로 대체하지 않습니다.
2. 기획 정본에서 승인한 진입 조건 · 상태 · 분기 · 예외를 입력과 구현에 반영합니다. 미확인 값은 추측하지 않습니다.
3. 기획의 화면 구성 · 표시 조건 · 입력 결과 · 상태 전이 · 오류 · 취소 · 복귀를 실제 조작으로 대조합니다.
4. 테스트용 응답과 디버그 조작은 구현 사양으로 구분하며, 이를 서비스 정책의 근거로 쓰지 않습니다.
5. 적용한 정본 ID · 반영 revision · 검수 결과를 기존 등록대장과 검수 기록에 연결합니다.

기획 검수의 상세 항목은 planning-spec 「기획 규칙의 적용 지점을 검수합니다」를 참조합니다. 아래 도구의 형식 검사와 HTML 조립 성공은
기획 내용 일치의 자동 검증을 뜻하지 않습니다. 관찰한 구현과 기획이 다르면 불일치로 기록하고,
기획 변경이 필요한 경우 정본에서 먼저 결정합니다.

### 시뮬레이터 전용 요소와 예시 데이터

시뮬레이터는 실제 앱처럼 보이도록 서비스에 없는 조작과 값을 함께 담습니다. 이것이 와이어프레임 ·
기획서 · 요약본 · TC로 옮겨지면 정해지지 않은 것이 정해진 사양처럼 읽힙니다. 그래서 둘을 서비스
사양과 나눠 다룹니다. 위 4번의 테스트 응답 · 디버그 조작도 여기에 속합니다.

| 구분 | 무엇이 해당하나 | 어떻게 다루나 |
|---|---|---|
| **시뮬레이터 전용 요소** | 셸의 조작 패널(진행 · 기록 · 테스트 탭), 「화면 구성 설정」, 테스트 메일 발송 같은 개발용 조작, 모의 결제 · 모의 로그인의 안내 문구(「모의 구매」 · 「로컬 체험 계정」), 실패 상태를 일부러 만드는 조작, 앱 정보의 빌드 · 소스 표기 | 파생물(와이어프레임 · 기획서 · 요약본 · TC 기대값)로 옮기지 않습니다. 파생물 캡처에 찍혔으면 그 부분을 빼거나 「시뮬레이터 전용」으로 표시합니다 |
| **예시 데이터** | 정본이 값을 정하지 않아 시뮬레이터가 채운 대사 · 상품 · 가격 · 수량 · 보상 · 날짜 · 순서 · AI 응답 | 코드 주석과 프로젝트 이력에 「시안 예시」로 표시합니다. 프로젝트 remaining-work 「사용자 결정 대기」에 무엇이 예시인지와 교체 조건(어떤 결정이 나면 무엇으로 바꾸는지)을 함께 올립니다 |

- 프로젝트는 시뮬레이터 전용 요소의 목록을 change-log 「현행 기준」에 둡니다. 새 전용 요소를 더하면
  그 목록도 함께 고칩니다. 목록이 없으면 파생물을 만드는 사람이 셸 조작과 앱 화면을 가를 수 없습니다.
- 정본이 값을 정하면 예시를 그 값으로 바꾸고, 「사용자 결정 대기」의 해당 항목을 닫습니다. 예시를
  그대로 두고 정본 값을 다른 곳에 따로 적지 않습니다.
- 화면이 성립하려면 예시 값이 필요한 파생물(와이어프레임의 상품 칸 등)은 그 기록에 예시임을 밝힙니다
  (`../../app-wireframe/rules/wireframe.md` 「다이얼로그·바텀시트·로딩의 화면 내 배치」와 같은 기준).
- 예: 상품 목록의 「30개 · 3,000원」은 가격 정책이 정해지지 않아 넣은 값입니다. 코드에는 `// 시안 예시 —
  가격 정책 확정 시 교체`를 달고, 결정 대기에는 「상품 수량 · 가격 확정 → 예시 목록 교체」를 올립니다.

## 1. 구조

시뮬레이터는 **셸 문서 하나 안에 앱 문서 하나**를 iframe으로 넣은 구조입니다.

| 층 | 하는 일 | 누가 만드나 |
|---|---|---|
| 셸 | 기기 틀(크기 · 회전), 개발용 조작 패널, 캡처 · 녹화, 탐색기 연결 전달 | 셸 화면은 프로젝트, 공용 동작은 모듈 실행기(`SimShell`) |
| 앱 문서 | 프로토타입 앱 화면과 동작. 에셋은 data URL로 담습니다 | 프로젝트 |

- 앱 문서는 셸의 `#app` iframe에 문자열로 써 넣습니다(`contentDocument.write`). 파일 하나로 열려야 하므로 앱 문서를 별도 파일로 두지 않습니다.
- 셸과 앱은 `postMessage`로만 대화합니다. 채널 이름은 프로젝트가 정하되 **셸 → 앱 명령 · 앱 → 셸 상태 · 탐색기 연결(앱이 받는 쪽 · 앱이 보내는 쪽)**을 서로 다른 채널로 둡니다.
- 크기가 큰 에셋(영상 · 그림)도 담기 때문에 산출물이 수십 MB가 될 수 있습니다. 앱 코드가 부르지 않는 에셋은 조립할 때 빼는 것을 권합니다(「조립 (`scripts/build_simulator.py`)」 `keep`). 크기를 관리하는 기준과 줄이는 순서는 「산출물 크기 예산」을 따릅니다.

## 2. 탐색기 연결 (`SimShell.wfx` · `SimShell.relay`)

워크플로우 탐색기는 시뮬레이터를 `?wfx`가 붙은 주소의 iframe으로 엽니다.

- `SimShell.wfx()` — 셸 주소에 `?wfx`가 있으면 참입니다. 셸은 이때 앱 문서에 표시(예: `window.{프로젝트}_WFX = true`)를 먼저 넣어, 앱의 연결 코드가 켜지게 합니다. 탐색기 안에서 연 시뮬레이터는 단독으로 연 것과 저장 자리를 나눕니다(탐색기의 상태 이동이 진행 기록을 덮어쓰기 때문).
- `SimShell.relay(frame, {host, app})` — 탐색기(부모 창)의 `wfx-host`를 앱의 `host` 채널로, 앱의 `app` 채널을 탐색기의 `wfx-app`으로 옮깁니다. 셸이 탐색기 안에 있을 때만 동작합니다.
- 메시지 내용(`hello` · `goto` · `press` / `ready` · `goto` · `press` · `action` · `event`와 판정용 상태 요약 `snap`)은 탐색기 규약이 정본입니다(→ `core/modules/workflow-explorer/rules/explorer.md` 「시뮬레이터 연결 규약」). 앱 쪽 연결 코드(사건 알림 · 상태 이동 준비 · `snap`)는 앱마다 함수가 달라 프로젝트가 씁니다.

## 3. 캡처 · 녹화 (`SimShell.capture`)

브라우저의 탭 화면 공유(`getDisplayMedia` · 「이 탭」)로 **보이는 그대로**(영상 · 흐림 효과 포함) 기기 화면을 저장합니다.

- 셸에는 `#capture`(캡처) · `#capture-stop`(연결 끊기) · `#capture-frame`(기기 틀 포함 체크) · `#capture-status`(안내 문구) · `#record`(녹화 시작 · 종료) 요소가 있어야 합니다.
- `SimShell.capture({frame, device, prefix, screenName})` — `frame`은 앱 iframe, `device`는 기기 틀 요소, `prefix`는 저장 파일 이름 앞부분, `screenName()`은 지금 화면 이름을 돌려주는 함수입니다(실패하면 `screen`). 파일 이름은 `{prefix}-{화면}[-frame]-{날짜시각}.png|mp4|webm`입니다.
- Chrome · Edge는 영역 캡처(`CropTarget`)로 대상 요소만 받고, 못 쓰면 창 전체 장면에서 좌표로 자릅니다. 기기 틀이 창 밖으로 나가 있으면 잠시 스크롤했다가 되돌립니다.
- 화면만 찍으면 실제 스크린샷처럼 모서리를 자르지 않고, 기기 틀 포함이면 둥근 모서리 밖을 투명하게 둡니다. 녹화는 화면만이면 MP4(지원할 때), 틀 포함이면 투명을 담는 WebM입니다.

## 4. 조립 (`scripts/build_simulator.py`)

프로젝트 조립 스크립트는 **어떤 소스를 어떤 순서로 붙일지**만 정하고, 아래 일은 모듈 도구로 합니다.

| 함수 | 하는 일 |
|---|---|
| `inline_assets(css, 에셋 폴더)` | CSS의 `{{asset:이름}}`을 그 파일의 data URL로 바꿉니다 |
| `collect_assets(폴더, keep, assets)` | 에셋을 이름순으로 담습니다. 내용이 같은 파일은 한 번만 담고 나머지는 별칭(`{이름: 원래 이름}`)으로 돌려줍니다. `keep(path)`로 뺄 것을 고릅니다 |
| `js_json(값)` | `<script>` 안에 넣어도 태그가 끊기지 않는 JSON |
| `runtime()` | 셸 공용 실행기 내용 — 셸의 `{{sim-shell-js}}` 자리에 넣습니다. 셸 스크립트에서 `SimShell`을 쓰기 전에 와야 합니다 |
| `fill(문서, 토큰)` | `{{토큰}}`을 채우고, 채우지 못한 토큰이 남으면 멈춥니다 |
| `write_or_check(산출물, 결과, check)` | 산출물을 쓰거나, `--check`면 지금 파일과 같은지만 봅니다(재생성 누락 확인) |

산출물은 자기완결 HTML 한 장이며 네트워크 요청을 하지 않습니다(→ `core/base/rules/html-output.md`). 시뮬레이터는 프로그램이라 문서 디자인 마스터를 따르지 않고 셸 화면은 프로젝트가 정합니다.

## 5. 화면 구성 설정 — 기획 대안 비교

정해졌지만 개발 일정을 따로 산출해야 하는 변경이나 아직 검토 중인 구조 대안을 기본 화면에 바로 넣으면,
시뮬레이터가 지금 만들 수 있는 앱이 아니라 나중의 앱을 보여 줍니다. 검토하는 사람은 어느 쪽을 보고
있는지 가를 수 없습니다. 그렇다고 시뮬레이터 사본을 따로 만들면 공통 부분의 수정이 두 벌로 갈라집니다.
그래서 시뮬레이터 하나 안에 「화면 구성 설정」 패널을 두고, 대안을 선택지로 골라 비교합니다.

### 5-1. 무엇을 선택지로 넣나

| 변경의 처지 | 처리 |
|---|---|
| 정본에서 정해졌고 지금 구현 대상입니다 | 설정 없이 바로 적용합니다 |
| 정본에서 정해졌지만 구현 일정을 산출해야 합니다 | 선택지로 넣고 기본값은 현재 동작으로 둡니다 |
| 검토 중인 구조 대안(시안)입니다 | 선택지로 넣고 기본값은 현재 동작으로 둡니다 |

어느 처지인지는 사용자가 정합니다. 정본 개정만 보고 「정해졌으니 바로 적용」으로 판단하지 않습니다.
모르면 묻고, 받은 답을 프로젝트 change-log 「현행 기준」에 적습니다. 진행 단계 · 계정 상태 같은
체험 상태의 이동은 이 패널이 아니라 셸의 개발용 조작 패널이 맡습니다.

### 5-2. 항목과 기본값

- 항목 하나는 화면 영역 하나 또는 구조 결정 하나입니다. 항목마다 코드에서 읽는 키, 묶음 이름, 라벨,
  선택지 목록(`[값, 표시 이름]`)을 둡니다. 묶음은 함께 정해진 변경 단위로 나눕니다(예: 「구조 변경(개정 날짜)」).
- **기본값은 현재 동작입니다.** 새 선택지는 사용자가 확정하고 기본 화면으로 바꾸라고 할 때만 기본값이 됩니다.
  그 전까지 정본과 기본 화면이 다른 것은 의도된 상태입니다. 정본 대조 검수는 해당 선택지를 골라서 하고,
  검수 기록에 어느 선택지로 확인했는지 적습니다. 차이를 불일치로 보고하거나 기본값을 바꾸자고 제안하지 않습니다.
- **새 선택지 이름에는 프로젝트가 정한 접두어를 붙입니다**(예: 기존 동작은 「기존 ·」, 새 구조는 「변경안 ·」).
  패널을 여는 사람이 이름만 보고 어느 것이 지금 앱인지 알 수 있어야 하기 때문입니다. 접두어는 change-log
  「현행 기준」에 적습니다.
- **선택지가 하나뿐인 항목은 패널에 보내지 않습니다.** 고를 수 없는 항목이 비교 대상처럼 보이기 때문입니다.
  설정값과 기본값은 그대로 두므로 화면은 바뀌지 않습니다. 항목이 모두 빠진 묶음의 제목도 함께 숨깁니다.
- 선택은 브라우저 저장소에 기억합니다. 저장된 값이 지금 선택지 목록에 없으면 기본값으로 되돌립니다. 기본값을
  바꾸는 개정에서는 저장 형식의 버전 표시를 올려, 이전에 저장된 값 대신 새 기본값이 열리게 합니다.
- 시뮬레이터에서 만드는 파생물(탐색기 캡처 · 와이어프레임)은 기본값 화면에서 만듭니다. 다른 선택지로 만든
  캡처는 그 기록에 선택지 이름을 적습니다.

```js
// 예: 기본값은 current(지금 앱). 새 선택지 이름은 「변경안 ·」으로 시작합니다.
{group: '구조 변경(개정 날짜)', key: 'bottomTabs', label: '하단 탭 구성',
 options: [['current', '기존 · 탭 네 개'], ['merged', '변경안 · 목록 탭과 검색 탭 통합']]}
```

### 5-3. 확정되거나 버려지면

- **확정:** 사용자가 한 선택지를 확정하면 다른 선택지를 지우고, 그 선택지만 쓰던 코드(화면 분기 · 이벤트 처리기 ·
  판별 함수 · 스타일 규칙)도 지웁니다. 저장된 이전 값과 상관없이 확정안이 열리게 저장값 정규화를 고칩니다.
  선택지가 하나 남은 항목은 5-2에 따라 패널에서 사라집니다. 지운 코드의 이름은 프로젝트 이력에 남기고,
  다른 화면에서 함께 쓰여 남긴 코드는 남긴 이유를 적습니다.
- **버림:** 새 선택지와 그 선택지만 쓰던 코드만 지우고 기존 동작을 남깁니다. 버린 이유는 정본의 결정 이력이
  담고, 시뮬레이터 이력은 그 결정을 가리킵니다.
- 확정이든 버림이든 선택지를 지운 뒤 시뮬레이터를 다시 만들고, 화면이 달라졌으면 그 화면의 파생물 캡처도
  다시 만듭니다.

## 6. 정본 입력 계약 검사

`write_or_check`는 산출물이 지금 입력으로 다시 만든 결과와 같은지만 봅니다. 그래서 생성기가 바뀐 정본을
읽지 않았거나, 정본 노드가 요구하는 상태 이동을 시뮬레이터가 구현하지 않았어도 검사는 통과합니다.
이런 산출물은 조용히 낡거나, 탐색기에서 고른 도형으로 시뮬레이터를 옮기지 못합니다. 그래서 정본에서
시뮬레이터와 탐색기를 함께 만드는 프로젝트는 생성기가 정본을 읽는 자리에서 아래 계약을 검사합니다.
**하나라도 어기면 산출물을 쓰지 않고 멈춥니다.**

| 검사 | 기준 | 어기면 |
|---|---|---|
| 정본 식별 | 생성 입력으로 등록된 실행 정본마다 머리에 정본 ID 줄과 개정 줄이 있습니다. 실행 정본이 아닌 참고 문서는 건너뜁니다 | `정본 ID·개정 누락: {경로}` |
| 노드 ID | 모든 정본의 노드 표를 합쳐 노드 ID가 겹치지 않습니다 | `정본 노드 ID 중복` |
| 도착점 | 모든 연결의 도착 노드가 정본에 있습니다 | `정본에 없는 도착점: {ID}` |
| 상태 이동 구현 | 노드가 요구하는 상태 키(`state`)마다 시뮬레이터에 상태 이동이 있습니다. 구현 목록은 시뮬레이터의 상태 이동 정의에서 읽습니다 | `시뮬레이터 상태 이동 미구현: {키 목록}` |
| 입력 지문 | 정본 목록(ID · 개정 · 경로 · 파일 SHA-256) · 노드 · 연결 · 상태 키 · 판정 경로 · 표현 계약 개정을 키 순서로 정렬한 JSON과 표현 계약 원문으로 SHA-256을 만들어 두 산출물의 머리 주석에 찍습니다 | `--check`가 두 산출물의 지문이 서로 다르거나 재생성 결과와 다르면 실패합니다 |

```markdown
- 정본 ID: `spec-account-login`
- 정본 개정: canonical-03
```

- 정본 식별 줄의 형식(위 예)과 실행 정본을 고르는 기준(구조 설정의 자리 · 부모)은 프로젝트가 정하고
  change-log 「현행 기준」에 적습니다. 이름이나 경로로 정본 ID를 추측하지 않습니다.
- 상태 키가 없는 노드는 이 검사의 대상이 아닙니다. 그 노드로 옮기는 방법은 탐색기의 `reach` · `reachNote`가
  맡습니다(`../../workflow-explorer/rules/explorer.md` 「데이터 형식」).
- 이 계약을 통과했다는 것은 입력이 빠짐없이 연결됐다는 뜻이지, 기획 내용이 구현과 같다는 뜻이 아닙니다.
  내용 대조는 planning-spec 「기획 규칙의 적용 지점을 검수합니다」로 따로 합니다.
- 지금 모듈 도구에는 이 검사가 없어 프로젝트 생성기가 구현합니다. 프로젝트 구현은 위 표의 검사와 오류 문구를
  지키고, 모듈 도구가 생기면 그것으로 바꿉니다.

## 7. 외부 앱 자산 반입 기록

시뮬레이터가 실제 앱과 같아 보이도록 앱 저장소의 그림 · 아이콘 · 글꼴이나 서버 응답의 콘텐츠를 가져올 수
있습니다. 이때 어느 버전의 무엇에서 왔고 변환으로 무엇이 바뀌었는지 남지 않으면, 앱과의 차이를 판정할 수 없고
저작권 · 개인 정보 확인도 할 수 없습니다. 그래서 반입 도구는 아래를 기록합니다.

- **파일마다:** 원본 위치(앱 저장소 안 상대 경로 또는 URL) · 원본 SHA-256(파일일 때) · 결과 파일 경로 ·
  결과 SHA-256 · 변환(「원본 복사」 · 「비율 · 투명도 보존 WebP, 긴 변 960px 이내」처럼 무엇을 했는지).
- **비교 기준:** 앱 저장소의 기준 원격 브랜치, 비교한 커밋, 확인한 날짜를 남깁니다. 로컬 클론이 원격보다
  뒤처졌는지 확인하지 않았으면 「확인 안 함」으로 두고 「최신」이라 부르지 않습니다.
- **응답 반입:** 서버 응답은 파일을 인자로 받아 허용 목록의 콘텐츠 필드만 꺼냅니다. 인증 토큰 · 계정 ID ·
  계정별 진행 · 보유 · 완료 상태는 받지 않으며, 기록에 「제외한 것」을 적습니다. 응답 원본 파일은 저장소에
  넣지 않고 해시만 남깁니다.
- **덮어쓰기:** 결과 폴더를 덮어쓰는 도구는 인자 없이 실행되지 않게 합니다(필수 인자나 `--write`). 인자가 없으면
  바뀔 파일 목록만 출력합니다. 확인하려고 실행했다가 자산을 덮어쓰는 일을 막기 위해서입니다.
- **자리:** 기록은 프로젝트 구조 설정의 reference 역할 자리에 출처별 파일로 둡니다. 공개 배포 전에는 반입 자산의
  공개 가능 범위를 확인하고 그 결과를 같은 기록에 적습니다.

```json
{
  "source": "앱 저장소 원격 develop 브랜치",
  "comparedCommit": "{커밋 해시}",
  "checkedAt": "YYYY-MM-DD",
  "remoteLatestVerified": false,
  "excluded": "인증 토큰 · 계정 ID · 계정별 진행 · 보유 상태",
  "publishScope": "확인 안 함",
  "assets": [
    {"source": "App/Resources/Assets/TabBarBackground.png",
     "sourceSha256": "{원본 해시}",
     "file": "docs/assets/simulator/tab-bar-background.png",
     "sha256": "{결과 해시}",
     "transform": "원본 복사"}
  ]
}
```

## 8. 산출물 크기 예산

자기완결 HTML은 그림 · 영상 · 음원 · 글꼴을 data URL로 담습니다. base64는 원본보다 약 3분의 1 커서 산출물이
빨리 커집니다. 저장소 호스팅은 파일 크기에 경고 · 거절 한도를 두므로(예: GitHub는 50 MB부터 경고, 100 MB 넘으면
push 거절), 한도를 넘기면 push가 막히거나 큰 파일이 이력에 남습니다.

1. 프로젝트는 산출물 크기의 경고 기준을 호스팅의 경고 한도보다 낮게 정하고 change-log 「현행 기준」에 적습니다.
   조립 스크립트는 산출물을 쓴 뒤 크기를 출력하고, 기준을 넘으면 경고합니다.
2. 기준에 다가가면 원본을 잃지 않는 축소부터 합니다.
   - 앱이 부르지 않는 에셋을 뺍니다(`keep`). 같은 내용은 조립 도구가 이미 별칭으로 한 번만 담습니다.
   - 그림 형식을 바꿉니다(PNG → 무손실이나 고품질 WebP).
   - 글꼴은 쓰는 글자만 남긴 서브셋으로 담습니다.
   - 음원은 압축 형식으로 재인코딩하고, 음성은 비트레이트를 낮춥니다. 영상은 재인코딩합니다.
   - 화질이 달라질 수 있는 축소는 전후 화면을 비교하고, 바꾼 방법과 전후 크기를 프로젝트 이력에 남깁니다.
3. 미디어를 HTML 밖으로 빼는 것은 자기완결 원칙(`core/base/rules/html-output.md`)과 문서 사이 링크 규칙을 바꾸는
   일이라 사용자 결정 뒤에만 합니다. 결정 전에는 「사용자 결정 대기」에 남은 축소 방법과 예상 감소량을 함께 올립니다.
4. 구조 설정에 등록되지 않은 공유용 사본(내보내기 폴더)은 `.gitignore`로 커밋 대상에서 뺍니다. 같은 큰 파일이
   두 벌 저장소에 쌓이고, 정본이 아닌 사본이 산출물처럼 보이기 때문입니다.
