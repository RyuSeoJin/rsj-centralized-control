# reverse-analysis — 소스 없이 동작을 알아내는 절차

출시된 게임 · 앱 · 웹사이트의 기능이 어떻게 동작하는지를 소스 코드 없이 알아낼 때의 규칙입니다.
분석 도구는 REA(MCP 서버 · 명령줄)를 기준으로 적었습니다. 설치와 연결 점검은 `rea` 호스트 모듈이
맡습니다(`core/modules/rea/module.md`).

목표는 **「그 기능이 어떻게 동작하는가」를 근거와 함께 설명하는 것**입니다. 남의 코드 · 그림 · 소리를
가져오는 것이 목표가 아닙니다. 이 차이가 §1(허가 범위)과 §5(원본 보호)의 기준입니다.

---

## 1. 시작 전 — 대상과 허가 범위

### 1-1. 기록에 먼저 적는 것

분석 도구를 부르기 전에 분석 기록(§4-3) 첫머리에 적습니다. 적지 못하는 항목이 있으면 사용자에게
묻고, 답을 받기 전에는 분석을 시작하지 않습니다.

| 항목 | 적는 것 |
|---|---|
| 대상 | 제품 이름 · 플랫폼 · **버전**(빌드 번호까지) |
| 입수 경로 | 정식 구매 · 무료 배포 · 자기 소유 · 의뢰받은 대상 등 |
| 허가 근거 | 왜 분석해도 되는가 — 아래 「하는 일」 중 어느 것인가, 의뢰라면 허가한 사람 |
| 분석 방식 | 정적(파일만 읽음) · 실행 · 네트워크 관찰 · 기기 조작 중 무엇을 쓸 것인가 |

### 1-2. 정적 분석과 실행 · 관찰은 허가가 다릅니다

파일을 읽기만 하는 정적 분석의 허가가 **실행 · 접속 · 네트워크 캡처 · 기기 조작의 허가를 뜻하지
않습니다.** 대상을 실행하거나 남의 서버와 주고받는 것을 관찰하는 분석은 그 방식마다 사용자에게
확인을 받고, 확인 사실을 기록에 적습니다. 믿을 수 없는 대상은 격리된 환경에서 실행합니다.

### 1-3. 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| 기능 · 시스템의 동작 원리 학습과 역기획 | DRM · 라이선스 확인 · 안티치트 등 기술적 보호 수단 우회 |
| 자기 제품과의 상호 운용 | 게임 치트 · 온라인 서비스 변조 |
| 자기 소유 · 의뢰받은 소프트웨어의 디버깅 · 감사 | 허가 없는 시스템의 인증 · 접근 제어 우회 |
| 자기 구현을 위한 동작 비교 | 보호되는 코드 · 그림 · 소리 · 데이터의 복제와 재배포 |

공개되어 있다는 것, 파일을 가지고 있다는 것만으로 모든 분석이 허가되지는 않습니다. 이용 약관 ·
라이선스가 역분석을 막는지 확실하지 않으면 사용자에게 알리고 판단을 받습니다. 판단은 사용자의 몫입니다.

## 2. 질문 하나를 정합니다

분석은 **질문 하나**로 시작하고, 그 질문에 답하면 끝납니다. 「이 게임 전체를 분석」은 끝나지 않습니다.

- 좋은 질문 — 「{기능}의 {값}은 어떻게 계산되는가」 · 「{화면}에서 {버튼}을 누르면 어떤 순서로 무엇이
  일어나는가」 · 「{시스템}은 어떤 데이터를 어디에 저장하는가」
- 끝나는 조건을 함께 적습니다 — 「계산식과 입력 변수를 근거와 함께 적으면 끝」처럼.
- 질문이 갈라지면 새 질문으로 기록에 따로 적고, 지금 질문을 먼저 끝냅니다.

## 3. 대상에 맞는 길을 고릅니다

가벼운 길부터 갑니다. **정적 · 메타데이터 → 의사코드 → 실행 관찰** 순서입니다. 앞 단계로 답이 나오면
뒤 단계로 가지 않습니다(뒤로 갈수록 허가 · 시간 · 위험이 큽니다).

| 대상 | 먼저 볼 것 | 필요한 것 |
|---|---|---|
| Unity(IL2CPP) 게임 | `global-metadata.dat`의 타입 · 메서드 이름 | 없음(내장) |
| Godot 게임 | PCK 묶음의 파일 목록 | 없음(내장) |
| 네이티브 실행 파일 · DLL | 문자열 · 심벌 · 호출 관계 → 의사코드 | Ghidra · Hopper · IDA 중 하나 |
| JavaScript · Electron 앱 | 모듈 · import · IPC · 소스맵 | Node.js |
| .NET 어셈블리 | 메타데이터 · CIL | 없음 |
| Android APK | 매니페스트 · 클래스 · 디컴파일한 메서드 | JADX · JDK |
| 웹사이트 | 페이지 구조 · 스크립트 · 네트워크 | Chrome 계열 브라우저 |
| 저장된 네트워크 캡처 | 요청 · 응답 · 실은 데이터 | HAR 등 캡처 파일 |

MCP로 분석할 때는 작업을 고르기 전에 세션 상태에서 지금 쓸 수 있는 작업을 확인합니다(REA의
`binary_session`을 빈 입력으로 부르면 작업별 가능 여부와 이유를 돌려줍니다). 엔진이 여럿이면 하나를
골라 기록에 적습니다 — 같은 질문을 엔진마다 다르게 풀면 결과를 비교할 수 없습니다.

## 4. 결론마다 근거와 확실도를 남깁니다

### 4-1. 확실도 세 단계

| 단계 | 뜻 | 예 |
|---|---|---|
| **확인** | 코드 · 데이터 · 실행 결과로 직접 확인함 | 상수 값을 바이너리에서 읽음 · 실행해서 같은 값이 나옴 |
| **추정** | 근거는 있으나 해석이 들어감 | 의사코드를 읽고 「이 분기가 치명타 판정일 것」이라 봄 |
| **모름** | 근거가 없거나 도구가 한계를 보고함 | 서버에서 계산되어 클라이언트에 없음 |

**추정을 확인처럼 쓰지 않습니다.** 의사코드는 컴파일러 최적화 · 도구의 해석이 섞인 결과라, 의사코드만
읽고 내린 결론은 추정입니다. 실행 비교 · 여러 입력 대조로 확인해야 「확인」으로 올립니다.

### 4-2. 근거로 적는 것

결론 한 줄마다 아래 중 하나 이상을 적어, 다른 사람이 같은 자리를 다시 열 수 있게 합니다.

- 함수 이름 · 주소, 파일 안 경로, 모듈 이름
- 분석 도구의 작업 이름과 입력(예: 어떤 대상에 어떤 명령을 줬는가)
- 도구가 돌려준 근거 · 한계 · 모르는 것 — **도구가 보고한 한계는 빼지 않고 그대로 옮깁니다**
- 실행 관찰이면 조건(버전 · 설정 · 입력)과 관찰 결과

### 4-3. 분석 기록의 모양

기록은 프로젝트의 조사 자료 자리(구조 설정이 없으면 `analysis/`)에 둡니다. 조사 자료이므로 여기의
수치는 기대값이 아닙니다 — 자기 사양으로 확정한 값만 확정 사양 자리로 옮깁니다.

```markdown
# {대상} {버전} — {질문}

- 입수 경로 · 허가 근거 · 분석 방식: …
- 끝나는 조건: …
- 엔진 · 도구 버전: …

| # | 결론 | 확실도 | 근거 |
|---|---|---|---|
| 1 | … | 확인 · 추정 · 모름 | 함수 · 주소 · 파일 · 도구 결과 |

## 모르는 것 · 다음 질문
```

## 5. 원본과 디컴파일 코드를 옮기지 않습니다

- **분석 대상 원본(실행 파일 · 패키지 · 추출한 그림 · 소리 · 데이터)과 네트워크 캡처는 저장소에 넣지
  않습니다.** 저장소 밖 자리에 두고 기록에는 그 자리를 자리 표시자로 적습니다. 저장소 안에 둘 수밖에
  없으면 `.gitignore`에 먼저 적습니다. 캡처에는 계정 · 개인 정보가 섞일 수 있습니다.
- **디컴파일 · 의사코드를 결과물(기획서 · 구현 · 공개 문서)에 그대로 붙이지 않습니다.** 결과물에는 동작
  설명(입력 · 계산 · 출력 · 순서)만 씁니다. 근거로 꼭 보여야 하면 기록 안에 짧게 인용하고 출처 자리를 적습니다.
- 추출한 그림 · 소리 · 문구는 분석 확인용으로만 보고, 결과물에 넣지 않습니다.

## 6. 결과를 넘깁니다

| 넘기는 곳 | 넘기는 것 | 함께 켜면 좋은 모듈 |
|---|---|---|
| 역기획서 · 자기 기획서 | 동작 설명 · 계산식 · 상태 흐름 — 확실도 표시를 유지합니다 | `gdd` |
| 테스트 케이스 | 관찰한 동작 → 기대 결과. 「추정」 결론에서 나온 케이스는 그렇다고 표시합니다 | `tc` |
| 자기 구현 | 아래 순서를 따릅니다 | — |

**자기 구현은 설명에서 다시 만듭니다.** ① 기록의 동작 설명만 보고 구현합니다 — 디컴파일 코드를 옮겨
적지 않습니다. ② 같은 입력을 원본과 자기 구현에 넣어 결과를 비교하는 시험을 만듭니다. ③ 차이가 나면
기록으로 돌아가 결론의 확실도를 고칩니다.

## 7. 알려진 함정

| 함정 | 어떻게 피하나 |
|---|---|
| 대상이 업데이트되면 기록의 주소 · 함수 이름이 맞지 않음 | 기록 첫머리에 버전을 적고, 버전이 바뀌면 결론을 다시 확인할 때까지 「추정」으로 내립니다 |
| 클라이언트에 없는 계산(서버 판정)을 클라이언트에서 찾느라 시간을 씀 | 네트워크 요청 직후 값이 바뀌면 서버 쪽 계산을 의심하고 「모름」으로 적습니다 — 서버를 두드리지 않습니다 |
| 도구가 「healthy=false」를 내도 지금 분석과 상관없는 항목일 수 있음 | 점검 범위를 이번에 쓰는 엔진 · 에이전트로 좁혀 다시 봅니다(`rea` 모듈의 알려진 함정) |
| 의사코드의 이상한 상수 · 분기를 기획 의도로 읽음 | 컴파일러 최적화의 흔적일 수 있습니다. 여러 입력으로 실행 비교해 확인합니다 |
| 질문이 계속 갈라져 끝나지 않음 | 갈라진 질문은 기록 아래 「다음 질문」에 적고 지금 질문의 끝나는 조건으로 돌아갑니다 |
