# agent-office — AI 사무실에 일을 맡기고, 에이전트들이 나눠 하는 일을 지켜보는 규칙

**AI 사무실**은 이 컴퓨터에서만 도는 로컬 앱입니다. 에이전트들이 일하는 모습을 한 화면(사무실 그림 ·
업무 일지)에 보여 줍니다. 이 규칙은 사무실을 쓰는 두 가지 방법을 다룹니다.

| 방법 | 누가 일하나 | 화면에 보이는 것 |
|---|---|---|
| **맡기기** | 사무실 앱이 직접 띄운 에이전트 둘 — 작성 담당과 검토 담당이 초안 → 검토 → 수정을 돌립니다 | 단계 · 도구 호출 · 단계별 작업물 |
| **지켜보기** | 사용자와 대화하는 세션(메인)이 띄운 서브에이전트 — 훅이 시작 · 끝을 사무실에 알립니다 | 서브에이전트마다 한 사람 · 맡은 일 한 줄 · 시작 · 끝 |

일을 나누는 법과 받는 법은 base의 `rules/agent-delegation.md`가 정본입니다. 이 문서는 그 일을
사무실에 **보이게** 하는 법과, 사무실에 맡길 때 더 지킬 것만 적습니다.

---

## 1. 층 하나에 저장소 하나

사무실의 **층**은 읽을 폴더 · 외부 MCP · 역할 문구 · 모델을 따로 갖는 작업 공간입니다.

1. **저장소 하나에 층 하나를 둡니다.** 층의 폴더는 그 저장소의 루트로 지정합니다. 저장소 둘을 한 층에
   넣으면 역할 문구가 어느 저장소의 규칙을 말하는지 흐려집니다.
2. **사무실은 폴더를 읽기만 합니다.** 저장소 파일을 고치는 일은 맡기지 않습니다 — 사무실이 내는 것은
   작업물(문서)이고, 저장소에 쓰는 것은 메인이 합니다(§4).
3. 저장소에 비밀값을 두지 않습니다. 앱이 숨김 파일 · `.env`를 가려도, 다른 이름의 비밀 파일까지
   가린다고 가정하지 않습니다.
4. 외부 MCP는 그 업무에 필요한 도구만 층에 등록합니다. 등록한 도구는 업무 중에 확인 없이 호출될 수
   있습니다. 토큰은 값이 아니라 환경변수 이름만 적습니다.

## 2. 중앙 규칙은 역할 문구로 전합니다

사무실 앱은 에이전트를 띄울 때 사용자 설정 · `CLAUDE.md` · 훅을 읽지 않게 합니다(업무마다 같은
조건에서 돌리기 위해서입니다). 그래서 **중앙 규칙과 프로젝트 규칙은 저절로 들어가지 않습니다.** 층의
역할 문구가 「폴더의 규칙 파일을 먼저 읽어라」라고 시킬 때만 전달됩니다.

1. 층을 만들면 작성 · 검토 역할 문구를 `templates/office-roles.md`의 견본으로 채웁니다. 견본은
   `CLAUDE.md` → 프로젝트 change-log의 현행 기준 → remaining-work → 업무에 관련된 `core/` 규칙
   순으로 읽게 합니다.
2. 층의 폴더가 비어 있거나 `core/`가 없는 폴더이면, 사무실은 규칙을 읽을 수 없습니다. 「규칙을 모든
   층에 적용해」 같은 업무를 맡기기 전에, 각 층의 폴더가 중앙 규칙을 받은 저장소인지 먼저 확인합니다
   (§6 점검 도구).
3. 역할 문구에 규칙 본문을 붙여 넣지 않습니다. 붙여 넣은 문구는 규칙이 바뀌어도 그대로 남습니다.
   파일을 가리키게만 합니다.

## 3. 맡기는 글(브리프)

사무실의 에이전트는 메인의 대화를 보지 못합니다. 브리프는 `rules/agent-delegation.md` §3의 항목을
그대로 채웁니다 — 서식은 `templates/office-brief.md`입니다.

- **대상 파일 · 먼저 읽을 파일**을 경로로 적습니다(층 폴더 기준).
- **사용자 결정은 원문 그대로** 적습니다.
- **끝났는지 보는 법**을 적습니다. 사무실은 명령을 실행하지 못하므로, 「검사가 통과한다」 대신 「어느
  규칙의 어느 절을 지킨다」처럼 읽어서 확인할 수 있는 기준으로 씁니다.
- 검토 · 수정 횟수는 일의 크기에 맞게 고릅니다. 횟수가 늘수록 모델 호출이 늘어 두 계정의 사용량이
  더 듭니다.

## 4. 작업물은 초안으로 받습니다

1. 사무실의 최종본은 **초안**입니다. 메인이 읽고, 사실 주장(「파일에 이것이 있다」 · 「규칙이 이렇다」)은
   직접 확인한 뒤 저장소에 옮겨 씁니다(`rules/agent-delegation.md` §4).
2. 저장소에 옮긴 뒤에는 그 프로젝트의 평소 절차(검사 · change-log 기록)를 그대로 거칩니다. 사무실을
   거쳤다고 검사를 줄이지 않습니다.
3. 사무실이 「자료가 없어 못 했다」고 끝낸 업무는 실패로 봅니다. 층 폴더 · 역할 문구를 고친 뒤 새 업무로
   다시 맡깁니다.

## 5. 세션의 서브에이전트를 사무실에 보이게 하기

메인이 서브에이전트를 띄울 때마다 훅이 사무실에 「누가 · 무엇을 맡아 시작했다 / 끝났다」를 알립니다.
사용자는 대화를 열지 않고 사무실 화면에서 지금 몇 명이 무엇을 하는지 봅니다.

### 5-1. 켜는 법

프로젝트의 `.claude/settings.json`(혼자 쓰는 설정이면 `.claude/settings.local.json`)에
`templates/claude-hooks.json`의 `hooks` 블록을 더합니다. 훅은 `scripts/office_hook.py`를 부릅니다.

### 5-2. 보내는 것과 보내지 않는 것

| 보냅니다 | 보내지 않습니다 |
|---|---|
| 일어난 일(시작 · 끝) · 세션 ID · 서브에이전트 ID · 종류 · 맡은 일 한 줄 설명(120자까지) · 저장소 폴더 이름 · 시각 | 지시 원문 · 대화 내용 · 작업 결과 · 파일 내용 · 환경변수 |

- 주소는 **이 컴퓨터(`127.0.0.1` · `localhost` · `[::1]`)만** 받습니다. 다른 주소가 설정되면 아무것도
  보내지 않습니다.
- 사무실이 꺼져 있거나, 아직 활동을 받지 못하는 앱이면 조용히 넘어갑니다. **훅이 작업을 막거나
  늦추지 않습니다** — 짧은 제한 시간 안에 끝나고, 실패해도 늘 정상 종료합니다.
- 훅의 표준 출력은 비워 둡니다. 훅의 출력은 세션이 읽는 자리라, 알림용 훅이 거기에 쓰면 세션의
  동작이 바뀔 수 있습니다.

### 5-3. 사무실 앱이 갖출 활동 입구

지켜보기는 사무실 앱에 아래 입구가 있어야 화면에 나옵니다. 입구가 없는 앱이면 훅은 보내기만 하고
화면에는 아무것도 생기지 않습니다(§6 점검 도구가 알려 줍니다).

| 입구 | 약속 |
|---|---|
| `POST /api/activity` | 본문은 JSON 하나입니다. 받으면 `202`. 다른 사이트의 요청을 막는 앱이면, 훅은 `Origin`을 사무실 주소로 보냅니다 |
| `GET /api/activity` | 최근 활동 목록(JSON 배열). 점검 도구가 입구가 있는지 이것으로 봅니다 |

보내는 본문:

```json
{
  "source": "claude-code",
  "event": "start",
  "sessionId": "…",
  "agentId": "…",
  "agentType": "general-purpose",
  "title": "맡은 일 한 줄 설명",
  "project": "저장소 폴더 이름",
  "time": "2026-01-01T00:00:00Z"
}
```

| `event` | 언제 | 채워지는 것 |
|---|---|---|
| `assign` | 메인이 서브에이전트를 띄우기 직전(`PreToolUse` · 도구 `Agent`) | `title` · `agentType` — `agentId`는 아직 없습니다 |
| `start` | 서브에이전트가 일을 시작할 때(`SubagentStart`) | `agentId` · `agentType` — `title`은 없습니다 |
| `stop` | 서브에이전트가 끝날 때(`SubagentStop`) | `agentId` · `agentType` |

- 같은 `agentId`의 `start`와 `stop`이 한 사람의 출근과 퇴근입니다.
- 맡은 일 설명은 `assign`에만 있습니다. 앱은 같은 `sessionId` · `agentType`에서 아직 짝이 없는 가장
  이른 `assign`을 다음 `start`에 붙여 이름표로 씁니다. 짝을 못 찾으면 `agentType`을 이름표로 씁니다.
- 비어 있는 필드는 빈 문자열로 옵니다. 앱은 모르는 `event`를 버리지 않고 업무 일지에만 남깁니다.
- 이 약속을 바꾸면 이 표 · `scripts/office_hook.py` · `check.py`를 같이 고칩니다.

## 6. 점검

```bash
python core/modules/agent-office/scripts/office_check.py --repo .
```

| 항목 | 통과 조건 |
|---|---|
| Node.js · CLI | `node`(20 이상)가 PATH에 있습니다. `claude` · `codex`가 PATH에 없으면 경고입니다 — 사무실 앱은 다른 설치 자리도 찾습니다 |
| 사무실 | 사무실 주소가 응답하고, 사무실이 두 CLI의 로그인을 확인합니다 |
| 층 | 이 저장소 루트를 폴더로 가진 층이 있고, 그 층의 역할 문구가 `CLAUDE.md`를 읽게 합니다 |
| 활동 입구 | `GET /api/activity`가 응답합니다. 없으면 경고 — 맡기기는 되지만 지켜보기는 화면에 안 나옵니다 |
| 훅 | 프로젝트 `.claude/settings*.json`에 `office_hook.py` 훅이 있습니다. 없으면 경고 |

사무실 주소는 기본 `http://127.0.0.1:4318`이고, 환경변수 `AGENT_OFFICE_URL`로 바꿉니다. 점검 도구는
읽기만 합니다 — 층을 만들거나 설정을 바꾸지 않습니다.

## 7. 사무실 꾸미기

층마다 사무실 그림을 바꿀 수 있습니다. 사무실 화면의 **사무실 꾸미기** 창에서 고치거나, 층의 배치 파일을
직접 고칩니다. 둘은 같은 파일을 씁니다.

| 바꾸는 것 | 내용 |
|---|---|
| 방 배치 | 가로 · 세로 방 수(1~4) · 방마다 이름 · 자리 · 바닥 종류와 색 · 지붕 색 |
| 가구 | 방마다 12개까지 · 종류와 위치(방 왼쪽 위 기준) · 책상 주인(Claude · Codex) |
| 방의 쓰임 | 작성 · 검토 · 자료 조회 · MCP 호출 · 차례 기다리기 · 쉬기 · 세션 에이전트 대기 · 끝난 뒤 가는 방 |
| 세션 에이전트가 일하는 방 | 에이전트 종류마다 방을 고릅니다. 정하지 않은 종류는 기본(`*`)을 따릅니다 |
| 캐릭터 모습 | Claude · Codex와 에이전트 종류마다 이름표 · 옷 · 머리 · 피부 색 |

1. **배치는 층에 붙습니다.** 층 하나에 저장소 하나이므로(§1), 저장소마다 사무실 모습이 다릅니다. 배치
   파일은 사무실 앱의 데이터 폴더에 있고, 저장소에는 두지 않습니다.
2. **방의 쓰임을 일의 흐름에 맞춥니다.** 예를 들어 탐색 · 조사를 맡는 종류는 자료실, 설계를 맡는 종류는
   기획실에 두면, 화면만 보고도 지금 무슨 일이 몇 갈래로 돌고 있는지 읽힙니다.
3. 처음 꾸밀 때는 `templates/office-layout.json`(기본 배치)을 보고 형식을 맞춥니다. 형식에 맞지 않는
   파일은 앱이 기본 배치로 그리고, 꾸미기 창에 이유를 보여 줍니다.
4. 꾸미기는 그림만 바꿉니다. 업무 실행 · 폴더 접근 · 훅 알림에는 영향이 없습니다.

### 7-1. 그림 바꾸기 — 사무실의 그림 업무

캐릭터 · 가구 · 바닥 · 벽 · 지붕을 이미지로 바꿀 수 있습니다. 앱의 그림 자리 약속(이름 · 크기 · 자홍 단색
배경 · 캐릭터 4칸)을 지키는 PNG만 쓰입니다.

1. **기획부터 사무실에 맡깁니다.** 아트 방향 · 그림별 프롬프트 · 만드는 순서를 브리프로 맡기고(§3), 최종본의
   프롬프트가 약속을 지키는지 메인이 확인한 뒤 프롬프트 목록에 넣습니다(§4).
2. **그림은 사무실의 그림 업무로 만듭니다.** 검토 담당(ChatGPT 로그인)이 이미지 생성으로 한 장씩 그리고, 앱이
   크기를 맞춰 바로 사무실에 넣습니다. 한 장마다 이미지 생성 사용량이 듭니다.
3. **기준 그림 몇 장을 먼저** 만들어 보고(넓은 면적의 바닥 · 자주 나오는 가구 · 주인공 캐릭터), 줄인 모습을
   확인한 뒤 나머지를 맡깁니다. 처음부터 전부 맡기면 방향이 틀렸을 때 사용량을 모두 다시 씁니다.
4. **이미 잘 만든 외부 픽셀 아트 묶음을 쓸 수도 있습니다.** 생성 그림이 작은 크기에서 뭉개지면, 같은 크기로
   처음부터 그려진 묶음이 낫습니다. 쓰기 전에 라이선스(재배포 · 상업 사용)를 묶음의 원본 페이지에서 확인하고,
   받은 출처 · 버전 · 라이선스 원문을 묶음과 함께 둡니다. 유료이거나 재배포를 막는 묶음은 받지 않습니다.
