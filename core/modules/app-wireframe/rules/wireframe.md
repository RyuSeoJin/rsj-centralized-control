## 입력과 산출물

프로젝트의 `wireframes/manifest.json`에 입력을 모읍니다. 서비스 사양을 복제하지 않고 정본 경로·revision·관련 노드를 참조합니다.
시뮬레이터는 배치 관찰 자료이며, 서비스 동작이 정본과 다르면 불일치를 기록합니다. 개발용 조작 패널은 화면 대상에서 제외합니다.

| 필드 | 의미 |
|---|---|
| `schemaVersion`, `revision` | 입력 형식 버전 1과 프로젝트 입력 개정 |
| `sources` | 정본·시뮬레이터 경로, revision과 선택적 sha256 |
| `target` | 편집할 Design URL. `boardUrl`은 선택적인 FigJam 참조 |
| `kits` | 후보의 고정 ID·이름·Community 출처·관찰 상태 |
| `selectedKit` | 하나의 기준 키트 ID. 미선정은 null |
| `kitBinding` | 복제 Design URL 또는 libraryKey, 접근 증거, 이용 조건 확인 증거 |
| `components` | UI 역할별 키트 ID, componentKey 또는 로컬 nodeId, 관찰한 속성과 스타일 |
| `screens` | 의미 있는 ID·이름·기능·모드·상태·출처·UI 역할·요소와 문구·진입 절차 |
| `transitions` | 출발 화면·유저 행동·도착 화면. 모달 닫기와 복귀도 포함 |
| `node-map.json` | 실제 생성·수정 도구가 반환한 파일 키·화면 ID별 nodeId·반영 입력 해시·검수 결과 |

## 키트를 정하고 연결합니다

1. 사용자가 준 후보 URL은 출처로 기록합니다. 접근하지 못한 후보를 관찰·사용 가능으로 표시하지 않습니다.
2. 실제 모바일 컴포넌트, 입력·카드·시트 상태, Auto Layout, 편집 가능 여부와 이용 조건을 확인합니다. 무료라는 이름만으로 재배포 허용을 추정하지 않습니다.
3. 프로젝트당 기준 키트 하나를 선택하고 원본 URL·확인 날짜·복제 파일 또는 라이브러리와 확인 근거를 기록합니다. 다른 키트는 기본적으로 참고용입니다. 사용자가 보조 키트를 지정하면 부족한 아이콘·부품에 한해 사용하며, `supplementalKitIds`와 보완 사유·주 키트 스타일 조정 근거를 기록합니다.
4. Design 파일의 라이브러리 목록과 로컬 컴포넌트를 먼저 확인합니다. 공개 라이브러리는 조회된 실제 키로, 복제 키트는 로컬 컴포넌트 ID로 연결합니다.
5. 컴포넌트 키가 조회돼도 다른 파일에서 import가 성공한다는 뜻은 아닙니다. 실제 대상 파일에서 가져오기를 확인하고 매핑의 `verifiedTargetFileKey`에 확인한 파일 키를 기록합니다. 가져오기가 실패하면 기존 원본 페이지를 보존한 같은 파일의 새 작업 페이지 또는 사용자가 대상 파일에 복사한 로컬 컴포넌트를 사용합니다.
6. Community 링크만 있고 도구에서 가져올 수 없으면 사용자가 복제한 Design 파일 또는 작업 파일로 복사한 컴포넌트를 요청합니다. 숫자 Community ID를 파일 키로 변환하거나 임의 키를 만들지 않습니다.
7. 링크가 FigJam이면 Design 작업 파일을 별도로 정합니다. Design의 편집 가능한 컴포넌트를 FigJam 도형으로 바꾸지 않습니다. 보드 연결은 링크·미리보기로 구분합니다.

## 대응표와 공통 부품을 만듭니다

시뮬레이터의 내비게이션·탭바·버튼·입력·카드·시트를 실제 키트 부품에 대응시킵니다. 텍스트 속성·variant·폰트·간격·색·테두리의 확인값을 기록합니다.
모든 제작은 기준 키트의 인스턴스를 우선 사용합니다. 이미지를 화면 전체에 붙인 결과를 편집 가능한 와이어프레임으로 보고하지 않습니다.
키트에 없는 UI는 같은 스타일로 프로젝트 공통 컴포넌트를 만들고 `extensionOf`에 기준 키트를 기록합니다. 새 부품의 필요성과 사용 화면을 기록합니다.
스타일은 실제 조회값에서 정합니다. 후보를 보지 못했을 때 비슷하다고 추측해 다른 디자인 시스템을 대신 적용하지 않습니다.

## 화면과 상태를 배치합니다

기능별 Section 아래 화면별 Frame을 두고 기본·빈 상태·잠금·팝업 상태를 구분합니다. 공통 UI를 재사용하고 퍼스트 플레이·일반의 차이는 상태와 버튼 노출로 표현합니다.
시뮬레이터의 정보 순서·문구·행동·조건은 보존하며 사진과 영상은 이름과 역할이 있는 자리표시자로 단순화합니다.
프레임 크기는 관찰한 앱 뷰포트에서 정하고 관련 요소는 Auto Layout으로 묶습니다. 키트 원본의 작업 페이지는 수정하지 않습니다.
Design 프로토타입으로 연결 가능한 이동은 실제 유저 행동에 연결합니다. 지원하지 않는 전이는 설명과 검수 항목으로 남기며 연결 완료로 표시하지 않습니다.

## 도구로 제작 준비를 확인합니다

저장소 루트에서 `python core/modules/app-wireframe/scripts/wireframe.py <프로젝트>/wireframes/manifest.json`을 실행합니다.
이 명령은 형식 오류와 제작 대기 사유를 출력합니다. `--ready`를 붙이면 미연결 키트·미검수 원본·누락 대응이 있을 때 실패합니다.
`--plan <프로젝트>/wireframes/plan.json`은 로컬 제작 계획을 씁니다. 계획 생성은 Figma 생성 완료가 아닙니다.
실제 Figma 작업은 설치된 Figma 도구와 그 스킬을 사용합니다. 제작 전 현재 파일·페이지·매핑된 노드를 읽고, 반환받은 모든 생성·수정 ID를 외부 node-map에 저장합니다.
도구 오류 후에는 캔버스를 읽고 실제 변경분을 확인한 뒤 이어갑니다. 부분 생성된 프레임을 다시 만들지 않습니다.

## 반복 갱신과 검수

화면 ID는 재배치해도 유지합니다. node-map에 있는 기존 프레임만 갱신하며, 매핑되지 않은 노드와 수동 편집 영역은 보존합니다.
삭제·키트 교체·전체 재생성은 영향 목록을 먼저 확인합니다. 원본 키트가 갱신돼도 자동으로 기준을 바꾸지 않습니다.
입력 해시·컴포넌트 매핑·노드 수·경계·문구·버튼 조건·연결을 대조하고 스크린샷으로 잘림·겹침을 확인합니다.
실제 화면 렌더와 키트 인스턴스 사용 여부까지 확인해야 검수 완료로 기록합니다. 구조 검사만 통과하면 시각 검수는 대기로 남깁니다.
외부 파일 생성은 로컬 재생성 명령에서 자동 실행하지 않습니다. 사용자가 승인한 Figma 대상과 범위에서만 실행합니다.


## 실제 화면을 대조한 뒤 순서도로 확장합니다

소스 코드 열람은 화면 관찰과 구분합니다. 키트에 맞추기 위해 실제 문구·정보 순서·버튼 위치·노출 조건을 예시로 대체하지 않습니다. 사진·영상만 역할과 비율을 보존한 자리표시자로 바꿀 수 있습니다. 키트가 제공하지 않는 앱 고유 구조는 실제 화면을 근거로 편집 가능한 요소로 구성합니다.

화면마다 `renderEvidence`에 `method`(browser-capture 또는 user-screenshot), `reference`(관찰 가능한 캡처 식별자·파일·도구 결과), `state`, `capturedAt`, `viewport`의 width·height를 기록합니다. 소스 근거만 있거나 캡처 상태가 다르면 제작 준비 완료로 처리하지 않습니다. 도구가 증거 필드의 형식을 검사해도 실제 일치는 사람이 화면을 보고 판정합니다.

브라우저 접근이 보안 정책으로 차단되면 다른 프로토콜·서버·브라우저로 우회하지 않습니다. 사용자 제공 화면 자료 등 허용된 근거가 올 때까지 화면 정확성 검수를 대기로 둡니다. 독립적으로 가능한 규칙·입력·대응표 정비는 계속합니다.

사용자가 제한을 안내받고도 계속 제작하도록 요청하면 읽을 수 있는 소스를 근거로 편집 가능한 초안을 작성할 수 있습니다. 이때 화면과 외부 대응 기록에 소스 기반·렌더 미검수 상태를 명시하고, `renderEvidence`를 만들어 채우거나 준비 검사의 `ready`를 강제로 바꾸지 않습니다. 실제 화면의 위치·상태를 확인하지 못한 부분, 데이터 자리표시자, 연결 미완료 범위를 따로 남깁니다. 초안 제작 완료와 화면 일치 검수 완료를 구분합니다.

### 순서도 배치

- 워크플로우는 단계·분기·복귀와 표시 규칙의 근거, 시뮬레이터 렌더는 UI 위치·크기·문구·상태의 근거로 사용합니다. 서비스 정책이 충돌하면 책임 정본과 승인 상태를 먼저 확인합니다.
- 프로젝트가 지정한 워크플로우 표현 계약을 참조합니다. 주 경로는 왼쪽에서 오른쪽으로, 같은 위계의 선택지는 오른쪽 같은 열에 세로로 배치하고 첫 자식은 부모 상단에 맞춥니다. 기능별 외곽 Section으로 묶습니다.
- 사용자 행동은 유저 구역의 도형, 자동 처리·조건은 시스템 구역의 도형으로 표시합니다. 화면이 실제로 달라지는 단계 아래 UI 구역에 대응 와이어프레임을 둡니다. 같은 화면을 처리 단계마다 반복 생성하지 않습니다.
- 일반 연결은 검정, 조건 충족은 파랑·예, 불충족은 빨강·아니오로 표시합니다. 동일 높이는 수평선, 다른 높이는 가장 가까운 직각 통로를 사용합니다. 선은 도형·화면·글자를 관통하지 않습니다.
- 예·아니오는 출발 쪽, 보충 설명은 도착 쪽의 흰 바탕·검정 라벨에 둡니다. 버튼 선택을 라벨만으로 대체하지 않습니다. 공통 화면의 호출·복귀는 실제 목적지와 조건을 표시합니다.
- 공통 기능은 한 번 작성하고 퍼스트 플레이·일반의 차이만 별도 상태로 나눕니다. 먼 복귀는 목적지 ID와 링크가 있는 연결자로 정리하며 링크를 열기 전에도 목적지를 알 수 있어야 합니다.
- 단계 ID·화면 상태 ID·Figma 노드 ID의 대응을 외부 파일에 저장합니다. 전 범위 목록과 제작·검수·미확인 상태를 기록하고 일부 화면 제작을 전체 확장 완료로 표시하지 않습니다.

### 대조 검수와 갱신

### 다이얼로그·바텀시트·로딩의 화면 내 배치

팝업을 독립 카드로만 그리지 않습니다. 호출 직전 화면을 유지한 프레임 위에 배경 흐림·딤·팝업을 실제 쌓임 순서로 겹칩니다. 시트 위의 확인창도 아래 시트를 유지합니다. 화면 상태마다 기준 뷰포트, 안전 영역, 가로 여백, 고정 또는 내용 기반 높이, 중앙·하단 등 기준점, 모서리, 닫기 위치를 기록합니다. 키트는 형태를 통일하는 데 사용하며 소스의 배치와 크기를 임의의 기본 카드 규격으로 바꾸지 않습니다.

시트의 헤더·하단 입력·확정 버튼이 고정되는 경우 스크롤 본문과 분리합니다. 실제 서비스에서 제공하는 닫기·뒤로가기만 표시하고, 화면 밖 설명을 화면 안 UI로 넣지 않습니다. 화면 상태를 나타내는 예시 수치·문구는 외부 기록에서 예시임을 밝힙니다.

로딩은 전체 화면, 화면 내 패널, 버튼 내부, 채팅 입력 영역, 진행률 표시를 구분합니다. 해당 위치·지름·선 두께·점 개수·진행 막대 높이를 보존합니다. 정적인 와이어프레임에는 대표 프레임을 그리고, 확인된 회전·점멸 주기와 진입·완료·실패 조건을 화면 밖에 적습니다. 동작을 구현하지 않았다면 애니메이션 구현 또는 클릭 검수 완료로 기록하지 않습니다. 토스트는 탭바·안전 영역과의 간격 및 유지 시간을 함께 다룹니다.

Figma 내부 검수는 팝업이 뷰포트 안에 있는지, 하단 기준점이 맞는지, 제목·버튼·스크롤 영역이 겹치지 않는지 확인합니다. 소스에서 계산한 위치·크기와 실제 렌더 관찰을 구분해 기록하며, 소스 기반 배치 확인으로 렌더 일치 검수를 대체하지 않습니다.

### 대조 검수 기록

각 화면의 문구, 헤더·탭바·본문·입력·시트 위치, 정렬, 스크롤, 버튼 노출, 입력 유무별 동작, 모달 아래 화면 유지와 닫기 목적지를 동일 상태의 렌더와 비교합니다. 완료 기록은 `layoutReview`(Figma 내부 잘림·겹침), `fidelityReview`(시뮬레이터 일치), `interactionReview`(실제 클릭)로 분리합니다. 프로토타입 API 등록 성공은 클릭 검수 통과가 아닙니다.

기존 결과가 화면을 정확히 재현하지 못하면 노드 ID를 유지해 수정하고 검수 상태를 먼저 정정합니다. 기존 변경 이력은 보존합니다. Figma 내부 스크린샷이 깨끗하다는 사실만으로 화면 일치 검수를 통과시키지 않습니다.
