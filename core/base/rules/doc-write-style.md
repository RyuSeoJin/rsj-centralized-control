이 워크스페이스에서 쓰는 문서의 문체와 문장 구조를 정합니다. 문서마다 말투와 설명 순서가
달라지면 읽는 사람이 매번 다시 적응해야 하므로, 기준을 한곳에 모읍니다.

**어디까지 강제하는지는 「적용 범위」가 정합니다.** 규칙 문서는 반드시 따르고 도구가 검사합니다.
산출물과 프로젝트 이력은 프로젝트나 켠 모듈이 문체를 정할 수 있습니다.

---

## 1. 문체 — 경어체

문서 본문은 경어체(`~합니다` / `~입니다`)로 씁니다.

**예외는 명사로 끝나는 표현입니다.** 표의 항목, 제목, 목록의 짧은 라벨처럼 서술이 아닌 자리에서는
명사로 끝내도 됩니다 — 소개, 규칙, 문서, 확인, 정리, 진입점 같은 표현이 여기 해당합니다.

| | 예 |
|---|---|
| 경어체로 씁니다 | 뼈대가 확정되기 전에는 상세 설계로 넘어가지 않습니다. |
| 이렇게 쓰지 않습니다 | 뼈대가 확정되기 전에는 상세 설계로 넘어가지 않는다. |
| 명사로 끝내도 됩니다 | 저장소 소개 / 운영 규칙 정의 / 절차 확인 문서 |

### 1-1. 판별은 종결 형태 하나로 합니다

「본문인가 라벨인가」를 매번 감으로 재면 같은 자리가 문서마다 달라집니다. 그래서 자리가 아니라
**문장이 어떻게 끝나는지**만 봅니다. 제목이든 표 안이든 그림 라벨이든 판별은 같습니다.

| 갈래 | 종결 형태 | 어떻게 쓰나 | 예 |
|---|---|---|---|
| **① 서술문** | 「~다」로 끝남 (~한다 · ~했다 · ~된다 · ~이다) | **경어체로 바꿉니다** | 분해했다 → **분해했습니다** · 깨진다 → **깨집니다** |
| **② 라벨** | 명사·명사구·동사의 명사형으로 끝남 | **그대로 둡니다** | 저장소 소개 / 시작점 정렬 / 결함 주입 |

**의문형과 감탄형은 ①이 아닙니다.** 「어떻게 일했나」처럼 묻는 형태의 제목은 그대로 둡니다.
바꿔야 하는 것은 **평서형 종결**뿐입니다.

한 문장을 ②로 줄일지 ①의 경어체로 늘릴지 고민된다면, **그 자리에 마침표를 찍고 싶은지**로
가릅니다. 찍고 싶으면 서술문이므로 경어체로 쓰고, 찍기 어색하면 라벨이므로 명사로 끝냅니다.

## 2. 문장 구조 — 이유 → 작업 → 결과

**이유를 먼저 씁니다.** 변경 내용을 먼저 읽고 마지막에 이유를 알게 되면, 독자는 앞으로 되돌아가
문장을 다시 해석해야 합니다. 이유가 앞에 있으면 그 되감기가 사라집니다.

**지금까지의 방식**
> 이력을 두 파일로 나눴습니다. 문서 이력은 작업 전 항상 읽는 파일, 옛 이력은 평소에 열지 않는
> 파일로 분리했습니다. 지나간 정보가 현재 작업에 섞여 들어오는 것을 막기 위해서입니다.

**이 규칙을 따른 방식**
> 지나간 정보가 현재 작업에 섞이지 않도록, 문서 이력과 옛 이력을 참조 규칙이 정반대인 두 파일로
> 나눴습니다. 그래서 평상시 작업에서는 옛 이력을 아예 열지 않습니다.

### 2-1. 문장이 길어진다고 판단되면 끊습니다

**끊는 지점은 길이가 아니라 의미의 경계에서 정합니다.** 이유에서 작업으로, 작업에서 결과로
넘어가는 지점이 자연스러운 경계입니다. 수식어와 그 대상 사이, 조건절 중간, 나열의 도중처럼
**의미가 아직 닫히지 않은 자리에서는 끊지 않습니다.** 마땅한 경계가 없는데 길다면 먼저 문장을
다시 구성해 보고, 그래도 길면 길게 둡니다(2-3).

### 2-2. 끊을 때 필요하면 접속사를 붙입니다

끊은 두 문장의 관계가 흐려지면 접속사(왜냐하면 · 그래서 · 하지만)로 관계를 드러냅니다.

### 2-3. 정확성이 길이보다 우선입니다

**문장은 길어져도 됩니다.** 짧게 만드느라 근거나 조건이 빠지면 읽는 사람이 그것을 추측하게 되고,
결국 잘못 이해합니다.

### 2-4. 말만 바꾼 반복을 피합니다

앞 문장을 표현만 바꿔 되풀이하지 않습니다. 결과 문장이 필요하면 **새로운 정보**(적용 범위 ·
조건 · 예외 · 이후 작업에 미치는 영향)를 담습니다. 그러면 반복이 아니라 확장이 됩니다.

## 3. 적용 예외

예외마다 면제되는 범위가 다릅니다.

### 3-1. 절차서 — 문장 구조(2)만 예외

`../doc-playbook.md`처럼 순서를 따라 손을 움직이게 하는 문서는 지시가 먼저 와야 합니다. 이유는
지시 뒤에 짧게 붙입니다. **문체(1)는 그대로 적용합니다.** 작업 전에 읽는 게이트 문서(`read-gates.md`
와 그것에서 만든 `AGENTS.md`)도 성격이 같아 이 예외를 따릅니다(`rule-conflict.md` 「적용 예」).

### 3-2. 데이터 표기 규약 — 문체 · 구조 모두 예외

시트 셀처럼 **문서 서술이 아니라 데이터가 들어가는 자리**의 표기 규약을 켠 모듈이 정하면, 그
규약을 따르고 경어체로 바꾸지 않습니다. 그 규약을 예시로 펼치는 문서는 검사 도구의 면제 목록
(`../scripts/check_rules.py`의 `WAIVER`)에 올립니다.

### 3-3. 코드 주석 · 독스트링 · SVG 내부 주석 — 문체 · 구조 모두 예외

고칠 사람이 읽는 기술 메모이고, 형식 예시나 데이터 샘플이 섞여 있어 문체를 손대면 예시까지
바뀔 위험이 있습니다. 주석의 **내용** 규칙은 `code-example.md` 「예제 코드의 주석」가 정합니다.

**다만 화면에 실리는 줄은 예외가 아닙니다.** 도구 목록을 만드는 생성기가 각 스크립트의 독스트링
첫 줄을 도구 설명으로 싣기 때문에, **그 첫 줄만은 본문과 같은 자리**입니다. 1-1의 갈래를 그대로
받습니다.

### 3-4. 인용 · 원문 발췌 — 문체 · 구조 모두 예외

외부 문서의 문구를 옮겨 적을 때는 원문을 고치지 않습니다. 설명 문장은 경어체이고 인용 블록만
원문입니다.

### 3-5. 커밋 메시지 — 작업 목록은 문체 · 구조 예외

커밋 제목과 `[작업 목록]`의 최상위 항목은 이력을 빠르게 훑는 라벨이므로 대상 + 동작 명사형으로
씁니다(`규칙 분리` · `검사 절차 추가`). **인과 관계는 생략하지 않습니다** — 원인 작업을 부모에 두고,
따라온 작업·이유·결과를 들여쓴 자식 항목으로 붙입니다. 형식의 정본은 `git-rules.md` 「커밋 메시지 규격」입니다.

## 4. 적용 범위

| 대상 | 문체(1) | 구조(2) | 도구 검사 |
|---|---|---|---|
| **규칙 문서** — `core/` 아래 md, 루트의 `CLAUDE.md` · `AGENTS.md` · `README.md` · `center-*.md` | 필수 | 필수 | 합니다 |
| **산출물 · 프로젝트 이력** — 프로젝트 폴더 안의 문서와 change-log · remaining-work | 프로젝트나 켠 모듈이 정합니다. 정하지 않았으면 경어체를 권합니다 | 권합니다 | 하지 않습니다 |
| **커밋 메시지** | 3-5 예외 | 필수 | 하지 않습니다 |

규칙 문서만 검사하는 이유는, 규칙 문서는 모든 프로젝트가 물려받아 말투가 한 번 갈리면 전
프로젝트로 퍼지지만, 산출물은 그 프로젝트 안에서 이미 자리 잡은 문체가 있을 수 있기 때문입니다.
프로젝트가 산출물 문체를 정했다면 그 프로젝트 change-log의 「현행 기준」에 적어 둡니다.

### 4-1. 독자용 산출물 문체 — 프로젝트가 고르는 선택지

다른 사람에게 기능을 설명하는 **독자용 산출물**(기능 설명서 · 발표 자료 · 배포용 PDF 등)에 쓸 수 있는
문체를 하나 정의해 둡니다. 시스템이 주어인 문장(「확인 팝업을 띄웁니다」)은 만드는 사람의 시점이고,
읽는 사람은 「내가 무엇을 하면 무엇이 되는가」를 알고 싶어 합니다. 행동과 결과가 한 문장에 있으면
독자가 문장을 다시 조립하지 않고 바로 이해합니다.

**이 문체는 프로젝트가 골라야 걸립니다.** 고르는 프로젝트는 change-log 「현행 기준」에
「산출물 문체: 행동 → 결과 문체(`doc-write-style.md` 「독자용 산출물 문체 — 프로젝트가 고르는 선택지」) ·
대상: {산출물 종류}」처럼 적습니다. 강제하지 않는 이유는 위 표와 같습니다 — 이미 자리 잡은 산출물
문체가 있는 프로젝트가 있고, 분석 보고서처럼 사용자 행동이 주제가 아닌 산출물도 있기 때문입니다.

| 쓰는 자리 | 문체 | 예 |
|---|---|---|
| 사용자 행동과 결과 | 「~하면 ~됩니다 · ~열립니다 · ~돌아갑니다」 | [삭제]를 누르면 고른 항목이 지워지고 목록으로 돌아갑니다 |
| 할 수 있는 것 · 없는 것 | 「~할 수 있습니다 · ~할 수 없습니다」 | 고른 항목이 없으면 [삭제]를 누를 수 없습니다 |
| 사용자가 누르지 않아도 일어나는 것 | 결과가 주어인 문장 「~가 뜹니다 · ~가 생깁니다 · ~가 그대로 남습니다」 | 저장이 끝나면 완료 안내가 뜹니다 |
| 화면에 보이는 것 | 「~가 보입니다 · ~가 있습니다」 | 상세 화면에서 주문 내역을 볼 수 있습니다 |

| 이렇게 쓰지 않습니다 (시스템 주어) | 이렇게 씁니다 (행동 → 결과) |
|---|---|
| [저장] 선택 시 확인 팝업을 띄웁니다 | [저장]을 누르면 확인 팝업이 뜹니다 |
| 목록이 비면 빈 화면 안내를 둡니다 | 목록이 비어 있으면 빈 화면 안내가 보입니다 |
| 처리 중에는 버튼을 비활성화합니다 | 처리 중에는 버튼을 누를 수 없습니다 |

- 「~를 엽니다 · ~를 둡니다 · ~를 띄웁니다 · ~를 끕니다 · ~를 줍니다」처럼 시스템이 주어인 서술은
  「~가 열립니다 · ~가 있습니다 · ~가 뜹니다 · ~를 누를 수 없습니다 · ~를 받습니다」로 바꿉니다.
- **문체만 바꿉니다.** 규칙의 뜻 · 값 · 식별자 · 화면 문구(「낫표」 안)는 바꾸지 않습니다. 문체 작업은
  표현 수정이므로 정본 개정이나 재승인이 필요하지 않습니다(`canonical-source.md` 「파생물은 적용한
  정본의 규칙을 지킵니다」).
- **정본은 대상이 아닙니다.** 정본은 조건 · 분기 · 상태를 빠짐없이 적는 자리라 시스템 기준 서술이
  필요할 수 있습니다. 이 문체는 정본을 읽기 쉽게 옮긴 독자용 산출물에만 씁니다.
- 경어체(「문체 — 경어체」)와 명사형 라벨의 예외는 그대로입니다. 표의 칸은 명사형으로 짧게 둘 수 있습니다.
- 처음 고른 뒤 기존 산출물에 적용하는 일은 별도 작업으로 남은 작업에 올립니다(`central-sync.md` 「받기」).

## 5. 검사는 도구가 합니다

문체는 눈으로 훑어서는 안 걸립니다. 제목 하나가 「~않는다」로 끝나 있어도 읽는 데 지장이 없어서
그대로 지나가고, 그렇게 몇 장이 쌓이면 문서마다 말투가 갈립니다.

```bash
python core/base/scripts/check_rules.py
```

제목의 평서형 · 본문의 비경어체 · 독스트링 첫 줄을 「적용 범위」의 규칙 문서에서만 봅니다. 코드 펜스와 인용,
표는 건너뜁니다. 커밋을 제안하기 전에 돌립니다(`git-rules.md` 「승인 플로우」).

## 6. 참조는 문서 이름과 항목 제목으로 씁니다

참조를 읽는 자리에서 무엇을 확인할지 알 수 있도록, **문서 이름 또는 실제 파일 경로와 항목 제목**을 함께 적습니다. 같은 문서 안에서는 항목 제목만 적어도 됩니다.

- 절 기호 · 번호만으로 다른 항목을 가리키지 않습니다. 예: `git-rules.md`의 「승인 플로우」를 따릅니다.
- 알파벳이나 약칭만으로 유형을 가리키지 않습니다. 「기존 템플릿 사용」 · 「마스터 갱신」 · 「신규 템플릿 제작」처럼 뜻이 드러나는 이름을 씁니다.
- 절차를 참조할 때는 「자료 수집」 · 「상세 설계」처럼 단계 이름을 씁니다. 번호는 순서를 나타내는 보조 표기로만 둡니다.
- 여러 항목을 참조할 때도 각 제목을 적습니다. 범위이면 시작과 끝의 제목을 모두 적습니다.
- 참조 문구를 다듬는 작업만으로 실제 경로 · 명령어 · 데이터 키 · 기능 ID를 바꾸지 않습니다. ID를 새로 정하거나 이전할 때는 아래 「ID는 대상과 역할이 드러나는 이름으로 정합니다」를 따릅니다. 설명에 필요한 약어는 처음에 뜻을 함께 적습니다.
- 과거 변경 이력 · 원문 인용은 당시 기록을 보존하고, 새로 쓰거나 고치는 현행 안내에 이 기준을 적용합니다.

## 7. ID는 대상과 역할이 드러나는 이름으로 정합니다

ID만 읽어도 무엇을 가리키는지 알 수 있도록 **종류 · 대상 · 동작이나 역할**을 의미 있는 단어로 씁니다.
새로 관리하는 정본 · 규칙 · 기능 · 화면 · 흐름 노드에 적용합니다. 순번이나 해독표가 필요한
약칭만으로 이름을 만들지 않습니다.

- 기본 형식은 소문자 영문 단어를 하이픈으로 잇습니다. 종류는 `feature` · `screen` · `flow` ·
  `rule` · `spec`처럼 풀어 쓰고, 뒤에는 실제 대상을 적습니다. 한글 이름과 뜻을 함께 등록합니다.
- `F-01`, `A1-02`, `F-Main-Sub`처럼 번호나 추상적인 계층 이름만으로는 대상을 설명할 수 없습니다.
  `feature-account-profile-edit`처럼 구체적인 목적을 적습니다. 종류 접두사만 풀어 쓰는 것으로 끝내지 않습니다.
- 순서 · 페이지 · 화면 좌표 · 전체 부모 경로를 ID에 넣지 않습니다. 순서와 부모 관계는 별도 정보로
  관리하며, 재배치만으로 ID를 바꾸지 않습니다. 같은 대상의 ID는 파생물에서도 동일하게 참조합니다.
- 이름이 충돌하면 의미 있는 범위나 동작을 보충합니다. 구분하려고 임의의 숫자를 붙이지 않습니다.
  숫자가 도메인 자체의 의미를 갖는 경우에는 그 의미를 설명하고 사용할 수 있습니다.
- 외부 시스템이 부여한 번호 · UUID · API 키처럼 직접 정할 수 없는 식별자는 원형을 유지합니다.
  기획 자료에서는 의미가 있는 관리 ID와 연결해 표시합니다.

### 기존 ID를 이전하는 순서

기존 ID를 바꾸기 전에 옛 ID · 새 ID · 한글 이름 · 소유 정본 · 참조 위치의 대응표를 만듭니다.
이름 변경과 기능 분할 · 통합을 구분하고, 이름만 바꾸는 작업으로 기능 책임을 바꾸지 않습니다.

1. 새 ID의 의미와 중복 여부를 확인하고, 승인된 정본의 변경 절차에 따라 반영합니다.
2. 정본과 현행 참조를 함께 변경합니다. 연결선 · 화면 이동 · 시뮬레이터 상태 연결 · 문서 링크 ·
   생성 입력과 검증 자료도 대조합니다. 과거 이력은 고쳐 쓰지 않고 대응표로 연결합니다.
3. 생성기가 번호 접두사에서 분류나 배치를 추론한다면 명시적인 관계 정보로 처리하도록 먼저
   보완합니다. 지원하지 않는 ID를 입력하고 완료했다고 보고하지 않습니다.
4. 파생물을 다시 만들고 중복 · 끊어진 참조 · 동작 연결 · 긴 이름의 잘림을 확인합니다.
   전환 중인 옛 ID는 호환용으로만 기록하며, 같은 대상을 새 기능으로 중복 등록하지 않습니다.

## 8. Markdown 범위 물결표는 `\~`로 씁니다

Markdown 본문에서 범위를 나타내는 물결표(「2\~16자」 · 「10시\~12시」)는 `\~`로 씁니다. 여러 Markdown
처리기(GitHub 등)는 `~`를 취소선 표시로도 읽어서, 앞 글자에 붙은 `~`가 한 문단이나 표 한 칸에 두 번
나오면 그 사이에 취소선을 긋습니다. 범위가 하나뿐일 때는 멀쩡하다가 같은 문단에 두 번째 범위가
들어오는 순간 깨지므로, 하나뿐이어도 처음부터 `\~`로 씁니다. `\~`는 처리기에서 글자 `~`로 보입니다.

| 원문 | 처리기에서 보이는 모습 |
|---|---|
| `2~16자, 1~3회` | 「16자, 1」에 취소선이 그어집니다 |
| `2\~16자, 1\~3회` | 2\~16자, 1\~3회 (취소선 없이 `~`로 보입니다) |

- **대상은 앞 글자 · 숫자에 바로 붙은 `~`입니다.** 범위 물결표가 대표입니다. 앞에 공백이나 여는
  괄호 · 낫표가 있는 `~`(「~합니다」처럼 어미를 가리키는 표기)는 취소선을 닫지 못하므로 그대로 둡니다.
  헷갈리면 `\~`로 씁니다 — 코드 밖에서는 어디에 써도 `~`로 보입니다.
- **코드 표시(백틱) · 코드 블록 · HTML 주석 안은 그대로 `~`로 씁니다.** 그 안에서는 이스케이프가 처리되지
  않아 `\`가 글자로 남습니다.
- **생성기는 읽을 때 되돌립니다.** Markdown 처리기를 거치지 않고 본문을 직접 읽어 HTML · 슬라이드 ·
  시트 · 앱 데이터로 옮기는 생성기는, 코드 표시 · 코드 블록 · 주석 밖의 `\~`를 `~`로 바꿔 씁니다.
  Markdown 처리기를 거치는 생성기는 처리기가 바꾸므로 따로 손대지 않습니다.
- **정본 해시는 원본 바이트로 계산합니다.** 대조 표 · 입력 지문에 적는 해시를 되돌린 글자로 계산하면
  같은 파일이 도구마다 다른 해시를 갖게 됩니다.
- **산출물에 `\~`가 새어 나오지 않았는지 확인합니다.** 생성한 HTML의 보이는 글자나 슬라이드 글에
  `\~`가 남아 있으면 되돌리기를 빠뜨린 것입니다. 생성기의 생성 후 검사에서 잡습니다.
- **현재 중앙 도구는 이 표기를 처리하거나 검사하지 않습니다.** Markdown을 직접 읽는 생성기를 가진
  모듈과 프로젝트가 위 세 가지(되돌리기 · 원본 해시 · 누출 확인)를 각자 지킵니다. 공통 함수와 검사는
  중앙 남은 작업입니다.
- 이미 있는 문서를 일괄로 고치는 일은 별도 작업입니다(`central-sync.md` 「받기」). 고칠 때는 보이는
  글자가 바뀌지 않으므로 규칙 · 값 · 승인 상태를 바꾸지 않습니다.
