같은 규칙을 여러 문서가 각각 결정하면 어느 것을 고쳐야 하는지 알 수 없습니다. 그래서 **책임
범위마다 정본을 하나만 두고**, 다른 문서와 산출물은 그 정본을 참조합니다. 모든 내용을 한 파일에
합치라는 뜻은 아닙니다. 공통 규칙과 개별 사양의 책임을 나누되 같은 규칙의 소유를 겹치지 않습니다.

이 문서는 정본의 소유·상속·등록·검수 기준을 정합니다. 승인 절차는 `change-scope.md`와
`../doc-playbook.md`, 충돌 처리는 `rule-conflict.md`, 자료의 자리는 `site-structure.md`를 따릅니다.
이번 단계에서는 Markdown 등록과 사람의 검수로 적용하며, 도구의 설정 형식은 바꾸지 않습니다.

## 1. 정본은 파일 형식이 아니라 결정 권한입니다

| 용어 | 뜻 |
|---|---|
| 정본 | 지정된 책임 범위의 규칙을 결정하는 자료 |
| 책임 범위 | 무엇을 결정하며 어디부터 다른 정본의 책임인지 명시한 경계 |
| 규칙 ID | 소유와 참조를 추적하기 위한 규칙의 고정 식별자 |
| 부모 정본 | 여러 자식에 적용할 공통 규칙을 소유하는 정본 |
| 자식 정본 | 부모의 공통 규칙을 따르며 자기 책임 범위의 개별 규칙을 소유하는 정본 |
| 파생물 | 정본을 설명·표현·실행하기 위해 만든 자료 |
| revision | 해당 정본의 내용을 다시 특정할 수 있는 버전 식별값 |

정본 지정과 내용 승인은 별개입니다. 초안을 정본 위치에 두어도 미승인 내용이 확정되지는 않습니다.
문서의 날짜, 파일 확장자, 화면의 완성도, 공유 횟수도 정본 권한을 만들지 않습니다.

**같은 규칙 ID의 현행 소유자는 하나입니다.** 표현을 바꾸거나 다른 ID를 붙여도 같은 책임을
결정한다면 중복 소유입니다. 문서를 나눌 때는 책임 범위의 포함·제외 대상과 규칙 ID를 함께 정합니다.
규칙 ID는 문서 이동이나 제목 변경 때문에 바꾸지 않습니다.
정본과 규칙 ID의 명명 · 기존 ID 이전은 `doc-write-style.md`의 「ID는 대상과 역할이 드러나는 이름으로 정합니다」를 따릅니다.

여러 프로젝트가 같은 범위를 쓰면 한 소유 프로젝트의 정본을 참조합니다. 소비 프로젝트는 소유
프로젝트·등록대장·정본 ID를 함께 적으며, 같은 규칙을 자기 소유로 다시 등록하지 않습니다.

## 2. 부모는 공통 규칙을, 자식은 개별 규칙을 소유합니다

상속 관계를 명시해야 공통 규칙이 빠지지 않습니다. 자식 정본은 부모 정본 ID를 등록하고, 작업 전에
부모부터 해당 자식까지 읽습니다. 부모가 없는 정본은 등록대장에 `—`를 적습니다. 부모 참조의 누락과
순환은 허용하지 않습니다.

자식은 부모의 규칙을 참조하고 자기 책임 범위의 규칙만 결정합니다. 이해를 위해 부모 내용을
요약할 때에는 출처 규칙 ID와 revision을 붙여 참조 요약임을 표시합니다. 그 요약이 별도 정본이
되거나 원문을 바꿀 권한을 갖지는 않습니다.

**자식이라는 이유로 부모를 재정의하지 않습니다.** 더 구체적인 문서이거나 더 최근에 작성했다는
이유로 부모와 다른 값을 선택하지 않습니다. 부모 규칙이 자식의 선택을 허용하려면 부모 정본에
위임 대상 규칙 ID·선택 항목·허용 범위·승인 조건을 명시합니다. 자식은 위임 근거와 선택값을
기록합니다. 위임된 선택값의 소유와 부모 규칙 자체의 소유를 구분합니다.

위임 범위를 벗어난 변경은 부모 정본의 변경 제안입니다. 기존 규칙과 충돌하면 `rule-conflict.md`에
따라 양쪽 경로와 규칙 ID를 제시하고, 승인 전에는 어느 쪽도 임의로 적용하지 않습니다.

구조 설정의 `parent`는 **탐색상의 상위 자료**입니다. 폴더 안에 있다는 사실이나 `parent` 등록만으로
규칙이 상속되지는 않습니다. `depends_on`도 자료 의존 관계이며 정본 소유·상속·승인을 대신하지
않습니다. 정본 상속은 아래 등록대장의 부모 정본 ID로 명시합니다.

## 3. 프로젝트마다 등록대장을 하나 둡니다

정본 관계를 여러 목록에서 따로 관리하면 목록 자체가 어긋납니다. 프로젝트 루트의
`canonical-registry.md` 하나에서 정본과 파생물의 관계를 관리합니다. 프로젝트 change-log의
현행 기준은 등록대장을 가리키고 주요 결정을 요약합니다. 정본 관계를 독립적으로 재정의하지 않습니다.

구조 설정이 있는 프로젝트는 등록대장을 기존 `resources`의 파일 자료로 등록합니다. `path`는
`canonical-registry.md`, `role`은 `policy`, `kind`는 `file`이며, `id`와 `label`은 프로젝트에서
정합니다. 구조 설정이 없으면 프로젝트 루트에 두고 change-log 현행 기준에서 가리킵니다. 정본 관계를 넣기
위해 구조 설정에 새 필드를 만들지 않습니다. 다른 프로젝트 파일은 소비 프로젝트의 구조 설정에
소유 자료로 등록하지 않고 Markdown 등록대장에서 소유자의 등록대장을 참조합니다.

### 3-1. 정본 표

| 정본 ID | 책임 범위 | 담당 규칙 ID | 파일·링크 | 부모 정본 ID | 승인 상태 | revision |
|---|---|---|---|---|---|---|
| {정본 ID} | {포함·제외 범위} | {소유한 규칙 ID 목록} | {정본 위치와 해당 절} | {부모 ID 또는 —} | {상태와 승인 근거} | {내용을 특정하는 버전} |

한 행은 한 정본의 현재 책임을 나타냅니다. 규칙 ID가 많으면 그 정본 안의 규칙 목록 절을 연결할 수
있지만, 어떤 ID를 소유하는지 확인할 수 있어야 합니다. 상속받은 규칙은 자식의 담당 규칙으로
중복 등록하지 않습니다. 외부 정본 ID는 소유 프로젝트와 등록대장을 함께 밝혀 충돌을 피합니다.

승인 상태는 기존 승인·미승인·미확인 상태를 그대로 구분하고 승인 근거를 연결합니다. 한 정본에
상태가 섞여 있으면 적용 범위별로 상태를 적습니다. 빈칸을 승인으로 해석하지 않습니다.
revision은 버전 번호·커밋·고정된 문서 버전 등 내용을 다시 특정할 수 있는 값을 씁니다.
`최신`이라는 말이나 수정 날짜만으로 여러 변경을 구분할 수 없다면 충분하지 않습니다.

### 3-2. 파생물 표

| 산출물 파일·링크 | source IDs | 반영 revision | 검수 상태 | artifact 역할 |
|---|---|---|---|---|
| {산출물 위치} | {참조 정본 ID 목록} | {각 ID별 반영 버전} | {미검수·검수 중·통과·불일치와 검수 기록} | {파생·제안/실험·동결} |

여러 정본을 함께 참조할 수 있습니다. 이때 각 정본의 담당 범위가 달라야 하며, ID별 반영 revision을
따로 적습니다. 부모에서 물려받은 규칙도 검수할 수 있도록 적용한 부모 정본 ID와 revision을
추적합니다. 일부만 반영했다면 그 범위와 미반영 내용을 기록하고 전체 검수 통과로 표시하지 않습니다.

artifact 역할은 이 등록대장에서 산출물을 어떻게 취급하는지 나타냅니다. 구조 설정의 `role`에
새 값을 추가하는 규약이 아닙니다. 검수 상태에는 확인한 범위·방법·결과를 연결하며, 코드 확인과
실제 실행 확인을 구분합니다. 파일이 생성됐다는 사실만으로 규칙 준수를 확인한 것은 아닙니다.

## 4. 파생물은 적용한 정본의 규칙을 지킵니다

같은 사양을 표현한 자료끼리 결론이 달라지지 않도록, 워크플로우·시뮬레이터·디자인·PPT 등은
적용한 정본의 공통 규칙과 개별 사양을 모두 따릅니다. 표현 매체에 맞춰 배치를 바꿀 수 있지만,
조건·분기·상태·순서·예외를 임의로 바꾸거나 생략해 다른 동작을 뜻하게 만들지 않습니다.

규칙 내용이 달라지는 변경은 다음 순서로 진행합니다. 정본의 의미를 유지하는 표현 수정이나
승인된 사양에 맞추는 구현 수정은 해당 입력 · 생성기 · 구현에서 처리하고 검수합니다. 이 경우
정본을 형식적으로 개정하거나 이미 받은 승인을 다시 요구하지 않습니다.

1. 바꿀 규칙 ID와 소유 정본을 찾고, 부모 규칙·위임 범위·승인 상태를 읽습니다.
2. 승인 범위에 맞게 정본을 먼저 고칩니다. 범위 밖의 판단이나 충돌은 제안하고 승인을 받습니다.
3. 정본 revision과 등록대장을 갱신하고 영향을 받는 파생물을 찾습니다.
4. 생성물은 정본이나 생성기를 고쳐 다시 만듭니다. 손으로 만드는 파생물도 같은 정본을 반영합니다.
5. 내용과 표현을 검수하고 파생물의 반영 revision·검수 상태를 갱신합니다.

정본을 바꾸기 전에 비교가 필요하면 제안·실험 자료로 분리합니다. 기준 정본과 revision, 실험한
차이, 미승인 상태를 표시하고 현행 파생물과 구분합니다. 실험이 잘 동작해도 자동으로 확정되지
않습니다. 승인된 변경을 정본에 반영한 다음 현행 파생물을 갱신합니다.

정본이 바뀌었는데 파생물이 아직 따라오지 못했다면 미반영 상태와 남은 작업을 기록합니다. 오래된
산출물의 검수 통과 표시는 새 revision의 통과를 뜻하지 않습니다. 동결한 배포본·검토본은 당시
revision을 유지하고 현행 자료와 구분합니다.

## 5. 공유본 편집과 정본 이전을 구분합니다

공유한 사본을 편집해도 원래의 결정 권한이 저절로 옮겨가지는 않습니다. 공유본의 변경은 먼저 제안으로
취급합니다. 복사·파일 이동·외부 서비스 업로드·이름 변경만으로 새 정본이 되지 않습니다.

정본을 옮겨야 할 때에는 다음 내용을 명시한 이전안을 승인받습니다.

- 기존 정본과 새 정본의 위치·ID, 이전할 책임 범위와 규칙 ID
- 기준 revision과 옮길 변경 내용, 승인 상태와 승인 근거
- 이전 적용 시점, 기존 자료의 동결·참조 처리, 소비 자료와 생성기의 참조 변경

승인 후에는 지정한 범위의 현행 소유가 하나가 되도록 등록대장과 참조를 함께 전환합니다. 기존
정본은 이전 사실과 새 위치를 가리키며, 보존해야 할 이력과 동결본을 지우지 않습니다. 이전 전후의
내용 차이와 파생물의 반영 상태를 확인합니다. 이전 승인이 내용 승인까지 뜻하는지는 별도로 밝히며,
미승인 내용을 파일 이전만으로 승인 상태로 올리지 않습니다.

## 6. 검사 범위와 현재의 한계

등록 형식만 맞아도 내용이 서로 모순될 수 있으므로, 작업 검수에서 다음을 사람이 확인합니다.

- 책임 범위와 규칙 ID의 현행 소유가 한 곳인지, 이름만 다른 중복 규칙이 없는지
- 정본·부모 참조가 존재하며 순환하지 않는지, 다른 프로젝트의 소유자를 확인할 수 있는지
- 자식이 부모 규칙을 따르는지, 다른 값을 정했다면 명시된 위임 안에 있는지
- 승인 근거와 revision을 확인할 수 있는지, 미확인 값을 확정값으로 취급하지 않았는지
- 파생물의 source IDs와 ID별 반영 revision이 맞는지, 조건·분기·상태·예외가 일치하는지
- 실험·미반영·동결 자료가 현행 검수 완료 자료와 구분되는지

현재 구조 검사기는 기존 자료 등록·경로·참조·생성 관계를 검사합니다. Markdown 등록대장의 소유
중복, 정본 상속, 위임 범위, 내용 일치까지 자동 검증하지 않습니다. 재생성 검사 통과도 의미상
일치나 실제 앱 실행을 보장하지 않습니다. 검수한 항목과 남은 확인을 기록하고 자동 검증 완료라고
보고하지 않습니다. 도구의 스키마와 자동 검사 확장은 별도 변경으로 다룹니다.

## 7. 기존 자료는 승인 상태를 보존하며 이행합니다

기존 문서의 정본 주장이 겹친다고 해서 최근 자료를 임의로 승격하면 과거 승인 근거가 사라집니다.
현재 사용하는 자료의 역할·책임 범위·승인 상태를 먼저 검토하고 등록대장에 정리합니다. 소유가
불분명하거나 내용이 충돌하면 해당 범위를 미확정으로 기록하고 결정 요청과 남은 작업으로 남깁니다.

검토가 끝나기 전에는 구현·시뮬레이터·기획서에서 발견한 값을 확정 사양으로 역수입하지 않습니다.
기존 자료를 새 위치에 등록하는 일과 내용을 승인하는 일을 구분합니다. 이미 동결한 자료는 당시
내용과 revision을 보존하고 현행 소유로 중복 등록하지 않습니다.

보관 자료를 일괄 열어 현재 규칙을 채우지 않습니다. 보관 자료는 기존 읽기 게이트에 따라 특정
이력 확인이 필요할 때만 읽습니다. 이번 이행으로 승인 상태를 덮어쓰거나 보관본을 다시 만드는
것은 요구하지 않습니다. 충돌이 해소된 범위부터 정본 참조와 파생물 반영을 완료하고 검수합니다.

## 8. 분야별 모듈은 공통 규칙을 참조하고 검수를 구체화합니다

소유 · 상속 · 승인 · 개정 · 정본 이전은 이 문서가 결정합니다. 모듈은 이를 복사해 별도 규칙으로
정의하지 않고 해당 절을 참조합니다. 분야별 작성 항목과 표현 방법, 확인할 지점만 추가합니다.
공통 규칙에 없는 예외를 모듈에서 임의로 만들지 않으며, 충돌은 `rule-conflict.md`로 처리합니다.

관련 모듈의 읽기 게이트에는 이 문서와 프로젝트 등록대장 · 해당 책임 정본을 연결합니다. 구현이나
자료 수집을 위한 모듈도 정본의 승인 상태를 따릅니다. 분야별 작성 모듈을 켜지 않았다는 이유로
공통 정본 관리 규칙을 면제하지 않습니다. base는 특정 모듈을 전제로 삼지 않습니다.

검수는 소유 정본 ID · 규칙 ID → 적용한 파생물과 지점 → 반영 revision → 검수 기록으로
추적합니다. 등록대장이나 기존 검수 기록을 참조하며 같은 상태를 별도 표마다 복제하지 않습니다.
검수 기록은 승인된 규칙에 따른 기대 결과와 실제 결과를 구분합니다. 현재 구현의 출력이나
테스트용 데이터만으로 기대 결과를 정하지 않습니다. 미반영 · 미검수 처리는 「파생물은 적용한 정본의 규칙을 지킵니다」를 따릅니다.

모듈은 이 연결에 분야별 식별자와 확인 항목을 더할 수 있습니다. 도구가 확인하는 항목과 사람이
대조하는 항목을 구분하여 보고하며, 의미상 일치의 검수 한계는 「검사 범위와 현재의 한계」을 따릅니다.
