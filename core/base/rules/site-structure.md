# site-structure — 무엇을 어디에 두고, 중앙과 프로젝트를 어떻게 가르는가

어떤 파일이 어느 자리에 놓이고 누가 그것을 만드는지를 정합니다. 자리를 정하지 않으면 같은 성격의
문서가 흩어지고, 만드는 주체를 정하지 않으면 손으로 고친 파일과 다시 만든 파일이 갈라집니다.
한 장을 어떻게 내보내는가는 `html-output.md`가, 문서 하나를 만드는 절차는 `../doc-playbook.md`가
담습니다. 이 문서는 **배치**만 정합니다.

---

## 1. 중앙 규칙과 프로젝트 규칙

폴더를 가르는 **첫 번째 축**입니다. 어느 쪽에 두는지가 「바뀌면 무엇이 함께 흔들리는가」를 정합니다.

| 갈래 | 자리 | 무엇이 사나 | 바뀌면 |
|---|---|---|---|
| **중앙 규칙** | `core/` (정본은 중앙 저장소) | 모든 프로젝트가 따르는 절차 · 판단 기준 · 형식 · 도구 | 모든 저장소 · 프로젝트에 영향을 줍니다. 그래서 **직접 수정을 요청받지 않는 한 바뀌지 않고**, 중앙 저장소에서만 고칩니다 |
| **프로젝트 규칙** | 프로젝트 폴더 | 그 프로젝트 안에서만 유효한 조사 · 판단 · 확정 사양 · 산출물 | 그 프로젝트만 흔들립니다 |

판별 기준은 **「문장에서 프로젝트 이름을 지워도 성립하는가」**입니다. 성립하면 중앙, 아니면
프로젝트입니다. 용어집 배치와 같은 기준을 쓰는 이유는, 규칙과 용어가 다른 기준으로 놓이면
「이것은 어디 것인가」를 매번 다시 판단해야 하기 때문입니다.

프로젝트 규칙에서 중앙 규칙과 어긋나는 것이 나오면 **한쪽을 임의로 맞추지 않습니다.** 어긋난
지점을 올리고 두 갈래를 사용자에게 되묻습니다 — ① 이 프로젝트의 예외로 둘 것인가, ② 중앙 규칙을
고칠 것인가. 어느 쪽으로 정했는지가 남아야 다음 프로젝트가 그 판단을 물려받습니다.

### 1-1. core 안의 두 번째 축 — base와 modules

| 갈래 | 자리 | 판별 | 참조 |
|---|---|---|---|
| **base** | `core/base/` — 절차서 · 용어집 · `rules/` · `scripts/` · `design-guide/` · `design-template/` | 안 켜면 워크스페이스 자체가 성립하지 않는 것 — 절차 · 문체 · 작성 원칙 · 배치 · 이력 · git · HTML 출력 · 기본 디자인 | 항상 |
| **modules** | `core/modules/{모듈}/` | 프로젝트나 저장소가 골라 켜는 규칙 · 서식 · 도구, 또는 컴퓨터 공통 환경 | **기본 금지.** 켰을 때만(`feature-request.md` §3) |

판별 문장은 **「이 규칙을 안 켠 프로젝트가 있을 수 있는가」**입니다. 있을 수 있으면 모듈입니다.

**모듈은 base 위에서만 돌고, base가 모듈을 부르는 반대 방향은 두지 않습니다.** base 문서는 모듈
이름이나 모듈 안의 파일을 적지 않습니다 — 적는 순간 `core/base/`만 떼어냈을 때 없는 파일을
가리키게 됩니다. base는 「켠 모듈이 이것을 정하면 그것을 따른다」처럼 **자리만** 정해 둡니다.
`check_rules.py`의 경로 검사가 이것을 봅니다. 모듈끼리는 전제할 수 있습니다.

## 2. 중앙 규칙에는 프로젝트를 적지 않습니다

중앙 규칙 안에 프로젝트 이야기가 한 자리라도 남으면 그 폴더는 다른 저장소로 그냥 옮길 수 없게
됩니다. 옮길 때마다 안을 뒤져야 하고, 놓친 자리는 에러 없이 옛 프로젝트를 가리킵니다.

| 갈래 | 어디에 두나 | 무엇이 막나 |
|---|---|---|
| 저장소 · 프로젝트 **이름** | 루트 `workspace.json` · 폴더 이름 | `check_rules.py` ④ · 사람 |
| 그 프로젝트의 **값** (임계 · 상태 목록 …) | 프로젝트의 입력 파일 · change-log 현행 기준 | 사람 |
| 규칙 예시에 쓰는 고유명사 · 실제 수치 | 자리 표시자(`{프로젝트}`)로 씁니다 | 사람 |
| **산출물** | 프로젝트 폴더 | 자리 |
| 모듈이 가리키는 파일 | 그 모듈 안 | `check_rules.py` ⑦ |

## 3. 저장소 이름표 — `workspace.json`

저장소마다 달라지는 값은 전부 루트의 `workspace.json` 한 곳에 둡니다. 도구는 위로 거슬러
올라가며 이 파일이 있는 폴더를 찾고, 그 폴더가 저장소 루트입니다.

```json
{
  "name": "저장소 이름",
  "subtitle": "한 줄 설명",
  "repo": "https://github.com/…",
  "visibility": "private",
  "project_roots": ["projects"],
  "modules": []
}
```

| 항목 | 필수 | 뜻 |
|---|---|---|
| `name` · `subtitle` · `repo` | 예 | 저장소 이름 · 부제 · 원격 주소 |
| `visibility` | 아니오 (기본 `public`) | 저작권 게이트의 강도(`git-rules.md` §1) |
| `project_roots` | 아니오 (기본 `["projects"]`) | 프로젝트를 찾을 자리. 첫 항목이 새 프로젝트가 생기는 자리입니다 |
| `modules` | 아니오 (기본 `[]`) | 저장소 전체에 켠 워크스페이스 모듈 |

**프로젝트 목록은 어디에도 적지 않습니다.** 적어 두면 폴더를 만들 때마다 두 곳을 고쳐야 하고,
한쪽만 고치면 어긋납니다. 그래서 **`{폴더}-modules.json`이 있는 폴더를 두는 것이 곧 등록**입니다.
`project_roots`는 목록이 아니라 **찾을 자리**입니다 — 옮기지 않고 등록한 옛 폴더가 있을 때만
기본값과 달라집니다(`project-scaffold.md` §5). 그 밖의 항목은 두지 않습니다 — `check_rules.py`가
모르는 항목을 잡습니다.

프로젝트별 표시 이름 · 파일 접두 · 관리 파일 이름은 그 프로젝트 폴더의 `{폴더}-site.json`에
둡니다. 없는 것이 기본입니다.

## 4. 프로젝트 내부 구조

중앙은 정본의 단일성 · 자료 소유 · 승인 상태 · 출처를 정하고, 내부 폴더의 이름과 계층은 프로젝트가
정할 수 있습니다. `project-scaffold.md`의 기본 구조는 설정이 없는 프로젝트의 기본안입니다.

구조 설정은 프로젝트 루트의 `{폴더}-structure.json`이며 `../scripts/project_structure.py`가 해석합니다.

| 항목 | 규약 |
|---|---|
| `schema_version` | 현재 1입니다. 알 수 없는 버전이나 항목은 오류입니다 |
| `resources` | id · label · path · role · kind. kind는 file 또는 directory입니다 |
| `parent` | 문서 탐색의 상위 자료 식별자 — 의존 관계와 구분합니다 |
| `depends_on` | 소비하는 자료 식별자 목록. 없는 참조와 순환을 허용하지 않습니다 |
| `jobs` | label · script · inputs · outputs — 프로젝트 안의 생성기와 입출력 |

자료 역할은 specification · policy · workflow · implementation · evidence · reference · archive ·
output · tool · navigation입니다. **역할과 승인 상태는 별개입니다** — 폴더를 옮겨도 초안이 승인된
사양이 되지 않습니다. archive 역할은 기본 참조에서 빠지고, reference · evidence 역할은 이름과
무관하게 저작권 검사 대상입니다. implementation · tool · output 역할의 기존 파일 수정은 저작권
게이트가 건너뜁니다(`git-rules.md` §5-1).

경로는 프로젝트 안의 상대 POSIX 경로로 제한합니다. 다른 프로젝트의 자료는 그 프로젝트가 소유하고,
구조 설정으로 남의 파일을 소유하지 않습니다. 설정이 잘못되면 도구는 오류로 멈춥니다 — 등록한
자료를 못 찾았다고 기본 자리를 조용히 쓰지 않습니다.

## 5. 탐색 층과 산출물

| 층 | 자리 | 무엇 | 누가 만드나 |
|---|---|---|---|
| **탐색** | 허브 · 용어집 · (켠 모듈이 만드는) 진입 페이지와 셸 | 문서 사이의 이동 · 목록 · 용어 | 손으로 또는 생성기로 — 그 층을 정한 프로젝트 · 모듈이 정합니다 |
| **산출물** | 프로젝트 폴더 안 | 설명 · 분석 · 설계 문서, 시트, 리포트 | 작성 절차 또는 생성기 |

- **자리는 소유가 정합니다.** 프로젝트에 속한 것은 하나도 빠짐없이 그 프로젝트 폴더 안에 둡니다.
  밖에 두면 프로젝트를 옮기거나 중앙 규칙을 떼어낼 때 섞입니다.
- 문서 사이의 이동은 탐색 층만 맡습니다(`html-output.md` §5).
- 허브가 여러 개면(지식 위키 허브 · 프로젝트 허브 등) 상위 허브에는 하위 허브로 가는 행 하나만
  두고, 개별 문서는 하위 허브가 관리합니다. 어느 허브가 무엇을 싣는지는 켠 모듈이 정합니다.

## 6. 파생물은 직접 고치지 않습니다

생성기가 만드는 파일은 파생물입니다. 화면에서 고치고 싶은 것이 생기면 정본이나 생성기를 고치고
다시 만듭니다. 파생물을 직접 고치면 다음 재생성에서 조용히 사라집니다. 무엇이 정본이고 무엇이
파생인지는 프로젝트 change-log의 현행 기준이 정합니다. 다시 만들기는 한 명령입니다.

```bash
python core/base/scripts/regen.py            # 다시 만듭니다
python core/base/scripts/regen.py --check    # 낡은 것만 봅니다
```

`regen.py`는 base가 만드는 것(읽기 게이트)과 프로젝트 구조 설정의 작업, 그리고 **켠 모듈이
`jobs.py`로 알려 준 것**을 돌립니다. base는 모듈 이름을 모르고 켠 모듈의 `jobs.py`를 훑기만 합니다.

## 7. 용어집 배치

- 워크스페이스 전반의 용어 → 중앙 `../dictionary.md` (색인이며 정의 정본은 `rules/`)
- 모듈의 용어 → 그 모듈의 `{모듈}-dictionary.md` 또는 `module.md`
- 프로젝트 고유명사 → 프로젝트의 dictionary 또는 그 프로젝트 허브의 용어집

배치 기준은 **「정의 문장에서 프로젝트 이름을 지워도 성립하는가」**입니다. 용어집은 정의를 새로
쓰지 않습니다 — 용어 · 한 줄 요약 · 정의가 사는 자리만 적습니다. 정의가 두 곳에 있으면 한쪽만
고쳐졌을 때 어느 쪽이 맞는지 알 수 없습니다.
