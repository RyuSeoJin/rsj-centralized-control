어떤 파일이 어느 자리에 놓이고 누가 그것을 만드는지를 정합니다. 자리를 정하지 않으면 같은 성격의
문서가 흩어지고, 만드는 주체를 정하지 않으면 손으로 고친 파일과 다시 만든 파일이 갈라집니다.
한 장을 어떻게 내보내는가는 `html-output.md`가, 문서 하나를 만드는 절차는 `../doc-playbook.md`가
담습니다. 이 문서는 **배치**만 정합니다.

---

## 1. 중앙 규칙과 프로젝트 규칙

폴더를 가르는 **첫 번째 축**입니다. 어느 쪽에 두는지가 「바뀌면 무엇이 함께 흔들리는가」를 정합니다.

| 갈래 | 자리 | 무엇이 사나 | 바뀌면 |
|---|---|---|---|
| **중앙 규칙** | `core/` (정본은 중앙 저장소) | 모든 프로젝트가 따르는 절차 · 판단 기준 · 형식 · 도구 | 모든 저장소 · 프로젝트에 영향을 줍니다. 그래서 **직접 수정을 요청받지 않는 한 바뀌지 않고**, 중앙 저장소에서만 고칩니다 |
| **프로젝트 규칙** | 프로젝트 폴더 | 그 프로젝트 안에서만 유효한 조사 · 판단 · 확정 사양 · 산출물 | 그 프로젝트만 흔들립니다 |

판별 기준은 **「문장에서 프로젝트 이름을 지워도 성립하는가」**입니다. 성립하면 중앙, 아니면
프로젝트입니다. 용어집 배치와 같은 기준을 쓰는 이유는, 규칙과 용어가 다른 기준으로 놓이면
「이것은 어디 것인가」를 매번 다시 판단해야 하기 때문입니다.

프로젝트 규칙에서 중앙 규칙과 어긋나는 것이 나오면 **한쪽을 임의로 맞추지 않습니다.** 어긋난
지점을 올리고 두 갈래를 사용자에게 되묻습니다 — ① 이 프로젝트의 예외로 둘 것인가, ② 중앙 규칙을
고칠 것인가. 어느 쪽으로 정했는지가 남아야 다음 프로젝트가 그 판단을 물려받습니다.

### 1-1. core 안의 두 번째 축 — base와 modules

| 갈래 | 자리 | 판별 | 참조 |
|---|---|---|---|
| **base** | `core/base/` — 절차서 · 용어집 · `rules/` · `scripts/` · `design-guide/` · `design-template/` | 안 켜면 워크스페이스 자체가 성립하지 않는 것 — 절차 · 문체 · 작성 원칙 · 배치 · 이력 · git · HTML 출력 · 기본 디자인 | 항상 |
| **modules** | `core/modules/{모듈}/` | 프로젝트나 저장소가 골라 켜는 규칙 · 서식 · 도구, 또는 컴퓨터 공통 환경 | **기본 금지.** 켰을 때만(`feature-request.md` 「모듈의 모양」) |

판별 문장은 **「이 규칙을 안 켠 프로젝트가 있을 수 있는가」**입니다. 있을 수 있으면 모듈입니다.

**모듈은 base 위에서만 돌고, base가 모듈을 부르는 반대 방향은 두지 않습니다.** base 문서는 모듈
이름이나 모듈 안의 파일을 적지 않습니다 — 적는 순간 `core/base/`만 떼어냈을 때 없는 파일을
가리키게 됩니다. base는 「켠 모듈이 이것을 정하면 그것을 따른다」처럼 **자리만** 정해 둡니다.
`check_rules.py`의 경로 검사가 이것을 봅니다. 모듈끼리는 전제할 수 있습니다.

## 2. 중앙 규칙에는 프로젝트를 적지 않습니다

중앙 규칙 안에 프로젝트 이야기가 한 자리라도 남으면 그 폴더는 다른 저장소로 그냥 옮길 수 없게
됩니다. 옮길 때마다 안을 뒤져야 하고, 놓친 자리는 에러 없이 옛 프로젝트를 가리킵니다.

| 갈래 | 어디에 두나 | 무엇이 막나 |
|---|---|---|
| 저장소 · 프로젝트 **이름** | 루트 `workspace.json` · 폴더 이름 | `check_rules.py` ④ · 사람 |
| 그 프로젝트의 **값** (임계 · 상태 목록 …) | 프로젝트의 입력 파일 · change-log 현행 기준 | 사람 |
| 규칙 예시에 쓰는 고유명사 · 실제 수치 | 자리 표시자(`{프로젝트}`)로 씁니다 | 사람 |
| **산출물** | 프로젝트 폴더 | 자리 |
| 모듈이 가리키는 파일 | 그 모듈 안 | `check_rules.py` ⑦ |

## 3. 저장소 이름표 — `workspace.json`

저장소마다 달라지는 값은 전부 루트의 `workspace.json` 한 곳에 둡니다. 도구는 위로 거슬러
올라가며 이 파일이 있는 폴더를 찾고, 그 폴더가 저장소 루트입니다.

```json
{
  "name": "저장소 이름",
  "subtitle": "한 줄 설명",
  "repo": "https://github.com/…",
  "visibility": "private",
  "project_roots": ["projects"],
  "modules": []
}
```

| 항목 | 필수 | 뜻 |
|---|---|---|
| `name` · `subtitle` · `repo` | 예 | 저장소 이름 · 부제 · 원격 주소 |
| `visibility` | 아니오 (기본 `public`) | 저작권 게이트의 강도(`git-rules.md` 「원칙」) |
| `project_roots` | 아니오 (기본 `["projects"]`) | 프로젝트를 찾을 자리. 첫 항목이 새 프로젝트가 생기는 자리입니다 |
| `modules` | 아니오 (기본 `[]`) | 저장소 전체에 켠 워크스페이스 모듈 |

**프로젝트 목록은 어디에도 적지 않습니다.** 적어 두면 폴더를 만들 때마다 두 곳을 고쳐야 하고,
한쪽만 고치면 어긋납니다. 그래서 **`{폴더}-modules.json`이 있는 폴더를 두는 것이 곧 등록**입니다.
`project_roots`는 목록이 아니라 **찾을 자리**입니다 — 옮기지 않고 등록한 옛 폴더가 있을 때만
기본값과 달라집니다(`project-scaffold.md` 「옛 프로젝트 등록 — 옮기지 않고」). 그 밖의 항목은 두지 않습니다 — `check_rules.py`가
모르는 항목을 잡습니다.

프로젝트별 표시 이름 · 파일 접두 · 관리 파일 이름은 그 프로젝트 폴더의 `{폴더}-site.json`에
둡니다. 없는 것이 기본입니다.

## 4. 프로젝트 내부 구조

중앙은 정본의 단일성 · 자료 소유 · 승인 상태 · 출처를 정하고, 내부 폴더의 이름과 계층은 프로젝트가
정할 수 있습니다. 책임 범위별 유일 정본과 부모 관계는 `canonical-source.md`가 정합니다.
`project-scaffold.md`의 기본 구조는 설정이 없는 프로젝트의 기본안입니다.

구조 설정은 프로젝트 루트의 `{폴더}-structure.json`이며 `../scripts/project_structure.py`가 해석합니다.

| 항목 | 규약 |
|---|---|
| `schema_version` | 현재 1입니다. 알 수 없는 버전이나 항목은 오류입니다 |
| `resources` | id · label · path · role · kind. kind는 file 또는 directory입니다 |
| `parent` | 문서 탐색의 상위 자료 식별자 — 정본 상속 관계가 아닙니다 |
| `depends_on` | 소비하는 자료 식별자 목록. 없는 참조와 순환을 허용하지 않습니다. 규칙 소유권이나 승인 상태를 정하지 않습니다 |
| `jobs` | label · script · inputs · outputs — 프로젝트 안의 생성기와 입출력 |

자료 역할은 specification · policy · workflow · implementation · evidence · reference · archive ·
output · tool · navigation입니다. **역할과 승인 상태는 별개입니다** — 폴더를 옮겨도 초안이 승인된
사양이 되지 않습니다. archive 역할은 기본 참조에서 빠지고, reference · evidence 역할은 이름과
무관하게 저작권 검사 대상입니다. implementation · tool · output 역할의 기존 파일 수정은 저작권
게이트가 건너뜁니다(`git-rules.md` 「커밋 전 — 이번 커밋에 들어갈 것」).

경로는 프로젝트 안의 상대 POSIX 경로로 제한합니다. 다른 프로젝트의 자료는 그 프로젝트가 소유하고,
구조 설정으로 남의 파일을 소유하지 않습니다. 설정이 잘못되면 도구는 오류로 멈춥니다 — 등록한
자료를 못 찾았다고 기본 자리를 조용히 쓰지 않습니다.

프로젝트의 `canonical-registry.md`는 기존 resources 형식으로 `role: policy` · `kind: file`에
등록합니다. 구조 설정이 없으면 프로젝트 루트에 두고 change-log 현행 기준에서 가리킵니다.
정본 소유와 상속은 이 등록대장이 맡으므로 구조 설정에 별도 정본 필드를 임의로 더하지 않습니다.

### 4-1. 증거 자료는 원문 그대로 보관합니다

evidence 역할은 측정 보고서 · 외부 시스템의 기록처럼 **「그때 무엇이 관찰되었나」**를 보여 주는
자료입니다. 확정 사양이 아니므로 그 수치를 곧바로 기대값 · 합격선 · 완료 판정으로 쓰지 않습니다.
기대값은 승인된 정본에서 가져옵니다. 증거는 나중에 「원래 무엇이라고 적혀 있었나」를 되짚는 데
쓰이므로, 보관하면서 한 글자라도 바뀌면 증거로서의 가치를 잃습니다.

1. **원문 전체를 Markdown 인용 블록으로 담습니다.** 각 줄 앞의 인용 표시(`> `, 빈 줄은 `>`) 말고는
   고치지 않습니다. 원문의 문체는 `doc-write-style.md` 「인용 · 원문 발췌」 예외이고, 새로 쓰는 머리말은
   문체 규칙을 따릅니다.
2. **인용 블록 위 머리말에 적습니다** — 출처 경로나 주소, 원문이 만들어진 시점(측정일 등), 보관 시각과
   시간대, 원문의 SHA-256, 원문의 줄바꿈 방식(LF · CRLF), 보관 범위(함께 복사한 자료 · 복사하지 않은 자료).
3. **보관 직후 해시를 확인합니다.** 인용 표시를 벗기고 원문의 줄바꿈 방식으로 되돌린 본문의 SHA-256이
   머리말의 원문 해시와 같아야 합니다. 다르면 보관을 완료로 보고하지 않습니다.
4. **정정은 원문에서 시작합니다.** 원 보고서를 먼저 고친 뒤 보관본 · 원문 해시 · 보관 시각을 갱신하고,
   이유를 프로젝트 이력에 남깁니다. 보관본만 고치지 않습니다.
5. **다시 측정하거나 다시 실행한 결과는 새 보관본으로 둡니다.** 기존 보관본을 덮어쓰지 않고, 파일 이름에
   시점과 실행 구별자를 붙여 가릅니다.
6. **복사하지 않은 연결 자료는 「보관」으로 표시하지 않습니다.** 원문의 근거 링크는 그대로 두되, 로컬
   경로라는 사실과 보관하지 않았다는 사실을 머리말에 적습니다. 다른 보관본은 머리말에 상대 링크로 잇습니다.
7. **인증 정보나 사용자 데이터가 든 원자료(원시 로그 · 캐시 데이터베이스 등)는 복사하지 않습니다.** 용량이
   큰 원자료(추적 파일 · 빌드 산출물 · 영상)는 따로 요청받은 범위에서만 검토합니다.

측정 조건을 어떻게 기록하고 조건이 다른 결과를 어떻게 비교하는지는 켠 모듈이 정하면 그것을 따릅니다.

## 5. 탐색 층과 산출물

| 층 | 자리 | 무엇 | 누가 만드나 |
|---|---|---|---|
| **탐색** | 허브 · 용어집 · (켠 모듈이 만드는) 진입 페이지와 셸 | 문서 사이의 이동 · 목록 · 용어 | 손으로 또는 생성기로 — 그 층을 정한 프로젝트 · 모듈이 정합니다 |
| **산출물** | 프로젝트 폴더 안 | 설명 · 분석 · 설계 문서, 시트, 리포트 | 작성 절차 또는 생성기 |

- **자리는 소유가 정합니다.** 프로젝트에 속한 것은 하나도 빠짐없이 그 프로젝트 폴더 안에 둡니다.
  밖에 두면 프로젝트를 옮기거나 중앙 규칙을 떼어낼 때 섞입니다.
- 문서 사이의 이동은 탐색 층만 맡습니다(`html-output.md` 「링크 — 문서 사이 이동은 탐색 층이 맡습니다」).
- 허브가 여러 개면(지식 위키 허브 · 프로젝트 허브 등) 상위 허브에는 하위 허브로 가는 행 하나만
  두고, 개별 문서는 하위 허브가 관리합니다. 어느 허브가 무엇을 싣는지는 켠 모듈이 정합니다.

### 5-1. 프로젝트 안에서 완결합니다

외부 도구의 계정이나 링크 상태가 작업을 막지 않도록, 프로젝트는 **자기 폴더의 파일만으로 이해 · 수정 ·
재생성 · 실행 · 검증할 수 있는 상태**를 목표로 합니다.

- **외부 도구는 출처 이력입니다.** 디자인 도구 · 화이트보드 · 외부 AI 작업 공간은 내용이 처음 정해진
  자리일 수 있지만, 구현하는 사람이 매번 열어 봐야 하는 사양 저장소로 쓰지 않습니다. 확정된 내용은
  프로젝트의 정본에 옮겨 적습니다.
- **완료 조건** — 외부 도구에 로그인하지 않은 사람이 전달받은 파일만으로 화면과 규칙을 이해하고, 같은
  산출물을 다시 만들고, 체험을 실행하고, 검증할 수 있어야 합니다.
- **원본 확정과 로컬 전사 완료는 다릅니다.** 외부 도구에서 확정된 내용이라도, 프로젝트 정본에 옮겨 적고
  원본과 대조를 마치기 전에는 「이관 완료」로 표시하지 않습니다. 대조 전에 옮겨 온 기존 표는 기존
  기록으로 구별합니다.
- **외부 서비스 연동은 따로 셉니다.** 실제 인증 · 서버 통신은 서비스 연동이며, 완결이 모든 서비스의
  무통신 실행을 뜻하지는 않습니다. 대신 연동 계약과 로컬 모의 동작을 함께 정의합니다.
- **전달할 때는 생성기 · 공통 부품 · 라이선스 · 런타임 의존성 · 실행 명령을 함께 넣고 새 환경에서 재현해
  봅니다.** 재현해 보지 않았으면 그 사실을 적습니다(`completion-evidence.md`).
- **지금 어디까지 완결인지 정직하게 적습니다.** 프로젝트의 생성기가 `core/`의 공통 도구를 부르는 동안에는
  프로젝트 폴더만 복사해서는 다시 만들 수 없습니다. 그 상태라면 「프로젝트 폴더 단독 전달은 완결이
  아님」을 프로젝트 소개나 change-log 「현행 기준」에 적고, 의존성 묶음 작업을 남은 작업에 올립니다.

## 6. 파생물은 정본을 따릅니다

파생물은 생성된 파일뿐 아니라 정본에 따라 손으로 만든 화면 · 구현 · 설명 자료도 포함합니다.
기준은 `canonical-registry.md`의 책임 정본과 부모 정본이며, change-log 현행 기준은 등록대장을
가리킵니다. 표현 형식이 달라도 승인된 동작과 조건을 바꾸지 않습니다(`canonical-source.md`).

생성기가 만드는 파일은 직접 고치지 않습니다. 정본이나 생성기를 고치고 다시 만듭니다. 직접
수정하면 다음 생성에서 사라지기 때문입니다. 손으로 관리하는 파생물은 정본에 맞춰 수정할 수
있으며, 새로운 동작은 정본 변경 절차를 먼저 거칩니다. 반영 후 기준 개정과 검증 결과를 남깁니다.
자동 재생성 대상은 다음 명령으로 다시 만듭니다.

```bash
python core/base/scripts/regen.py            # 다시 만듭니다
python core/base/scripts/regen.py --check    # 낡은 것만 봅니다
```

`regen.py`는 base가 만드는 것(읽기 게이트)과 프로젝트 구조 설정의 작업, 그리고 **켠 모듈이
`jobs.py`로 알려 준 것**을 돌립니다. base는 모듈 이름을 모르고 켠 모듈의 `jobs.py`를 훑기만 합니다.

## 7. 용어집 배치

- 워크스페이스 전반의 용어 → 중앙 `../dictionary.md` (색인이며 정의 정본은 `rules/`)
- 모듈의 용어 → 그 모듈의 `{모듈}-dictionary.md` 또는 `module.md`
- 프로젝트 고유명사 → 프로젝트의 dictionary 또는 그 프로젝트 허브의 용어집

배치 기준은 **「정의 문장에서 프로젝트 이름을 지워도 성립하는가」**입니다. 용어집은 정의를 새로
쓰지 않습니다 — 용어 · 한 줄 요약 · 정의가 사는 자리만 적습니다. 정의가 두 곳에 있으면 한쪽만
고쳐졌을 때 어느 쪽이 맞는지 알 수 없습니다.

## 8. 프로젝트 묶음 — 한 제품의 여러 업무 프로젝트

한 제품을 여러 업무(기획 · 그래픽 · 검증 등)가 나눠 맡으면, 업무마다 프로젝트를 두고 제품 폴더 아래에
묶습니다(`{프로젝트 자리}/{제품}/{업무}/`, `project-scaffold.md` 「기본 구조」). **제품 폴더는 프로젝트가
아니라 묶음입니다.** 그래서 제품 폴더에는 `{제품}-modules.json`을 두지 않습니다 — 두면 도구가 제품 폴더를
프로젝트로 등록하고, 그 아래 업무 프로젝트를 찾지 못합니다.

### 8-1. 묶음이 갖는 것

- 제품 공통 이력(change-log · remaining-work)과 묶음 소개(readme)
- 업무 사이의 수정 책임 경계 — 어느 업무가 어떤 범위의 정본을 소유하는지. 정본 소유 자체는 각 업무의
  등록대장이 정합니다(`canonical-source.md`)
- 여러 업무가 함께 쓰는 공통 화면(허브 셸 등)과 그 생성기
- 제품 공통 모듈 설정(「제품 공통 모듈 설정 — 업무별 설정과 합집합」)

업무 프로젝트의 자료는 그 업무 폴더가 소유합니다. 묶음이 업무의 파일을 고쳐 쓰지 않고, 업무끼리도
서로의 파일을 소유하지 않습니다(「프로젝트 내부 구조」).

### 8-2. 제품 공통 모듈 설정 — 업무별 설정과 합집합

여러 업무가 같은 모듈을 쓰면 업무마다 켜지 않고 제품 폴더의 `{제품}-module-config.json`(형식은
`{"on": [모듈 이름 …]}`)에 한 번만 켭니다. 업무 하나가 쓸 수 있는 모듈은 다음의 합집합입니다.

> 저장소 모듈(`workspace.json`의 `modules`) ∪ 제품 공통 설정의 `on` ∪ 그 업무의 `{업무}-modules.json`의 `on`

- **같은 모듈을 제품 설정과 업무 설정에 함께 적지 않습니다.** 두 곳에 있으면 한쪽만 끄고 꺼졌다고 믿게
  됩니다.
- **다른 제품의 설정은 상속하지 않습니다.** 합집합은 자기 제품 폴더의 설정만 더합니다.
- **쓸 수 있는 것과 화면에 넣는 것은 별개입니다.** 공통 설정에 켜도 각 업무가 실제로 고른 산출물에만
  들어갑니다.
- **공통 설정 변경은 제품 전체에 영향을 줍니다.** 사용자 승인 뒤에 고치고, 생성 검사를 돌립니다.
- 제품 설정에는 프로젝트 범위(`scope: project`)의 모듈만 둡니다. 저장소 전체에 켜는 모듈은
  `workspace.json`에 둡니다(`feature-request.md` 「모듈의 모양」).

### 8-3. 업무별 허브와 통합 허브

- 각 업무의 허브 설정을 모아 **통합 허브**와 **업무별 허브**를 만들 수 있습니다. 업무별 허브는 자기 탭과
  자기 검색만 담고, 다른 업무의 문서는 검색 결과 · 미리보기에 보이지 않습니다.
- **화면 분리는 접근 통제가 아닙니다.** 같은 배포에 들어 있으면 누구나 열 수 있습니다. 비공개가 필요하면
  배포 단위를 나눕니다.
- 허브를 만드는 방식(설정 형식 · 탭 구성 · 검색)은 켠 모듈이 정합니다.

### 8-4. 현재 도구 지원 범위

| 기능 | 지원 |
|---|---|
| 제품/업무 두 단 경로로 프로젝트 만들기 · 찾기 | 지원합니다 — `../scripts/new_project.py` · `../scripts/project_paths.py` |
| 업무 프로젝트 안에 다른 업무 프로젝트 만들기 막기 | 지원합니다 — `../scripts/new_project.py` |
| 제품 공통 모듈 설정 읽기 | **지원하지 않습니다.** `../scripts/module.py`(켜기 · 끄기 · 목록 · 전제 검사)와 `../scripts/regen.py`(켠 모듈의 생성 작업)는 업무의 `{업무}-modules.json`과 `workspace.json`의 `modules`만 읽습니다 |
| 제품 설정과 업무 설정의 중복 검사 | 지원하지 않습니다 |
| 작업자가 읽을 모듈 고르기 | 지원합니다 — `read-gates.md` 「경로별 참조 규칙」이 제품 공통 설정에 켠 모듈도 그 제품의 업무에서 읽게 합니다 |
| 통합 · 업무별 허브 생성 | 중앙 도구가 없습니다 |

그래서 지금 제품 공통 모듈 설정을 쓰면 다음을 감수합니다.

- 합집합은 **제품의 생성기가 직접 계산합니다.** 중앙 도구는 제품 설정에 켠 모듈을 모르므로, 그 모듈의
  생성 작업(`jobs.py`)은 `regen.py`로 돌지 않고 제품 생성기가 돌립니다.
- 제품 설정에만 켠 모듈을 전제로 하는 모듈을 업무에서 켜려 하면 `module.py on`이 전제가 꺼져 있다고
  멈춥니다. 이때 전제 모듈을 업무 설정으로 옮길지 사용자에게 묻습니다.
- 제품 설정의 변경과 처리 결과를 제품 change-log에 적습니다. 도구 지원은 중앙 남은 작업입니다.
