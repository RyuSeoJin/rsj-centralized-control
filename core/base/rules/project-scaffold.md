# project-scaffold — 새 프로젝트가 무엇을 갖고 시작하는가

프로젝트마다 자리가 다르면 「어디를 보면 되는가」를 매번 다시 찾아야 합니다. 그래서 시작 모양을
하나로 고정하고, 손이 아니라 도구가 찍습니다 — `core/base/scripts/new_project.py`.

```bash
python core/base/scripts/new_project.py {슬러그}
```

---

## 1. 반드시 갖는 것

```
projects/{슬러그}/
├─ {슬러그}-change-log.md         무언가 변경될 때 쓰는 로그
├─ {슬러그}-remaining-work.md     이후 작업할 것을 정리해 두는 자리
├─ {슬러그}-dictionary.md         이 프로젝트를 이해하는 데 필요한 용어 사전
├─ {슬러그}-modules.json          어느 모듈을 켰는가 (처음에는 비어 있습니다)
├─ spec/
│   ├─ design/                    확정 사양
│   ├─ rationale/                 판단 근거
│   └─ archive/                   지나간 것
├─ test-case/
├─ analysis/
├─ reference/
├─ rules/                         이 프로젝트에서만 통하는 규칙이 자라는 자리
└─ docs/                          읽는 HTML이 놓이는 자리 (파생물)
```

**모듈을 켰든 안 켰든 이 모양으로 시작합니다.** 자리를 조건부로 만들면 「이 프로젝트에는 왜
없지」를 매번 확인해야 하고, 나중에 켤 때 자리를 새로 정하게 됩니다. 빈 폴더는 `.gitkeep`으로
자리를 지킵니다 — git이 빈 폴더를 버리기 때문입니다.

`analysis/`·`reference/`는 조사를 하지 않는 프로젝트에서도 만듭니다. **비어 있는 것이 곧
「이 프로젝트는 조사를 하지 않았다」는 기록**입니다.

## 2. 만들지 않는 것

`docs/`에는 **읽는 HTML만** 놓입니다 — 용어집·기능 골격·TC 시트·추적 매트릭스·리포트와
그 문서에 싣는 이미지입니다. 전부 정본에서 찍어낸 파생물이라 **하나도 손으로 고치지
않습니다**(→ `site-structure.md` §파생물은 직접 고치지 않습니다). `regen.py`가 채웁니다.

`rules/`는 **비어 있는 채로 시작합니다.** 이 프로젝트에서만 통하는 규칙이 생기면 여기 쓰고,
나중에 다른 프로젝트도 쓸 만해지면 모듈로 올립니다(→ `feature-request.md` §4).

**`spec/{슬러그}-feature-tree.md`는 만들지 않습니다.** 빈 정본이 있으면 생성기가 0노드짜리
문서를 찍어내고, 그것이 「골격이 있다」는 신호로 읽힙니다. 골격은 서식이 아니라 내용이라
도구가 만들 수 없습니다 — tc 모듈을 켠 뒤 사람이 씁니다.

같은 이유로 `sut/`·`automation/`·`spec/sut-design/`도 만들지 않습니다. 이 셋은 sut 모듈을
켠 프로젝트에만 생기며, 있으면 「검증 대상을 직접 만든다」는 뜻입니다.

## 3. 세 문서의 역할

| 파일 | 담는 것 | 갱신 방향 |
|---|---|---|
| `change-log` | 한 일 — 변경 이력·확정 결정·현재 상태 | 쌓이기만 합니다 |
| `remaining-work` | 할 일 — 다음 작업 큐·결정 대기·백로그 | 끝나면 **지웁니다** |
| `dictionary` | 이 프로젝트에서만 통하는 말 | 생기는 즉시 추가 |

앞의 둘은 **작업 전 항상 먼저 읽는 파일**입니다(→ `remaining-work.md`). 갱신 방향이 반대라
한 파일에 섞지 않습니다.

## 4. 서식은 코드 밖에 있습니다

세 문서의 빈 서식은 `core/base/design-template/project/`에 있고, 도구는 그것을 복사해
`{프로젝트}`와 `{날짜}`만 채웁니다. 문구를 도구 코드 안에 두면 **서식을 고치려고 스크립트를
열어야 하고**, 그때부터 문구 수정과 동작 수정이 같은 파일에서 섞입니다.

## 5. 만든 다음

1. `change-log`의 **§프로젝트 정의**를 채웁니다 — 무엇을 다루고 무엇을 남기는가
2. **필요한 모듈을 켭니다.** 무엇이 있고 언제 켜는지는 도구가 보여 줍니다.
   무엇을 켤지 고르는 흐름은 `feature-request.md`이고, **모듈은 저절로 켜지지 않습니다** —
   제안하고 동의를 받은 뒤에 켭니다

   ```bash
   python core/base/scripts/module.py list {슬러그}
   ```
3. 그 뒤의 순서는 켠 모듈이 정합니다

**목록에 등록하는 절차는 없습니다.** 폴더를 만드는 것이 곧 등록이고, 생성기가 `projects/`를
훑습니다(→ `site-structure.md` §목록은 손으로 갱신하지 않습니다).
