# feature-request — 「이 기능을 넣고 싶다」가 나왔을 때 무엇부터 보는가

프로젝트를 하다 보면 「A 기능을 넣고 싶다」가 나옵니다. 그때 **바로 만들지 않습니다.** 이미 있는
것을 못 보고 새로 만들면 같은 규칙이 두 벌이 되고, 반대로 이 프로젝트에만 필요한 것을 중앙에
올리면 다른 프로젝트가 쓰지 않는 규칙을 물려받습니다.

그래서 **찾고 → 묻고 → 만듭니다.** 이 문서는 그 순서를 정합니다. 여기서 「기능」은 규칙 · 서식 ·
도구 · 절차처럼 작업 방식을 바꾸는 것을 말합니다. 게임이나 앱 자체의 기능 개발은 문서 제작
절차(`../doc-playbook.md`)와 프로젝트 규칙을 따릅니다.

---

## 0. 먼저 무엇이 필요한지 한 문장으로 적습니다

## 1. 판별 흐름

```
그 기능이 이미 있는가?
│
├─ base에 있다 ─────────────── ① 업데이트 제안
├─ 모듈에 있다 · 켜져 있다 ──── ① 업데이트 제안
├─ 모듈에 있다 · 꺼져 있다
│   ├─ 그대로 쓸 수 있다 ────── ② 켤지 묻는다
│   └─ 고쳐야 쓸 수 있다 ────── ③ 고칠 방향을 설명하고 묻는다
└─ 어디에도 없다
    ├─ 다른 프로젝트도 쓸 만하다 ── ④ 새 모듈로 만든다
    └─ 이 프로젝트만의 것이다 ───── ⑤ 프로젝트 안에 만든다
```

**어느 갈래든 사용자에게 묻고 동의를 받은 뒤에 손댑니다.** 무엇이 있는지는 도구로 봅니다.

```bash
python core/base/scripts/module.py list {프로젝트}
```

## 2. 다섯 갈래

### ① 이미 있는 것을 고쳐야 하는 경우 (base · 켜진 모듈)

바로 고치지 않습니다. **무엇을 어떻게 바꿔야 하는지 먼저 분석해서 보여 줍니다.**

- 어떤 파일의 어느 부분이 바뀌는가
- 그 변경이 **다른 프로젝트 · 다른 저장소에 어떤 영향을 주는가** — base와 모듈은 여러 곳이
  물려받으므로 이쪽이 제일 중요합니다
- 바꾸지 않고 우회할 방법이 있는가

**「이미 만든 것은 어떻게 할지」를 함께 정해서 제시합니다.** 이게 빠지면 규칙만 새것이 되고
산출물은 옛것으로 남는데, 그 상태는 에러가 나지 않아 오래 발견되지 않습니다.

| 질문 | 예이면 |
|---|---|
| ① 옛것을 그대로 두면 **틀린 정보를 주거나 동작이 깨지는가?** | **지금 고칩니다** |
| ② 옛것이 **그때의 기록인가?** (change-log · 파일 CHANGELOG · archive) | **고치지 않습니다** — 그때 무슨 일이 있었는지가 사라집니다 |
| ③ 둘 다 아니면 | **다음에 그 파일을 만질 때 함께 맞춥니다** — remaining-work에 적습니다 |

중앙 규칙(`core/`)을 고치는 일이면 받아 가는 저장소에서 고치지 않고 **중앙 저장소에서**
고칩니다(`central-sync.md` §3).

### ② 꺼진 모듈을 그대로 쓰면 되는 경우

**「그 기능은 `{모듈}` 모듈에 이미 있습니다. 켤까요?」**를 묻습니다. 켜면 무엇이 따라오는지 —
규칙 문서, 도구, 프로젝트에 생기는 폴더, 전제 모듈 — 를 함께 보여 줍니다. 모듈을 켜는 것은 그
모듈의 규칙 **전부**를 따르겠다는 뜻이라, 필요한 한 조각만 가져올 수는 없습니다.

### ③ 꺼진 모듈을 고쳐야 쓸 수 있는 경우

**고칠 방향을 먼저 설명합니다.** 고치는 것이 **모듈 쪽인지 프로젝트 쪽인지**를 반드시 가립니다.

| 어느 쪽을 고치나 | 판별 |
|---|---|
| 모듈을 고친다 | 지금 모듈이 **틀렸거나 좁다**. 다른 프로젝트에도 그 수정이 맞다 |
| 프로젝트에서 덮어쓴다 | 모듈은 맞는데 **이 프로젝트만 값이 다르다** |

값만 다르면 모듈을 고치지 않습니다 — 프로젝트가 자기 값을 정하는 자리가 이미 있습니다.

### ④ 없는데 다른 프로젝트도 쓸 만한 경우

**새 모듈을 만듭니다.** 판별 질문은 **「문장에서 프로젝트 이름을 지워도 성립하는가」**입니다.
성립하면 모듈입니다. 새 모듈에 들어가는 것은 §3의 모양입니다.

### ⑤ 이 프로젝트만의 것인 경우

**중앙에는 아무것도 만들지 않습니다.** 프로젝트 폴더의 `rules/`(또는 그 프로젝트가 규칙을 두는
자리)에 씁니다. 안을 제시하고 동의를 받은 뒤에 씁니다. 나중에 다른 프로젝트에서도 필요해지면
그때 모듈로 올립니다(§4).

## 3. 모듈의 모양

```
core/modules/{모듈}/
├─ module.md        자기소개 — 언제 켜나 · 켜면 따라오는 것 · 전제 모듈
├─ module.json      적용 범위(scope) · 켜면 프로젝트에 만들 폴더(creates) — 필요할 때만
├─ rules/           규칙
├─ scripts/         도구 — 있으면 check.py를 반드시 둡니다
├─ check.py         모듈 자기 점검 (modcheck.py로 몇 줄)
├─ jobs.py          다시 만들 산출물을 regen.py에 알려 주는 자리 — 산출물이 있을 때만
└─ design-template/ 서식 — 있으면 {모듈}-template-catalog.md를 반드시 둡니다
```

| `module.json`의 `scope` | 뜻 | 어디서 켜나 |
|---|---|---|
| `project` (기본) | 프로젝트별 선택 규칙 | 프로젝트의 `{폴더}-modules.json` |
| `workspace` | 저장소 전체에 걸리는 규칙 · 산출물(진입 층 등) | `workspace.json`의 `modules` |
| `host` | 한 컴퓨터에 설치되어 여러 프로젝트가 함께 쓰는 환경 | 켜지 않습니다 — 점검 도구로 설치 상태만 확인합니다 |

**모듈은 저절로 켜지지 않습니다.** 켜는 순간 규칙 전부가 적용되고, 폴더가 늘고, 재생성 대상이
바뀝니다. 그래서 항상 **제안 → 동의 → 활성화**입니다. 전제도 자동으로 켜지지 않습니다 — 꺼진
전제가 있으면 도구가 멈추고 켜야 하는 사슬 전체를 보여 줍니다.

```bash
python core/base/scripts/module.py on {프로젝트} {모듈}   # 동의를 받은 뒤에
```

각 모듈의 `module.md` 전제 절에는 **바로 위 모듈 하나만** 적습니다. 그 위는 도구가 따라 올라갑니다.
켠 사실의 정본은 `{폴더}-modules.json`이고, change-log에 **왜 켰는지**를 한 줄 남깁니다.

## 4. 프로젝트에서 자란 것을 모듈로 올리기

1. **이름과 수치를 벗깁니다** — 프로젝트 이름 · 고유명사 · 그 프로젝트에서만 맞는 값.
   벗기고 나서도 말이 되는지가 판별입니다. 남는 게 없으면 그것은 그 프로젝트의 사정입니다.
2. 중앙 저장소에 `core/modules/{모듈}/`을 만들고 §3의 모양대로 채웁니다.
3. `center-change-log.md`에 태그를 달아 기록합니다(`change-log-writing.md` §6).
4. 받아 가는 저장소는 받은 뒤 그 모듈을 **켜서** 쓰고, 자기 프로젝트 안의 원본은 지웁니다.

## 5. 겪은 것을 중앙에 되돌리기

모듈의 점검이 무엇을 보는지는 처음부터 두껍게 쓰지 않습니다. 아직 돌려 보지 않은 도구에 두꺼운
점검을 쓰면 추측이 되므로, 처음에는 「도구가 뜨는가」까지만 두고 **실제로 걸린 것이 나올 때마다
두꺼워집니다.** 규칙 문서도 같습니다 — 겪지 않은 예외는 미리 적을 수 없습니다.

1. 받아 가는 저장소에서 발견한 중앙 규칙의 문제는 `repo-remaining-work.md`의 「중앙에 되돌려 보낼
   것」에 남깁니다. 중앙 저장소에서는 `center-remaining-work.md`가 출발점입니다.
2. **못 잡은 케이스를 점검에 넣습니다.** 고치기만 하고 케이스를 안 남기면 같은 것이 다시 지나갑니다.
3. **올릴 때 일반화합니다.** 점검 코드의 시험 데이터에도 프로젝트 고유명사를 넣지 않습니다.
