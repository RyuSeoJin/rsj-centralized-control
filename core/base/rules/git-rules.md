# git-rules — 커밋 · push · 브랜치 · 버전 태그 규칙

이 규칙을 받아 간 저장소의 모든 git 작업이 따르는 규칙입니다. Claude는 이 규칙 밖의 git 작업을
임의로 하지 않습니다.

## 1. 원칙

- **커밋 · push는 사용자 요청 시에만 합니다.** 작업 단위가 끝나면 「커밋 시점 같습니다」를
  제안만 하고, 실제 커밋은 사용자가 요청하고 내용을 승인했을 때만 합니다.
- **커밋과 push는 별개 승인입니다.** 커밋 승인이 push 승인을 포함하지 않습니다.
- **공개 범위는 `workspace.json`의 `visibility`가 정합니다.** `public`이면 push가 곧 공개이므로
  저작권 게이트(§5)를 **커밋 전과 push 전** 두 곳에서 통과해야 합니다. `private`이어도 게이트는
  돌리되 결과를 참고로 보고하고, **공개로 바꾸기 전에는 전체 이력에 대해 반드시 통과시킵니다.**
  커밋에 한번 들어가면 파일을 지워도 이력에는 남기 때문입니다.

## 2. 커밋 단위

- 한 커밋은 한 작업 단위입니다. 뼈대 수정 1건, 문서 1건 생성, 규칙 1건 개정이 그 예입니다.
- **영역을 섞지 않습니다.** 영역은 §6-1이 정합니다. 여러 영역이 한 번에 바뀌었으면 영역별로
  커밋을 나눕니다.
- 하나의 원인으로 여러 영역이 함께 바뀐 경우(예: 마스터 갱신 + 그 마스터로 만든 문서)는 한
  커밋으로 묶되 본문에 영역별로 나눠 적습니다.

### 2-1. 나눌지 판별하는 순서

묶을지 나눌지는 파일 개수나 변경 크기로 정하지 않습니다. **원인으로 셉니다** — 나중에 이력을
되짚는 사람이 찾는 것이 「무엇 때문에 이렇게 되었는가」이기 때문입니다.

1. **원인을 셉니다.** 「무엇 때문에 이 변경을 했는가」를 한 문장씩 적습니다. 하나면 한 커밋입니다.
2. **원인 사이에 인과가 있는지 봅니다.** 앞 작업을 **끝내려면 뒤 작업이 필요했다면** 묶고, 본문
   [작업 목록]에서 단위를 나눠 적습니다. **하다가 눈에 띈 것은 인과가 아닙니다.** 한 세션에서
   이어서 했다는 사실은 원인이 아니라 시간입니다.
3. **인과가 없으면 나눕니다.** 파일이 겹쳐도 나눕니다. 겹치는 파일은 hunk 단위로 갈라 담고,
   갈라지지 않는 파일은 커밋 순서대로 다시 만듭니다.
4. **나눈 뒤 제목을 써 봅니다.** 제목에 동작이 둘 들어가면 아직 덜 나뉜 것입니다.

## 3. 커밋 메시지 규격

```
[{영역}] {무엇을} {어떻게 했는지 — 정보 누락 없이}

[작업 목록]

* (작업 단위 1 — 대상 + 동작 명사형)
   * (원인 → 파생 작업 → 결과를 짧게 적어 인과를 드러냅니다)

* (작업 단위 2 — 최상위 항목 사이는 빈 줄로 띄웁니다)

[스펙 변경]

* (수치 · 용어 · 규칙 변경 전부. 기존 사용 방식에 미치는 영향을 함께 적습니다)

[변경 파일]

* 신규 — (파일 · 폴더)
* 수정 — (파일 · 폴더)
* 재생성 — (파생물)

[상세 로그]

* {이력 종류}
  * "{항목 제목}" · YYYY-MM-DD hh:mm

[주의]

* (다음 작업자가 놓치기 쉬운 경계 · 예외 — 있을 때만)

[작업자]

* 담당자 — {이름}
* Co-Authored-By: {실제로 작업한 AI 모델의 정확한 표시명}
```

- 해당 없는 섹션은 **통째로 생략합니다.** 승인용 제안에서는 제목만 요약하지 않고 본문 전체를
  보여 줍니다.
- [작업 목록] 최상위 항목은 대상 + 동작 명사형입니다(`doc-write-style.md` §3-5). 원인과 파생
  관계는 들여써서 보존합니다.
- [스펙 변경]에는 앞으로 달라지는 규칙과 사용 방식을 적습니다. 알아야 할 변화가 없으면 생략합니다.
- [변경 파일]은 신규 · 수정 · 재생성으로 나누고, 범위를 복원할 수 있게 경로를 묶어 적습니다.
- [상세 로그]는 이력 항목의 **고정 식별자**(종류 + 제목 + 날짜 시각)로 적습니다. 원인 항목부터
  파생 항목 순서입니다(`change-log-writing.md` §3).
- **담당자의 기본값은 `git config user.name`입니다.** 커밋을 제안할 때 실제로 내용을 판단 · 확인한
  사람을 확인해 그 커밋에만 적습니다. 템플릿에 특정 사람 이름을 박아 두지 않습니다.
- **Co-Authored-By에는 실제로 작업한 모델의 정확한 표시명**을 적습니다. 세션 중 모델이 바뀌면
  바뀐 모델로 적습니다. 실행 환경이 정한 표기(서명 줄)가 있으면 그것을 따릅니다.
- **change-log와의 역할 분담**: 상세 기록의 정본은 change-log입니다. 커밋 본문은 요약이며 같은
  내용을 양쪽에 전문으로 적지 않습니다.

## 4. 승인 플로우

0. **커밋을 제안하기 전에 검사 셋을 돌립니다.**

   ```bash
   python core/base/scripts/regen.py --check        # 낡은 산출물이 있는가
   python core/base/scripts/check_rules.py          # 규칙과 다른 곳이 있는가
   python core/base/scripts/check_copyright.py      # 저작권을 사람이 봐야 하는가 (§5)
   ```

   정본을 고치고 산출물을 다시 만들지 않은 상태도, 문체가 어긋난 문장도, 없는 파일을 가리키는
   규칙도 **에러가 나지 않아** 그대로 커밋됩니다. 눈으로 훑어서는 안 걸리므로 기계가 봅니다.
1. 작업 완료 → 「커밋 시점 같습니다」를 제안합니다.
2. 사용자가 커밋을 요청하면 **① 제목 ② 본문 ③ 대상 브랜치 ④ 검사 결과**를 제시합니다.
   저작권 게이트에 걸린 것이 있으면 제안을 멈추고 §5의 넷을 먼저 보고합니다.
3. 사용자가 승인하면 커밋합니다. 수정 지시가 있으면 반영한 뒤 다시 제시합니다.
4. push는 별도입니다. 요청을 받으면 §5-2를 확인한 뒤 push합니다.

## 5. 저작권 게이트

점검 항목은 커밋과 push에서 같습니다. 다른 것은 **무엇을 대상으로 보는가**입니다.

- [ ] 남의 스크린샷 포함 여부
- [ ] 원문 텍스트 인용 포함 여부 (인용 시 최소 범위 · 출처 표기 확인)
- [ ] 상표 · 로고 노출 여부
- [ ] 비공개 자료(유출본 · 내부 문서) 포함 여부 — 발견 시 커밋 · push 금지

### 5-1. 커밋 전 — 이번 커밋에 들어갈 것

```bash
python core/base/scripts/check_copyright.py
```

도구는 **커밋에 들어갈 후보 전부**(스테이징된 것 · 스테이징 안 한 수정 · 추적되지 않은 새 파일)를
봅니다. 도구가 판단하는 것은 저작권이 아니라 **사람을 불러야 하는 커밋인가**입니다. 통과도 한
줄로 남깁니다 — 아무 말도 없으면 게이트를 돌았는지 건너뛴 건지 알 수 없기 때문입니다.

**도구가 못 잡는 것이 하나 있습니다** — 원문 텍스트를 문서에 그대로 붙여 넣는 것입니다. 그 자리는
자료를 처음 다루는 시점의 체크리스트(`../doc-playbook.md` STEP 1)가 덮습니다.

자기 제작 자산이 많은 저장소(게임 프로젝트의 그림 · 소리 등)는 이진 파일마다 도구가 사람을
부릅니다. 그런 자리는 프로젝트 구조 설정(`{폴더}-structure.json`)에 `implementation` 역할로
등록해 두면, 게이트가 새 파일이 들어올 때만 확인을 요청합니다.

### 5-2. push 전 — 올라갈 커밋 전체

```bash
python core/base/scripts/check_copyright.py --range origin/main..HEAD
```

커밋 게이트를 통과한 것들인데도 다시 보는 이유는 셋입니다 — 게이트를 세우기 전에 쌓인 커밋,
다른 곳에서 들어온 커밋, 그리고 한 커밋씩은 괜찮아도 **합쳐 놓으면 자료 한 벌이 되는** 경우입니다.
`public` 저장소에서 걸리면 **push를 보류하고 사용자에게 보고합니다.**

## 6. 저장소와 브랜치

중앙 규칙은 **별도 중앙 저장소**에 있고, 각 저장소는 `core/`를 받아 씁니다(`central-sync.md`).
각 저장소는 **하나의 `main`**에서 일하고, 격리가 필요한 작업(기능 실험 · 동시에 진행하는 큰 작업 ·
되돌릴 가능성이 높은 변경)만 짧은 기능 브랜치 `feature/{무엇을-하는가}`를 씁니다.

### 6-1. 영역

| 영역 | 어디서 | 무엇 |
|---|---|---|
| `[Center]` | 중앙 저장소 | 중앙 규칙 · 공용 모듈 · 중앙 이력 |
| `[Repo]` | 받아 가는 저장소 | 저장소 설정(`workspace.json` · 진입점 · 저장소 이력) · **중앙 규칙 받기** |
| `[{프로젝트}]` | 받아 가는 저장소 | 그 프로젝트 폴더 안의 변경 |

- 받아 가는 저장소에서 `core/`가 바뀌는 커밋은 **받기 커밋 하나뿐**입니다. 제목은
  `[Repo] 중앙 규칙 받기 — {태그 또는 커밋}`이고, 그 커밋에 프로젝트 파일을 섞지 않습니다.
- 중앙 저장소의 `[Center]` 커밋에는 특정 프로젝트의 값 · 이름이 들어가지 않습니다
  (`site-structure.md` §중앙 규칙에는 프로젝트를 적지 않습니다).

## 7. 태그 (버전 좌표)

- 태그는 「완성 시점의 이정표」로만 씁니다. 작업 과정은 커밋 이력이 담습니다.
- 중앙 규칙 버전은 `core-v{주}.{부}.{수}`로 씁니다. 커밋 수나 이력 항목 수는 버전을 올리는
  근거가 아닙니다.
- 프로젝트 이정표 태그는 `{프로젝트}-{무엇}-v{버전}`으로 씁니다.

### 7-1. 중앙 버전을 제안하는 때

아래 셋 중 하나가 실제로 일어날 때만 중앙 버전을 제안합니다.

1. 다른 저장소가 중앙 규칙 묶음을 처음 받아 가거나, 받아 가는 저장소가 늘 때
2. 받아 가는 쪽에 할 일이 생기는 태그(`change-log-writing.md` §6의 번호 목록)가 쌓였을 때
3. 사용자가 현재 상태를 기준 버전으로 고정하자고 할 때

### 7-2. 제안과 확정

먼저 규칙 문서 · 도구 · 모듈이 프로젝트 정보 없이 성립하는지 검사합니다(`check_rules.py`).
번호는 이번 묶음이 받아 가는 쪽에 미치는 영향과 직전 태그를 함께 보여 제안하고, **승인 뒤에만**
annotated tag로 만듭니다.

## 8. 기타

- 원격은 `workspace.json`의 `repo`가 가리키는 저장소입니다. 저장소 이름을 규칙 문서에 적지 않습니다.
- 되돌림은 `git revert`(새 커밋으로 되돌리기)를 기본으로 합니다. 이력을 지우는 force push는
  사용자의 명시 요청 없이 하지 않습니다.
