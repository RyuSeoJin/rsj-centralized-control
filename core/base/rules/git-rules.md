# git-rules — GitHub 커밋·push·브랜치 규칙

이 저장소의 모든 git 작업이 따르는 규칙입니다. 2026-07-31 확정했습니다.
Claude는 이 규칙 밖의 git 작업을 임의로 수행하지 않습니다.

## 1. 원칙

- **커밋·push는 사용자 요청 시에만 합니다.** Claude는 작업 단위가 끝나면 "커밋 시점"임을 제안만 하고, 실제 커밋은 사용자가 요청하고 내용을 승인했을 때만 수행합니다.
- **커밋과 push는 별개 승인입니다(분리형).** 커밋 승인이 push 승인을 포함하지 않습니다. 로컬에 커밋을 쌓아두고, 사용자가 push를 요청할 때만 공개합니다.
- **이 저장소는 public이므로 push가 곧 공개입니다.** 그래서 저작권 게이트(§5)를 **커밋 전과 push 전** 두 곳에서 통과해야 합니다. 커밋에 한번 들어가면 파일을 지워도 이력에는 남아, push 시점에 잡으면 `amend`나 `rebase`로 이력을 고쳐야 하기 때문입니다.

## 2. 커밋 단위

- 한 커밋은 한 작업 단위입니다. 골격 수정 1건, 문서 1건 생성, 규칙 1건 개정이 그 예입니다.
- **영역을 섞지 않습니다.** 프로젝트 작업과 규약(core/) 수정, 디자인 시스템 갱신이 한 번에 발생했다면 영역별로 커밋을 나눕니다. 제목이 "정보 누락 없이"를 지키려면 커밋이 단일 영역이어야 하기 때문입니다.
- 예외로, 하나의 원인으로 여러 영역이 함께 바뀐 경우(예: Case B 마스터 갱신 + 그 마스터로 만든 문서)는 한 커밋으로 묶되 본문에 영역별로 나눠 적습니다.
- **원인이 다른 작업이 한 커밋에 들어가는 경우에도 본문에서 작업 단위를 나눠 적습니다.** 같은 흐름의 규칙 정비이거나, 한 파일이 여러 작업에 걸쳐 부분 스테이징 없이는 갈라지지 않을 때가 여기 해당합니다. 이때는 [작업 목록]의 항목을 작업 단위별로 묶고 무엇이 한 단위인지 드러나게 적습니다. 커밋 하나에 여러 결정이 들어 있어도 나중에 단위별로 복원되어야 하기 때문입니다.
- 다만 이 묶음은 편의를 위한 것이 아닙니다. 작업 단위가 서로 무관하고 파일도 겹치지 않는다면 커밋을 나눕니다.

## 3. 커밋 메시지 규격

한 화면에서 섹션이 구분되어 읽히도록, 대괄호 헤더와 빈 줄로 본문을 가릅니다(2026-08-01 개정).

```
[{영역}] {무엇을} {어떻게 했는지 — 정보 누락 없이}

[작업 목록]

* (작업 단위 1 — 이유→작업 순서로)
   * (다른 작업이 원인이 되어 파생된 것은 들여써서 인과를 드러낸다. 부모에 붙여 씀)

* (작업 단위 2 — 최상위 항목 사이는 빈 줄로 띄운다)

[스펙 변경]

* (수치·용어·규칙 변경 전부. 골격 버전 변화, 이전 산출물과 비호환이 되는 삭제,
   마스터/템플릿 갱신(Case B/C), 미확인(?) 증감, 이슈/TC 참조도 여기에 항목으로)

[변경 파일]

* (목록 요약)

[상세]

* {프로젝트}-change-log.md 또는 spec/archive/{프로젝트}-tree-change-log.md 해당 항목

[주의]

* (다음 작업자가 놓치기 쉬운 것 — 있을 때만)

Co-Authored-By: Claude {모델} <noreply@anthropic.com>
```

- `{영역}` = 프로젝트명(예: `demo-vn`) 또는 `process`(규약) · `design`(디자인 시스템) · `repo`(루트/구조).
- 해당 없는 섹션은 빈 채로 두지 않고 **통째로 생략합니다.** 본문에는 실제 정보만 남깁니다.
- **[작업 목록] 항목은 한 문장에 욱여넣지 않습니다.** 한 줄로 압축하면 인과가 사라져 나중에 왜 그렇게 했는지 복원할 수 없습니다. 여러 갈래의 이유가 있으면 갈래마다 항목을 나눠 적고, 앞선 작업 때문에 파생된 작업은 들여쓰기로 중첩해 "무엇 때문에 무엇을 하게 됐는지"가 읽히게 합니다.
- **[작업 목록] 항목은 이유 → 작업 → 결과 순서로 씁니다.** 문장 구조 규칙의 정본은 `doc-write-style.md` §2이며, 커밋 메시지 본문도 적용 범위입니다. 작업을 앞에 쓰고 이유를 뒤에 붙이면 나중에 이력을 되짚을 때 이유가 늦게 드러나 문장을 다시 해석해야 하므로, "무엇을 했다 — 왜냐하면"이 아니라 "무엇 때문에 무엇을 했다"로 적습니다.
- **change-log와의 역할 분담**: 상세 기록의 정본은 change-log입니다. 커밋 본문은 요약이며 `상세:` 줄로 change-log를 가리킵니다. 같은 내용을 양쪽에 전문으로 중복 기재하지 않습니다.
- Co-Authored-By 서명은 유지합니다(AI 협업 워크플로우 증빙). `{모델}` 자리에는 실제로 작업한 모델명을 적습니다 — 증빙이므로 템플릿에 특정 모델명을 박아두지 않습니다.
- **커밋 직전에 서명의 모델명을 매번 확인합니다.** 앞선 커밋 메시지를 그대로 베끼면 세션 중
  모델이 바뀌었을 때 서명이 조용히 틀어집니다(2026-08-02까지 두 차례 발생). 이력에 남는 증빙이
  실제와 다르면 협업 기록으로서의 값어치가 사라지므로, 직전 커밋을 참고하더라도 서명 줄만은
  현재 세션의 모델명으로 다시 적습니다.

## 4. 승인 플로우

0. **커밋을 제안하기 전에 검사 셋을 돌립니다.**

   ```bash
   python core/base/scripts/regen.py --check        # 낡은 산출물이 있는가
   python core/base/scripts/check_rules.py          # 규칙과 다른 곳이 있는가
   python core/base/scripts/check_copyright.py      # 저작권을 사람이 봐야 하는가 (§5-1)
   ```

   정본을 고치고 산출물을 다시 만들지 않은 상태도, 문체가 어긋난 문장도, 이름표에 프로젝트
   항목이 들어온 것도 **에러가 나지 않아** 그대로 커밋됩니다. 눈으로 훑어서는 안 걸리므로
   기계가 봅니다.
1. 작업 완료 → Claude가 "커밋 시점 같습니다"라고 제안합니다.
2. 사용자가 커밋 요청 → Claude가 **① 제목 ② 본문 ③ 대상 브랜치**에 **④ 저작권 게이트 결과**를
   더해 제시합니다. 게이트에 걸린 것이 있으면 제안을 멈추고 §5-1의 넷을 먼저 보고합니다 —
   무엇을 뺄지 정한 다음에 제안이 나갑니다.
3. 사용자가 승인 → 커밋을 수행합니다. 수정 지시가 있으면 반영 후 다시 제시합니다.
4. push는 별도입니다. 사용자가 push를 요청하면 저작권 게이트(§5-2) 통과를 확인한 뒤 push합니다.
5. **중앙 저장소로 올리는 PR도 별도 승인입니다.** Claude는 「이 변경은 중앙 규칙이라 올릴 수
   있습니다」를 제안만 하고, 사용자가 요청하면 §6-1의 순서로 가지를 파서 PR을 냅니다. PR 본문에는
   **무엇이 왜 규칙이 되었는가**를 적고, 그 판단이 나온 프로젝트의 이름은 적지 않습니다.

## 5. 저작권 게이트 — 커밋과 push 두 곳

점검 항목은 두 곳이 같습니다. 다른 것은 **무엇을 대상으로 보는가**입니다.

- [ ] 대상 서비스의 스크린샷 포함 여부
- [ ] 게임/서비스 원문 텍스트 인용 포함 여부 (인용 시 최소 범위·출처 표기 확인)
- [ ] 상표·로고 노출 여부
- [ ] 비공개 자료(유출본·내부 문서) 포함 여부 — 발견 시 커밋·push 금지

### 5-1. 커밋 전 — 이번 커밋에 들어갈 것

```bash
python core/base/scripts/check_copyright.py
```

도구는 **커밋에 들어갈 후보 전부**를 봅니다 — 스테이징된 것, 아직 스테이징 안 한 수정,
추적되지 않은 새 파일. 게이트가 도는 자리가 커밋을 제안하기 **전**이라 대개 아직 `git add`
전이고, 스테이징만 보면 매번 빈손으로 돌기 때문입니다.

걸린 것이 있으면 **커밋 제안을 멈추고 위 넷을 사용자에게 보고합니다.** 하나라도 걸리면
커밋하지 않습니다. 여기서 빼는 것은 스테이징에서 빼기만 하면 되지만, 커밋에 한번 들어가면
파일을 지워도 **이력에는 남아** `amend`나 `rebase`가 필요해집니다.

도구가 판단하는 것은 저작권이 아니라 **사람을 불러야 하는 커밋인가**입니다. 이 그림이 남의
스크린샷인지, 이 문장이 원문 인용인지는 기계가 볼 수 없습니다. 그래서 통과도 한 줄로
남깁니다 — 아무 말도 나오지 않으면 게이트를 돌았는지 건너뛴 건지 알 수 없기 때문입니다.

**도구가 못 잡는 것이 하나 있습니다** — 원문 텍스트를 문서에 그대로 붙여 넣는 것입니다.
이미지도 이진 파일도 아니라 신호가 없습니다. 규칙대로 `analysis/`에 두면 자리로 잡히지만,
곧장 `spec/`에 붙이면 조용합니다. 그 자리는 도구가 아니라 절차가 덮습니다 —
자료를 **처음 다루는 시점**의 체크리스트(doc-playbook.md STEP 1)가 그것입니다.

### 5-2. push 전 — 이번에 올라갈 커밋 전체

```bash
python core/base/scripts/check_copyright.py --range origin/main..HEAD
```

커밋 게이트를 통과한 것들인데도 다시 보는 이유는 셋입니다.

1. 게이트를 세우기 전에 쌓인 커밋이 있습니다.
2. 다른 곳에서 들어온 커밋이 섞일 수 있습니다.
3. 한 커밋씩은 괜찮아도 **합쳐 놓으면 자료 한 벌이 되는** 경우가 있습니다.

걸리면 **push를 보류하고 사용자에게 보고합니다.**

## 6. 저장소 전략 — 중앙과 fork (2026-09-04 개정)

저장소를 **둘**로 씁니다. 중앙 규칙이 프로젝트를 거치며 자라되, 프로젝트 정보는 중앙으로
한 줄도 올라가지 않게 하려는 것입니다.

| 저장소 | 무엇이 사나 | 누가 만지나 |
|---|---|---|
| **중앙(upstream)** | `core/` · 규칙 문서 · 도구. `projects/`는 **비어 있습니다** | PR로만 |
| **fork** | 중앙을 복제한 것 + `projects/{프로젝트}/` | 직커밋 |

중앙 저장소는 **프로젝트가 하나도 없어도 그대로 굴러가야 합니다.** 그것이 「가져다 쓸 수 있는
규칙 뭉치」의 정의이고, §6-3의 게이트가 매 PR마다 그것을 검사합니다.

### 6-1. 브랜치는 두 갈래입니다

**§6 개정 전에는 「브랜치도 PR도 쓰지 않는다」였습니다.** fork 모델에서는 성립하지 않습니다 —
fork의 `main`에는 프로젝트 커밋이 섞여 있어, 거기서 PR을 올리면 프로젝트 파일이 딸려 갑니다.

| 무엇을 하나 | 어디서 | 어떻게 |
|---|---|---|
| **프로젝트 작업** | fork의 `main` | 직커밋. 브랜치를 나누지 않습니다 |
| **중앙 규칙 기여** | `upstream/main`에서 판 새 가지 | 그 가지에서 `core/`만 고치고 중앙으로 PR |

기여용 가지를 **fork의 `main`이 아니라 `upstream/main`에서 파는** 이유가 이것입니다. fork의
main에서 파면 그 시점까지의 프로젝트 커밋이 전부 따라옵니다.

```bash
git remote add upstream <중앙 저장소 주소>     # 최초 1회
git fetch upstream
git switch -c rule/{무엇을-고치는가} upstream/main
#   core/ 만 고칩니다. projects/ 와 workspace.json 은 손대지 않습니다
git push -u origin rule/{무엇을-고치는가}
#   PR 대상은 upstream/main
```

가지 이름은 `rule/{무엇을-고치는가}`로 씁니다. 프로젝트 슬러그를 가지 이름에 넣지 않습니다 —
**가지 이름도 중앙 저장소에 남는 기록**이기 때문입니다.

### 6-2. PR에 담지 않는 것

- `projects/` 아래 **어떤 파일도** 담지 않습니다
- `workspace.json`을 담지 않습니다 — 저장소 이름·주소는 fork마다 다릅니다
- 규칙 문서의 예시에 **프로젝트 슬러그·고유명사·실제 수치**를 쓰지 않습니다.
  예시가 필요하면 `{프로젝트}`·`{슬러그}` 같은 자리 표시자를 씁니다

세 번째가 사람이 제일 자주 놓치는 자리입니다. 「이 프로젝트에서 이렇게 했다」를 규칙 문서의
예시로 적는 순간, 중앙 규칙이 남의 프로젝트 이야기를 하게 됩니다.

### 6-3. 게이트는 사람이 아니라 CI가 지킵니다

규칙 문장만으로는 언젠가 새어 나갑니다. 중앙 저장소의 `.github/workflows/`가 들어오는 PR마다
아래를 검사하고, **하나라도 걸리면 머지할 수 없습니다.**

| 게이트 | 검사 |
|---|---|
| ① 프로젝트 파일 차단 | 변경 파일에 `projects/` 경로가 있으면 실패 |
| ② 프로젝트 산출물 차단 | `intro/` 경로가 있으면 실패 — 그 폴더는 두지 않습니다 |
| ③ 프로젝트 CI 차단 | `.github/workflows/`에 `central-gate.yml` 아닌 파일이 오면 실패 |
| ④ 인스턴스 값 차단 | `workspace.json` 변경이 있으면 실패 |
| ⑤ **자기완결 검사** | 프로젝트가 **0개인 상태에서** 골격 생성과 문서 생성이 도는지 실행 |
| ⑥ **모듈 자기 점검** | `core/modules/*/check.py`를 훑어 저마다 돌림 |

⑤가 실질적인 게이트입니다. 규칙 문서에 프로젝트 이름이 안 적혀 있어도 **도구가 프로젝트
데이터를 읽기 시작하면** 중앙 저장소는 혼자 돌지 못합니다. ①~④는 파일 이름만 보지만 ⑤는
실제로 돌려 봅니다.

②·③은 **프로젝트가 `projects/` 밖으로 새어 나가는 두 길**을 막습니다. 읽는 HTML을 한 폴더에
모으던 시절의 자리와, 프로젝트별 CI 워크플로입니다. 둘 다 규칙으로는 없앴지만 **규칙은 잊히고
게이트는 잊히지 않습니다.**

#### ⑥ 모듈 자기 점검이 따르는 규칙

중앙 저장소는 어떤 모듈도 켜지 않지만, **모듈 코드를 보관하므로 그것이 도는지 볼 책임이
있습니다.** 켜는 것은 「이 프로젝트가 이 규칙을 따르는가」이고, 게이트가 보는 것은 「코드가
성립하는가」라 층이 다릅니다.

| | 규칙 |
|---|---|
| **자리** | `core/modules/{모듈}/check.py`. 게이트는 이 자리만 보고 **모듈 이름을 적지 않습니다** — 모듈이 늘어도 게이트를 손대지 않습니다 |
| **범위** | 점검도 **프로젝트 없이 돌아야 합니다.** `projects/`를 읽는 점검은 중앙에서 반드시 실패합니다. 곧 모듈도 자기완결이어야 한다는 뜻입니다 |
| **판정** | 종료 코드입니다. `0`이면 통과, 그 밖이면 실패. `check_rules.py`·`regen --check`와 같은 규약입니다 |
| **의존성** | 모듈이 `core/modules/{모듈}/requirements.txt`에 스스로 적습니다. 게이트는 있으면 설치하고 없으면 지나갑니다 — 새 모듈이 라이브러리를 써도 게이트를 고치지 않습니다 |
| **의무** | **도구(`scripts/`)를 가진 모듈은 점검을 가집니다.** 규칙 문서만 있는 모듈은 돌릴 것이 없어 강제하지 않습니다. 빠뜨리면 `check_rules.py` 검사 ⑥이 잡습니다 |

거들 도구가 `base/scripts/modcheck.py`에 있어, 점검 하나는 대개 몇 줄입니다.

**점검이 무엇을 보는지는 규칙이 정하지 않습니다.** 자리와 의무만 규칙이 강제하고, 내용은
프로젝트에서 실제로 걸린 것이 채웁니다(→ `feature-request.md` §5). 아직 돌려 보지 않은 도구에
두꺼운 점검을 쓰면 **추측으로 쓴 점검**이 되고, 그것은 허술한 점검보다 나쁩니다 — 틀린 것을
통과시키면서 통과했다고 말하기 때문입니다. 처음에는 「도구가 뜨는가」까지만 둡니다.

### 6-4. 중앙이 자랐을 때 fork가 받아 오기

```bash
git fetch upstream
git merge upstream/main          # fork의 main에서
```

`workspace.json`은 fork마다 값이 달라 **충돌하는 유일한 파일**입니다. 3줄짜리이므로 fork 쪽
값을 고르면 됩니다. 이 충돌은 정상이며, 게이트 ②가 그 파일이 거꾸로 올라가는 것을 막습니다.

**merge는 규칙만 가져옵니다.** `core/` 안의 규칙과 도구는 새것이 되지만 `projects/` 안의
문서와 산출물은 그대로 남습니다. 그래서 merge 직후는 **규칙은 새것, 산출물은 옛것**인
상태이고, 이 상태는 **에러가 나지 않습니다** — 옛 xlsx는 그냥 열리고 옛 HTML은 그냥 보입니다.
그래서 아래 네 걸음을 반드시 밟습니다.

| | 무엇을 |
|---|---|
| ① | merge 한다 |
| ② | **새로 들어온 항목의 태그를 읽는다** — `git diff HEAD..upstream/main -- center-change-log.md` |
| ③ | **번호 없는 줄을 먼저 읽는다** — 앞으로 일하는 법이 달라진 것 |
| ④ | **번호 목록을 위에서부터 한다** — 값 입력·직접 수정·재생성 |
| ⑤ | **미룰 것은 `remaining-work`로 옮겨 적는다** |

②에서 파일 전체를 읽지 않습니다. `git diff`가 이번에 들어온 항목만 보여 줍니다.

③을 ④보다 먼저 하는 이유는, **모르고 할 일을 먼저 하면 옛 방식으로 하게 되기** 때문입니다.

⑤를 빠뜨리면 미룬 일이 아무 데도 안 남습니다. change-log는 한 일을 쌓는 자리라 항목이
아래로 밀려 내려가고, 다시 보지 않게 됩니다.

**태그를 놓쳤을 때를 대비해 마지막에 한 번 확인합니다.**

```bash
python core/base/scripts/regen.py --check
```

정본보다 오래된 산출물을 목록으로 냅니다. 사람의 기억에 기대지 않으려는 것입니다.

옮겨 적는 자리는 **고칠 대상이 어디 있느냐**로 갈립니다.

| 고칠 대상 | 어디에 |
|---|---|
| 중앙 규칙 문서 (`core/` 안) | `center-remaining-work.md` |
| 프로젝트 문서·산출물 (`projects/` 안) | `projects/{프로젝트}/{프로젝트}-remaining-work.md` |

같은 개정 하나가 두 곳에 항목을 남길 수 있습니다 — 고치는 시점이 서로 다르기 때문입니다.

### 6-5. 다시 볼 조건

여러 사람이 같은 fork를 동시에 만지게 되면 프로젝트 작업 쪽에도 브랜치가 필요해집니다.
혼자 쓰는 동안에는 나누지 않습니다.

> 2026-08-03~09-04에는 「`main` 단일 직커밋, 브랜치도 PR도 쓰지 않음」이었습니다. 저장소 하나로
> 한 프로젝트만 만들던 때의 규칙입니다. 중앙 규칙을 여러 프로젝트가 물려받는 구조가 되면서
> **중앙에 올리는 길과 프로젝트를 만드는 길을 갈라야** 했습니다.

## 7. 태그 (버전 좌표)

- 태그는 "완성 시점의 이정표"로만 씁니다. 커밋 이력이 작업 과정을 담고, 태그가 버전 좌표를 담습니다.
- 형식: 골격 major 개정은 `{프로젝트}-tree-v2.0`, TC 세트 완성은 `{프로젝트}-tc-v1.0`.
- **중앙 규칙에도 버전을 붙입니다** — `core-v1.0.0` 형식으로, 중앙 저장소에서만 찍습니다.
  복제한 쪽이 「나는 어느 시점 규칙을 쓰고 있는가」를 말할 수 있어야 하기 때문입니다.
  저장소가 여럿이 되면 「A는 core-v1.2.0, B는 core-v1.0.0」을 구분해야 합니다.

### 7-1. 자리는 change-log 태그가 정합니다

버전 숫자가 말해야 하는 것은 **「받아 가는 데 얼마나 드는가」**입니다. 그것은 이미 change-log
태그가 항목마다 말하고 있으므로, 새로 판단하지 않고 **모으기만 합니다.**

| 자리 | 올리는 조건 | 받아 가는 쪽에게 |
|---|---|---|
| **첫째** `2.0.0` | change-log에 **새 날짜 묶음**을 엶 | 규칙을 처음부터 다시 읽어야 합니다 |
| **둘째** `1.3.0` | `직접 수정해야 함` · `재생성해야 함` | **안 하면 산출물이 규칙과 갈라진 채 남습니다** |
| **셋째** `1.2.4` | `값 입력해야 함` · `방식 변경됨` · `변경할 사항 없음` | 안 해도 기존 것은 그대로 맞습니다 |

둘째와 셋째를 가르는 것은 **「가만두면 어긋나는가」**입니다. 정본을 고치고 재생성하지 않으면
옛 HTML이 새 규칙과 다른 말을 하고, 파일이 옮겨졌는데 참조를 안 고치면 없는 자리를
가리킵니다 — 둘 다 **틀린 상태**가 됩니다. 반면 값을 안 넣으면 기본값으로 돌 뿐이고, 방식
변경을 안 읽으면 다음에 옛 방식으로 일할 뿐 **기존 산출물은 멀쩡합니다.**

**첫째 자리만 태그로 계산되지 않습니다.** 대신 `center-change-log.md`의 **날짜 묶음 제목
하나가 첫째 자리 하나**입니다. 「이건 대규모인가」를 매번 새로 고민하지 않고, change-log를
쓸 때 어차피 하는 판단 하나에 얹습니다. 그 대신 **묶음 제목은 가볍게 열지 않습니다.**

#### 계산과 초기화

> **마지막 태그 이후 쌓인 항목 중 가장 무거운 것**이 자리를 정하고, 그 아래 자리는 `0`이 됩니다.

| 쌓인 것 | `core-v1.2.3` 다음 |
|---|---|
| `값 입력해야 함` 2건 | `core-v1.2.4` |
| `방식 변경됨` 1건 + `재생성해야 함` 1건 | `core-v1.3.0` |
| 새 날짜 묶음을 엶 | `core-v2.0.0` |

무거운 것이 하나라도 있으면 가벼운 것은 그 안에 묻힙니다 — 받아 가는 쪽은 어차피 무거운 쪽
일을 해야 하기 때문입니다.

### 7-2. 시점은 「규칙 문서와 생성 프로그램이 자기 힘으로 서는가」가 정합니다

항목이 쌓일 때마다 찍지 않습니다. 시간이나 개수로 끊으면 **반쯤 고치던 규칙 위에 버전이
찍히고**, 그 버전으로 복제한 사람은 어중간한 상태를 받습니다.

찍어도 되는지는 마지막 태그 이후 항목을 하나씩 보며 묻습니다.

```
이 항목 없이도 규칙 문서와 생성 프로그램만으로 같은 결과가 나오는가?
├─ 전부 예    → 찍습니다
└─ 하나라도   → 아직입니다. 규칙 문서에 빠진 것을 채우고 다시 봅니다
   아니오
```

**버전은 「지금 복제해도 규칙과 생성 프로그램만으로 일할 수 있다」는 표시**입니다. 그래서
버전을 끊는 일이 곧 **규칙 문서와 생성 프로그램이 자기 힘으로 서는지 점검하는 자리**가 됩니다.
**규칙과 「왜 그렇게 정했는가」가 둘 다 문서에 있어야 합니다** — 이유 없는 규칙은 다음 사람이
「이거 왜 있지」 하고 걷어냅니다.

찍는 절차는 커밋과 같습니다. Claude가 **「지금이 찍을 때 같습니다」를 제안하고, 버전 자리와
근거가 된 태그를 보인 뒤 승인을 받습니다.**

### 7-3. 첫째 자리와 둘째 자리의 10단위에서 change-log를 자릅니다

**자르는 시점은 첫째 자리가 바뀌거나 둘째 자리가 다음 10단위에 닿을 때입니다.** 첫 버전인
`1.0.0`도 첫째 자리가 정해지는 시점이라 자릅니다. 둘째 자리의 중간 값과 셋째 자리는 태그만
찍고 change-log는 그대로 둡니다.

| 새 버전 | 자르나 | 이유 |
|---|---|---|
| `1.0.0` | 예 | 첫째 자리가 처음 정해집니다 |
| `1.1.0`~`1.9.x` | 아니오 | 둘째 자리의 10단위에 아직 닿지 않았습니다 |
| `1.10.0` | 예 | 둘째 자리가 다음 10단위에 닿았습니다 |
| `1.11.0`~`1.19.x` | 아니오 | 다음 10단위까지 이어서 쌓습니다 |
| `2.0.0` | 예 | 첫째 자리가 바뀝니다 |

자를 때 항목마다 다시 묻습니다.

```
이 항목 없이도 규칙 문서와 생성 프로그램만으로 같은 결과가 나오는가?
├─ 예     → archive로 옮깁니다
└─ 아니오 → center-change-log.md에 남기고 빠진 규칙이나 프로그램을 보완합니다
```

통과한 항목은 `archive/center-change-log-v{a}.{b}.{c}.md`로 **옮깁니다.** 루트
`center-change-log.md`의 읽는 법·항목 서식·태그 규칙은 앞으로도 쓰므로 옮기지 않습니다.
archive는 `spec/archive/`와 같은 규칙이라 **기본 참조 금지**이고, 「언제부터 이랬지」처럼
이력을 물을 때만 엽니다.

지우지 않고 옮기는 이유는 판단 근거와 변경 이력을 보존하기 위해서입니다. 문서 생성과 현재
작업은 archive를 읽지 않아도 같은 결과가 나와야 합니다.

§7-2를 통과한 버전이라면 그 시점까지의 변경 항목은 모두 옮길 수 있습니다. 하나라도 루트에
남는다면 아직 규칙 문서나 생성 프로그램에 빠진 것이 있다는 뜻이므로, 보완한 뒤 다시 묻습니다.
- annotated tag로 만들고, 메시지에 한 줄 요약을 담습니다.
- **archive 파일명과 중앙 태그의 버전 좌표는 항상 일치시킵니다** (예: 태그
  `core-v1.10.0` ↔ `archive/center-change-log-v1.10.0.md`).

## 8. 기타

- 원격: `workspace.json`의 `repo`가 가리키는 GitHub public 저장소. 저장소 이름을 이 문서에
  적지 않는 이유는 §프로젝트 관련된 내용은 중앙 규칙에 적지 않습니다(`site-structure.md`)와 같습니다.
- 되돌림이 필요하면 `git revert`(새 커밋으로 되돌리기)를 기본으로 합니다. 이력을 지우는 force push는 사용자의 명시 요청 없이 수행하지 않습니다.
