# doc-playbook — 문서 제작 요청을 받았을 때 처음부터 끝까지 따르는 절차

설명·분석·설계·기획서 같은 **문서 제작 요청**이 오면 이 절차를 처음부터 끝까지 따릅니다.
규칙의 정의는 `rules/`의 각 문서가 정본이며, 이 문서는 그것들을 **순서**로 엮습니다.

문체와 문장 구조는 `rules/doc-write-style.md`를 따릅니다. 이 절차서는 문장 구조 규칙의
예외입니다 — 지시가 먼저 오고 이유는 뒤에 붙습니다.

**켠 모듈이 이 절차에 단계를 더할 수 있습니다.** 모듈의 규칙이 「저장 위치」·「허브」·「추가
단계」를 정하면 그 모듈 문서가 정본이고, 이 절차는 그 자리를 비워 둡니다. 어느 모듈이 켜져
있는지는 프로젝트의 `{폴더}-modules.json`과 저장소 이름표(`workspace.json`)의 `modules`가
정본입니다.

---

## 한눈에 보기

```
문서 요청
  → STEP 0  상태 파악 (읽기 게이트 · 착수 보고)
  → STEP 1  자료 수집 + 저작권 점검
  → STEP 2  초안 아웃라인 (+ 템플릿 · 저장 위치 가판별) → 사용자 확인 ① (방향)
  → STEP 3  작업 판별 (Case A/B/C) → 사용자 확인 ② (템플릿 · 마스터 · 저장 위치)
  → STEP 4  (Case B/C일 때) 마스터 또는 템플릿 갱신
  → STEP 5  상세 설계
  → STEP 6  본문 작성 · 출력 (rules/html-output.md)
  → STEP 7  허브 · 용어집 연결
  → STEP 8  이력 기록 · 커밋 시점 제안
```

**사용자 확인 ①·②를 받기 전에는 본문 작성(파일 생성)을 시작하지 않습니다.**

---

## 작성 원칙

모든 문서는 `rules/writing-principles.md`(초보자도 혼자 따라 할 수 있게 쓰는 법)를 충족합니다.
코드가 들어가면 `rules/code-example.md`(파일 표기 · 주석 · 비유 범위)를 함께 따릅니다.
두 문서는 STEP 2에서 설명 전략을 세울 때와 STEP 6에서 본문을 쓸 때 모두 기준입니다.

---

## STEP 0 — 상태 파악

1. `rules/read-gates.md`의 「읽기 게이트」에서 이번 작업에 해당하는 줄을 **전부** 실제로
   열어 읽습니다. 「기본 참조 금지」로 묶인 자리도 거기에 있습니다.
2. 같은 파일의 「착수 보고」를 냅니다. 본문 작성보다 먼저입니다.
3. 프로젝트 작업이면 그 프로젝트의 change-log(「현행 기준」 블록 먼저)와 remaining-work를
   읽습니다. 파일 이름은 `{폴더}-site.json`이 따로 정하지 않았다면 `{접두}-change-log.md`·
   `{접두}-remaining-work.md`입니다.
4. 신규 프로젝트라면 아래 [신규 프로젝트 시작 절차](#신규-프로젝트-시작-절차)를 먼저 수행합니다.

## STEP 1 — 자료 수집 + 저작권 점검

수집 우선순위: 공식 1차 자료(문서·헬프센터·공지) → 스토어·배포 페이지 → 직접 실측 →
커뮤니티·언론. 로그인·게이팅된 영역은 사용자 승인 없이 들어가지 않습니다.

**저작권 체크리스트 — 자료를 처음 다루는 이 시점부터 적용합니다** (push 시점이 아닙니다).

- [ ] 남의 스크린샷을 산출물에 넣는가? → 필요 최소한으로, 출처 명기
- [ ] 원문 텍스트 인용이 있는가? → 최소 범위 인용 + 출처 명기
- [ ] 상표·로고가 노출되는가?
- [ ] 비공개 자료(유출본·내부 문서)인가? → **사용 금지**

걸리는 항목은 설계 단계에서 빼거나 사용자에게 확인받습니다. 비공개 저장소여도 적용합니다 —
나중에 공개로 바꾸거나 파일을 밖으로 보낼 때 이미 섞여 있으면 걸러 낼 수 없기 때문입니다.
**원문 텍스트를 그대로 붙여 넣는 것은 커밋 게이트의 도구가 잡지 못하므로** 이 시점이 마지막
사람 검사입니다.

**원칙**: 추측으로 값을 채우지 않습니다(미확인은 `?`로 두고 미확인 목록에 모읍니다). 용어를
지어내지 않습니다. 자료 사이의 수치가 어긋나면 양쪽을 비고에 적고 실측으로 확정합니다.

## STEP 2 — 초안 아웃라인 & 사용자 확인 ①

판별보다 **먼저** 문서의 큰 뼈대를 잡습니다. 목적은 두 가지입니다 — 어떤 섹션과 컴포넌트가
필요한지 파악하는 것, 그리고 **독자가 혼자 읽고 따라 하려면 어떻게 설명해야 하는지** 미리
설계하는 것입니다. 아웃라인은 목차 나열이 아니라 작성 원칙을 어떤 구성으로 실현할지의 설계입니다.

1. **섹션 목록** — 독자가 이해에 도달하는 순서로 나열합니다. 이해 순서는 템플릿마다 다르므로
   템플릿 카탈로그(`design-template/template-catalog.md`와 켠 모듈의 카탈로그)의 **템플릿별 섹션
   구조**를 기준으로 삼습니다. 요청에 맞게 섹션을 더하거나 합치거나 줄일 수 있습니다.
2. **섹션별 핵심 컴포넌트** — 「이 컴포넌트가 독자의 이해를 어떻게 돕는가」를 기준으로 고릅니다
   (순서 있는 절차 → 파이프라인, 구조 → 관계도, 복사할 코드 → 코드 탭).
3. **섹션별 설명 전략 메모** — 독자가 막힐 지점(처음 나오는 용어 · 전제 조건 · 건너뛰기 쉬운 중간
   단계)을 표시하고, 혼자 따라 하게 만들 설명 방식을 한 줄씩 적습니다.
4. **템플릿 · 저장 위치 가판별** — 어느 템플릿에 얹히는지, 어디에 저장되는지 내부적으로
   정합니다. 저장 위치 규칙을 켠 모듈이 정하면 그 규칙을 따르고, 새 하위 폴더가 필요하면
   후보도 함께 정합니다.
5. **사용자에게 공유 (확인 ①)** — 아웃라인과 설명 전략 요지, 저장 위치(새 폴더 여부 포함)를
   보여 주고 방향을 확인받습니다. 어긋나면 고쳐 다시 확인받습니다.

뼈대를 먼저 잡는 이유는, 뼈대 없이 판별하면 작업 도중에 마스터에 없는 컴포넌트가 뒤늦게
발견되어 마스터를 다시 건드리게 되기 때문입니다.

## STEP 3 — 작업 판별 & 사용자 확인 ②

확인 ①로 정한 아웃라인을 근거로 케이스를 판별하고 재확인 질문을 합니다. 판별 기준의 정본은
`design-template/template-catalog.md`입니다.

| 케이스 | 조건 | 질문 (문구 준수) |
|---|---|---|
| **Case A** | 기존 템플릿으로 가능하고 모든 컴포넌트가 마스터에 있음 | 「~ 요청에 대한 문서 작업은 [템플릿명] 템플릿을 기반으로 작성되어 [저장 위치]에 저장될 예정인데 괜찮을까요?」 |
| **Case B** | 템플릿은 맞지만 마스터로 표현할 수 없는 디자인이 있음 | 「~ 요청에 대한 문서 작업은 [템플릿명] 템플릿을 기반으로 작성되어 [저장 위치]에 저장될 예정인데, {특정 기능}에 대해 마스터를 갱신하고 진행해도 괜찮을까요?」 — {특정 기능}에는 신규 디자인을 짧게 설명합니다 |
| **Case C** | 부합하는 템플릿이 없음 | 「~ 요청에 대한 문서 작업은 부합하는 템플릿이 없는데, 새로운 템플릿 규칙서를 작성 후 그에 따라 진행해도 괜찮을까요? (저장 위치는 [저장 위치] 예정)」 |

- 승인되면 Case A는 STEP 5로, Case B·C는 STEP 4를 거쳐 STEP 5로 갑니다.
- 거절되거나 다른 방향이 나오면 STEP 2 또는 판별부터 다시 합니다.
- 갭 판단은 아웃라인의 컴포넌트를 하나씩 시각 규칙서의 데모와 대조해 합니다. **색이나 변형만
  달라도 갭입니다** — 결과물에만 새 스타일을 넣지 않습니다.

## STEP 4 — 마스터 · 템플릿 갱신 (Case B · C만)

**갱신 원칙 — 추가는 하되 제거하지 않습니다.** 마스터와 템플릿은 다른 문서가 이미 기대고 있는
누적 자산입니다.

1. **승인 범위만** 갱신합니다. 승인받지 않은 항목을 끼워 넣지 않습니다.
2. **없는 것만** 추가합니다. 비슷한 컴포넌트가 있으면 새로 만들지 않고 변형(variant)으로 더합니다.
3. **이번 문서에서 안 쓰여도 제거하지 않습니다.** 다른 문서가 쓰고 있을 수 있습니다.
4. 제거나 동작이 달라지는 변경은 **별도 승인** 사항이며, CHANGELOG에 `(제거)`·`(변경)`으로 적습니다.

**Case B — 마스터 갱신은 한 묶음입니다.** 다음 넷을 함께 끝냅니다. CSS만 올리고 시각 규칙서를
두면, 다음 사람이 이미 있는 요소를 없다고 보고 같은 것을 또 만듭니다.

1. 마스터 CSS에 토큰·컴포넌트를 추가합니다. 새 색이 필요하면 팔레트 톤에 맞는 한 색만 더합니다.
   이름은 기존 관습을 따릅니다.
2. 시각 규칙서에 실물 데모와 「언제 쓰는가」를 추가합니다.
3. 두 파일의 버전을 한 단 올리고 CHANGELOG를 적습니다(`rules/change-log-writing.md` §파일 CHANGELOG).
4. 갱신된 마스터로 STEP 5를 잇습니다. 결과물은 갱신된 CSS를 inline합니다.

**Case C — 신규 템플릿은 새 번호로 만들고 카탈로그에 등록합니다.** 기존 템플릿에 섹션을 덧대
변형하지 않습니다. 새 템플릿에 마스터에 없는 컴포넌트가 필요하면 Case B 묶음을 먼저 합니다.
**카탈로그에 등록해야 템플릿으로 인정됩니다.** 등록 항목과 자리는 `design-template/template-catalog.md`
§신규 템플릿 등록이 정합니다.

## STEP 5 — 상세 설계

템플릿과 마스터가 확정된 상태에서 아웃라인을 상세 구조로 바꿉니다. 여기서 정한 설계를 그대로
따라 쓰므로, 작성 중 구조 변경이 줄어듭니다.

1. **섹션별 상세 구성** — 소제목, 컴포넌트, 담을 내용 요지.
2. **컴포넌트 배치 순서** — 어느 섹션의 어느 위치에 무엇을 넣는지.
3. **용어 계획** — 핵심 용어 블록에 넣을 용어와 앵커 ID(`id="term-…"`).
4. **코드 범위** — 코드 탭에 넣을 파일 목록과 파일별 핵심.

템플릿의 **섹션 순서와 컴포넌트 사용법**을 따릅니다. 켠 모듈이 이 사이에 단계를 더하면(예: 기능
골격 정규화, 책임 배치 결정표) 그 모듈 문서가 순서를 정합니다.

## STEP 6 — 본문 작성 · 출력

- 작성 원칙(`rules/writing-principles.md`)과 코드 규칙(`rules/code-example.md`)을 충족합니다.
- 출력은 `rules/html-output.md`를 따릅니다 — 마스터 CSS inline, 글꼴 내장, 다이어그램과 코드
  하이라이팅은 구워 넣기, 네트워크 요청 0건, 본문에서 다른 문서로 상대 링크 금지.
- 렌더해서 눈으로 봅니다. 콘솔 에러 0건, 탭·복사 동작, 좁은 화면을 확인합니다.

## STEP 7 — 허브 · 용어집 연결

문서를 만들 때마다 문서 사이의 연결을 맡는 자리를 갱신합니다. 어느 허브에 싣는지는 켠 모듈이나
프로젝트가 정하고, 공통 원칙은 이렇습니다.

1. **문서 목록 등록** — 허브의 문서 목록에 한 행을 더합니다(문서명 · 유형 · 날짜 · 링크).
   생성기가 폴더를 훑어 목록을 만드는 저장소는 문서를 규칙대로 된 자리에 두는 것이 곧 등록입니다.
2. **용어집 추가** — 어려운 용어를 배치 기준에 맞는 용어집에 더합니다. 기준은 **「정의 문장에서
   프로젝트 이름을 지워도 성립하는가」**입니다 — 성립하면 중앙, 아니면 프로젝트 용어집입니다.
3. **앵커 ID** — 용어를 본격 설명한 자리에 `id="term-…"`를 달아 용어집 링크가 그 자리로 가게 합니다.

## STEP 8 — 이력 기록 · 커밋 시점 제안

1. 바뀐 파일마다 상단 CHANGELOG 주석을 적습니다.
2. 프로젝트 change-log에 항목을 더하고, 「현행 기준」이 바뀌었으면 그 블록도 고칩니다.
3. 할 일이 생겼거나 끝났으면 remaining-work를 고칩니다.
4. 검사 셋을 돌리고 「커밋 시점 같습니다」를 제안합니다(`rules/git-rules.md` §4).

형식의 정본은 `rules/change-log-writing.md`와 `rules/remaining-work.md`입니다.

## 실행 체크리스트

- [ ] 읽기 게이트를 지나고 착수 보고를 냈다 (STEP 0)
- [ ] 자료의 저작권 체크리스트를 적용했다 (STEP 1)
- [ ] 아웃라인(섹션 · 컴포넌트 · 설명 전략 · 템플릿 · 저장 위치)으로 확인 ①을 받았다 (STEP 2)
- [ ] Case를 판별하고 정해진 문구로 확인 ②를 받았다 (STEP 3)
- [ ] Case B · C면 승인 범위만 갱신했다 — 마스터는 CSS · 규칙서 · 버전 · CHANGELOG 한 묶음 (STEP 4)
- [ ] 상세 설계(구성 · 배치 · 용어 · 코드 범위)를 확정했다 (STEP 5)
- [ ] 작성 원칙 · 코드 규칙을 충족했다 (STEP 6)
- [ ] 출력 규칙을 지키고 렌더해 확인했다 — 네트워크 0건 · 콘솔 에러 0건 (STEP 6)
- [ ] 허브 · 용어집 · 앵커를 갱신했다 (STEP 7)
- [ ] 파일 CHANGELOG · change-log · remaining-work를 갱신하고 커밋 시점을 제안했다 (STEP 8)

## 신규 프로젝트 시작 절차

1. **골격을 도구로 세웁니다** — `python core/base/scripts/new_project.py {제품}/{슬러그}`.
   무엇이 생기고 무엇을 일부러 만들지 않는지의 정본은 `rules/project-scaffold.md`입니다.
   이미 있는 폴더를 옮기지 않고 등록만 하는 방법도 거기 있습니다.
2. change-log의 **§프로젝트 정의**를 채우고, 필요한 모듈을 제안해 동의를 받은 뒤 켭니다
   (`rules/feature-request.md`). 안 켠 모듈의 규칙(`core/modules/{모듈}/`)은 읽지 않습니다.
3. **재사용 확인** — 기존 프로젝트와 함께 쓸 뼈대가 있는지 봅니다. 있어 보이면 ① 「○○ 프로젝트에서
   가져와도 되나요?」를 확인하고 ② 그 뼈대 전체를 보여 준 뒤 가져올 부분을 묻고 ③ 고른 부분만
   복사합니다. 이전 프로젝트의 고유명사와 수치는 지웁니다.
4. **복사한 순간부터 완전히 독립합니다.** 이후 수정은 새 프로젝트 안에서만 합니다.
