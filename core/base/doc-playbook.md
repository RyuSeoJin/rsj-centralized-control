# doc-playbook — 분석→골격→TC 파이프라인 절차서

문서 제작 요청(역분석·기획서 분석·기능 골격·TC 설계)이 오면 이 절차를 처음부터 끝까지 따릅니다.
규칙의 정의 자체는 `rules/`의 각 문서가 정본이며, 이 문서는 그것들을 **순서**로 엮습니다.

문서를 쓰거나 고칠 때의 문체와 문장 구조는 `rules/doc-write-style.md`를 따릅니다.
(이 절차서 자체는 문장 구조 규칙의 예외입니다. 지시가 먼저 오고 이유는 뒤에 붙습니다.)

---

## STEP 0 — 상태 파악

1. 대상 프로젝트의 `{프로젝트}-change-log.md`(현재 상태·최근 변경점)와 `{프로젝트}-remaining-work.md`(다음 작업 큐·결정 대기)를 읽습니다 — 규칙은 `rules/remaining-work.md`.
2. `spec/archive/` 아래는 열지 않습니다 — 골격 이력(`{프로젝트}-tree-change-log.md`)과 동결 스냅샷이 여기 있고, 둘 다 기본 참조 금지입니다(CLAUDE.md 참조).
3. 신규 프로젝트라면 [신규 프로젝트 시작 절차](#신규-프로젝트-시작-절차)를 먼저 수행합니다.

## STEP 1 — 자료 수집 + 저작권 점검

수집 우선순위: 공식 1차 자료(헬프센터·운영정책·공지) → 스토어 리스팅 → 브라우저 실측 → 커뮤니티·언론.
로그인·게이팅된 영역은 사용자 승인 없이 진입하지 않습니다.

**저작권 체크리스트 — 자료를 처음 다루는 이 시점부터 적용합니다** (push 시점이 아닙니다):

- [ ] 대상 서비스 스크린샷을 산출물에 넣는가? → 필요 최소한으로, 출처 명기
- [ ] 게임/서비스 원문 텍스트 인용이 있는가? → 최소 범위 인용 + 출처 명기
- [ ] 상표·로고가 노출되는가?
- [ ] 비공개 자료(유출본·내부 문서)인가? → **사용 금지**

걸리는 항목은 산출물 설계 단계에서 제외하거나 사용자에게 확인받습니다. public 저장소이므로 여기서 거른 것이 커밋·push 게이트(`rules/git-rules.md` §5)의 부담을 줄입니다.

**여기가 마지막 사람 검사인 항목이 하나 있습니다.** 커밋 게이트는 이미지와 이진 파일, 조사 자료 자리를 도구가 판별하지만, **원문 텍스트를 문서에 그대로 붙여 넣는 것**은 잡지 못합니다. 위 둘째 항목(원문 인용)은 이 시점에 걸러야 뒤에서 걸리지 않습니다.

**원칙**: 추측으로 기대값을 채우지 않습니다(미확인은 `?`). 용어를 지어내지 않습니다. 문서 간 수치가 상충하면 양쪽을 비고에 적고 실측으로 확정합니다.

## STEP 2 — 아웃라인 초안 & 사용자 확인 ①

독자의 이해 경로 기준으로 섹션 목록 + 섹션별 구성 요소를 초안으로 만들고, `base/design-template/template-catalog.md`로 템플릿을 가판별한 뒤 **사용자에게 공유하고 방향 확인을 받습니다. 확인 전에는 본문 작성을 시작하지 않습니다.**

## STEP 3 — 템플릿 판별 & 사용자 확인 ②

카탈로그 기준으로 케이스를 판별하고 재확인 질문을 합니다.

- **Case A** 기존 템플릿으로 가능 → "[템플릿명] 기반으로 작성 예정인데 괜찮을까요?"
- **Case B** 템플릿은 맞으나 마스터에 없는 디자인 필요 → "[템플릿명] 기반으로 작성하되, {신규 디자인 간략 설명}에 대해 마스터를 갱신하고 진행해도 괜찮을까요?"
- **Case C** 부합 템플릿 없음 → "새 템플릿 규칙서를 작성 후 진행해도 괜찮을까요?" → 승인 시 신규 템플릿 생성 + 카탈로그 등록

## STEP 4 — 마스터/템플릿 갱신 (Case B·C만)

승인 범위만, 없는 것만 추가합니다. 마스터 갱신 시 `design-guide-master.css`·`master.html` 먼저(버전 +1), 신규 템플릿은 `base/design-template/NN-{템플릿명}.html` 생성 + 카탈로그 등록. 기존 토큰·컴포넌트는 이번 문서에서 미사용이어도 제거하지 않습니다(제거는 별도 사용자 승인).

## STEP 5 — 기능 골격 작업

정본은 `spec/{프로젝트}-feature-tree.md` 하나뿐입니다.

`analysis/`는 조사 전량, `reference/`는 채택분, `spec/`은 확정 결정입니다. TC의 기대값은 `spec/`의 문서에서만 가져옵니다 — analysis·reference의 수치를 TC에 직접 쓰지 않습니다. 아직 남의 값이거나 미확정 값이기 때문입니다.

`spec/` 평면에는 기획 골격 트리 정본만 둡니다. 기획 확정 사양은 `spec/design/`, SUT 전용 사양은 `spec/sut-design/`(SUT를 만드는 프로젝트만), 판단 기록은 `spec/rationale/`(도메인 판단 addition-rationale · SUT 판단 sut-rationale), 지나간 것은 `spec/archive/`입니다. **기획 TC의 기대값은 트리와 `design/`에서만** 가져오고, SUT 구현·자동화 층이 `sut-design/`을 추가로 참조합니다 — `rationale/`은 판단 기록이라 기대값이 아닙니다. 기획 레이어는 SUT 없이도 자기완결입니다(조사→채택→기획 확정→TC 설계). 근거 문서는 두 부류를 섹션으로 나눠 담습니다.

- **§1 노드 보강** — 레퍼런스에 없어 직접 세운 노드(`ADD`)의 근거. "조사에 없다"는 사실과 그래도 넣는 이유를 함께 적습니다
- **§2 수치 확정** — 노드는 레퍼런스에 있으나 값이 공개되지 않아 직접 정한 것의 근거. 관계 단계 임계나 엔딩 경계처럼 "왜 이 숫자인가"를 묻게 되는 값이 여기 해당합니다

근거는 판단한 시점에 한 줄씩 적립합니다. 하루 지나 되짚으면 근거가 빈약해지고, 그러면 조사로 방어되지 않는 항목이 트리에서 가장 약한 칸으로 남습니다.

1. **Depth 정규화** — 명칭이 아니라 역할로 묶고, 상태(로그인·구독·플랫폼)는 Depth가 아니라 Pre-Condition으로 흡수합니다. → `rules/depth-and-tn.md`
2. **검증유형 표기** — 출력이 매번 같지 않은 기능이 있으면 검증유형 분리가 기능 목록보다 먼저입니다. → `rules/verification-types.md`
3. **지원 표기** — `O / X / △ / ?`. `?`는 정본의 "미확인 목록" 섹션에 모읍니다(실측 우선순위).
4. **정본 수정 체크리스트(한 묶음)** — ① md 수정 → ② `feature-tree.html` 재생성 → ③ `spec/archive/{프로젝트}-tree-change-log.md` 기록(날짜/노드 경로/유형/사유/변경 전 상태) + 골격 버전이 바뀌면 프로젝트 change-log에 한 줄 포인터 → ④ 커밋 시점 제안.
5. **버전** — 방향성이 바뀌는 큰 개정 = major(v1.x→v2.0), 노드 추가·수정 = minor. major 개정 시 개정 직전 정본을 `spec/archive/{프로젝트}-feature-tree-vX.Y.md`로 동결하고, 태그(`{프로젝트}-tree-vX.Y`)와 버전을 일치시킵니다.

사용자가 골격을 1차 확인·최종 확정한 뒤에만 STEP 6으로 넘어갑니다.

## STEP 6 — TC 설계 & 산출

1. **시트 규칙 확인** — `rules/tc-sheet-format.md`를 읽고 `modules/tc/design-template/tc-sheet-master.xlsx`의 '명세서' 시트와 교차 검증합니다. 불일치 시 사용자에게 질문합니다(임의 판단 금지).
2. **케이스 전개** — 노드마다 정상 · 경계 · 예외 · 우회. → `rules/case-expansion.md`
3. **TN 부여·우선순위** — 한 행 = 한 TN = 한 스텝. Pre-Condition·Priority는 TN 1행에만. → `rules/depth-and-tn.md`
4. **관계도(선택)** — 선행 TC는 설계 입력(json)에만 두고 시트에는 싣지 않습니다. → `rules/tc-relations.md`
5. **산출** — `scripts/`로 정본 md에서 xlsx를 생성합니다. 기준 골격 버전을 시트에 기록하고, 이슈 관리 시트를 내장합니다. 수식 검증(recalc)을 수행합니다.

**산출 후 점검 체크리스트**

- [ ] TN이 케이스마다 1부터 끊김 없이 이어지는가
- [ ] Pre-Condition·Priority가 TN 1행에만 있는가
- [ ] Test-Step `~한다` / Expected-Result `~된다` 체이고, 기대 결과가 판정 가능한 문장인가(임계·합격선·시도 횟수는 문장 안에 숫자로)
- [ ] (관계도) 선행 TC가 실재하고 순환이 없는가
- [ ] `?` 항목이 미확인 목록에 빠짐없이 있는가
- [ ] 기준 골격 버전이 시트에 기록됐는가
- [ ] HTML 산출물은 렌더해 눈으로 확인했는가 — 콘솔 에러 0

## 신규 프로젝트 시작 절차

1. **골격을 도구로 세웁니다** — `python core/base/scripts/new_project.py {슬러그}`.
   무엇이 생기고 무엇을 일부러 만들지 않는지의 정본은 `rules/project-scaffold.md`입니다.
   손으로 만들면 프로젝트마다 자리가 갈립니다.
2. `change-log`의 **§프로젝트 정의**와 **§켠 모듈**을 채웁니다. 안 켠 모듈의 규칙
   (`core/modules/{모듈}/`)은 읽지 않습니다.
3. **골격 재사용 체크** — 기존 프로젝트와 공통으로 쓸 방향이 있는지 확인합니다. 없으면 백지에서 시작합니다.
4. 있어 보이면: ① "○○ 프로젝트에서 끌어다 써도 되는 게 맞나요?" 재확인 → ② 그 골격 **전체를 보여주고** 어떤 부분을 끌어올지 재질문 → ③ 선택분만 신규 feature-tree.md의 시작점으로 복사(이전 프로젝트 고유명사·고유 수치는 제거).
5. **복사된 순간부터 완전 독립** — 이후 수정은 새 프로젝트 안에서만 이루어집니다. 원본 정본에는 영향이 없습니다. 별도 시드 파일은 두지 않습니다.

**목록에 등록하는 절차는 없습니다.** 폴더를 만드는 것이 곧 등록이고, 생성기가 `projects/`를
훑습니다(→ `rules/site-structure.md` §목록은 손으로 갱신하지 않습니다).

## 산출물 출력 방식

- HTML 산출물은 생성 시점 마스터 CSS를 `<style>`에 inline한 자기완결 단일 파일입니다. 네트워크 요청은 0건이어야 하고, 기준 마스터 버전을 CHANGELOG 주석·footer에 기록합니다.
- 차트·다이어그램도 인라인합니다(런타임 CDN 금지). 상세 규칙은 `rules/html-report-guide.md`에 있습니다.
- 구조도·다이어그램은 SVG 파일이 정본이고 사본을 두지 않습니다 — 그림을 싣는 페이지의 생성기가 만들 때마다 읽어 넣습니다.
- 문서 목록은 생성기가 폴더를 훑어 만듭니다(→ `rules/site-structure.md`). 새 문서는 규칙대로 된 자리에 두고, 어려운 용어는 배치 기준에 맞는 용어집에 추가합니다.
